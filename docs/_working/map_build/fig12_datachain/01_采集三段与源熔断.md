**族职责一句话**：把 23 家外部源的行为差异吸进 provider 归一层，按 29 个 cron 档期中的 18 个采集档期产出 normalized rows，并在全链路用"fallback 换源 + 自动熔断 + 手动停源"三层韧性把单源故障挡住在生产段。

**时区口径（本簿所有 CH 实测的读法，先立后破）**：CH 服务端 `timezone()='Etc/UTC'`、`now()=2026-09-24 06:37:10`，本机 wall clock 同一刻为 `14:37 +08:00`（实测 `python -c datetime.now()` + `SELECT now(),timezone()`）。故 **`system.parts.modification_time` 与 `ingest_ts` 均为 UTC，判档期吻合须 +8h 折北京时间**。骨架 §7-E 用 `max(date)` 判"今日活跃"未做此折算，其"盘中活跃"结论恰好成立（tick/kline_1min 末写 06:28 UTC = 14:28 北京，确在盘中），但 `sector_*` 一类 `DateTime64(3,'UTC')` 列的 max 值直接读会被误当成北京时间。

**第三腿替代口径（本车道方法论）**：本 worktree 无 `.runtime/logs/`（实测 `ls .runtime` 仅 `tmp`），`tmp/scheduler_instance.lock`、`tmp/scheduler_loaded_state.json`（scheduler.py:78/83 默认路径）、`data/runtime/`、`.runtime/logs/resource_samples/*.jsonl`（config/resource_profile_registry.yaml:612/1116 声明的 samples 落点）全部不在位。因此第三腿用 **CH `system.parts` 的 `max(modification_time)` = 该表最后一次真实数据写入时刻**充当执行见证，并与该表所属槽的 cron 时刻做吻合度检验。**两者一致才 ✅**；表新鲜但写时刻不落在任何档期窗内 → 判"产数活跃、档期执行不可证"，降 🔨 并点名。

**读侧纪律（本簿全部数字的来源通道）**：`ch_writer.query` 与 `ch_reader.query` **都会静默失败**——`src/zephyr/data/ch_reader.py:13` 逐字 `[ERROR_CONTRACT] query失败->返回空字符串(同ch_writer); count失败->返回0`（骨架只点了 ch_writer 一侧，**欠一条**）。本车道实测：`SELECT toDayOfWeekName(...)` 触发 Code 46 → HTTP 404 → 返回 `''`；`SELECT uniqExact(14 平铺列)` 触发 Code 42 → 返回 `''`。故本簿所有关键数字改走 **`zephyr.infrastructure.database_service.get_db_service().get_clickhouse_conn(role="reader").execute()`**（失败即抛 ServerException，实测可红），仅结构枚举用 ch_reader 交叉。
