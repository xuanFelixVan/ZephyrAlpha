## §3 D12-06 幂等写与判重

**上**：幂等决策在写侧按表引擎分流——`get_table_engine()`（ch_writer.py:776）/ `is_replacing_engine()`（:808）；`[INVARIANTS] 幂等性由调用方决定(ReplacingMergeTree直接INSERT/MergeTree写前DELETE)`（:8）。写前 DELETE 通道 = `delete_where()`（:1001）/ `delete_by_date_range()`（:1050）。实测派生族（D12-07/08/09）走"窗口 DELETE + INSERT"幂等（`kline_resampler` INVARIANTS "DELETE+INSERT幂等写入"；`ch_tick_kline` INVARIANTS "目标表幂等=ALTER DELETE(BETWEEN trade_date)+INSERT（同 kline_resampler 模式）"）。
**下**：判重结论是**破坏性操作的准入闸**——data_ops_policy §6.1 与 RULE-DATA-OPS 把"判重必用 `check_tick_duplication.py`、禁用聚合 count 判重"写成硬规；`scripts/governance/data_quality/check_tick_duplication.py:9 [MODIFY-GUARD] 同步更新 trae_063_data_ops_discipline.yaml 中引用本脚本的 invariants` → 脚本与规则 YAML 双向锁。
**内（为何"禁聚合数判重"——拿实码 + 实测说清聚合口径漏/多什么）**
1. **事故根因（脚本自述）**：:17-21 "本脚本是 2026-07-16 tick_data **21 个月数据误删事故**的治本工具之一。事故根因：AI 用 `count() - uniqExact(排序键)` 算'重复'，把同一时间戳**不同价位**的有效记录误判为'重复'，执行 `INSERT GROUP BY + REPLACE PARTITION` 删除了 21 个月有效数据。"
2. **真重复定义（铁律）**：:22-27 + `INVARIANTS 真重复定义=全字段(14字段)相同; 禁止用 count()-uniqExact(排序键) 算"重复"`（:8）。14 字段清单 :84-99（`trade_date,timestamp,symbol,market_type,price,volume,amount,direction,data_source,bid_price,ask_price,bid_volume,ask_volume,quality_flag`，真源标注=tick_subscriber `_TICK_COLUMNS`）。
3. **聚合口径为什么会漏/多判——实测键差**：`c1_market.tick_data` 引擎与键（实测 `system.tables`）：
   - `engine = ReplacingMergeTree`
   - `sorting_key = market_type, symbol, trade_date, timestamp, price` ← **只有 14 个业务字段中的 5 个**
   - `partition_key = toYYYYMM(trade_date)`
   → 聚合口径 `count() - uniqExact(排序键)` 会把"同 (market_type,symbol,trade_date,timestamp,price) 但 volume/amount/bid/ask/direction/quality_flag 不同"的行算成重复（**假阳性→误删的入口**）；反过来它又**看不见**"排序键不同但全字段相同"的真重复（跨 market_type 打标变更类，**假阴性**）。
4. **同一天两种口径的实测对照（样本 `symbol='600519' AND trade_date='2026-09-23'`，走 DatabaseService reader，会抛）**：
   - `count() = 4833`；`uniqExact(排序键5列) = 4831`；`uniqExact(tuple(14列)) = 4831`
   - 脚本自己的正确口径：全字段 `GROUP BY ... HAVING dup_cnt>1` → **真重复 2 组、涉及 4 行**（实测）
   - 该样本里两口径恰好同数（因 `price` 已在排序键中），**但这只是运气**：脚本报告文本仍逐字提醒"⚠ 行数差 ≠ 真重复数…禁止用 count() - uniqExact(排序键) 作为'重复'判据"（:278-281, :285-287 "若行数差>0 但真重复组数=0，说明差异来自排序键合并，这是引擎行为，**不是数据问题，禁止删除**"）。→ **本簿把它变成可判读事实：tick 表里"真重复"确实存在（2026-09-23 单日单标的即有 2 组），所以"有重复"不能推出"可删"，也不能推出"排序键合并造成的差是同一回事"。**
   - **FINAL 口径**：`FINAL` 与非 `FINAL` 在本样本未测出差异（ReplacingMergeTree 未 merge 时多版本会同时可见）→ 凡引用 `max()`/`count()` 作 ✅ 判据，须**同时给 FINAL 版**（ch_reader 自动注 FINAL，DatabaseService 不注——本簿双通道即为此）。
5. **判重器自身的可用性缺陷（本簿坐实 D12-06 不能给 ✅ 的核心证据）**
   - `_SQL_TOTAL_ROW`（:125）用 `uniqExact({cols})` 的**平铺 14 列**形式；`_build_total_row_query()`（:162-170）确实按 `", ".join(_TICK_COLUMNS)` 平铺传入。
   - 实测 `c1_market.tick_data` 有 **4 个 `Nullable(...)` 列**（`system.columns` countIf），ClickHouse 对含 Nullable 参数的聚合函数限 **最多 8 个参数** → 该 SQL **必抛 `Code 42: Maximum number of arguments for aggregate function with Nullable types is 8`**（本簿原样复跑复现，改 `uniqExact(tuple(...))` 即通过 → 修法明确）。
   - 后果链：`check_duplication()` 用 `ch_reader.query()` → 返回 `''` → `_parse_tsv('', 2)` → `[]` → `if total_rows:`（:230）为假 → **`total_row_cnt`/`uniq_full_field_cnt` 保持初始 0**（:218-219）→ 人类报告打印"**该月总行数: 0 / 全字段去重后行数: 0 / 行数差 0**"（:271-273）→ `exit` 码只由 `dup_group_cnt>0` 决定（:353）。即 **`[ERROR_CONTRACT]` 承诺的"失败→exit 2"在最常用的一条腿上没兑现，工具给出"半假绿"**：真重复腿（GROUP BY 版）正常，聚合对照腿恒为 0。
   - 另注（环境级隐患，与本环节直接相关因为它是判重执行体）：脚本 :47 硬编码 `_SRC_DIR = r"d:\ZephyrAlpha\src"` 并 `sys.path.insert(0, ...)` → **在 worktree 里跑它会加载主区代码**，产出的判重结论与被审仓不同源（列溢出-5）。
