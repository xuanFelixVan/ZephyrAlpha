### 隔夜全球市场传导与事件影响评估模型（Overnight Global Market Contagion & Event Impact Assessment Model）

**架构现状**: 完全缺失。"外围消息面"无量化评估框架。

**核心逻辑**: "外围消息面"在专业量化中对应**Global Market Contagion**——隔夜海外市场收益/波动率对A股开盘的传导效应。专业机构用统计模型量化传导系数，而非"美股跌了所以A股也要跌"的直觉。

**缺失功能**:

#### 21.1 全球市场传导量化

| 功能点 | 量化方法 | 说明 |
|--------|---------|------|
| 隔夜传导系数 | A股开盘收益 vs 美股收盘收益的β | β>0.5=显著传导 |
| 传导衰减 | 传导效应在开盘后N分钟内衰减 | 通常30分钟内消化 |
| 波动率传导 | VIX变化 → A股隐含波动率变化 | VIX飙升>5%→A股开盘波动率上升 |

#### 21.2 事件影响评估

| 功能点 | 量化方法 | 说明 |
|--------|---------|------|
| 事件分类 | 按类型（政策/地缘/数据/黑天鹅）和预期内/预期外分类 | 不同类型影响模式不同 |
| 异常收益 | 事件窗口[-1,+3]日的累计异常收益(CAR) | 事件研究法 |
| 影响持续时间 | CAR从显著变为不显著的天数 | 预期内事件1-2天；预期外5-10天 |

#### 21.3 学术与业界对标

**对标1: Baur & Fry "Multivariate Contagion" (2009, JBF)**

全球市场传导的统计模型。传导系数β量化一个市场对另一个市场的影响。

**对标2: MacKinlay "Event Studies in Economics and Finance" (1997, JEL)**

事件研究法：用CAR（累计异常收益）量化事件影响。是事件影响评估的学术标准。

**建议归属层**: L1 因子计算层（传导系数因子+事件影响因子）+ L2-C 市场状态层（外部环境判定）

## §2 集成风格

> 集成风格决定系统间通信的时序、耦合度和故障传播模式。本系统采用四类集成风格，按场景选择。

### §2.1 同步调用

> 适用：低延迟要求、需要即时响应的场景。

| 场景 | 调用方 | 被调用方 | 降级 |
|------|--------|---------|------|
| 下单执行 | C-002执行域 | miniQMT xttrader | 熔断→告警→人工 |
| 实时行情查询 | C-001数据域 | miniQMT xtdata | 降级为iFind |
| 风控检查 | C-004风控域 | 内部风控引擎 | Fail-Closed（拒绝交易） |
| LLM推理 | C-006策略工厂 | 本地LLM | 降级为外部API |
| iFind数据拉取 | C-001数据域 | iFind API | 降级为tushare |

> 超时/重试配置详见§6.3超时与重试矩阵。

**同步调用铁律**：
- 交易关键路径（行情→信号→风控→下单）禁止超过3层同步调用
- 所有同步调用必须设置超时（无超时=无边界=线程耗尽风险）
- 风控调用不可降级（Fail-Closed原则）

### §2.2 异步消息

> 适用：无需即时响应、允许最终一致性的场景。

| 场景 | 生产者 | 消费者 | 消息通道 | 投递保证 |
|------|--------|--------|---------|---------|
| 成交回报 | miniQMT回调 | C-002执行域 | Redis Stream | At-Least-Once + 幂等消费 |
| 委托状态变更 | miniQMT回调 | C-002/C-004 | Redis Stream | At-Least-Once |
| 数据更新通知 | C-001数据域 | C-009因子域 | Redis Pub/Sub | At-Most-Once（可重算） |
| 告警推送 | C-004/C-008 | C-015通知域 | Redis Stream | At-Least-Once |

**异步消息铁律**：
- 所有异步消息必须携带幂等Key（INV-007）
- 交易相关消息使用Redis Stream（持久化+消费者组）
- 非交易消息可使用Redis Pub/Sub（性能优先）
- 消息格式统一为JSON，包含：event_id / event_type / timestamp / payload / idempotency_key

### §2.3 事件驱动

> 适用：跨域解耦、一对多通知、审计追溯场景。参考CQRS+Event Sourcing模式。

| 事件 | 发布者 | 订阅者 | 触发条件 | 审计要求 |
|------|--------|--------|---------|---------|
| OrderPlaced | C-002执行域 | C-004风控/C-010报告/C-030可解释性 | 订单提交成功 | 7年保留 |
| OrderFilled | C-002执行域 | C-005预案/C-010报告/C-017运营 | 成交回报 | 7年保留 |
| RiskThresholdBreached | C-004风控域 | C-008运维/C-015通知/C-031协作 | 风控阈值触发 | 7年保留 |
| DataQualityDegraded | C-022数据质量 | C-001数据域/C-008运维 | 数据质量SLA违约 | 3年保留 |
| StrategyRetired | C-006策略工厂 | C-007进化/C-010报告 | 策略退役 | 3年保留 |
| ModelDriftDetected | C-029模型工厂 | C-007进化/C-008运维 | 模型漂移超阈值 | 3年保留 |

**事件驱动铁律**：
- 事件不可变（Immutable）：发布后不可修改，只能追加补偿事件
- 事件必须包含asof_ts（PIT时间戳），满足INV-004零前瞻偏差
- 事件溯源（Event Sourcing）：关键聚合根（Order/Position/Portfolio）状态变更必须记录事件
- CQRS分离：命令端（写）与查询端（读）使用不同数据模型，命令端产生事件→查询端异步更新

### §2.4 批量导入

> 适用：盘前数据准备、历史数据回填、大规模数据迁移。

| 场景 | 数据源 | 目标 | 执行时段 | 数据量 | 校验 |
|------|--------|------|---------|--------|------|
| 日K线批量拉取 | iFind | ClickHouse温层 | 盘前8:00-9:00 | ~5000只×250天 | 完整性+新鲜度 |
| 财务数据批量更新 | iFind | Parquet冷层 | 盘后15:30 | ~5000只×4季度 | 交叉校验 |
| 因子批量计算 | 本地计算 | Redis热层+Parquet | 盘前+盘中增量 | ~200因子×5000只 | IC校验 |
| 历史数据回填 | tushare/iFind | Parquet冷层 | 非交易时段 | 按需 | PIT一致性校验 |

**批量导入铁律**：
- 盘前批量拉取优先使用iFind（减少盘中QPS压力）
- 所有批量数据必须通过数据质量门禁（C-022）后才可消费
- 历史数据回填必须标注PIT时间戳，防止前瞻偏差

### §2.5 集成风格决策矩阵

```
需要即时响应？
├── 是 → 延迟要求？
│   ├── <1s → 同步调用（风控/执行）
│   └── >1s → 同步调用+超时+降级（LLM/数据拉取）
└── 否 → 一对一还是一对多？
    ├── 一对一 → 可靠性要求？
    │   ├── 高 → 异步消息（Redis Stream）
    │   └── 低 → 异步消息（Redis Pub/Sub）
    └── 一对多 → 需要审计追溯？
        ├── 是 → 事件驱动（Event Sourcing）
        └── 否 → 异步消息
```

## §3 接口契约治理

### §3.1 API版本管理

> 参考：SemVer（MAJOR.MINOR.PATCH）+ Stripe式日期版本 + OpenAPI 4.0契约主权。

#### §3.1.1 版本策略

| 外部系统 | 版本策略 | 版本标识位置 | 理由 |
|---------|---------|------------|------|
| miniQMT xtquant | 日期锁定 | 依赖版本编码日锁定 | 券商接口无SemVer，按QMT客户端发布日期锁定 |
| iFind API | 日期锁定 | 请求Header: X-iFind-Version | iFind按日期发布，字段可能静默变更 |
| tushare API | 日期锁定 | 请求Header: X-Tushare-Version | 同iFind策略 |
| LLM API | SemVer | URL Path: /v1/chat/completions | 主流LLM API均采用URL Path版本 |
| MCP协议 | 协议版本号 | 请求Header: Mcp-Protocol-Version | MCP 2026-07-28规范要求 |

#### §3.1.2 变更分类与处置

| 变更类型 | 定义 | 示例 | 处置规则 |
|---------|------|------|---------|
| 非破坏性（Additive） | 新增字段/接口，不影响现有消费 | iFind新增财务指标字段 | 自动兼容，记录变更日志 |
| 破坏性（Breaking） | 删除/重命名字段，变更类型/语义 | miniQMT回调参数格式变更 | 必须拒绝→告警→人工处理 |
| 语义漂移（Semantic Drift） | Schema不变但行为/性能变化 | iFind返回数据延迟从100ms变为2s | 视同破坏性变更，触发告警 |
| Deprecating | 字段/接口已弃用但仍可用 | 过渡期3个月→自动升级 | ①标记弃用日期 ②3个月后移除 ③消费者契约测试验证 |

#### §3.1.3 版本兼容性矩阵

| 消费者版本 \ 提供者版本 | V1（当前） | V2（新增字段） | V3（破坏性变更） |
|----------------------|-----------|--------------|----------------|
| V1消费者 | ✅ 正常 | ✅ 忽略新字段 | ❌ 拒绝+告警 |
| V2消费者 | ✅ 缺省字段 | ✅ 正常 | ❌ 拒绝+告警 |
| V3消费者 | ⚠️ 降级运行 | ⚠️ 降级运行 | ✅ 正常 |

### §3.2 兼容性策略

#### §3.2.1 兼容性检查机制

| 检查点 | 检查内容 | 执行时机 | 失败动作 |
|--------|---------|---------|---------|
| 启动时版本校验 | xtquant版本号 vs 锁定版本 | 系统启动 | 启动拒绝+告警 |
| 运行时Schema校验 | API返回字段 vs 预期Schema | 每次调用 | 标记数据质量降级 |
| 定时漂移检测 | API行为基线 vs 实际行为 | 每日盘后 | 生成漂移报告+告警 |
| 契约变更检测 | 外部API Changelog监控 | 每周 | 评估影响+更新锁定版本 |

#### §3.2.2 契约漂移检测

> 参考：OpenAPI 4.0契约主权——从"文档驱动"到"可信契约治理"。

```
契约注册（启动时）
    │
    ├──→ 基线快照：记录当前API的Schema+行为基线
    │
    ├──→ 运行时校验：每次调用比对响应Schema
    │         │
    │         ├── Schema匹配 → 正常
    │         ├── 新增字段 → 记录+兼容
    │         └── 缺失/变更字段 → 告警+降级
    │
    └──→ 定期审计：盘后比对行为基线
              │
              ├── 延迟漂移>2σ → 告警
              ├── 数据质量下降 → 降级
              └── 字段覆盖率下降 → 告警
```

> **运行时契约引擎（D-INTEGRATION-02增强）**：§3.2.2描述的"契约注册+运行时校验+定期审计"是静态注册表模式。§25.3增强项将D-INTEGRATION-02从"契约注册表"升级为"运行时契约引擎"——契约不仅是注册和校验的被动记录，还是路由决策（版本不匹配→拒绝路由）、限流决策（契约漂移→降级限流）、熔断决策（行为基线偏离→触发熔断）的主动决策依据。升级路径：阶段1实现§3.2.2的静态注册表 → 阶段2实现运行时契约引擎（契约状态驱动路由/限流/熔断联动）。

> **交易契约桥（D-INTEGRATION-40）**：§3定义的接口契约治理覆盖所有外部API的通用契约管理。D-INTEGRATION-40（交易契约桥）是§3契约治理在交易领域的具体实现——定义L04-L06跨层集成契约+执行/市场子契约，蓝图映射MOD-INF-016(trading_contracts/)已建设。详见§28.3。

### §3.3 降级策略

#### §3.3.1 降级分级

| 降级等级 | 触发条件 | 行为 | 恢复条件 |
|---------|---------|------|---------|
| L0 正常 | 所有API版本匹配+行为正常 | 全功能运行 | — |
| L1 轻度降级 | 非关键字段缺失/新增 | 忽略缺失字段，使用默认值 | 字段恢复 |

```
         ├── 非关键字段？ → L1（忽略+记录）

```

## §4 数据源故障降级

### §4.1 三源互补

> 设计决策D-02：单源故障即全盘失效，双源无法仲裁数据质量差异，三源可投票仲裁。

#### §4.1.1 三源互补架构

```
                    ┌─────────────┐
                    │  数据源管理器  │
                    │  (仲裁层)     │
                    └──────┬──────┘
                           │
          ┌────────────────┼────────────────┐
          │                │                │
    ┌─────▼─────┐   ┌─────▼─────┐   ┌─────▼─────┐
    │ 主源       │   │ 备源1      │   │ 备源2      │
    │ miniQMT   │   │ iFind     │   │ tushare/  │
    │ xtdata    │   │           │   │ AkShare   │
    │ (实时行情) │   │ (研究数据) │   │ (降级源)  │
    └─────┬─────┘   └─────┬─────┘   └─────┬─────┘
          │                │                │
          └────────────────┼────────────────┘
                           │
                    ┌──────▼──────┐
                    │  数据质量    │
                    │  门禁+仲裁  │
                    └─────────────┘
```

#### §4.1.2 三源投票仲裁规则

| 场景 | 主源 | 备源1 | 备源2 | 仲裁结果 |
|------|------|-------|-------|---------|
| 全部正常 | ✅ | ✅ | ✅ | 使用主源，三源交叉校验 |
| 主源故障 | ❌ | ✅ | ✅ | 使用备源1，备源2校验 |
| 主源+备源1故障 | ❌ | ❌ | ✅ | 使用备源2，标记数据质量降级 |
| 仅主源正常 | ✅ | ❌ | ❌ | 使用主源，跳过校验，标记轻度降级 |
| 主源+一个备源正常 | ✅ | ✅ | ❌ | 使用主源，备源1校验 |
| 全部故障 | ❌ | ❌ | ❌ | L3重度降级：暂停信号生成 |

#### §4.1.3 数据质量校验维度

| 维度 | 校验方法 | 通过标准 | 不通过处置 |
|------|---------|---------|-----------|
| 新鲜度 | 数据时间戳 vs 当前时间 | 偏差<SLA（实时<10s，日频<1h） | 触发降级 |
| 完整性 | 预期字段覆盖率 | >99% | 标记缺失字段+降级 |
| 一致性 | 三源交叉比对 | 偏差<品种阈值（A股/ETF: 0.1%；可转债: 0.5%；期权: 2.0%） | 投票仲裁 |
| 合理性 | 统计异常检测（3σ规则） | 价格变动<日涨跌停限制 | 标记异常+人工确认 |

### §4.2 自动切换

#### §4.2.1 故障检测与切换流程

```
心跳检测（每3秒）
    │
    ├── 连续3次心跳失败（~9秒）→ 标记数据源不健康
    │
    ├── 自动切换到最高优先级健康数据源
    │
    ├── 切换后数据质量校验
    │         │
    │         ├── 校验通过 → 进入降级运行模式
    │         └── 校验失败 → 继续降级到下一优先级
    │
    └── 故障源恢复检测（每30秒试探）
              │
              ├── 恢复 → 数据一致性校验 → 切回主源
              └── 未恢复 → 继续降级运行
```

#### §4.2.2 切换参数

| 参数 | 值 | 理由 |
|------|-----|------|
| 心跳间隔 | 3秒 | 平衡检测速度与API开销 |
| 故障判定 | 连续3次失败 | 避免网络抖动误判 |
| 切换延迟目标 | ≤3秒 | §11成功指标要求 |
| 恢复试探间隔 | 30秒 | 避免对故障源造成压力 |
| 恢复校验窗口 | 5分钟连续正常 | 确认真正恢复再切回 |
| 数据一致性校验 | 切换后首个数据点 | 先切换再校验（§12冲突矩阵：切换速度优先） |

### §4.3 数据质量降级

#### §4.3.1 降级模式与数据消费规则

| 降级模式 | 数据新鲜度 | 因子计算 | 信号生成 | 交易执行 | 风控 |
|---------|-----------|---------|---------|---------|------|
| 正常模式 | 实时（<10s） | 全量因子 | 全量信号 | 正常执行 | 正常 |
| 延迟模式 | 延迟（10s~5min） | 仅核心因子 | 仅核心信号 | 正常执行（谨慎） | 正常 |
| 日频模式 | 日频（>1h） | 仅日频因子 | 仅日频信号 | 暂停新开仓 | 正常 |
| 停摆模式 | 无数据 | 暂停 | 暂停 | 仅平仓/风控 | 正常（加强） |

#### §4.3.2 降级自动恢复条件

| 从降级等级 | 恢复到 | 条件 | 人工确认 |
|-----------|--------|------|---------|
| L1→L0 | 轻度→正常 | 主源连续5分钟正常+数据校验通过 | 不需要 |
| L2→L1 | 中度→轻度 | 主源恢复+数据校验通过 | 不需要 |
| L3→L2 | 重度→中度 | 任一数据源恢复+数据校验通过 | 需要 |
| L4→L3 | 停机→重度 | 交易通道恢复 | 需要 |

### §5A A2A协议集成（Agent-to-Agent）

> A2A协议与MCP协议互补：MCP是Agent→工具的纵向调用，A2A是Agent→Agent的横向协作。2025年Google发布A2A协议规范，定义Agent Card发现+Task委托+Artifact交换。

#### §5A.1 A2A与MCP边界裁定

| 通信模式 | 协议 | 场景 | 裁定 |
|---------|------|------|------|
| Agent→工具调用 | MCP | 行情查询/因子计算/运维操作 | ✅能建（§5已定义） |
| Agent→Agent协商 | A2A | 策略投票/因子协商/运维委托 | ✅能建（项目内有蓝图MOD-INF-025脚手架，详见§28.7 D-INTEGRATION-09） |
| Agent→Agent交易委托 | 禁止 | 下单/撤单/风控检查 | ❌不能建（HB-07下单零重试+交易通道唯一性）。未来开通门禁：①A2A协议支持事务性消息确认（at-exactly-once语义）②A2A协商延迟可量化且P99<100ms③A2A-01铁律修订经架构评审通过④QP-02门禁全部满足（MCP交易Server安全条件同样适用于A2A交易委托） |
| 混合模式(A2A编排+MCP执行) | A2A+MCP | Agent A委托Agent B，Agent B通过MCP调用工具 | ✅能建 |

#### §5A.2 A2A能力矩阵

| 能力 | 二元结论 | 实现方式 | 门禁条件 |
|------|---------|---------|---------|
| Agent Card发现机制 | ✅能建 | 每个Agent注册能力描述Card+Redis存储 | 无 |
| Task委托协议 | ✅能建 | Agent间Task创建+状态追踪+结果回调 | 无 |
| Artifact交换 | ✅能建 | Agent间成果交换+版本标记 | 无 |
| A2A消息加密 | ✅能建 | 进程内通信无需加密，日志脱敏 | 无 |
| A2A→MCP混合编排 | ✅能建 | A2A编排层+MCP执行层 | 无 |
| 跨进程A2A通信 | ❌不能建 | 需要多进程架构+网络通信 | ①多进程架构(>5服务) ②进程间通信需要加密 |

#### §5A.3 A2A铁律

| 编号 | 规则 | 理由 |
|------|------|------|
| A2A-01 | 交易执行相关操作禁止走A2A | HB-07下单零重试+交易通道唯一性，A2A协商延迟不可控 |
| A2A-02 | A2A协商超时必须降级为默认策略 | 协商超时不能阻塞交易决策 |
| A2A-03 | A2A消息必须记录审计日志 | Agent间协商过程可追溯 |
| A2A-04 | A2A协商结果必须可人工覆盖 | AI协商结果不可信时人工介入 |

> **A2A消息传输层裁定**：A2A消息分两层传输——①**协商层**（进程内直接调用）：Agent间Task委托/Artifact交换/投票协商均为进程内函数调用，延迟最低，不经过Redis Stream；②**审计层**（Redis Stream异步持久化）：每次A2A协商完成后，协商摘要（参与Agent+协商结果+时间戳+idempotency_key）异步写入Redis Stream的`a2a.audit`通道，满足A2A-03审计追溯要求，但不阻塞协商流程。此设计与§2.3事件驱动架构的关系：A2A协商本身不属于Event Sourcing领域事件（不改变Order/Position/Portfolio聚合根状态），但A2A审计日志遵循Event Sourcing的不可变追加原则。

## §6 隔离策略

> 设计决策D-03：熔断器防级联故障，舱壁隔离防资源耗尽，两者互补缺一不可。
> 参考：Netflix Hystrix→Resilience4j演进；2026年交易系统架构"fails closed is better than fails open"原则。

### §6.1 熔断器

#### §6.1.1 熔断器状态机

```
              失败率>阈值
    ┌──────────────────────┐
    │                      │
    │                      ▼
┌───┴───┐            ┌─────────┐     等待超时     ┌──────────┐
│ CLOSED │            │  OPEN   │ ──────────────→ │ HALF_OPEN│
│ (正常)  │            │ (熔断)   │                 │ (试探)    │
└───┬───┘            └─────────┘                 └────┬─────┘
    │                      ▲                           │
    │                      │                           │
    │                      │     试探失败率>阈值         │
    │                      │◄──────────────────────────┘
    │                                                  │
    │              试探失败率<阈值                        │
    └──────────────────────────────────────────────────┘
                         → CLOSED
```

#### §6.1.2 熔断器配置矩阵

> **初始默认值说明**：以下熔断阈值为系统初始默认值，可通过§24闭环优化机制根据运行数据反馈调整（调整必须经过人工审批CL-01+交易时段禁止变更CL-04）。

| 外部系统 | failureRateThreshold | slidingWindowSize | waitDurationInOpenState | permittedCallsInHalfOpen | 恢复策略 |
|---------|---------------------|-------------------|------------------------|-------------------------|---------|
| miniQMT xttrader | 30% | 10次 | 人工确认 | — | 仅人工确认 |
| miniQMT xtdata | 50% | 20次 | 15s | 5次 | 自动 |
| iFind API | 50% | 20次 | 60s | 5次 | 自动 |
| tushare API | 60% | 10次 | 120s | 3次 | 自动 |
| LLM API（外部） | 50% | 10次 | 30s | 3次 | 自动+降级本地 |
| 微信Webhook | 80% | 5次 | 300s | 1次 | 自动 |

#### §6.1.3 熔断器降级行为

| 熔断对象 | 熔断后行为 | Fallback |
|---------|-----------|---------|
| miniQMT xttrader | 暂停所有下单→C-004风控加强监控 | 仅允许风控触发的平仓操作 |
| miniQMT xtdata | 切换iFind实时行情 | 降级为iFind 15s轮询 |
| iFind API | 切换tushare/AkShare | 三源互补仲裁 |
| LLM API | 切换本地LLM | 本地LLM兜底 |
| 微信Webhook | 降级为日志记录 | 不影响核心交易 |

#### §6.1.4 交易通道特殊熔断规则

> 交易通道熔断≠普通服务熔断。交易通道断开意味着资金风险敞口无法控制。

| 规则 | 说明 |
|------|------|
| 交易通道熔断必须人工介入 | 不可自动恢复，必须人工确认交易通道正常后才可恢复 |
| 熔断期间风控不可停 | 即使交易通道断开，风控监控必须继续运行（基于最后已知状态） |
| 熔断期间持仓保护 | 已有持仓不受影响，仅暂停新开仓和主动调仓 |
| 熔断恢复后必须全量同步 | 恢复后必须重新同步持仓/委托/成交状态，防止状态不一致 |

### §6.2 舱壁隔离

> 参考：多维度舱壁隔离——按关键性等级+操作类型隔离资源池。

#### §6.2.1 资源池隔离矩阵

| 资源池 | 容量 | 隔离维度 | 共享对象 | 独占对象 |
|--------|------|---------|---------|---------|
| 交易执行池 | 专用线程×2 | 关键性等级 | — | miniQMT下单/撤单/查询 |
| 行情接收池 | 专用线程×2 | 关键性等级 | — | miniQMT Tick回调/iFind行情 |
| 风控计算池 | 专用线程×2 | 关键性等级 | — | C-004风控引擎 |
| 数据拉取池 | 线程池×4 | 操作类型 | iFind/tushare/AkShare | — |
| LLM推理池 | GPU显存8GB | 操作类型 | 本地LLM/Whisper | — |
| 通知推送池 | 线程池×2 | 操作类型 | 微信/邮件 | — |

#### §6.2.2 舱壁隔离规则

| 规则 | 说明 | 执行机制 |
|------|------|---------|
| 交易/行情/风控三个池互不共享 | 核心交易链路不可被其他操作阻塞 | 独立线程池+独立事件循环 |
| 数据拉取池与LLM推理池互不共享 | 数据拉取阻塞不应影响AI推理 | 独立线程池 |
| GPU显存硬上限21.6GB | 约束二：显存<90%=21.6GB | C-029模型调度"谁上岗谁待命" |
| 单一外部系统不可耗尽共享池 | 防止iFind慢查询耗尽数据拉取池 | 每个外部系统在共享池内有子配额 |

#### §6.2.3 舱壁溢出处置

| 资源池 | 溢出检测 | 溢出处置 |
|--------|---------|---------|
| 交易执行池 | 队列深度>5 | 拒绝新请求+告警（交易不可排队） |
| 行情接收池 | 队列深度>10 | 丢弃最旧行情+告警 |
| 风控计算池 | 队列深度>3 | Fail-Closed：拒绝交易+告警 |
| 数据拉取池 | 队列深度>20 | 降级为批量模式+告警 |
| LLM推理池 | GPU显存>80% | 拒绝新推理请求→降级为外部API |
| 通知推送池 | 队列深度>50 | 丢弃低优先级通知+告警 |

### §6.4 Kill-Switch多层防御

> 参考：algotradingdesk.com 2025 "Automatic Kill-Switches in HFT Systems"；alphastrat.io 2026 "Kill switch design for automated trading"；IVRYN 2026 五层风险架构。
> 核心原则：**Preserve capital first, diagnose later.** 如果系统能自动交易，它也必须能自动停止交易。

#### §6.4.1 四级Kill-Switch阶梯

| 等级 | 名称 | 触发条件 | 动作 | 自动恢复 |
|------|------|---------|------|---------|
| KS-L1 | 软暂停 | 滑点>N次超阈值 / 单策略日内亏损超限 | 暂停新开仓，保留平仓能力 | ✅ 冷却期后自动恢复 |
| KS-L2 | 会话熔断 | 连续N笔亏损 / 模型漂移超阈值 / 策略逻辑完整性校验失败 | 禁用该策略本交易时段 | ❌ 需人工确认 |
| KS-L3 | 通道断开 | 下单拒绝率飙升 / miniQMT心跳失败 / API版本不匹配 | 断开交易通道+撤销所有挂单 | ❌ 需人工确认+全量同步 |
| KS-L4 | 硬停机 | 持仓异常 / 账户级日亏损超硬限 / NaN/负价格等数学腐败 | 终止所有自动化，保留证据 | ❌ 需人工确认+检查清单 |

#### §6.4.2 Kill-Switch多层防御架构

```
┌──────────────────────────────────────────────────────────┐
│ Layer 5: 交易所侧控制（券商提供的Kill-Switch）            │
│ └─ 最后防线，软件Bug无法绕过                              │
├──────────────────────────────────────────────────────────┤
│ Layer 4: 网关层=E0.5 API网关层（§19，连接/速率控制）      │
│ └─ KS-L3: 通道断开 + 撤销挂单                            │
├──────────────────────────────────────────────────────────┤
│ Layer 3: 执行层（订单级校验）                             │
│ └─ 订单速率限制 / 价格偏离检查 / 重复订单拦截             │
├──────────────────────────────────────────────────────────┤
│ Layer 2: 风控引擎层（组合/敞口限制）                      │
│ └─ KS-L2: 会话熔断 / 日亏损硬限 / 持仓限制               │
├──────────────────────────────────────────────────────────┤
│ Layer 1: 策略层（逻辑级检查）                             │
│ └─ KS-L1: 软暂停 / NaN检测 / 信号合理性校验              │
└──────────────────────────────────────────────────────────┘
```

#### §6.4.3 Kill-Switch触发器设计原则

| 原则 | 说明 |
|------|------|
| 客观可度量 | 触发条件必须基于可量化指标，不可基于"感觉" |
| 窗口化度量 | 避免单Tick噪声触发停机，使用滑动窗口统计 |
| 对称风险 | 不允许"可能会恢复"而继续承受下行风险 |
| 高等级禁止静默重启 | KS-L3/L4必须经过检查清单+人工审批 |
| 证据保留 | Kill-Switch触发后必须保留完整现场快照（时间戳/持仓/委托/行情/日志） |

#### §6.4.4 Kill-Switch恢复协议

| 从等级 | 恢复步骤 |
|--------|---------|
| KS-L1→正常 | 冷却期（5分钟）→ 自动恢复 |
| KS-L2→正常 | ①捕获事件快照 ②确认策略逻辑完整性 ③纸面验证1次 ④人工确认恢复 |
| KS-L3→正常 | ①捕获事件快照 ②验证配置Hash/版本匹配 ③全量同步持仓/委托/成交 ④小额实盘验证 ⑤人工确认恢复 |
| KS-L4→正常 | ①完整事后分析报告 ②根因确认+修复 ③全系统健康检查 ④纸面验证1个完整交易日 ⑤人工确认恢复+降低限额运行1天（持仓50%+单笔50%） |

| 规则 | 说明 |
|------|------|
| 非交易时段执行 | 混沌实验仅在非交易时段执行，避免影响实盘 |

## §9 方法论约束与设计决策

> 记录集成架构的关键设计决策及其理由，避免未来重复争论。

| 决策编号 | 决策 | 理由 | 替代方案 |
|---------|------|------|---------|
| D-01 | 需要独立集成架构而非嵌入各层 | 集成是横切关注点，嵌入各层会导致重复实现、策略不一致、故障隔离失效 | 各层自行集成（导致耦合扩散、隔离失效） |
| D-02 | 需要三源互补 | 单源故障即全盘失效，双源无法仲裁数据质量差异，三源可投票仲裁 | 双源热备（无法仲裁）、单源+缓存（新鲜度不足） |
| D-03 | 需要熔断器+舱壁隔离 | 熔断器防级联故障，舱壁隔离防资源耗尽，两者互补缺一不可 | 仅熔断器（资源仍可耗尽）、仅舱壁（无法快速失败） |
| D-04 | MCP协议是集成架构的一部分 | MCP是外部AI服务交互的标准协议，属于集成边界职责，需统一治理 | 各Agent自行对接（协议不一致、安全失控） |
| D-05 | API版本管理是硬约束 | 外部API无版本控制将导致静默兼容性故障，排查成本极高 | 宽松兼容（隐藏故障风险）、运行时动态适配（复杂度失控） |
| D-06 | 交易通道熔断需人工恢复 | 交易通道断开=资金风险敞口失控，自动恢复可能导致状态不一致下的错误交易 | 自动恢复（状态不一致风险） |
| D-07 | 下单零重试策略 | 下单重试=重复下单风险，即使幂等Key也无法100%防止券商端重复 | 带幂等Key重试（仍存在极端场景重复风险） |
| D-08 | 事件驱动+Event Sourcing用于关键聚合根 | 交易/持仓/组合状态变更必须可追溯、可审计、可重放，Event Sourcing是唯一满足三者的模式 | 仅CRUD（无审计链）、仅日志（不可重放） |
| D-09 | CQRS分离命令与查询 | 交易系统读写模式差异极大（写低频高价值/读高频低价值），统一模型无法同时优化 | 统一数据模型（读写互相拖累） |
| D-10 | iFind QPS精细分时段管理 | 20 QPS是账号总上限，不分时段管理会导致盘中QPS超限 | 固定QPS分配（浪费盘前/盘后配额） |
| D-11 | 需要轻量级API网关而非独立网关进程 | Python单机架构无需独立网关进程，FastAPI中间件即可实现统一入口+限流+熔断+审计 | 独立网关进程（Kong/APISIX，资源开销过大） |
| D-12 | 需要Python原生可观测性而非OpenTelemetry | OTel为微服务分布式系统设计，单机Python+少量外部API用structlog+prometheus_client+loguru即可 | OpenTelemetry全栈（5+依赖库+Collector+存储后端，过度工程） |
| D-13 | 需要消费者驱动契约测试 | 外部API无版本控制将导致静默兼容性故障，契约测试是唯一防线 | 仅Schema校验（无法发现行为漂移）、仅人工测试（不可持续） |
| D-14 | 需要四级限流架构 | iFind QPS=20是账号总上限，不分层级管理会导致关键操作被非关键操作挤占 | 固定QPS分配（浪费优先级调度能力） |
| D-15 | 下单执行使用编排式Saga | 下单流程有严格顺序依赖和超时约束，编排式可保证原子性+补偿 | 协调式Saga（无中央协调器，难以保证顺序和超时） |
| D-16 | 需要A2A协议与MCP协议双协议架构 | MCP是Agent→工具纵向调用，A2A是Agent→Agent横向协作，两者互补而非替代 | 仅MCP（无法支持Agent间协商）、仅A2A（无法调用工具） |
| D-17 | 需要集成闭环优化但必须人工审批 | 集成参数（熔断阈值/QPS分配/降级策略）需要根据运行数据持续优化，但自动调整可能导致级联故障 | 全自动调整（级联故障风险）、静态配置（无法适应运行时变化） |
| D-18 | 需要合规网关层嵌入API网关 | 2025-2026年监管要求外部接口纳入合规治理，合规检查必须在集成层执行点 | 合规检查仅在业务层（无法拦截违规API调用） |
| D-19 | 需要集成层灾备的状态可重建性 | 灾备不仅是数据备份，而是确保集成状态可从声明式配置+数据快照完全重建 | 仅数据备份（配置/契约/基线无法恢复） |
| D-20 | 需要成本感知LLM路由 | LLM API成本是主要变量，不同查询类型应路由到不同成本层 | 统一路由（浪费成本或精度不足） |
| D-21 | 需要蓝图-架构双向映射 | 项目蓝图是代码实现的唯一真源，架构文档必须与蓝图双向映射——蓝图已建设的模块标注建设状态，蓝图未定义的模块标注为场外新增 | 仅架构文档无蓝图映射（架构与代码脱节）、仅蓝图无架构文档（蓝图缺乏架构上下文） |
| D-22 | 需要功能开关管理器支持渐进式集成 | 新模块上线不应是全量切换，而应通过功能开关渐进式引入——先1%流量验证→10%→50%→100% | 全量上线（回滚风险大）、手动切换（不可审计不可追溯） |

## §12 冲突与矛盾矩阵

> 集成架构中不可同时最优的维度，需明确仲裁规则。

| 冲突方A | 冲突方B | 冲突场景 | 仲裁规则 | 优先级 |
|--------|--------|---------|---------|--------|
| 数据新鲜度 | 数据成本 | 实时数据源费用高昂，延迟数据免费 | 核心交易通道优先新鲜度，研究场景可接受延迟 | 新鲜度优先（交易通道） |
| 故障切换速度 | 数据一致性 | 快速切换可能导致短暂数据不一致 | 先切换再校验，事后补偿一致性问题 | 切换速度优先 |
| 集成丰富度 | 隔离安全性 | 接入更多外部系统增加攻击面 | 每个新增集成必须通过安全评审，白名单管控 | 安全性优先 |
| API版本升级 | 兼容性 | 升级外部API可能破坏现有集成 | 强制版本管理，不兼容版本必须拒绝并告警 | 兼容性优先（硬约束） |
| 重试可靠性 | 操作幂等性 | 重试可提高可靠性但增加重复操作风险 | 下单零重试，查询有限重试 | 幂等性优先 |
| 隔离粒度 | 资源效率 | 更细粒度的舱壁隔离消耗更多资源 | 核心路径（交易/行情/风控）独立池，非核心路径共享池 | 核心路径隔离优先 |
| MCP能力开放 | 安全边界 | MCP工具越多，AI能力越强但安全风险越大 | 写操作必须人工审批，读操作自动放行 | 安全边界优先 |
| 限流精度 | 系统复杂度 | 更精细的限流需要更多配置和监控 | 四级限流已足够，不引入自适应限流 | 精度优先（在四级框架内） |
| 契约测试覆盖 | 测试维护成本 | 更多契约测试=更多维护 | 核心API(交易/行情/风控)100%覆盖，非核心API按需覆盖 | 核心覆盖优先 |
| 数据一致性 | 系统性能 | 更强一致性需要更多同步等待 | 核心数据(持仓/行情)3-10秒SLA，非核心数据异步 | 核心数据一致性优先 |
| A2A协商延迟 | 交易实时性 | A2A协商可能引入不可控延迟 | 交易执行禁止走A2A(A2A-01) | 交易实时性优先 |
| 闭环参数优化 | 系统稳定性 | 参数变更可能引入不稳定 | 参数变更必须人工审批(CL-01) | 稳定性优先 |
| 合规拦截 | 交易效率 | 合规检查增加调用延迟 | 合规检查嵌入网关层(非业务层) | 合规优先 |

## §15 遗留问题裁定

> 17项遗留问题的二元裁定。基于当前13条硬边界（HB-01~HB-13），每项功能只有两个结论：✅ 现在能建 或 ❌ 现在不能建。不能建的写明未来开通的硬边界门禁条件。

### §15.1 QP-01：交易通道熔断自动恢复

> **大白话**：交易通道断了（比如miniQMT崩了），系统发现通道恢复了，是自己先试着连回去，还是必须等人按按钮才能连回去？

| 维度 | 结论 |
|------|------|
| 二元结论 | **❌ 不能建自动恢复** → 必须纯人工恢复 |
| 硬边界门禁 | HB-06（交易通道熔断必须人工恢复）+ HB-07（下单不可自动重试）双重锁定 |
| 理由 | 交易通道恢复时持仓/委托/成交状态可能不一致，自动恢复可能在状态混乱时下单。Knight Capital 4.4亿美元亏损就是状态不一致+无Kill-Switch的后果。专业HFT机构对交易通道恢复一律要求人工确认 |
| 行业证据 | algotradingdesk.com 2025：交易通道断开=资金风险敞口失控，自动恢复可能导致状态不一致下的错误交易 |
| 未来开通条件 | ①券商提供原子化状态同步API（可一键获取完整持仓+委托+成交快照）②实现自动全量状态对账+差异告警③连续3次人工恢复均无状态差异后，可申请评审是否降级为"自动试探+人工确认" |

### §15.2 QP-02：MCP交易执行Server

> **大白话**：让AI Agent通过MCP协议直接调用"下单"工具，还是下单操作永远不经过MCP，只走内部专用通道？

| 维度 | 结论 |
|------|------|
| 二元结论 | **❌ 不能建** → 下单操作不通过MCP暴露 |
| 硬边界门禁 | HB-08（外部API禁止传输持仓/策略数据）+ HB-07（下单不可自动重试）+ HB-05（隔离策略不可绕过） |

## §21 数据一致性保证

### §21.1 数据一致性SLA

| 数据类型 | 一致性SLA | 实现机制 | 不一致处置 |
|---------|----------|---------|-----------|
| 持仓数据 | 3秒内一致 | miniQMT回调+Redis Stream增量同步 | 超时→全量同步+告警 |
| 行情数据 | 10秒内一致 | miniQMT Tick推送+iFind 15s轮询降级 | 超时→降级模式 |
| 因子数据 | 5分钟内一致 | 批量计算+Redis Pub/Sub通知 | 超时→标记因子过期 |
| 报告数据 | 1小时内一致 | 事件驱动异步聚合 | 超时→标记报告待更新 |

### §21.2 下单执行Saga

> 下单流程使用编排式Saga，保证跨系统操作的原子性。

```
下单Saga（编排式）:
  Step 1: 风控检查 → 失败补偿: 无需补偿（检查操作）
  Step 2: 信号确认 → 失败补偿: 无需补偿（确认操作）
  Step 3: 下单提交 → 失败补偿: 撤单（如果已报）
  Step 4: 成交确认 → 失败补偿: 无需补偿（被动等待）
  Step 5: 持仓更新 → 失败补偿: 持仓回滚
  Step 6: 报告生成 → 失败补偿: 标记报告待更新（异步）
```

### §21.3 Saga设计原则

| 原则 | 说明 |
|------|------|
| 补偿必须幂等 | 撤单操作如果已成交则忽略，持仓回滚如果已更新则覆盖 |
| Saga状态持久化 | Redis Stream记录每个Saga步骤执行状态（§2.3 Event Sourcing机制），故障恢复后从断点继续 |
| 下单Saga使用编排式 | 下单流程有严格顺序依赖和超时约束 |
| 数据同步使用协调式 | 数据更新事件发布后，各消费域自行决定如何处理 |
| Saga超时硬约束 | 整个Saga执行时间不可超过业务SLA（下单Saga≤5s） |

> **交易契约桥（D-INTEGRATION-40）**：§21下单Saga的各步骤（风控→信号→下单→成交→持仓→报告）遵循D-INTEGRATION-40定义的L04-L06跨层集成契约+执行/市场子契约。Saga编排是契约的运行时执行，契约是Saga的结构约束。详见§28.3。

## §22 术语表

| 术语 | 定义 | 歧义消解 |
|------|------|---------|
| 熔断器(Circuit Breaker) | 外部系统故障时快速失败的隔离机制，三态机：Closed→Open→Half-Open | 非交易通道熔断=自动恢复；交易通道熔断=人工恢复（§6.1.4特殊规则） |
| 舱壁隔离(Bulkhead) | 按关键性等级隔离资源池，防止一个外部系统耗尽所有资源 | 与熔断器互补：熔断器防级联故障，舱壁防资源耗尽 |
| Kill-Switch | 多层防御的紧急停机机制，四级阶梯：KS-L1~L4 | 非熔断器：熔断器是单系统隔离，Kill-Switch是全系统防御 |
| 三源互补 | 三个数据源互为备份+投票仲裁的容错架构 | 非三主架构：主源→备源1→备源2优先级降级 |
| 契约漂移(Contract Drift) | API Schema不变但行为/性能变化的隐性兼容性故障 | 视同破坏性变更，触发告警+降级 |
| 降级(Degradation) | 外部系统不可用时降低功能等级但保持核心运行的策略 | 降级≠停机：L0正常→L4停机共5级。**歧义消解**：本文"降级"有三种语义，按上下文区分——①**功能降级**（§3.3）：系统运行等级降低，如"L2中度降级""风控不可降级"；②**路由降级**（§4/§1.3.2）：从主源/首选切换到备源/备选，如"降级为iFind""降级为外部API"，本质是路由切换动作，可能触发功能降级但本身不是功能等级降低；③**容量降级**（§20.2）：降低QPS/容量以适应限制，如"降级为批量模式""反爬降级"。判定规则：若"降级"后跟具体系统名（降级为X），则为路由降级；若"降级"前有等级修饰（L1/L2/L3降级、轻度/中度/重度降级），则为功能降级；若"降级"涉及QPS/批量/轮询间隔，则为容量降级 |
| MCP(Model Context Protocol) | AI服务与外部工具/数据的标准交互协议(JSON-RPC 2.0) | 非A2A协议：MCP是Agent↔工具，A2A是Agent↔Agent |
| Saga | 跨系统长事务的编排模式，每步有补偿操作 | 非数据库事务：Saga不保证ACID，保证最终一致性+补偿 |
| SLI/SLO/SLA | 指标/目标/协议——SLI量化度量→SLO目标值→SLA承诺 | 本系统仅定义SLI+SLO，不对外承诺SLA |
| 误差预算(Error Budget) | SLO允许的误差总量，耗尽后触发自动降级 | 非预算制度：是可靠性工程的概念 |
| A2A协议(Agent-to-Agent) | Agent间协作的标准协议，包含Agent Card发现+Task委托+Artifact交换 | 非MCP协议：MCP是Agent→工具，A2A是Agent→Agent |
| 集成闭环优化 | 集成参数通过运行数据反馈持续优化的机制，所有变更必须人工审批 | 非自动调参：闭环=反馈+建议+审批，非自动生效 |
| 合规网关层 | API网关中嵌入的合规检查层，在路由+限流+熔断之外增加合规维度 | 非业务层合规：合规检查在网关层执行，拦截违规API调用 |
| 状态可重建性 | 系统状态可从声明式配置+数据快照完全重建的能力 | 非数据备份：备份仅恢复数据，可重建性恢复数据+配置+契约+基线 |
| Deprecating变更 | 字段/接口已弃用但仍可用的过渡期变更级别 | 非破坏性变更：Deprecating有3个月过渡期，到期后变为破坏性 |
| 蓝图(Blueprint) | ZephyrAlpha项目SYSTEMS_GUIDE中定义的模块编号（如MOD-INF-016），是代码实现的唯一真源。§28中"蓝图映射"指将集成域子模块与项目蓝图编号交叉对照 | 非架构设计蓝图：本文"蓝图"特指项目代码库中的SYSTEMS_GUIDE蓝图编号，非泛指的架构设计文档。四级状态：已建设(引用的代码路径已实现且可运行)/部分建设(引用的代码路径已存在但功能不完整)/有蓝图未建设(仅脚手架或未实现)/无蓝图(场外设计新增) |

## §27 集成层灾备与状态可重建性

> 2025-2026年单机架构灾备从"数据备份"升级为"状态可重建性"——不仅备份数据，还要保证状态机可从零重建。

### §27.1 集成层灾备场景

> **Kill-Switch与灾备的关系裁定**：Kill-Switch（§6.4）是**主动防御机制**——检测到异常信号（滑点超限/连续亏损/心跳失败）后主动触发止损动作，防止损失扩大；灾备（§27）是**被动恢复机制**——故障已经发生后，如何从故障状态恢复到正常运行。两者衔接关系：**Kill-Switch触发 → 灾备接管恢复**。以miniQMT连接断开为例：§6.4 KS-L3检测到心跳失败→主动断开交易通道+撤销挂单（防御）→§27.1场景2接管恢复流程→仅保留持仓监控→人工确认恢复（恢复）。Kill-Switch解决"何时停"，灾备解决"如何恢复"。

| 灾备场景 | 触发条件 | 影响范围 | 恢复策略 | RTO |
|---------|---------|---------|---------|-----|
| iFind API行为变更 | 契约漂移检测触发 | 行情/因子数据降级 | 自动切换tushare备源 | <1s |
