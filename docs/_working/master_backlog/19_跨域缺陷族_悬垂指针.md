# 19 · 跨域缺陷族：悬垂指针 / 静默空转

> **为什么单列一卷**：本轮核查发现有一类缺陷**横跨多个地图**，单看任何一域都只是"一个小问题"，
> 但合起来是**同一个病**：**真身搬走了/从未落位，指向它的指针没跟着改**。
> 后果不是报错，而是**静默空转 / 静默假绿**——系统看起来在跑，实际什么都没做。
>
> 本卷由 gp-11 / gp-12 / gp-2 / gp-8 / gp-6 五条车道交叉归纳而成。

---

## §1 病理解剖

```
真身迁移 / 从未落位
        │
        ▼
指针没跟着改  ──►  exists() 判"不存在"  ──►  ① 被记成"文件没了"（幽灵条目假阳性）
        │                                    ② log-and-skip（静默跳过，不报错、不出数）
        │                                    ③ 只判"文件存在"即 GREEN（假门禁）
        │                                    ④ revoke/resolve 静默失效
        ▼
  系统表现为：门是绿的、日志是干净的、但产出恒为 0
```

### §2.0.1 建议立统一项：「**假成功哨兵**」（P-10 + P-12 同病）

> 三者共同点：**执行侧状态位可信度为 0，只能从产出侧形状反推失效**。

| 病灶 | 执行侧状态 | 产出侧真相 |
|---|---|---|

### 判据⑥：**报"静默失败"前先分级**

```
⑥ 静默降级分两级，别混为一谈：
   · 一级·无信号：系统内部根本没有记录失效 ⇒ 必须改代码，通常要 Owner 批

```

> **这条对"是否必须等 Owner 批"的分流很实用**——二级问题不该堵在审批队列里。

## §4.5 🔴 通用解法：把 `module_ref` 做成常态核销（**本卷最重要的建议**）

> 来源：gp-7 第 4 次增量。本卷 P-4/P-5 与 `09` 卷 EX-5（制度五查）、EX-12（MOD-RK-049）
> **都是靠人工逐条对账才发现**的。而制度侧其实**早就给了机器可判的依据**。

`config/trading_decision_map.yaml` 里每个节点都有 `module_ref`（责任模块）+ `module_id` + `activation` + `invalidation`。
**字段已经把「制度要求」和「实现文件」绑定好了，缺的只是一道自动核销。**

**建议的核销规则（三项断言，可机读）**：

| 断言 | 判据 | 对应病例 |
|---|---|---|
| ①**存在性** | `module_ref` 指向的文件在 HEAD 中存在 | P-1 / P-2 / P-4 |
| ②**被调用性** | 该模块在 `src/` + `scripts/` **生产侧**有真实调用方（排除仅 re-export / 仅测试） | EX-12 / P-2 |
| ③**激活一致性** | 若 `activation: continuous`，则必须有调度/常驻入口；否则判"制度要求持续但实现未接" | EX-12 |

> **⚠ 判据口径**：gp-11 自曝过「只扫 `.py` 就判未接线」的片面性——
> 核销脚本的**输入面必须含非 `.py` 面**（`config/*.yaml` / `scripts/` 内 `from|import` / 计划任务注册 / CLI `--help`），
> 否则会把"已接线"误判成"未接线"。

**收益**：本卷 10 个病例里，**至少 5 个可由这三条断言自动捞出**，无需人工逐条对账。
建议作为**独立的治理增强项**立项（可与 `19` 卷 R-1/R-2/R-3 三条评估纪律同批）。
