## 2. post-flush 复发根因（file:line 级机理）

### 2.1 三个问题的直接回答

**Q1 每次 flush 都重登记吗？——是（脚本必跑），但 DB 重写与提交有条件。**
`git_commit_gateway.py:1831`（sync 路径）与 `:1894`（worker 路径）在每笔经 reconcile 链路的 gateway 提交 flush 后**无条件**调 `_post_flush_rules_integrity_re_register`；`:1737-1746` 无条件 spawn `validate_rules_integrity.py --register` 子进程（timeout=30s）。两道下游闸门决定是否真的落 commit：
- `validate_rules_integrity.py:282`：`if new_files == old_files: return {"status": "unchanged"}`——hash 全同则**不写 DB**（2026-06-30 治本，register 语义已从"无条件重写"改为"仅在变化时重写"）。
- `git_commit_gateway.py:1759-1761`：register 后 `git diff --name-only -- <db>` 为空 → return 不提交。

**Q2 DB 内容真的变了吗？——真变了，零空转。**
对窗口内全部 31 笔 integrity 提交逐笔 `git show <hash> -- scripts/governance/meta/rules_integrity_db.json` 取证：**每一笔都改了真实 hash 行**（最少 2 行非时间戳变更 = 一旧一新 hash；`registered_at` 时间戳仅随真变更顺带更新；`last_check_at` 冻结在 2026-08-02）。**不存在"内容没变也提交"的 DB 层自激环**——两道防空转闸均有效。
hash 变更来源分布（31 笔合计）：`capability_canonical_file_registry.yaml` **26 笔**、`code_algorithm_extractor.py` 7 笔、`test_code_algorithm_extractor.py` 6 笔、`git_commit_gateway.py` 2 笔、`reconciliation_registry.py` 1 笔、`commit_gate_registry.py` 1 笔。

**Q3 是否存在自激环？——DB 层无；结构层有。**
结构性自激链：`capability_canonical_file_registry.yaml` 是 CREATE-GUARD creation_token 真源且被锚入 golden-hash 保护清单（`validate_rules_integrity.py:123-127`）。窗口内 **42 笔提交触碰该文件**（几乎每笔建新文件的提交都同批登记 token）→ 受保护文件高频真变 → 每笔触碰它的提交 flush 后派生一笔**独立** integrity commit。31 笔中 26 笔源于此文件。
相邻性实证：30/31 笔 integrity 提交的紧邻前一笔是 REAL/CHORE/RECONCILER 提交（派生自真实提交，1:1 跟单）；仅 1 例 integrity→integrity 相邻（`831c426704` ← `5440514c77`，间隔 5.5min，多会话并发下 registry 在两次 flush 间再次移动）。

### 2.2 复发频率实测（证伪"每 3-4 分钟"为稳态）

31 笔间隔（分钟）：**min 1.9 / P50 28.4 / mean 46.3 / max 245.6**。"每 3-4 分钟复发"仅在提交密集爆发段成立（如 09-17 01:04→01:06 间隔 1.9min；02:24→03:39 段多笔 ≤15min）；24h 全程中位数 28 分钟。**复发频率 ≈ 触碰受保护文件的提交频率**，不是独立时钟。

### 2.3 "时序竞态治本 2026-08-02"的真实含义

2026-08-02 修复（docstring `git_commit_gateway.py:1711-1727`）治的病是：reconcile 内 `--register` 读 pre-flush HEAD → DB 基线滞后一周期 → 永久 TAMPERED。修复把基线读准了（post-flush HEAD），但成本形态变成"每触碰受保护文件一次就 +1 笔独立 commit"——**治好了基线滞后，留下了独立提交税**。且该提交自称"治本"却持续复发，原因是它治的是时序竞态，不是提交税。

### 2.4 连带伤害（队列死信，实锤）

24h 内 176 笔死信中 **23 笔（13.1%）dead_reason 明写 `rules_integrity_db.json`**（"NOTHING_TO_COMMIT 但快照未真应用 (blob 与 old_dev 不符)"）——队列件入队时携带 DB 快照，落地前 DB 已被另一笔 integrity 提交移动 → blob 不匹配 → 静默丢失死信。全时段 733 笔死信中 **131 笔（17.9%）**涉该文件。integrity 环不仅加税，还杀其他车道的队列件。

## 5. 给 L0 的结论摘要（≤10 行）

1. 窗口实测 309 笔提交（指令书 314，窗口边界差异），衍生税 79 笔 = 25.6%，真实交付 230 = 74.4%。
2. 严格可消除 34 笔 = 11.0%（integrity 31 + watchdog 3）；reconciler 并入触发 commit 则 52 笔 = 16.8%。
3. integrity 复发**不是**"内容没变也提交"——31 笔全部改了真实 hash，两道防空转闸（`validate:282` + `gateway:1759`）均有效。
4. 真根因：`capability_canonical_file_registry.yaml`（creation_token 真源）锚在 golden-hash 清单里，窗口内 42 笔提交触碰它 → 每笔 flush 派生 1 笔独立 integrity commit（26/31 源于此）。
5. "每 3-4 分钟"非稳态：间隔 min 1.9min / P50 28.4min；复发频率 = 触碰受保护文件的提交频率。
6. 连带实锤：24h 176 死信中 23 笔（13.1%）死于 integrity DB 漂移；全时段 131/733 = 17.9%。
7. 队列 24h：done 130 / dead 176，死信率 57.5%；52.3% 死因为门禁落地期阻断，15.3% CLAIM_REQUIRED。
8. 建议方向（非裁定）：integrity 重登记与 reconciler 派生物并入触发 commit（S18-R2）；watchdog 状态不变不落盘；入队即预检门禁 + claim 前置。
9. 最终裁定归 L0；本 lane 未改任何既有文件、零 git 写操作。
