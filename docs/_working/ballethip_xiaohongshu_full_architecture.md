## 一、低学历勇闯量化赛道(第一篇) — 性能优化

### 1.0 团队背景与优化范围(正文)

博主在大厂积累了**底层和性能分析**经验,创业后负责低延迟系统开发和策略性能调优。团队选择从 **Polymarket 市场开始试水**(BTC 5分钟预测),用 **Rust** 从零构建系统。

**优化覆盖面**(从正文):
- 行情系统到特征工程建立
- CPU 上疯狂优化: 逻辑变成 **cache-friendly 代码**
- 网络文件 IO 优化
- 系统调用、中断、内存管理优化
- 线程调度亲和性
- 网卡高性能

> "从微秒到纳秒,终于把**行情流入到决策做出压缩到700ns之内**。"

**性能分析工具**: 吃透 **perf** 和 **Intel VTune** 的报告,对 CPU 非常了解。

**关键认知(评论区Q&A)**:
- 700ns 只是**进程内 pipeline latency**(网络部分还没开始优化)
- "平均在700ns但是p99 p999都很难看,**尾部延迟还有抗抖动做的都不好**,这是后面的优化要做的"
- "不是说平均快就快,**要极差小才好**"
- 后续计划: 对网络还有机器特调
- "我们不用做的那么那么快,只要做的比不懂性能优化操作系统调优的人快就可以了"

## 二、低学历勇闯量化赛道(第二篇) — 生产监控与工程演进

### 2.0 实盘结果与问题承认(正文)

**实盘测试结果**(3周):
- 周盈利率 **80%**, 胜率 **100%**, 没有回撤
- 处于**逐步灰度放开仓位阶段**(金丝雀发布原则)
- 博主明确承认"**我们非常清楚的认识到这是有问题的**"

**已识别的问题**:

| 问题 | 详情 |
|------|------|
| **人手不够** | 核心瓶颈,导致很多优化没做 |
| **市场深度未测出** | 测试资金不多,100/1000/1w/10w在不同资金下同策略可能分歧很大 |
| **吃单率/排队/竞对分析欠缺** | 下单是低shares多单还是多shares低单没做数据统计 |
| **仓位风险资金管理建模未做** | 因素叠加未做最大化收益 |
| **置信度过于保守** | 99~99.5 confidence 才下单,损失很多机会;实盘数据显示不需要这么高 |
| **故意屏蔽风险选择收益** | 为了100%胜率给初创团队信心,但不是利益最大化 |

**选择 Polymarket 的原因**: 损失可控、市场干净噪声小,适合没经验的新人和新手团队磨合。

**端到端延迟**: 行情信号从来到下单可控制在 **120ms** 左右(对比第一篇的 700ns pipeline latency,差距来自网络+下单IO)。博主表示"有可能再有几个月就是 **20ms**"。

**网络问题**: 日本到上海家里的服务器在**晚高峰有时会有很严重的数据积压**,针对这一块做了**主动探测和 QoS 管理**。

**后续优化计划**: 重写 PM SDK 做更高性能优化;补上日志系统和本地数据库缓存的性能分析。

### 3.2 高精度时间获取(度量衡基石)

**核心问题**: 行情服务器和下单服务器不在同一台机器上时,**时间没有对齐**。

| 场景 | 时间对齐方案 |
|------|-------------|
| 同供应商机器(如都在AWS) | 确认 **PTP(Precision Time Protocol)** 服务是否开启 |
| 跨供应商机器 | 需要自己建立可观测数据做 **offset 校准** |

> **"时间是评价测量的标准,如果时间不准确,后面的延迟评估会非常糟糕。"**

博主把时间放在第一个点讲的原因:
1. 没有基准时间,可观测网络建立会非常麻烦——到底哪里慢,可能分析出来的是一个飘忽不定的结果
2. 对于 HFT 高频交易团队,极限性能压榨的指标非常看重
3. 必须先建立最基本的度量衡,才能做后续的延迟分析和网络可观测

### 3.3 网络问题:跨境组网

#### 3.3.1 境内基建 + AWS 交易系统的网络困境

初创团队因成本原因,部分基建放在境内,但交易系统在 AWS 上。当数据库在境内、下单/撤单数据需要回传时,网络成为绕不开的问题。

**方案一: 反向连接**

让需要上报 AWS 的客户端主动反向请求连接到境内服务器:
- 家用 IP 因 PPPoE 拨号不固定 → 使用 **域名 + DDNS** 方案动态绑定域名到动态 IP
- 多数情况下可以连通,但"能连通不代表没问题"

**163 骨干网问题**:
- 中国电信家用网一般是 **163 骨干网**(电信网络系统中最差的一套)
- 跨境网络带宽非常小,**晚高峰 TCP 连接数据积压非常严重**
- 造成各种上报丢包、数据晚到、丢包、不可达等问题

> "再次强调可观测系统的重要性"——积压问题是靠可观测系统发现的。

#### 3.3.2 主备双活: Cloudflare Zero Trust + Tunnel

**方案二: Cloudflare Tunnel 加速**

利用 Cloudflare 的 Zero Trust 访问系统跨域组网:
1. 通过 **Cloudflare Tunnel** 将家里主机接入 Cloudflare 边缘节点
2. 通过 Cloudflare 的网络进行加速,分配独立域名
3. AWS 节点访问该域名 → 接入最近的 Cloudflare 节点 → 走 Cloudflare 自有网络进入国内 → 离家最近的节点下车 → 进入服务器

**Cloudflare 优势**:
- 自有 BGP 路由分配系统
- 使用 **CN2 网络**(比163骨干网稳定可靠得多)
- **免费**

**降级逻辑设计**:
- 默认使用反向直连(域名+DDNS)
- 当反向直连域名网络不可用时,接入 Cloudflare 网络
- **建议用 IPv6 接入**(IPv4 的 CF 网络在国内可能无法连接)

### 3.4 主备双活容灾设计

#### 3.4.1 行情线路双活

> "主备双活是非常重要的,简而言之就是容灾,尤其是行情线路最好是多条同时存在。"

| 场景 | 后果 |
|------|------|
| 行情线路故障,无备用 | 暂停下单 → 最多吃不到 |
| **撤单信号传不过去** | **资损!** |

- 行情线路最好多条同时存在,某些场景甚至会有**三活**
- 一旦行情出现问题,备用线路系统迅速顶上

#### 3.4.2 稳定性 > 低延迟

> **"对于我们高频交易系统开发来说,相比于低延迟我们会更加担心稳定性。延迟高一点我们可以想办法从模型测做一些弥补,但是稳定性达不到、忽高忽低会非常要命。"**

| 维度 | 低延迟 | 稳定性 |
|------|--------|--------|
| 可补偿性 | 模型侧可弥补 | 忽高忽低无法补偿 |
| QoS 可管理性 | — | 很难主动管理,对突发状况不具备短时预见性 |
| AWS VPC | 无法带来极致低延迟 | **大幅降低抖动**,数据传输稳定性有保障 |

**基建决策原则**: 想清楚什么东西可以省,什么事不能省。例如 AWS VPC 虽然不是最低延迟,但稳定性保障不可省。

#### 3.4.3 数据上报侧主备双活

数据上报侧同样需要主备双活:
- **默认**: 普通宽带
- **特殊情况**: 切换到 Cloudflare 通道

需要警醒的问题:
1. 数据是否有**事务性提交**?
2. 是否对网络主动做 **QoS 探测**监视线路质量?

### 3.5 事务性提交与 WAL

博主的数据上报设计:

```
数据 → 先写入 RocksDB(内存数据库) → 再写入服务端(事务性操作)
                    ↓ 两条网线都断了时
              RocksDB 数据序列化到本地保存
                    ↓ 线路恢复后
              回写回去(保证不丢数据)
```

> **"这其实也是事务性提交的根本思想——加入中间缓冲层 WAL,这个在我们的行情录制系统中也是这么做的。"**

这一设计与 Part 2 的边缘 WAL + 后端 WAL 双层架构一脉相承,从数据上报侧再次印证了 WAL 作为事务性缓冲层的核心价值。

### 3.6 第三篇核心总结

| 主题 | 关键要点 |
|------|---------|
| **高精度时间** | 时间是度量衡基石;同供应商用PTP,跨供应商做offset校准;无基准则延迟分析飘忽不定 |
| **跨境网络** | 163骨干网晚高峰严重积压;Cloudflare Tunnel+CN2免费加速;IPv6接入;DDNS反向连接 |
| **主备双活** | 行情线路双活/三活(撤单失败=资损);数据上报侧主备;AWS VPC稳定性优先 |
| **稳定性 > 低延迟** | 延迟可由模型弥补,稳定性不可补偿;QoS突发状况难预见 |
| **WAL事务性提交** | RocksDB先写本地再写服务端;断网时序列化本地;恢复后回写;与行情录制系统WAL一致 |

> **下一篇预告**: 基建网络的搭建和选型,包括技术层和业务层的选择以及整套系统框架的搭建。

## 四、行情与回测系统 Part 1 — 行情录制端

> 原文标题: "从实时盘口到可验证回放: 我怎么做pm回测系统(第一篇)"

### 4.1 核心理念

> "我们要建立的不是一根从 WebSocket 通往数据库的管道,而是一条**从实时市场到可验证回放的数据证据链**。"

一套可以长期运行的行情系统,不仅要追求接收速度,还要回答几个更难的问题:
1. 一个标记为"五分钟"的市场究竟应该从什么时候开始录制?
2. WebSocket 已连接,是否意味着数据一定完整?
3. 连接轮换、程序升级或服务器故障时,如何避免不可恢复的缺口?
4. 几个月之后,如何证明回测看到的盘口接近当时的真实市场?

### 4.2 系统全局架构

```
┌─────────────┐    ┌──────────────┐    ┌─────────────┐    ┌──────────────┐    ┌─────────────┐
│  市场数据源   │───▶│   行情录制    │───▶│  可靠传输    │───▶│  后端加工    │───▶│  回测系统    │
│             │    │              │    │             │    │             │    │             │
│ WebSocket   │    │ 双主机双线路  │    │ Collector   │    │ 后端WAL     │    │ 盘口重建    │
│ REST链上事件 │    │ 统一事件模型  │    │ 边缘WAL     │    │ 去重        │    │ 校验        │
│ 参考价格     │    │              │    │ 主备链路     │    │ 批量写入    │    │ 延迟建模    │
│             │    │              │    │             │    │ ClickHouse  │    │ 策略回放    │
└─────────────┘    └──────────────┘    └─────────────┘    └──────────────┘    └─────────────┘
     Part 1              Part 1              Part 2              Part 2              Part 3
```

每一层的责任:
- **录制端**: 尽可能完整地观察市场
- **传输层**: 保证已经接住的数据可以重放
- **后端**: 保留原始事实并按数据语义加工
- **回测系统**: 把事实转换成可以验证和复现的历史市场

### 4.3 "五分钟市场"为什么不能只录五分钟

录制五分钟市场最容易犯的错误: 在名义上的五分钟开始时启动,结束时关闭。

实际市场生命周期不严格等于名称中的五分钟。假设市场的标记时间为 E,录制器需要覆盖的时间关系:

```
[预热期]────[名义5分钟市场窗口 E]────[延迟退出/结算]
   ↑                                    ↑
 提前启动                            等待尾部和结算事件
```

### 4.4 提前启动不等于完成预热

一个录制进程从启动到真正能完整接收行情,需要完成:

1. 发现新的市场
2. 获取 condition、token 和 outcome 等元数据
3. 完成 DNS、TCP 和 TLS 连接
4. 建立 WebSocket 并发送订阅
5. 等待新连接交付第一条真实数据
6. 取得能够建立盘口基准的初始快照

> **"socket已连接"不等于录制器已经ready。真正的可用状态是订阅完成并且已经开始收到真实事件;对于盘口数据,还必须尽早取得初始快照。**

如果在交易正式开始时才执行这些步骤,连接建立和订阅确认所消耗的时间本身就会形成数据缺口。

### 4.5 双主机、双线路主动录制

两台录制主机不是传统的"主机工作、备机等待"。两边通过独立运行环境和网络线路,**同时订阅并记录相同市场**,逻辑上互为备份,但运行状态都是主节点。

**WebSocket 并不是完整性承诺**: 网络抖动、代理异常、上游服务切换、客户端消费阻塞或瞬时重连,都可能造成某条线路出现缺口。一条线路没收到的数据,另一条线路仍可能收到。

**双活录制不会让单条 WebSocket 变得绝对可靠,但能把"单个连接的偶发问题"从不可恢复事故,降低为可以通过另一份记录发现和修正的问题。**

**录制程序也必须能够升级**: 如果只有一套录制实例,每次发布版本、重启服务或调整订阅逻辑都可能造成中断。双活部署允许**滚动升级**: 先更新其中一台,确认恢复录制后再更新另一台。

### 4.6 WebSocket 连接轮换(make-before-break)

WebSocket 连接本身存在生命周期,部分上游会定时关闭长连接。连接轮换不能采用"先断开旧连接再建立新连接"的方式,否则每次轮换都会人为制造空窗。

**make-before-break 策略**:
1. 先建立新连接
2. 完成订阅
3. 等待新连接收到真实数据
4. 让新旧连接短时间重叠
5. 最后再关闭旧连接

对于具有稳定事件 ID 或序列号的数据,可以确定性处理重叠期间的重复事件。但 Polymarket 的盘口流没有可以完全依赖的单调 sequence,因此不会人为制造看似精确的序列号,而是**保留真实到达信息,并依靠后续快照校正盘口状态**。

### 4.7 WebSocket 成交不是完整成交事实

双主机能降低连接丢包风险,但无法解决数据源自身的覆盖限制。对于成交数据,单边 WebSocket 接口能覆盖的记录量只有约 **4000条**;在成交密集的市场中,超过这一范围的部分不能假设仍然可以从 WebSocket 完整取得。

**解决方案: 成交记录拆成两条相互独立的事实线**:

| 事实线 | 特点 | 用途 |
|--------|------|------|
| WebSocket 成交 | 到达速度快 | 代表实时系统在当时能够观察到的低延迟视角 |
| 链上 OrderFilled | 以最终落链事件为准 | 成交完整性校验和缺口回补 |

**链上录制器**持续扫描 Polygon 上的 OrderFilled 事件,使用 `transaction-hash + log-index` 构造确定性唯一标识。

链上数据分两个阶段:
1. **实时扫描**: 持续读取已确认的区块,尽快获取链上成交
2. **结束后 sweep**: 市场结束后重新扫描完整区块范围,回补实时阶段的遗漏

第二次扫描可修复: RPC 暂时不可用、进程重启、区块跨度遗漏、长时间网络中断、WebSocket 成交超出接口覆盖范围等问题。扫描结束后比较实时记录和全量扫描结果;如果 sweep 补出了明显缺口,就产生监控信号。

> **链上回补有明确边界**: 能补成交,不能补历史订单簿。价格档位的出现、修改和取消不会全部上链,因此盘口数据仍然必须依靠实时录制。

### 4.8 保留多条独立证据

为了让数据能在后续阶段被验证,录制端不会过早把所有来源合成一条"最终行情",而是分别保留:

| 证据类型 | 说明 | 校验用途 |
|---------|------|---------|
| 盘口快照与增量 | Snapshot 提供完整状态基准,Delta 记录价格档位变化 | 快照检查增量重建后的盘口是否漂移 |
| 独立 BBO | 保留 BestBid/BestAsk | 校验重建盘口的最优价格 |
| WebSocket 成交 | 低延迟观察 | — |
| 链上成交 | 链上最终成交事实 | 发现 WebSocket 缺失 |
| 状态与参考价格 | ticksize、结算状态、Binance/Chainlink 参考数据 | 结算事件决定市场是否真正结束 |

这些数据既有重叠,也能相互校验: 快照检查盘口漂移;BBO 检查最优买卖价;链上成交发现 WebSocket 缺失;结算事件决定市场是否真正结束,而不是简单依赖定时器。

### 4.9 Snapshot 与 Delta 语义

**语义必须明确**:
- **Snapshot**: 某一时刻的完整盘口
- **Delta**: 某个价格档位更新后的**绝对数量**,数量为零则代表删除该档位
- Delta **不是**"在原数量基础上增加或减少多少"

> 这个区别会直接决定后续回测能否正确重建订单簿。

**双时间戳**: 每条行情事件至少包含两个关键时间:
- **event-time**: 上游事件发生的时间(恢复市场事件顺序)
- **recorded-time**: 录制器实际收到并记录事件的时间(分析传输延迟,构建策略的本地观察视角)

> 只保存其中一个时间都会丢失重要信息。

### 4.10 录制端的分层边界

为了避免数据库和跨地区网络反过来阻塞行情接收,TradeDataCapture **不会在 WebSocket 热路径中直接写 ClickHouse**。

录制程序只负责: 接收、轻量标准化和交付类型化事件。数据随后进入本机 Collector,再由 Collector 负责组批、本地 WAL 和远程传输。后端接收后还有独立 WAL,并在后台异步完成数据加工和 ClickHouse 批量写入。

**分层把行情接收速度与网络、后端和数据库状态解耦**:
- 行情端: 尽可能完整、低延迟地观察市场
- 传输层: 让已经接住的数据可以重试和重放
- 后端: 根据不同数据语义去重、加工和落表
- 回测系统: 重建、校验并消费历史市场

### 4.11 录制端核心设计总结

一组相互配合的设计:
1. 提前预热,覆盖市场真正的完整生命周期
2. 延迟退出,等待尾部和结算事件
3. 双主机、双线路主动录制
4. WebSocket 连接采用重叠轮换(make-before-break)
5. WebSocket 成交与链上成交独立记录
6. 市场结束后执行链上全量扫描(sweep)
7. 分别保存 Snapshot、Delta、BBO 和成交
8. 同时记录事件时间和本地接收时间
9. 保留原始事实,为后端校验和回测重建留下空间

> "低延迟决定我们能多快看到市场;完整性和可验证性决定这些数据在几个月甚至几年后是否仍然值得信任。"

> "行情录制是整套系统的起点,也是唯一无法在事后完全重来的部分。后端服务可以重启,WAL 可以重放,数据库中的原始数据可以重新加工,回测文件也可以重新生成。但如果某一段盘口从一开始就没有被录下来,后面的系统再完善也无法凭空恢复当时每一个价格档位的变化。"

## 五、行情与回测系统 Part 2 — 数据传输与后端加工

> 原文标题: "回测系统: 采集的数据我是怎么加工处理的"

### 5.1 术语定义

| 术语 | 全称 | 在系统中的职责 |
|------|------|---------------|
| **WAL** | Write-Ahead Log(预写日志) | 可恢复的磁盘队列: 数据先写本地磁盘,系统确认接收后异步发送或加工。重启/中断/故障后尚未完成的数据可继续重放 |
| **Collector** | 本地采集汇器 | 运行在录制主机上的独立进程,接收 TradeDataCapture 数据,组批入边缘WAL,选择主/备线路发送 |
| **IPC/UDS** | 进程间通信/Unix域套接字 | 同机进程通信,比绕本机HTTP更短,不把远程网络状态带入行情接收线程 |
| **Proto** | Protocol Buffers二进制编码 | 结构化二进制序列化,强类型行情事件编码成紧凑字节,便于进程和网络间高效传输 |
| **RocksDB** | 嵌入式键值存储 | 直接嵌入进程,持久化到本地磁盘。承载边缘和后端WAL,不是最终查询数据库 |
| **Batch/Bucket/Chunk** | 批次/时间桶/数据块 | 事件按短时间窗口组成批次;高频批次过大时拆成多个有序数据块,分别发送和重试 |
| **Primary/Fallback** | 主线路/备用线路 | Primary日常使用,Fallback备用;主线路异常时切到备用(故障切换),恢复后切回(failback) |
| **Backlog/Drain** | 积压/排空 | 到达速度高于发送或写库速度时等待处理的数据=积压;故障恢复后后台任务持续处理直到追上实时流=排空 |
| **At-least-once** | 至少一次 | 允许同一批数据因重试而重复到达,但不因临时故障消失 |
| **Exactly-once** | 恰好一次 | 既不丢也不重复,通常需跨系统事务,复杂度和成本更高 |
| **ClickHouse** | 列式分析数据库 | 最终保存行情事实的数据仓库,擅长批量追加、压缩和大范围时间序列扫描 |
| **MergeTree** | ClickHouse表引擎 | 保留追加的原始记录 |
| **ReplacingMergeTree** | ClickHouse表引擎 | 按排序键在后台合并重复版本;需立即看到去重结果时查询使用FINAL或统一读取层 |
| **Snapshot/Delta/BBO** | 快照/增量/最优报价 | Snapshot=某时刻完整盘口,Delta=此后档位变化,BBO=最优买卖价;第三篇用于重建和校验 |

### 5.2 为什么录制程序不直接写数据库

最直观的实现是在 WebSocket 回调中把每条事件直接写数据库。数据量很小时可以工作,但会把三个完全不同的系统耦合在一起:
1. 行情源什么时候发送数据
2. 跨地区网络什么时候能完成传输
3. 数据库什么时候能完成一次写入

如果数据库写入变慢,录制线程就会被拖慢;如果跨地区网络抖动,WebSocket 消费也可能积压;如果每条事件单独执行一次写入(INSERT),还会在 ClickHouse 中制造大量小数据片段(part)。

### 5.3 热路径压缩

录制热路径压缩到尽可能少的工作:
1. 接收上游事件
2. 补充录制时间和来源信息
3. 转换成强类型传输行
4. 交给后台转发任务

**Proto 二进制编码、本地进程间通信(IPC)、WAL 写入、压缩和 HTTP 传输都在后台任务中完成。** 录制进程本身不再建立后端连接,也不需要知道 ClickHouse 当前是否健康。

> 解耦的核心不只是提高速度,而是让网络和数据库故障不再直接反压行情接收线程。

### 5.4 从 TradeDataCapture 到本机 Collector

录制器生成的是按表定义的强类型事件(不是无结构JSON)。每张表拥有自己的后台转发任务,负责完成 Proto 编码,并把已序列化的数据交给共享的 Collector 发送组件。

发送组件通过 **Unix 域套接字(UDS)** 与本机 Collector 通信。选择本地 IPC 是因为它比绕一圈本机 HTTP 更轻量,也让录制器完全不需要处理远程网络状态。

### 5.5 边缘WAL: 先落本机磁盘,再考虑跨地区网络

Collector 为每个"录制实例与目标表"的组合建立**独立写入器**。数据进入写入器后,先按**五秒时间桶**在内存中聚合,然后写入本机 **RocksDB WAL**。

**五秒桶是吞吐、延迟和重试粒度之间的平衡**:
- 桶太小: 产生大量请求和磁盘键
- 桶太大: 单次请求耗时增加,失败后重试成本更高
- 高频表在一个五秒桶内仍可能很大,因此**每个 WAL 数据块最多约 3000 行**
- 同一时间桶可拆成多个带顺序号的数据块,分别发送和重试

**热冷分层**:
- 热 WAL 保留最近约 **15分钟** 的桶
- 长时间断网时,更老的数据转入带容量上限的**冷溢写文件**
- 链路恢复后,先恢复实时传输,再按时间顺序回灌积压数据
- 当前默认: 单个写入器最多约 **10GiB**、整个进程最多约 **20GiB**

> 容量上限非常重要。如果磁盘积压无限增长,最终只会把整台主机写满。热WAL、冷溢写文件、进程总磁盘占用和内存都必须有明确上限,并把超限和丢弃暴露为指标。

### 5.6 有界队列: 为什么所有内存队列都必须有边界

录制器到发送组件、发送组件到 Collector、Collector 到 WAL 写入器之间都使用**有界队列**。

> 下游长期不可用时,无限增长的内存队列最终会耗尽整台录制主机的内存(OOM)。

有界队列意味着极端拥塞下 WAL 之前仍可能出现丢弃。系统不会把整条链路描述成绝对无损,而是记录: 队列丢弃、Collector 接收量、WAL 积压和连接状态,再结合双主机录制降低单点拥塞影响。

> **真正可重放的边界是数据成功进入磁盘 WAL 之后。** 在此之前,低延迟和资源上限仍需要明确取舍。

### 5.7 主线路和备用线路

"双线路"不是同一个域名换两个 DNS,也不是在同一条网络上重复发送两次。两套相互独立的后端入口:

| 线路 | 方案 | 链路 |
|------|------|------|
| **主线路** | Caddy HTTPS 直连入口 | 录制器 → 公网HTTPS → Caddy → 后端服务 |
| **备用线路** | Cloudflare Tunnel + Access | 录制器 → Cloudflare边缘 → cloudflared → 后端服务 |

**主线路(Caddy直连)详情**:
- 境外录制主机直接连接后端公网入口
- Caddy 负责 TLS 终结和反向代理,证书通过 **DNS-01** 自动签发
- 路由器使用 **DNAT 和来源 IP 白名单**限制访问

**备用线路(Cloudflare)详情**:
- 录制主机先连接 Cloudflare 边缘,通过 **Access Service Token** 鉴权
- 再由 cloudflared 隧道进入同一个后端服务
- 不需要直接暴露源站入口

#### 为什么主线路选择直连

行情数据量远大于控制面配置。早期全部走 Cloudflare 时,数据需经过 Cloudflare 边缘和 cloudflared 隧道;后端为稳定连接 Cloudflare,cloudflared 出站还需经过代理。大体量行情持续消耗代理流量,实测**每月约 150GB**。

直连入口绕开 Cloudflare 中转和代理路径: 链路更短、吞吐更高、不会把日常行情上报变成持续代理流量成本。Caddy 提供标准 HTTPS,DNS-01 解决源站无法使用普通 80/443 验证的问题,来源 IP 白名单弥补没有 Cloudflare Access 后的访问控制。

#### 为什么仍保留 Cloudflare 备用线路

直连依赖公网路由、端口映射、来源 IP 白名单和跨境路径,任何一处变化都可能让直连突然不可用或变慢。Cloudflare Tunnel 走另一套入口和路由,具备 Access 鉴权、源站隐藏和更稳定的全球接入能力。不适合长期承载全部高频行情流量,但非常适合在直连异常时临时接管。

#### 策略总结

- **控制面**始终优先 Cloudflare: 配置和管理流量很小,安全性和可达性更重要
- **数据面**正常走 Caddy 直连: 减少中转、代理流量和额外成本
- **数据面异常时**自动降级到 Cloudflare: 用更昂贵但更独立的线路换取连续性
- 两条线路保护的是"后端入口和跨境路径",不是两套后端
- 若后端主机本身不可用,两条入口都会失败,此时依靠**边缘 WAL**而不是网络切换

### 5.8 故障复盘: 日本录制节点积压

> "一次持续约50分钟的502,暴露了'有WAL也可能丢数据'"

**事故**: 2026年6月,日本录制节点到后端的直连入口持续返回 502,时间接近 **50分钟**。pm-book-delta 等高频表快速积压。当时每个写入器的冷溢写空间只有 **256MB**,容量耗尽后系统只能淘汰最老的数据,最终形成真实缺口。

**根因分析**: 同一阶段发现原来的 WAL 使用**整分钟桶**。高频表一分钟可能达到 5~7万行、10~15MB,单次请求很容易超时,导致主线路和备用线路反复抖动。问题不只是"网络断了",还包括**请求粒度过大、重试成本过高和磁盘预算不足**。

**事故后修改**:
1. **整分钟桶改成五秒桶**: 缩短单次传输和失败重试的时间范围
2. **高频桶继续分块**: 单个数据块最多约 3000 行,避免一个大请求同时拖垮两条线路
3. **扩大并统一 Collector 磁盘预算**: 当前默认单写入器约 10GiB、进程总量约 20GiB
4. **恢复自动双线切换**: 直连异常或吞吐不足时由 Cloudflare 备用入口接管
5. **启用 BBR 拥塞控制与 fq 公平队列**: 降低跨境丢包时传统拥塞窗口快速坍缩对吞吐的影响
6. **补齐积压、淘汰和线路状态指标**: 磁盘容量不再是一个静默边界

### 5.9 自动降级和热切换

Collector 为每个"录制实例与目标表"的写入器**独立维护线路状态**。一个高频盘口表因积压切到备用线路,不会强制所有低频表一起切换。

#### 切换逻辑

| 状态 | 线路 | 行为 |
|------|------|------|
| 自动切换(主→备) | 主线路 Caddy直连 | 正常发送;出现临时错误时同一批次立即尝试备用线路;即使没报错,只要积压超阈值也主动判定主线路跟不上 |
| 自动切换(备) | 备用线路 Cloudflare | 接管当前批次和后续流量;每隔固定冷却时间重新试探直连;直连恢复就自动切回,仍失败则无缝回落 |

**默认切换逻辑**:
1. 正常状态通过 Caddy 直连发送
2. 主线路出现一次临时失败后,同一批次立即尝试 Cloudflare
3. 备用线路发送成功后,该写入器进入备用线路状态
4. 即使没有明确错误,只要**五秒WAL桶积压达到约24个(约2分钟)**,系统也主动绕过"还活着但已经跟不上"的主线路
5. 备用线路状态下,**每60秒**允许下一批数据重新探测一次直连
6. 直连探测成功就恢复主线路,失败则让同一批次继续走备用线路
7. 两条线路都失败时,批次保留在 WAL 中,使用**最长60秒的指数退避**继续重试

> 这是一种**真正的热切换**: 不需要重启录制器,不需要重新编码,也不需要建立第二套数据游标。Proto 批次和 zstd 压缩只做一次,同一份字节可直接交给任意入口;只有收到成功响应,WAL 才推进。

#### 自动切回的坑

最早的自动回切逻辑要求积压量降到零才允许重新探测主线路。但正在发送的那个桶必须等请求成功后才从 WAL 删除,所以发送过程中积压量天然至少为一。这个看似合理的条件永远无法成立,结果是一旦切到 Cloudflare 就只能通过重启进程回到直连。

后来改成**纯时间驱动**: 在备用线路上稳定发送的同时,每隔60秒让下一批数据试一次主线路。成功就保留在主线路,失败就让同一批数据透明回落。

#### 无符号下溢 bug

WAL 时间桶计数在异常清理路径中发生**无符号下溢**,积压量从零回绕成接近 **2^64**。线路状态机把它理解成"存在天文数字级积压",于是把高频表永久压在吞吐较低的备用线路上,反过来制造了 GB 级积压。

> 现在所有时间桶计数都使用**饱和递减**,最低只能到零。

> 自动切换不能只看连接是否存活。它必须同时感知失败、吞吐和积压,自动恢复也不能依赖一个在传输过程中永远达不到的静态条件。

### 5.10 为什么客户端和后端都需要WAL(双层WAL)

主备链路解决的是"当前从哪里送出去",WAL 解决的是"两条线路都送不出去时数据放在哪里"。两者承担不同责任。

| WAL层 | 故障边界 | 保护范围 |
|-------|---------|---------|
| **边缘WAL** | 录制主机 → 后端接收服务 | 网络中断、入口切换或后端暂时不可达时,批次留在录制主机 |
| **后端WAL** | 后端接收服务 → ClickHouse | 数据库变慢、重启或不可用时,后端仍能暂时接住数据 |

- 如果**只有客户端WAL**: 后端必须等 ClickHouse 写入完成后才返回成功。数据库写入延迟直接变成跨地区 HTTP 请求延迟,客户端容易超时并重复发送。
- 如果**只有后端WAL**: 客户端连接不到后端时没有持久化缓冲,录制进程重启后尚未发送的数据无法恢复。

> **两层WAL保护的是两个不同的故障域,不能互相替代。**

### 5.11 后端"写入WAL就返回成功"

后端收到 Proto 批次后:
1. 处理压缩并轻量检查**信封**中的目标表、来源主机、录制实例和行数
2. 信封合法后,原始请求体追加到行情专用的 **RocksDB WAL**
3. **只有 WAL 追加成功,后端才返回 HTTP 200**

> 此时的 200 表示"这批数据已被后端持久接收,可由后台任务继续处理";**不表示 ClickHouse 已完成最终写入**。

- 如果后端 WAL 已满,接口返回 **503**,让上游保留原批次并重试
- 如果 WAL 写入自身失败,返回服务端错误,不向客户端谎报成功

**行情数据面拥有独立的采集 WAL 和分发组件(CaptureDispatcher)**,与交易业务数据面的 WAL 和数据库连接相互隔离。即使行情 ClickHouse 写入出现问题,也不会占住交易数据的接收队列。

### 5.12 后端加工与 ClickHouse 写入

后台排空任务按 **FIFO** 顺序读取 WAL,但不会为每个请求单独执行一次数据库写入。

它会先根据**数据类型和目标表分组**,把同一张表的多个 WAL 记录合并成较大的插入批次,再交给对应的分发组件完成:
1. Proto 解码
2. 类型转换
3. ClickHouse 写入

### 6.2 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 语义保证 | At-least-once(非Exactly-once) | 避免跨系统事务复杂度,允许重复由后端去重 |
| WAL引擎 | RocksDB | 嵌入式,不需要独立服务,持久化到本地磁盘 |
| 序列化 | Proto + zstd | 紧凑二进制,一次编码多入口复用 |
| IPC | UDS | 比本机HTTP更轻量,隔离远程网络状态 |
| 时间桶 | 5秒 | 吞吐/延迟/重试粒度平衡(从事故中学习: 整分钟桶→5秒桶) |
| 分块上限 | 3000行/块 | 避免大请求拖垮双线路 |
| 热WAL | 15分钟 | 短期断网恢复用热WAL |
| 冷溢写 | 带容量上限(单写入器10GiB/进程20GiB) | 长断网时转冷文件,防止写满磁盘 |
| 线路切换阈值 | 24桶(2分钟)积压 | 不只看连接存活,还看吞吐跟不上 |
| 切回探测 | 60秒时间驱动 | 不依赖积压归零(传输过程中永远≥1) |
| 重试退避 | 指数退避,最长60秒 | 双线都失败时的最后手段 |
| 后端确认 | WAL写入即返回200 | 不等CH写入,避免跨地区HTTP超时 |
| 数据面隔离 | CaptureDispatcher独立 | 行情CH故障不影响交易数据接收 |
| 数据深度 | L1数据足够(不依赖L2) | 评论区确认,策略不依赖L2盘口深度 |
| 数据库选型 | ClickHouse(对比PG/MySQL) | 适合批量追加、压缩和大范围时间序列扫描 |
| 网络QoS | 主动探测+QoS管理 | 日本→上海晚高峰数据积压(正文提及) |

### 6.2.1 延迟分层架构(正文+评论区综合)

博主的系统有**两层延迟**的概念,这一关键信息只在正文/评论区中提及:

```
┌─────────────────────────────────────────────────────────────────┐
│                    端到端延迟: ~120ms (目标20ms)                 │
│                                                                 │
│  ┌─────────────────────────────────────────┐                    │
│  │     进程内 pipeline latency: ~700ns      │                    │
│  │  (行情流入 → 决策做出, 不含网络)          │                    │
│  │                                         │                    │
│  │  WS recv(198ns) → on_trade(34ns)        │                    │
│  │  → build_input(50ns) → predict(137ns)  │                    │
│  │  → TOTAL p50=536ns, p99=17μs            │                    │
│  └─────────────────────────────────────────┘                    │
│                                                                 │
│  网络传输 + 下单IO + PM SDK + 确认 ≈ 剩余 ~119ms                 │
│  (日本→上海/伦敦, 晚高峰积压, PM API延迟)                       │
└─────────────────────────────────────────────────────────────────┘
```

**关键认知**:
- 700ns 只是进程内 pipeline,**网络部分还没开始优化**
- p50=536ns 但 p99=17μs, max=40μs — **尾部延迟和抗抖动是后续重点**
- "不是说平均快就快,**要极差小才好**"
- 端到端从 120ms → 目标 20ms(需优化网络+PM SDK+日志/缓存开销)

### 6.4 策略与风控(正文)

- 置信度门槛: **99~99.5 confidence** 才下单(博主承认过于保守)
- 发布策略: **金丝雀发布**(逐步灰度放开仓位)
- 实盘周期: 3周,周盈利率80%,胜率100%

## 七、对 ZephyrAlpha 的适用性分析

### 7.1 场景差异

| 维度 | 博主(BalletHip) | ZephyrAlpha |
|------|-----------------|-------------|
| 市场 | Polymarket预测市场(高频) | A股实时(~1700tick/s) |
| 语言 | Rust(编译型) | Python(解释型) |
| 数据源 | 跨境WebSocket | 本地QMT/miniQMT API |
| 后端 | 跨地区后端服务→CH | 本地直连CH |
| 架构 | 多进程(Collector+IPC+后端) | 单进程 |
| 故障模式 | 跨境网络50分钟中断 | CH重启(秒~分钟级) |
| 交易执行 | 有(下单/redeem) | 无(数据+回测系统) |

### 7.2 已落地借鉴(P0+P1)

| 博主技术 | ZephyrAlpha适配 | 实现状态 |
|---------|----------------|---------|
| 主动WAL(先落盘再drain) | WalWriter(被动local_replay→主动WAL) | ✅ 已完成 |
| 5秒桶/3000行分块 | segment_max_seconds=5.0 / segment_max_rows=3000 | ✅ 已完成 |
| 有界队列+背压 | _check_wal_capacity + _apply_backpressure (2GB上限) | ✅ 已完成 |
| Prometheus /metrics | metrics_server.py 端口9925 + 9项指标 | ✅ 已完成 |
| CH表引擎确认 | is_replacing_engine() + DDL | ✅ 已完成 |
| 指数退避故障恢复 | _drain_loop 2s→4s→...→60s | ✅ 已完成 |
| WAL事务性提交(第三篇印证) | RocksDB先写本地再写服务端→WalWriter先落盘再drain CH | ✅ 已完成(同一设计思想) |

> **设计哲学借鉴(第三篇)**: 博主提出"**稳定性 > 低延迟**——延迟可由模型弥补,稳定性不可补偿"。ZephyrAlpha 的 WalWriter 设计(先落盘保证不丢,再异步drain)正是这一哲学的体现:宁可增加毫秒级落盘开销,也不在 CH 抖动时丢失数据。

### 7.3 正确判定为过度工程(不照搬)

| 博主技术 | 不照搬原因 |
|---------|-----------|
| 双层WAL(边缘+后端) | 单进程直连CH,无中间服务层 |
| Collector独立进程+UDS | 单进程,无需IPC |
| 主备双线路(Caddy+Cloudflare) | 本地QMT API,无跨境网络 |
| Proto二进制编码 | 单进程Python dict,TSV够用 |
| 纳秒级分阶段延迟打点 | Python+1700tick/s,毫秒级足够 |
| 热冷WAL分层(15min+冷溢写) | 本地CH故障秒~分钟级,2GB够用 |
| 信封校验(跨进程传输) | 单进程无传输损坏风险 |
| BBR拥塞控制+fq公平队列 | 无跨境网络 |
| 饱和递减防下溢 | WalWriter无递减操作,下溢风险不存在 |
| 后端按表分组合并 | per-table WalWriter实例,天然隔离 |
| PTP高精度时间同步(第三篇) | 单机运行,行情和下单在同一台机器,本机时间即基准 |
| 跨供应商offset时间校准(第三篇) | 无跨供应商场景 |
| 163骨干网/CN2/Cloudflare Tunnel跨境组网(第三篇) | 本地QMT API,无跨境网络需求 |
| DDNS反向连接(第三篇) | 无动态IP+反向连接场景 |
| AWS VPC抖动抑制(第三篇) | 无AWS部署,本地直连 |
| 行情线路双活/三活(第三篇) | 单一本地数据源(QMT API),已有redundant_source模块覆盖 |

### 7.4 有价值但非紧急

| 项目 | 价值 | 状态 |
|------|------|------|
| Grafana双数据源(Prometheus+CH) | 有合理价值,但是运维配置非代码工程 | ⏳ P2规划 |
| 三段耗时打点(build/sign/post) | 不适用(无交易执行层),但概念可借鉴到数据层 | 不适用 |
