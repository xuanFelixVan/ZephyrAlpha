## 顺序与理由

`S0 → S1 → S2 → S3` 是**串行主链**：一切提速的地基是"校验读不可变树"，不先做它，后面所有分片都只是把排队切成小段。
`S4` 与主链并行推进（它只依赖 S0 的表和 B0），因为它解的是吞吐而非延迟；但 **S4 的"袋带 base 溯源"必须早于 S5**——A1 实测今日 4 张热册的键级差分**有 79/80、22/22、21/22、21/22 不可测**（袋未记 base），没有 base 就没有条目级三方 merge，S5 的热册道会退化成整册独占。
`S5 → S6 → S7` 是并发与批处理的展开，必须在主链之后：车道数从 1 变 N 时，只有校验已经不读共享态（S1）且重活已出路径（S3），并发才不会被"任何他人提交即缓存全废"重新 serialize 回 1。

## 风险最高的一档（明说）

**S1。** 它一次改掉 72 台门的输入源，失败模式是**静默假绿**而不是报错：

- 15 台门读共享暂存区却**没有** own-scope 收窄（A3 `shared_index_without_own_scope=15`），它们的语义里"看到别人的在途件"是**有意设计**（跨件断链/克隆检测要全域视野）。收口时若把这些一起 own-tree 化 ⇒ 判定退化，而链条全绿。
- 缓解（判据级，不靠自觉）：① 这 15 台一律走 S3 的"出等待路径 + 车道全量"，**不允许**在 S1 里被 own-tree 化；② S1 的发布判据是"重放 100→1000 笔逐台 verdict 全等"，差异集非空即不发布；③ `CommitTreeView` 内置"工作树直读探针"，防止改造后门悄悄退回读物理路径；④ 每把尺先自证能红（本仓一晚四次假绿的教训在册）。
- 次高风险是 **S4**（动的是真源方向与热册字节），失败模式是**静默净删**（他队条目被整册覆盖吞掉）。故 S4 判据里带"逐字段差分零净删"，且与已登记的整合者键集差分口径同源。

## 每档的"治理不回退"检查（与 A2 第 7 节配对）

1. 门禁**集合**不变：`total_gates` 字段随档核对，S1–S7 任何一档落地后名册台数不减。
2. 位置可逆：所有"搬位置"的决定必须是 `gate_position_registry` 里的数据，改回一行即恢复同步阻断。
3. verdict 可查：每件从"受理→落地/退件"必须有逐台门结论落库（S0 装表的自然产物），否则 S3/S7 不发布。
4. flag 出厂态不动：本阶梯不翻转任何出厂默认；灰度经 Owner 窗口（沿用战役红线）。
