## 4. 缺口与根因

1. **根因 A：三套"有没有人用"的口径互斥，所以 114 这个数无法被任何一方代表。** ①族①扫描器 root=仓库根、含 `.md`（提一句就算有客）；②ORPHAN-MODULE 门只扫 `src/**/*.py`（scripts 不算）；③CNS 案卷自己又跑一次 5,277 文件全词扫描。⇒ 协调册 §3.4 已经**定档了单一口径**（`src/`+`scripts/`+`config/` 的 `.py`/`.yaml`，排除 `.md` 与 `docs/`），**本项的缺口不是"再算一遍"，而是"改 `indicator_usage_audit.py` 的三处缺陷去对齐那个口径"**（consumer 清单化 / `.md` 不算客 / `stale` 态可达或显式退役——协调册要求二选一写明理由）。
2. **根因 B：接线与退役被混成一项。** CNS-01（接线：为已声明的 FCT-TECH 建计算链）与 CNS-02（退役听证：114 条逐条）是**相反方向**的动作，共用同一份"零客"名单却**没有共用的证据格式**；M3 更揭示第三类（老架构零客表，未走退役登记）。⇒ 根因是**"死亡证明"没有登记格式**，于是"接线/退役/留观"三态无法在一条流水里表达，只能靠案卷分列。
3. **根因 C：机账没人读 ⇒ 计数永远不会被消费掉。** M2 的 138 vs M1 的 143 差（CHIPS 5 条未入账）之所以能长期存在，就是因为没有读者。⇒ 与本战役多处"配了没人读"（`potential_consumers` 死维度、`wiring_registry` 手工）同族：**写了产物≠接了线**。
4. 非根因：不是"指标真的没人用"（M1 列了 6 个真实下游件）。
