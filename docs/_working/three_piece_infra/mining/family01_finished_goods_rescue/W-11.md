## 4. 缺口与根因

1. **根因 A：成品分两类却只有一个编号。** "案卷件"与"实现件"的完成判据不同（前者=登记+不撞文档门；后者=符号在册+测试+ALGO-NOTE 同步），而 W-11 把它们打包成一个 169 ⇒ 排产时无法表达"先落实现件、案卷件随后"，也无法在部分落地时给出诚实进度。⇒ 缺的是**按面积分的机生清单**（与 W-40/W-10 同一味药）。
2. **根因 B：`A `（staged）态是本仓最脆弱的一档。** M1 有 87 件已 `git add` 在车道 index 里：它们**不在任何 commit、不在主区、不在队列**，一次 `git checkout`/worktree 清理即失。X 册 §七 的硬结论（44 条真车道 dirty 有内容而自有 commit=0）把这类道统称"一次还原就全丢"。⇒ **本项的最高优先动作不是落地，是把 169 件（含 index 内容）再固化一次**（补丁已在冷库，但 `A` 与 `M` 的区分需要 `git diff --cached` 才保真，本层未验历史固化是否含 cached 面——若不含，则 87 件的"已 add 状态"信息已在固化中丢失，属可追的取证缺口）。
3. **根因 C：X-02 的雷是**必须逐 hunk 排**，不是"落地前提醒一下"。** M3 证明车道基底就是 outage 原状（两门同 77）⇒ 从该基底生成的整份补丁天然含"把已修好的停摆改回去"的 hunk。**若走"整目录覆盖"式抢救（最自然的偷懒法），必复发 outage。** ⇒ 处方：落地袋**不得**包含 `priority` 相关 hunk，且落地前后各跑一次两门 priority 对比（HEAD vs 落地后），不等即拒。
4. 非根因：不是"AI 层功能没做完"——那是族 11 的 W-111（点火三缺），与本项（落地）不同对象。
