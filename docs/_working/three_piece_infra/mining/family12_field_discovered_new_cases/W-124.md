## 4. 缺口与根因

1. **根因 A：真正的病不是"没落地"，是"从未入库 ⇒ 从未跑过"。** W-10/W-11 的病是"成品在车道、HEAD 没有"（可捞）；本案 M2 说**全分支零 A**，即这些字节**从未进过 git 对象库**，也没有补丁可捞（X 册 §七 的固化只覆盖 `.aidrafts/*`/`.worktrees/*` 的 worktree，M4 显示这两件连那里都没有）。⇒ **捞回类尺（`git cat-file -e HEAD:`）在这里会给出"红"，但红之后没有东西可搬**，必须重写。这是"抢救"与"重做"的分岔，案卷目前把两者混在同一个"捞回清单"里。
2. **根因 B：案卷自身的字面（大小写、文件名）会制造假零命中。** 本窗 M3 证实：若按文档字面 `DEEP_DIVE_R1.md` 去 `git cat-file`，会得到 0 命中并误判"盘面也无"；而 HEAD 真名是 `deep_dive_r1.md`。⇒ **X-16 的取证纪律不是客套，是本案的可复现教训**，且它意味着：**这条纪律本身需要一把尺**（见 §5 副尺 2），否则下一班还会犯。
3. **根因 C：三案一号（W-124 / W-101 / W-153）。** 两枚测试、图14/图15 未被打过、场景⑦未补跑——**都是"红蓝覆盖存在洞"这一个对象的三个表述**（骨架册 §五 停止判据三问的第③问："只是同一病的不同案卷表述 → **不拆**"）。⇒ 本层判：应合并为一次红蓝补跑工程，产出**一份**覆盖差集；三案各排一次＝三次施工一个洞。
4. 非根因：不是"红队报告不可信"（X-59/X-60/X-66 已示范逐条复验，本案即成功样本）。

## 5. 能红判据

- **副尺 1（从未入库清单机生化，就绪）**：对案卷点名的每一件，断言 `git log --all --diff-filter=A -- <pathspec>` 非空；空 ⇒ 归入"从未入库"产物，并**再分一类**："盘面有副本（可捞）"vs"盘面也无（须重写）"（用文件存在性判定，M4 是现成分类样本）。
  **必红变异体**：拿 `test_redblue_governance.py` 跑 ⇒ 必归"从未入库 + 须重写"；拿 `dead_triage.yaml` 跑 ⇒ 必归"已入库"。**若两者同类，尺无效**（它必须能区分这两件，这正是 X-16 修正的内容）。
- **副尺 2（大小写不敏感取证，就绪且通用）**：任何"某文件不存在"的判定，必须同时用 `-i` 匹配（`git ls-files -i`/`find -iname`/`git ls-tree | grep -i`）；尺实现里若只用精确路径 ⇒ 尺自身红。
  **必红变异体**：把 `deep_dive_r1.md` 写成大写交给尺 ⇒ 尺**不得**判"不存在"（必须报"实存，真名小写"）。这条尺**服务全战役**（X-16 归位列把它放在"波 1.8"，本层认为它应升为通用取证规范）。
- **主尺（红蓝覆盖差集，未就绪）**：断言"每张图/每个场景都有独立红队件"需要先有一张**场景×图×测试**的机读矩阵；该矩阵不存在（协调册 §2.1 实测"四向对账"类件零命中）。⇒ 本案判据**依赖 W-154/包 13.4 的矩阵先落地**，否则只能逐次人工补跑、每次都不知道还剩哪些洞。
- **就绪度**：副尺 1/2 **就绪**（纯 git）；主尺 **未就绪**（前置＝矩阵）。
