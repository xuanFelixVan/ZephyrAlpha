## 4. 缺口与根因

1. **根因：逃生标记只验"格式"，不验"援引"。** `allow-*` 与 `emergency_commit` 的语义是"我引用了一次授权"，而系统里**没有任何件把这句引用与裁定册对号**（M3 零命中即为结果）。⇒ 一个不存在的批准可以被写进 commit message 并被下游文档照抄（骨架册照抄了"678 件"，X-12 差点把四台禁用误判成"装载失败"）。**这是 W-81（伪造/悬空裁定署名防线）的实证样本，也是它最该长成的样子**：不是猜，是有两个确定坐标（M1 件数、M3 零命中）。
2. **根因（为什么"审它"很难）**：禁用窗没有边界记录。四台的 `enabled: false` 各自有注释，但**没有 `disabled_at` 字段**，也没有门状态变更事件流 ⇒ "禁窗内落了什么"里的"窗"目前**只能靠 commit message 反推**。⇒ 本案第一步不是审计，是**给门状态变更建事件面**（与 W-20b 的 `disabled_by/recheck_predicate/recheck_due` 三字段是**同一批改法**，禁两次施工）。
3. **根因（数字面的第二条）**：M1 的 528 vs 678。commit message 自述件数在 HEAD 上**可查而不被查**——没有任何尺比对"消息自称 N"与"`--stat` 实报 M"。这与 X-38（"quant_methodology 实 10 件但 message/LEDGER 称 11"）、X-52（多处计数不符）同族 ⇒ **一条通用尺：凡 commit message 出现"件/N 件"字样，必与 `git show --stat` 对账**。本案是它最贵的一个实例（差 150）。
4. 非根因：**不判"该 commit 违法"**。四门禁用是事实、emergency 通道是否满足"注册表/锁不可用"前置是待核问题（X-11 原文即"是否符 emergency 使用条件"），本层只登记核对方法。
