## 4. 缺口与根因

1. **根因 A：token 的生命周期缺一半。** 登记发生在写文件**之前**（放行用），而**没有任何件在落地之后回收/核销 token**。⇒ 车道可以（本例就是）为一批文件领 token，然后把文件留在自己 worktree 里蒸发，名册上永久留着"这批文件已获准创建"的**假事实**。这不是数据脏，是**证据语义被污染**：后续会话读名册会以为 `fullflow_closure_wave2` 这个 capability 已存在（`capability_lookup.find()` 检索面含 `canonical_file` ⇒ 返回假可用）。
2. **根因 B：既有锚点校验台的扫描面不含 `creation_tokens`。** X-14 自己把本案归到 "REGISTRY-CODE-ANCHOR/DOC-REF-BROKEN 同族"，但那两台的语义是"册里写的脚本路径要实存"——本案**形式上正是它该抓的**却没抓到，说明**它们的遍历面是那几本别的册**（或只扫 `canonical_file` 不扫 `creation_tokens`）。⇒ **本案第一步是"点名那两台的遍历清单"，不是新写第三台**（内收判据）。
3. **根因 C：`merge_evaluation` 字段是自由文本**（M1 原文"内收复核逐条给"）⇒ 一个从未落地的批可以自带"已复核、无平行结构"的评语。评语被下游当结论引用＝**自证链**。这与 W-120（消息自称 678）同构。
4. 非根因：不是队列合并器把文件吞了（M4 从未 A 过）。

  **必红变异体**：拿 `fullflow crosscheck` 关键词查 ⇒ 今天会返回命中且无标注 ⇒ 尺红。
- **就绪度**：主尺完全就绪（纯 git 操作，零数据库、零权限）。副尺需接触 `capability_lookup` 返回结构，属丙道/丁道交界面 ⇒ 与协调册包 13.2 冲突面须先由总裁定档（禁两处各改一次返回结构）。
