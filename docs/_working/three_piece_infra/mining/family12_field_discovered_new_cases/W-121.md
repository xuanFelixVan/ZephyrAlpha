## 4. 缺口与根因

1. **根因 A：写保护靠"每个人都记得用 `safe_write_text`"，而该函数**没有强制面**。** 宪法把它列为硬规则 13，但没有任何台在提交期检查"动过该册的袋里，写入是不是 CAS 产生的"⇒ 一次整文件 Edit/Write 就把别人落地的 16 条抹了。⇒ **CAS 是"写时互斥"，本案是"写时全量覆盖"**，两者不是一回事：CAS 只防并发写，不防陈旧读-改-写（lost update 的经典形态：A 读旧内容 → B 落地 → A 写回旧内容+自己的改动 ⇒ B 蒸发，且 A 侧毫无异常）。**M5/M6 就是这一形态的现场。**
2. **根因 B：三态（HEAD/index/disk）中任何一态的偏离都不报错。** M1 的 `MM` 态**本身就是答案**：index 删 2、工作区又删 16，两层各自独立发生，说明**至少两个写入者/两次操作**都在这册上留下了非自身内容。⇒ 病不在"一次事故"，在"册是单文件万级条目的共享写入面"这一物理形态（协调册 §一 已判"该册 71 封死信的历史死因就是多道同写一册"，本窗给它补了一个**仍在流血**的读数）。
3. **根因 C：修复配方存在，**回收**配方不存在。** X-13 的处置是"本班实跑三态分诊 + 修复（盘缺 HEAD 16→0）"——**修的是"盘缺"**。M5 显示现在 9 条是"盘上文件也没了"：这些是**该恢复实体还是该确认退役**，配方没答；若无脑按 HEAD 恢复实体，会把别的会话**故意删除**的东西复活（M4 的 `three_piece_infra/*` 恰恰由总筹在写，可能刚被另一层改）。⇒ **本案第一步是分类归位（Z-00-C 三段式），不是恢复。**
4. 非根因：不是 YAML 解析崩（册仍可解析，条目数正常读出）。

## 5. 能红判据（即 X-13 悬空的 W-28b）

- **主尺（三态键集差，就绪且今天必红）**：对声明为"热册"的文件集，比较 `git show HEAD:<f>` / index（`git show :<f>`）/ 工作区三方的**归一键集合**（`file:` 值去引号、去前缀），输出四计数：`盘缺HEAD`、`HEAD缺盘`、`index删`、`工作区删`。断言：任一"删"计数 >0 ⇒ **点名并阻止裸提交**（或至少 warn+审计留痕，取哪种由总筹定档，禁自裁）。
  **必红变异体**：今天跑 ⇒ 应得 `HEAD-only=10 / DISK-only=2 / index 删=2 / 工作区删=16`（M3/M6 是**本窗已实测**的红证，无需变异体即红）。**再造一例**：手工删掉任意一条 `- file:` 行 ⇒ 尺必点名该行；若尺只报总数不报行，说明它没做键集差而只做了计数比较 ⇒ 尺无效（计数会把 M7 的引号差与"删 A 加 B"抵消成 0，这是本案最阴的假绿路径）。
- **副尺（CAS 强制性，就绪）**：断言"动热册的袋"里，该册的改动**只能是纯插入或键集差可解释**（协调册 §2.2-3 的"块原文集合差纯插入"）。
  **必红变异体**：提交一个含"删 N 条他人 token"的袋 ⇒ 必被拒并列出被删键；若放行 ⇒ 尺红（这正是本案要拦的动作）。
- **就绪度**：**完全就绪**——尺的输入全是 git 三态，零数据库、零进程、可沙盘跑；且**自带今日红证**（M3/M6）。⇒ 本层判定：**这是全 132 个 W-xx 里"最小成本、最高即时收益"的一颗**，因为它防的是**正在发生的持续损失**，且每落地一天就少丢一批他人成果。
