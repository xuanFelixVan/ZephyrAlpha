## 4. 缺口与根因

1. **根因 A：判据用"PID 存在"代替"进程身份存在"。** PID 是**可复用资源**（M2 `:1005`），Windows 上尤其如此；一旦原孵化进程退出、PID 被系统分给 `svchost`，`pid in live_pids` 仍为真 ⇒ 进入 kill 分支。⇒ **正解不是"更小心地杀"，而是把身份判据换成三元组**（PID + 活体 name/cmdline + **create_time**）；M3 已证 `create_time` 就在同一文件可得（对照腿已这么用），所以这不是新设计而是**把已有判据搬过来**（X-08 的"处方内收为复用已有 recheck 判据 + 加 create_time 第三要素，禁写第二套"）。
2. **根因 B：白名单在身份判定**之前**还是**之后**参与，决定误杀面。** M2 的顺序是：存在性 → 时间窗 → 白名单。⇒ 白名单只保护"命令行含 keep 子串"的进程；被复用成 `svchost` 的 PID 其活体命令行与登记 `cmd` 完全不同，**白名单不可能命中它**，保护网天然漏。⇒ 根因不是 keep 名单不够长，是**"先认人、后决定杀不杀"这一步不存在**。这也解释了 X-08 的形态：真 KILLED 里出现 conhost/bash/backgroundTaskHost 这类"绝不可能是自家孵化子进程"的名字 ⇒ **缺的是一道"活体名 ∉ 自家 python 形态 ⇒ 直接跳过"的粗筛**。
3. **根因 C（与 Z-23 的差异）**：Z-23 写"实测今日 7 条 KILLED name=svchost.exe"；X-08 复算为"5 条全带 `[FAILED]`（即**没杀掉**）+ 07:17 与 09:01 两条发生在 AccessDenied 治本 `dc1c66e651`（02:30）之后"。⇒ **两读并存且方向相反**（Z-23 读成"误杀成功"，X-08 读成"误杀尝试失败但仍暴露判据缺陷"）。本层采 X 册（口径真源），并指出：**即使 5 条 `[FAILED]` 全部失败，判据缺陷也已坐实**（它尝试杀了非自家进程），故 Z-23 的"修"不因失败读数而作废。呈报时**必须并列两数**（同 W-120 M1 的处理法）。
4. 非根因：不是 keep 匹配面太宽（那是 W-47 的对象，处方=⚑-3，方向相反：收紧=把在跑进程重新纳入可杀集合）。

## 5. 能红判据

- **主尺（身份三元组，就绪）**：构造台账记录 `child_pid=<某活体 PID>`、`cmd=<python -m zephyr…>`，而活体表里该 PID 的 `name=svchost.exe`、`create_time` 晚于 `spawned_at` ⇒ 断言**必跳过**并记 `identity_mismatch`。
  **必红变异体**：在当前 HEAD 上跑 ⇒ 必红（M2 段内无 create_time、无 name 一致性比对，会进入 kill 分支）。若实现只加 `name` 比对、不加 `create_time` ⇒ 第二条用例（同 name 异 create_time，即"同种进程换实例"）**必须仍红**。⇒ 两例分层，防"半只鞋"。
- **副尺 1（DRY-RUN 不可混读）**：断言 `report` 的 verdict 字段可区分 `KILLED`/`DRY-RUN`/`FAILED` 三态且统计口径分别产出（X-08 的 15 条 DRY-RUN 被当实杀读＝本案的证据污染面）。**必红**：把一条 DRY-RUN 计入 KILLED ⇒ 尺红。
- **副尺 2（保命轨自身受检）**：断言 reaper 作为"永久系统"具备四要素（自动触发/运行/维护/关闭）且 `--status` 在缺计划任务时**必报红**（宪法 §0-2 把它当写操作前置，但前置成立与否目前靠人跑一次）。未跑即视为未验。
- **就绪度**：主尺/副尺 1 就绪（可用假进程表注入，不需真杀）；副尺 2 半就绪（需读 `--status` 实现）。
