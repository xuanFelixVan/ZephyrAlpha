## 4. 缺口与根因

1. **根因：触发面是名册字段，而这台门的"该不该跑"是**代码内部自己判断**的（marker continue 分支 `:520-523`），名册层看不到、也就无法被审计。** ⇒ 加 `files_trigger` 不是性能优化，是把"这台门在什么条件下参与"从**代码私有知识**变成**机读声明**。这与波 1A"名册声明/实载/触发面命中一张表"是同一颗钉子的一块板。
2. **根因（为什么"批量化"不够）**：即便把 N 次 grep 合成 1 次（协调册包 13.1 的正解），**无触发面时它仍参与每一次提交**（哪怕本次 diff 一个 `.py` 都没新建）⇒ 批量化只降系数、不降次数。两件事必须同批，缺一个都只是半只鞋。
3. **根因（成本不可证）**：M4 的 13.6% 来自门内自报读数（E2），本仓**没有**一把"门的耗时对账"尺 ⇒ 优化后无法证明"没变慢也没变松"。协调册要求的"100 笔重放自证"是本项唯一可接受的度量通道。

## 5. 能红判据

- **尺 1（声明在场）**：断言 `in_process_gate_registry` 中 `CREATE-GUARD` 条目含机读 `files_trigger`。
  **必红变异体**：在当前 HEAD 上跑 ⇒ **必红**（M2 已证字段缺失）。若绿，尺无效。
  反事实控制：对 `CAPABILITY-OVERLAP`（在册 29 个 `files_trigger` 之一者）跑同断言 ⇒ 必不点名。
- **尺 2（语义不变，硬门槛）**：同 100 笔历史袋重放，逐袋 verdict（PASS/FAIL+点名集）与改前**全等**；任一袋不等 ⇒ FAIL。
  **必红变异体**：故意把 `files_trigger` 写窄到"只匹配 `src/zephyr/gov_enforcement/**`"⇒ 那些"在别处新建 .py"的袋必须从 PASS 变 FAIL 或反之，**尺必须抓到差异**；若仍全等说明尺比对的是"门有没有跑"而不是"判定结果"。
- **尺 3（成本可复算）**：断言 `class 级 git grep 次数 == 新建 .py 文件数`（改前）→ 改后 `== 1`（每袋）。计数从 `gateway.run_git` 的调用计数器取，**禁引散文秒数**。
  **必红变异体**：把批量化改成"只对第一个 class 生效" ⇒ 次数仍 >1 且 verdict 与逐条版不等 ⇒ 尺 2、尺 3 双红。
- **就绪度**：三把尺都能写出变异体 ⇒ 就绪施工。
