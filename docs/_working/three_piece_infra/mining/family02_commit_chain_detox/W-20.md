## 4. 缺口与根因

**C1（本叶簿最重要的一条，与在册裁定冲突，显式记录不擅改）**
- Z-05 处方原文：*"两条 id 相同但一为 `status: promoted` 的历史核销条、一为新案条，保留信息更全者并把另一条的独有字段并入"*，并给出"改号为 `CAND-GOVTEST-005-B` 或降级为议题条目"。
- 实测（M3/M4）：两条**不是同一件事的两个版本**，而是**两个不相干的候选共用了一个号**——一条讲"commit queue P1/P2 扩展（已晋升）"，一条讲"测试身份穿透主仓的 commit 泄漏（P1 新案，附 `ee40160919`/`c284589d` 双 commit 对账取证）"。
- ⇒ **"保留信息更全者并并入独有字段"会造出一条把两件不相干的事焊在一起的新条**，等于把 P1 安全案（测试身份泄漏）**静默注销**。Z-05 的后半句（改号或降级）才是对的；前半句不可执行。
- 根因：**号段分配无唯一性执法**。同一号被两次独立分配（`2026-08-20` 与 `2026-09-02`，相隔 13 天，两个不同会话），且 `CAND-{DOMAIN}-{SEQ}` 的 SEQ 由各会话自取 ⇒ 与 W-55（取号器不在 HEAD）、W-56（悬空裁定号）、W-71/W-133（candidate 007 重编号）**同一条根**：本仓"编号不回收 + 自赋号"没有中央发号器，只有落地期的合并器当"事后捕手"，而捕手只会杀袋、不会修号。

**C2（结构性，为什么"改一条"不能收工）**
- 合并器的身份键来自**册头自声明** `unique_key`（M5），声明本身无校验：若某册声明过窄（如只 `[id]`，而实际业务身份是 `id+variant`），则该册**结构性不可合并**——`commit_queue_landing.py:361-366` 的注释正是这一形态的实战记录（翻译册 `entries`/`algo_submodules` 两族合法持同 `module_path` 多条，HEAD 实测 194 个 module_path 多条形态 ⇒ 一进合并即死 ⇒ **逼出直连绕行 `a0562e88f2`，"批A 同款死两次实证"**）。
- ⇒ 本项的真实工作量不是"删一条"，而是"**给每本热册的声明键做一次与业务身份的对账**"。W-20（候选册）、W-71（同册另一号）、W-133（同袋序）、以及翻译册的既有热修，是**同一个对账任务的四个样本**。

**C3**：病在登记期无执法、在落地期以"整袋死信"形式变现 ⇒ 修完 M1 的这 1 组后，若不同批立"登记期唯一性尺"，下一次自赋撞号仍会以死信形式消耗一整个袋（含该袋内**无辜的其它文件**，即连坐面）。
