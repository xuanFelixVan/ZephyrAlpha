## 4. 缺口与根因

1. **根因 A（最要害）：活性判据是"PID 在不在"，不是"有没有在干活"。** M2 明写"PID 存活即不清扫"。一个 **keeper 进程**只要活着，它注册的 session 就永久免死；而 keeper 的语义恰恰是"替一个已死的工作会话维持注册"。X-19 的实测（真身 PID 3584/33548 已亡，keeper 37548 每 300s re-register 并持 3 个业务文件 claim）在这套代码下**不是缺陷绕过，而是完全按设计工作**。⇒ 症状"避让判据被带偏"（X-19 的定性）与"清扫不动手"是同一枚判据的两面。**根因层级修法＝把活性定义从 pid 改成 claim + 产物 mtime（Z-14/X-19 的处方方向），而不是给 keeper 加白/黑名单。**
2. **根因 B：三处 fail-open 叠成"永远没人知道"。** M1 注册表查询失败=debug+return；json 解析失败=return；M3 索引锁=return。三种失败都不产生任何 verdict 记录 ⇒ 与 W-25 的 `return 0`、W-26 的 `degraded fail-open` 是**同一个仓级模式**（"读不到→静默→当作无事"），本层三次独立命中，应作为一条**跨族共性**上报总筹（见文末）。
3. **根因 C：判据与宪法 §9.3 的冲突没有被执法面看见。** 看门狗自己带 `# noqa: m10-time-trigger`（M4）——即"时间触发 daemon"是**在册豁免**的形态；而"各家手跑 keeper 旁路"（X-19、骨架册 §一"仅 1 条活跃会话"）用的是**同一个豁免先例**却**没有登记号**。⇒ 真正的缺口不是"有 sleep-loop"，而是"**豁免无中央台账**"：谁都能援引 `heartbeat_daemon 先例` 自免。而唯一该抓这件事的门 `PERMANENT-SYSTEM-TRIGGER` 恰好关着（§3 执法向）——**两案互为因果，必须一起读**。
4. **根因 D**：M6——会话真态在 `.runtime/session_registry.json`（未跟踪），"谁在跑什么"**不可考古**，事后无法判定某次回退/误清扫发生在哪个会话活着时。

## 5. 能红判据

- **尺 1（活性判据换轨）**：断言存在一条用例——"session 注册存在、pid 活着、**claim 指向的产物 mtime 超过阈值且无 git 写入**"⇒ 该 session **必被判非活**（不再免死）。
  **必红变异体**：今天的代码对同一输入走 M2 分支（免死）⇒ 尺必红；**若实现者只把阈值调大而不换判据，该用例仍绿** ⇒ 需再加反例："keeper 每 300s re-register（心跳新鲜）但产物 mtime 陈旧"⇒ 必判非活。这条是防"用心跳掩盖空转"的第二把锁。
- **尺 2（失败必点名）**：三处 fail-open（M1×2、M3）各自注入异常时，**必产出一条 verdict 记录**（而非 debug）。变异体：注入 `json.JSONDecodeError` ⇒ 无记录则尺红。
- **尺 3（豁免有号）**：断言每个 `# noqa: m10-time-trigger` 出现处，其 5 行内含**在册**豁免号（`#ARCH-…` 或 `裁定#≤413`）。
  **必红变异体**：今天跑 ⇒ M4 那处应红（只有"同 heartbeat_daemon 先例"的文字，无机读号）；给某处**随便编一个不存在的裁定号** ⇒ 尺必红（这条同时服务 W-81 防伪面）。
- **就绪度**：尺 1/2/3 都可写变异体 ⇒ 就绪。**注意**：尺 1 涉及"把在跑进程重新判成非活"＝改变保命/避让面，与 W-47（keep 判据收紧）同类，**属 ⚑-3 门位，禁自裁上线**；本层判据只到"案卷 + 沙盘断言"，真行为切换需批文。
