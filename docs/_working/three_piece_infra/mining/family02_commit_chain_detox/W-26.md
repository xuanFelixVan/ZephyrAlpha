## 4. 缺口与根因

1. **根因：预检被实现在"命令入口"而不是"数据入口"。** `run_enqueue_preflight` 挂在 CLI `enqueue` 子命令里（M1），而"形成一个队列项"这个**动作**有两个实现（`enqueue_item` / `requeue_dead_item`）。任何新入口（未来的 MCP 工具、reconciler 代投、脚本直调）都会天然旁路。⇒ 正解是把预检**下沉到 `enqueue_item` 内部**，CLI 只传参；`requeue` 路径复用同一函数而非"再判一次"。这与 W-25 的根因是**同一个模式**（契约写在调用方而不是被调方）。
2. **根因（requeue 的语义空洞）**：`requeue` 的前提是"读 dead_reason 修正后再投"（宪法 §2-6），但 requeue 本身**不校验修正是否发生**——袋内容与死信时**逐字节相同**也能回队 ⇒ 队列成为"同一失败反复消耗门链预算"的循环。701 封死信的存在本身说明这个循环跑过很久。
3. **根因（fail-open 未分级）**：M4 让预检在自身异常时放行。预检的一部分检查（冲突标记扫描、token 在册性）是**结构校验**，异常通常意味着"读不到册"，此时放行＝把 W-20/W-23 那一类必死袋直接送进队列，代价由 20+ 分钟门链承担。**处方不是"改成 fail-closed"**（那会把队列变成不可用）而是**分级**：构造失败→放行并记 degraded；判定为"必拒类"→拒。Z-11 的"28 可自动修 / 20 必拒"就是这个分级表，但它目前**在裁定文本里，不在代码里**。
4. 非根因：不是 serializer 抢锁（#ARCH-330 已 resolved，X-57 在册）。

## 5. 能红判据

- **尺 1（入口收敛）**：断言 `git grep -n "run_enqueue_preflight" HEAD` 的**调用点集合**包含 `enqueue_item` 与 `requeue_dead_item` 所在函数体；且 CLI 侧不再直接调用（避免两次判定产生两套结论）。
  **必红变异体**：今天跑 ⇒ 必红（M1 只有 1 点）。修好后：直调 `enqueue_item(files=<含未登记 token 的新建 .py>)` ⇒ 必拒并返回处方文本；**把预检从 `enqueue_item` 里摘掉 ⇒ 尺必红**。
- **尺 2（requeue 无修正必拒）**：取任一 dead 项，**不改任何字节**直接 requeue ⇒ 必拒（点名"与死信时同内容"）；改后再 requeue ⇒ 必放行到队列。
  **必红变异体**：反向——改了内容仍被拒 ⇒ 尺也要红（证明它不是"一律拒"）。
- **尺 3（degraded 可见）**：把预检内部构造人为抛错 ⇒ 队列项**必须**带上 `degraded: true` 标记并可被事后反查（今天 M4 只 `warn`，反查面为零）。
- **就绪度**：尺 1/2/3 都能写变异体 ⇒ 就绪。但尺 3 需要"degraded 标记"这一新数据位 ⇒ 触发 §6 对价审查。

## 6. 内收对价

- **不新增门**：三把尺都落在既有 `commit_queue` 测试族与既有 `enqueue_preflight` 模块内。
- `degraded` 标记**必须内收进既有队列项 schema 的"落地结果"面**（dead 项已有 `dead_reason`，done 项已有回执）——对价声明：`degraded` 与 `dead_reason` 语义重叠部分**以 `dead_reason` 为唯一真源**，`degraded` 只表示"预检没跑成"这一新增态；若最终发现既有 `note`/`warn` 字段可承载，则**不新增字段**（零触发零消费→退役）。
- **合并替代**：Z-11 散文里的"28 可自动修 / 20 必拒"分类表一旦进入代码（作为机读枚举），**91 册（一键册）里对应的手工分类文字即退役**，改指该枚举（同真源可派生→必并）。
