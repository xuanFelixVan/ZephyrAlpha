## §二 与我方方案的具体差异（逐条：我方现在怎么做 → 业界怎么做 → 差异的代价）

> 编号 D-xx 与 §一 的 1-1..6-4 交叉引用。此处只陈述"差异与其代价"，不给裁定、不给施工步骤。

**D-01 死信治理：一次性清库 vs 常设属主制**（引 3-1、3-3）
- 我方现在怎么做：波 6.1 把 700 封死信当**历史数据**做"内容驱动四态处置（已复活→归档／应废弃→逐文件 `git cat-file -e` 终验／可回队→裁到仅含 HEAD 缺件分批重投／需属主→**废属主判定改代投**）"，排产是"每批 ≤10 封、处置一批验一批"＝约 70 批人工；11 册 R-3 给了 14 行签名簇对照表供人工比对。R-0 实跑凭据 `dead=700 / pending=0`。
- 业界怎么做：Google **Build Cop**——"keeping all the tests passing in their particular project, **regardless of who breaks them**"，被通知即"drop whatever they are doing and fix the build"（SWE at Google ch23，2020）。死信是**当天必须有人中断工作去修的活信号**，不是待归档的存量。Evil Martians（2025）再加两条：**重试有上限**、**禁止无限期隔离**、**每周固定评审直到修复**。
- 差异的代价：①我方**主动废弃了"需属主"这一态**（R-3 明写"废属主判定改代投"），即把 Build Cop 语义反过来了——代投会让"谁弄坏的"信息只留在 commit message 里，复发时无人被叫醒；②清库式处置**没有复发计数熔断**，71 袋同签名簇（"注册表三向合并失败家族"）清完还会再来，因为根因（热册并发写）在波 5 才动；③`pending=0` 说明队列已停摆——**存量清完而入口未通，清库本身不产生吞吐**；④无重试上限⇒ 同一 payload 可被反复 requeue 而无台账（R-3 只有"同 payload 禁双 requeue"的纪律、无度量）。

**D-02 队列失败语义：归档停摆 vs 摘除+后继重建**（引 1-1、1-2、1-7）
- 我方现在怎么做：袋失败→进 `dead` 目录；`requeue` 时"取工作树现字节重建快照，但**不吸收新 staged 文件**"（R-3）；其余 pending 袋**不因前袋失败而重建基底**。实测 `pending=0 processing=0 dead=700 done=741`。
- 业界怎么做：**三家独立同构**——GitHub Merge Queue"某 PR 检查失败＝把它移出队列，其余 PR 只要末态通过就继续落地"（GitHub Docs）；GitLab Merge Trains"某一节失败＝把它摘掉，**其后各节的流水线重跑以反映新的组合**"（GitLab Docs，默认并行上限 20）；Zuul gate pipeline"某变更失败即从队列摘除，**其后叠在它上面做过投机测试的变更会被重新入队、按不含失败者的新组合重建**"（Zuul/OpenDev Docs）。
- 差异的代价：这是本卷**唯一被三个独立一手来源共同指认**的缺口。代价具体化为：①我方"袋失败"与"队列死亡"是同一件事（pending 归 0），业界是两件事；②后继袋拿旧累积状态继续跑，直接生产痛点⑤（热册被陈旧快照整档回退）与痛点④（外来 staged 连坐）；③波 2.1 的"基底不可知 2 封＝enqueue 必带 `--base-head`"是**给单个袋打补丁**，业界做法是**让队列自己维护基底有效性**（Zuul 的 speculative execution 本质就是"每袋都测'合入之后的那个状态'"）。

**D-03 CREATE-GUARD 的 `files_trigger`：槽位全在、没填没消费**（引 2-1、2-5）
- 我方现在怎么做：波 1.5 已精确定位——`files_trigger=''` + `always_run:false`，成本源 `create_guard.py:527` 每类一次全树 `git grep`；实测 1519 次/19186s/均 12.63s（09-25 后均 24.09s），占全部门 141565s 的 13.6%。处方是"登记 `files_trigger` **或**改 own-scope 差分（不退役，Owner 明令）"。同族还有 W-23：R5-DIGIT-SUFFIX 命中 8067+1342+4020 文件"近 always-fire"；X-50：密钥三门"判据本身能命中，零命中的真因是 `files_trigger` 走**路径子串**匹配"。
- 业界怎么做：Google TAP——"**can quickly determine which tests are downstream from any change and run the minimal set to be sure the change is safe**"（SWE at Google ch23，2020），提交平均等待 ~11 分钟。Bazel 把这件事做成三个可组合的开关：`--test_tag_filters`（只测带某标签的目标）、`--build_tests_only`（只构建跑测试所需的最小集）、`--test_filter`（测试运行器内再筛子集），加 query 侧 `tests()`/依赖追踪定位受影响目标。
- 差异的代价：①我方**不是缺机制、是缺登记**——`files_trigger`/`always_run`/`own_scope` 三个字段全在 GateSpec 与 `gate_registry.yaml` 里，`generate_project_depgraph.py` 也已在产依赖图，即"标签 + 反向依赖"两半我方都有，只差"从 changed files 反查 affected gates"这一步查询；②因为没填，X-50 出现了**反向事故**——密钥三门本该拦的泄露面零命中（触发面是路径子串，匹配不到内容），即"选择性跑"没做成、"该跑的没跑"先发生了；③13.6% 的门禁时间预算被单一台门吃掉，直接推高每袋落地时延，间接推高痛点⑦（车道长期悬挂）。

**D-04 选择性化的"召回下界"缺失（假绿风险）**（引 2-2、2-3）
- 我方现在怎么做：波 1.5 的验收判据是"红证=新文件缺 token 时必拦（现状已能红，改后须仍能红）+ **重放 100 笔 verdict 全等**"。11 册 R-5 给了"能红判据模板"三问。
- 业界怎么做：Facebook/Meta Predictive Test Selection 的验收是**成对的**——"reduces the total infrastructure cost of testing code changes **by a factor of two**, while guaranteeing that **over 95% of individual test failures** and **over 99.9% of faulty changes** are still reported back to developers"（arXiv:1810.05286，2018；工程博客 2018-11-21 口径为"只跑三分之一的测试、捕获 >99.9% 回归"）。**成本减半必须同时报出召回下界**，否则选择性跑＝假绿。
- 差异的代价："重放 100 笔 verdict 全等"只测**一致性**（改前改后同一批输入给同一批结论），**不测漏检**（改造后有多少本该拦的没拦）。若 `files_trigger` 填窄了，100 笔重放可能全等而召回已塌——这与痛点②"4 台门静默不装载＝提交面空转（假绿）"是**同族病**，而波 1.1 的红证设计（"故意塞一台引用不存在模块的门，尺必须红"）恰恰证明本仓有能力做召回尺，只是 1.5 没配。

**D-05 "外来 staged 连坐"：own-scope warn vs 摘除失败项**（引 1-1、1-2、1-7）
- 我方现在怎么做：AGENTS.md 第 3 节第 1 条 定"内容扫描型 gate 默认 own-diff 作用域；**外来 staged 违规=warn+审计（`_audit_foreign_staged`），不阻断无辜提交人**"；第 3 节第 4 条"他会话在途违规不代修：owner 责任制"。但 10 册波 1.9 又**主动撤下**了 own-scope 治本（"六图役 7 袋实测死于 13 类不同死因……全 dead 文本含'外来 staged'仅 2 封"⇒ 降级为观察项 W-22）。
- 业界怎么做：GitHub/GitLab/Zuul 三家都不是"给检查缩作用域"来解决连坐，而是**在队列层解决**——失败者被摘除，无辜者继续；后继者按新组合重建（见 D-02）。也就是说：**连坐是队列语义问题，不是检查作用域问题**。
- 差异的代价：我方把"外来 staged 连坐"当门禁作用域问题治（own-scope），实测证伪（仅 2/700 封 dead 提到外来 staged）后降级为观察项——**这一步判断与业界口径一致，是对的**；但**没有把它转成队列语义问题接着治**。代价＝痛点④仍在，只是不再被记账：多会话共用一个 git index（MEMORY 侧记为"index＝多会话混合池 547 条"），而 serializer 落地的仍是"整档快照"（R-7 明写"袋=整档快照 ⇒ 你无法只提交自己那几行"），**只要袋是整档快照，连坐就结构性存在**。

**D-06 热册并发写：一次性人工分诊 vs 409 三步协议产品化 + 常开收敛**（引 5-1、5-2）
- 我方现在怎么做：AGENTS.md 补充铁律 #13 要求热文件必用 `safe_write_text`（CAS 防并发覆盖）；11 册 R-1 给了三态分诊（A 型/B 型）+ 块级集合差纯插入 + CAS（`expected_base_sha256`）+ 写后进程外复验 + "连拒两次即停手"；R-6.2 补了"根键唯一性必查"（PyYAML 不报重复根键）。但**合并逻辑住在一次性探针脚本** `.runtime/tmp/total_command_closeout/repair_capability_tokens_v3.py`，而 W-156 已把 `repair_capability_tokens*.py` 列为"被登记但零消费者/被 .gitignore 排除"的**孤儿件**。自检尺（波 0.2、波 5.2"热件盘-HEAD 键集合差自检尺"）是**波次内跑一次**。
- 业界怎么做：Kubernetes 乐观并发——写请求回传 `resourceVersion`，不一致返回 **409 Conflict**，客户端**必须**"re-fetch → merge → re-apply"三步重试（官方 API Concepts 文档）；变更侦测走 **watch 流**而非轮询。Argo CD——OutOfSync 即触发 sync，`selfHeal` 默认**等 5 秒**（debounce）后把实况纠正回 Git 声明态，重试走**指数退避**；并明确"**automated sync 只事后纠正漂移，并不预防漂移**"。
