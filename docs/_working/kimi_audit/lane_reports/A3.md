- verdict 分布：`grace_suppressed` 90,124（**57.4%**）、`alerted` 18,564（11.8%）、`quarantine_retention_sweep` 10,912、`healed` 10,812、`auto_staged` 7,060、`claimed` 4,772、`quarantine_tamper` 4,646、`shielded_add` 2,785、`observed` 2,542、`merge_suppressed` 2,045……

### 2.2 核心问题：它是不是只在状态变化时落盘？——**设计上有一半是，实测上不是**

**设计面**（`src/zephyr/gov_enforcement/rule_bridge/worktree_drift_watchdog.py`）：
- 有去重：`prev.work_hash == wh` → `dedup_skipped` 直接 continue 不落盘（`:1170-1172`）。daemon 路径（`alert_enabled=True`）确实按签名去重。
- **但状态持久化被 `alert_enabled` 门控**：`scan_once` 收尾处 `_save_state(root, state)` 只在 `alert_enabled=True` 分支内执行（`:1249-1267` 自愈块内，`_save_state` 在其末尾）。而审计写 `_audit` **不受** `alert_enabled` 门控——`grace_suppressed`（`:1190`）、`observed`（`:1213`）等分支照写。
- **于是 observe-only 路径（网关 post-commit 即时扫，`alert_enabled=False`，reconciler 挂点 `:1430` 起）陷入自激**：读旧 state → 对每个漂移文件写审计 → 内存里推进 files_state → **不落盘** → 下一笔 commit 再触发即时扫 → 再读旧 state → 同样文件同样哈希再写一遍。

**实测面（逐文件相邻同哈希同 verdict 重复判定）**：
- **全账本 37.0%（58,121 条）是"状态零变化重复写"**；同哈希重复（跨 verdict）40.5%。
- 按 verdict：`grace_suppressed` 重复率 **47.2%**（42,570/90,124）、`auto_staged` **89.4%**（6,315/7,060）、`derived_auto_committed` 83.2%、`merge_suppressed` 51.1%、`shielded_add` 44.2%。
- 放大器①：宽限窗 600s（`:92` `_GRACE_AFTER_COMMIT`）远大于活跃期提交间隔（指令书：314 笔/24h ≈ 每 4.6min 一笔）→ **活跃期 grace 几乎常开** → 每笔派生回写都产 `grace_suppressed` 记录，占总量 57%。
- 放大器②（自激闭环）：watchdog 的 B 类派生自动收敛（`_auto_commit_derived`，`:833`）**自己发起提交 554 笔**（峰值 09-08 单日 120 笔 ≈5/h——**当天即占单通道上限的 21%**）；每笔自动提交又触发 post-commit 即时扫 + 新开 600s 宽限窗 → 又一轮 grace_suppressed 记录。
- 放大器③：`auto_staged` 89.4% 重复=「commit 失败 → index 被 reset → 护盾重新 git add → 再审计」的循环（与现行宪法「并发与提交」节第 8 条 stash/reset 事故链同构）。

**结论一句话**：watchdog 不是只在状态变化时落盘——observe-only 即时扫不写 state 导致同哈希重复落盘（37% 无变化写），grace 常开 + 自身派生提交构成自激环；09-16 它一天写了 3 万条，峰值期自身派生提交吃掉单通道上限的两成。

### 3.2 当前架构上限计算

系统 = 两级串联：**claim 层**（决定了多少尝试能到达提交点）→ **serializer 单通道**（绝对硬顶）。

**(a) serializer 硬顶**：

```
X_ser = 3600 / S = 3600 / 149 ≈ 24.2 笔/h（理论 ρ=1）
可持续  X_ser × 0.85 ≈ 20 笔/h
```

**验证：近窗实测小时落地峰值恰为 24 笔/h（§1.3）——模型上限与实测上限吻合，serializer 是当前唯一硬瓶颈。**

**(b) claim 碰撞层**：C 个并发在飞提交时，单笔被挡概率 `P = 1-(1-p_pair)^(C-1)`：

| C | 2 | 5 | 10 | 20 | 50 |
|---|---|---|---|---|---|
| P | 0.13 | 0.44 | 0.73 | 0.94 | ≈1.00 |

夜间饱和时 C ≈ X×W = 24×0.5h = 12 → **P_block ≈ 79%**。被挡者等到对方释放或 TTL 30min——延迟爆炸但 serializer 仍有喂料（队列缓冲），所以低 N 时上限仍由 (a) 定；**N=100 时碰撞率→~100%，大量车道卡在 TTL 级等待，有效送达率 Π 崩到 ~0.05–0.3，系统有效吞吐跌破硬顶**（观察佐证：09-16 门禁空转税 1.46 次/笔、dead 率 44.6%、LOCK_TIMEOUT 死信 39 件、P90 落地延迟 7h）。

**(c) 当前架构系统上限结论**：

| 场景 | 需求 | 硬顶 | 碰撞修正后有效吞吐 | 判定 |
|---|---|---|---|---|
| 当前低并发（实测） | ~13 笔/h | 24/h | ≈20–24/h | 恰好顶到天花板（实测峰值 24） |
| N=50 | 100/h | 24/h | ≈12–20/h（ρ=4.2 过载 + 79% 碰撞） | **缺口 5–8 倍** |
| N=100 | 200/h | 24/h | ≈5–15/h（碰撞层崩落） | **缺口 13–40 倍** |

### 3.4 组合情景与夜间达标判定

| 组合 | 可持续上限 | N=50（需求 100/h） | N=100（需求 200/h） |

### 3.5 灵敏度

- 若每车道夜间提交率 1 笔/h（而非 2）：需求减半，①+②(k4)+③ 下 N=100 也达标（ρ≈0.6）。
- 若 S 取 mean=201s（悲观）：当前硬顶 18/h，③ 后 25/h，k4 后 85/h——结论方向不变，k 需求 +1。
- p_pair 随治理派生税削减（A1 lane 结论）会进一步下降——① 的分片收益是下限估计。

## 4. 给 L0 的结论（≤10 行）

1. **当前架构系统上限 = 24 笔/小时**：serializer 单通道 S=149s（实测 P50），理论 24.2/h 与实测小时峰值 24 精确吻合——单通道就是唯一硬顶。
2. N=50 需求 ~100/h（缺口 5 倍）、N=100 ~200/h（缺口 13–40 倍且 claim 碰撞率→~100% 致有效吞吐崩落至 5–15/h）；实测 P90 落地延迟 7h、门禁空转 1.46 次/笔即过载实证。
3. 三瓶颈提速：①claim 绑定移到提交前+TTL 300s+热点注册表分片 → 高并发有效吞吐 1.6–4.8 倍（是②③的前置）；②4 分区通道 → 3.4 倍（82/h）；③头部 O(仓库) 门禁 diff 化 → 1.4 倍（33/h/通道）。
4. 组合 ①+②(k4)+③ ≈112/h 可达 N=50 达标；N=100 需 k=8（~163–196/h）或配合派生税削减降需求。
5. **watchdog 自激实锤**：156,900 条中 37% 是同哈希零变化重复写；根因=observe-only 即时扫写审计但不落 state（`worktree_drift_watchdog.py:1249-1267` `_save_state` 被 `alert_enabled` 门控）；放大器=600s grace 常开（57% 流量）+ 自身派生提交 554 笔（峰值日占单通道上限 21%）。
6. 治本方向：observe-only 扫描要么落 state 要么读共享去重签名；grace 窗收窄或按派生白名单豁免落盘；watchdog 派生提交并入触发它的那一笔。
7. 潜伏风险（未触发但结构存在）：serializer lease 无续租，单项落地锁等待 300s 恰等于 lease TTL 300s，批拉长即现双写者窗口。
8. 三瓶颈相互依赖：②③ 不加①会在 claim 层崩落；建议裁定顺序 ①→③→②。
9. 本 lane 零 git 写、零既有文件改动；全部常数来自上述四份账本 + 队列代码实测。
