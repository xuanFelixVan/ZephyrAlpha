## 2. R-10 设计（最高优先）

### 2.1 触发位判定：lock_files.py cleanup，而非 gateway pre-commit

理由三条：
1. **同族家务**：`cmd_cleanup` 已负责死锁清理（TTL/PID/会话判活设施齐备），死会话遗物是同一族「死了没人收」问题，设施零新建。
2. **时机正确**：RULE-GUARDIAN 规定每班开工必跑 `lock_files.py cleanup`——遗物在下一班开工即被回收，正是 e19bc24c 事故缺失的环节。gateway pre-commit 是被动位（commit 才触发），且门禁链 P50 已 46.4s（S18 R-03），不该让每笔提交为低频家务付墙钟。
3. **职责分离**：gateway commit 路径对 MERGE_HEAD 已有 B2 治本①的拒绝语义（exit 10）；回收是写副作用家务，进 commit 链会混淆「拒绝」与「处置」两条语义线。
同时保留 `salvage <sid> [--dry-run]` 显式子命令供审计/人工处置。

### 2.2 双证判死（缺一不动，红线=误收活会话）

- **证据①（心跳/注册表证死）**：raw 读 SessionRegistry（绕过 `get_session` 的「死即 None」语义），条目在且 `_is_session_alive=False`（心跳 90s/PID 亡/TTL 3600s）→ 成立。条目不在 → 进程证据兜底：≥1 条 claim 且全部 claim PID 死/零才成立（零 claim 零条目=无任何死亡证据，不成立）。
- **证据②（全部 claim TTL 过期）**：.ailocks 有 claim 时全部 `expires_at < now` 才成立（任一新鲜=会话可能心跳间隙在干活，禁收）；零 claim 时 SessionRegistry held_files 无 TTL，仅当证据①是「条目证死」才视为可释放（裁定#252 锁存活=会话存活）。

### 2.3 回收三件套

1. **MERGE_HEAD abort**：仅主区（worktree 物理隔离各自收尾）。归属判定保守双条件——(a) 无「注册时间先于 MERGE_HEAD mtime」的存活会话（班后 cleanup 的当前会话 start_time 晚于晾置 merge，天然不挡道；merge 进行中的会话必挡住）；(b) 死会话活动窗覆盖 mtime（±300s 宽限）。归属不明→不 abort，如实记录待人工。abort 前留 MERGE_HEAD sha 进审计。
2. **stash 归档**：`git stash push -m "dead-session salvage <sid>" -- <claim路径>`——pathspec 限定只动该会话名下文件（禁全量 stash 误卷他人 WIP）；归档不丢弃，`stash pop` 可恢复（测试实证）。merge 存续未 abort 时跳过（merge index 神圣）。
3. **claim 释放**：.ailocks（锁目录+registry 条目，绕过归属校验——死者无法自释）+ SessionRegistry（release_files_batch + unregister）两登记处全放（T10 教训）。

全程审计 `.ailocks/salvage_audit.jsonl`（含 skip 记录）。幂等：无 MERGE_HEAD/无改动/二次运行均安全。

## 3. R-04 设计

### 3.1 claim 生命周期（git_commit.py）

决策表（单一真源 `_settle_claims_after_commit`）：`OK`/`NOTHING_TO_COMMIT` → 释放；其余（gate 阻断/锁超时/异常/预检快败）→ **保留** + `.ailocks` TTL 收窄至 300s（`--failed-claim-ttl` / `ZEPHYR_FAILED_CLAIM_TTL_S` 参数化）+ 审计 `.runtime/claim_snapshots/claim_retention.jsonl`。

**与「失败释放防锁尸」语义的兼容方案**：防锁尸动机不由释放动作而由三层接管——①收窄 TTL 300s，死者 claim 过期即走既有 `_is_stale` 回收（reclaim 审计已在案）；②裁定#252 SessionRegistry 侧随会话死亡自动失效；③R-10 回收兜底清点。`--release-only` 显式释放路径不动。reconciler-verify 部分 claim 失败仍即释（防跨坐，语义正确保留）。

### 3.2 派生写入归属（gateway，纯增量）

台账 `.runtime/gate_audit/derived_write_attribution.jsonl`，模块级真源 `record_derived_write` / `lookup_derived_write_owners` + gateway 薄封装。挂账点两选（实证覆盖全部 reconciler 派生提交）：①`_commit_auto` 成功两处（锁内+fail-open 降级）——batcher flush 亦汇入本函数，单点全覆盖；②`_post_flush_rules_integrity_re_register` 提交前先挂 `committed=False`——auto-commit 失败时工作区残留仍可溯源。后续 lane 可让 CLAIM-REQUIRED/FOREIGN-CHANGE 查台账区分「已归因派生写入」与匿名外来变更（本 lane 不碰 gate 逻辑，见 §5 风险）。

3. **台账消费方未接线**：本 lane 只建台账+挂账点，gate 查询接线留给 gate lane（防一次手术横跨两条语义线）。
