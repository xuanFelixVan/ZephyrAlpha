# Hyper-V Ubuntu ClickHouse 迁移施工方案

> 状态：待 Owner 确认施工授权
>
> 范围：将“历史数据仓库、数据写入和无人值守回测”从 WSL2 迁至 D 盘上的 Hyper-V Ubuntu VM；Windows 保留开发、控制台和报告职责。
>
> 非范围：实盘交易数据库、交易执行链路、删除源数据、创建/迁移 VM、修改生产配置。本文件本身不是施工授权。

## 1. 裁定与成功定义

### 1.1 架构裁定

采用 **Hyper-V Ubuntu VM 内同机部署 ClickHouse、数据写入调度器和回测 worker**。Windows 只通过 SSH 或受控 API 发起任务、取回小型结果和报告；不再让 Windows 回测进程跨 WSL/VM 网络反复读取大批行情数据。

WSL2 保留为开发与短任务环境，不再承担离机数小时的回测主运行时。原因不是 ClickHouse 不适合回测，而是已经观察到 WSL 服务级异常；此前调度器又曾把 systemd 用户会话错误误判为 VM 故障并主动关闭 WSL。该误判已修复，但 WSL 仍不具备目标运行时所需的故障隔离边界。

### 1.2 可验收的目标

1. 同一基准回测的结果（行数、关键聚合、交易记录和收益指标）一致。
2. 基准回测墙钟耗时不高于当前基线的 110%；达不到则不得切换。
3. 数据写入、回测 worker 和 ClickHouse 全部在同一 VM 内，宿主机不传输大块行情数据。
4. 连续 8--12 小时在“数据写入 + 多事件驱动回测”混合负载下运行，无 VM/ClickHouse 进程异常退出、无任务假成功、无未解释的数据缺口。
5. 迁移完成后仅保留一个工作库；旧 WSL 数据盘仅在验收后按 Owner 明确授权删除。

### 1.3 明确不能承诺的事项

不能承诺绝对零故障或“性能必然更快”。可承诺的是：采用同机计算、NVMe 盘、资源隔离和准入验收，任何未达到指标的版本都不切流。用户已确认可以不保留完整数据备份、损坏后可重新下载；此授权降低恢复目标，但不取消每批数据的完整性校验。

## 2. 已验证事实（2026-07-15）

| 项目 | 实测结果 | 对设计的含义 |
|---|---|---|
| CPU | Intel i7-12700KF，12 核 / 20 逻辑处理器 | 可配置 12 vCPU 给 VM，仍为 Windows 留出资源。 |
| 内存 | 64GB；检查时宿主可用约 25GB | WSL 配额 24GB 时内部可用约 18GB；非当前瓶颈。 |
| D 盘 | Kingston SNV2S1000G NVMe；731.2GB 分区，217.6GB 空闲 | 性能目标盘，但空间极紧，必须滚动迁移与容量门禁。 |
| E 盘 | WD Green 2.5-inch SATA；931.5GB，499.8GB 空闲 | 不能作为主 ClickHouse 数据盘；可作为非关键导出或人工下载缓存。 |
| 当前 ClickHouse | WSL Ubuntu 内 `active` | 当前 Windows 调度器与 WSL ClickHouse 跨运行时访问。 |
| 活跃 parts | 18,246，375.83GiB | 合并和查询需保留明显余量。 |
| `/var/lib/clickhouse` | 405GB | 这是容量规划的基线，不可以 428GB VHDX 文件大小替代。 |
| ClickHouse 日志 | 3.8GB | 纳入日志轮转与容量报警。 |
| 最大数据表 | `tick_data` 231.92GiB；`kline_1min` 77.55GiB | 必须逐月/逐分区迁移，不能全表复制。 |

## 3. 目标拓扑与资源边界

```text
Windows host
├─ IDE / Dashboard / 任务提交客户端
├─ WSL2：开发、单元测试、短诊断任务
└─ Hyper-V Ubuntu VM（D: NVMe）
   ├─ ClickHouse：历史研究与回测数据仓库
   ├─ data scheduler：下载、缓冲写入、重放
   ├─ event dispatcher：事件驱动任务分发
   ├─ backtest workers：受配额并发执行
   └─ result exporter：仅导出指标、日志和报告到 Windows
```

初始配置（压力测试后才可放大）：

| 资源 | 初始值 | 边界 |
|---|---:|---|
| VM vCPU | 12 | Windows 保留 8 个逻辑处理器的调度余量。 |
| VM 内存 | 32GB 固定 | Windows 至少保留 16GB；若压测显示 ClickHouse page cache 与 worker 不足，再升至 40GB。 |
| Ubuntu 系统盘 | 80GB 动态 VHDX | 与数据盘分离。 |
| ClickHouse 数据盘 | 最大 600GB 动态 VHDX | 客户机内设置容量与宿主 D 盘双重水位线，禁止无上限增长。 |
| 重型逐笔回测 | 初始最多 2 并发 | 每个 worker 设置 CPU/内存预算；达到基准后再增加。 |
| 分钟/日线回测 | 初始最多 4 并发 | 写入 worker 与回测 worker 使用独立队列和并发上限。 |

> [ASSUMPTION] 600GB 数据盘是当前 D 盘约束下的上线值，不是长期扩容上限。数据增长达到水位线时，扩容存储优先于降低 ClickHouse 安全余量。

## 4. D 盘容量模型与停止条件

迁移期间不保存完整备份，但技术上任何已验证批次都会短暂出现“源与目标各一份”；这是复制的物理必然。策略是只保留一个小批次的短暂重叠，在释放源分区并回收 WSL VHDX 空洞后继续下一批。

| 容量项目 | 目标值 | 管控方式 |
|---|---:|---|
| 当前实际库 | 405GB | 从 `system.parts` 与 `du` 定期复核。 |
| Ubuntu 与服务 | 25--40GB | 与数据 VHDX 分盘。 |
| ClickHouse 合并、日志、写入余量 | 最低 100GB | 客户机内 `df` 低于阈值即暂停迁移/写入。 |
| 宿主 D 盘余量 | 最低 80GB | Hyper-V VHDX 扩容前检查；低于阈值即停止。 |
| 单批迁移上限 | 初始 20GB | 只在源侧删除并成功回收空间后进入下一批。 |

任何一条未满足，迁移立即停止，不进行“赌空间”的下一批。D 盘最终能否长期容纳增长，取决于当前非 WSL 文件占用和数据增长率；若水位线频繁触发，唯一正确的扩容方向是新增 NVMe，而不是把主库降级至 E 盘机械硬盘。

## 5. 施工阶段与检查点

### Phase 0：设计冻结与环境准入（不改业务入口）

1. 以管理员权限验证 Hyper-V 已启用、BIOS 虚拟化可用、D 盘 SMART/健康状态正常。
2. 建立迁移清单：所有 `wsl`、`Ubuntu`、`127.0.0.1`、端口 `9000/18123/8123`、`/mnt/*`、`ext4.vhdx`、ClickHouse endpoint 的代码、配置、脚本、服务定义、文档索引与测试引用。
3. 对每个条目标记：运行时真源、派生索引、只读文档、可删除旧兼容路径；不允许靠全局替换。
4. 记录基准：各表行数、按月/按日聚合校验值、表定义/引擎、最大 15 表尺寸、代表性回测结果和耗时。
5. 冻结源端写入窗口的切换规则：迁移批次内源表只读，或使用明确的增量水位线补齐；不得一边无界写入一边复制。

**Phase 0 准入**：清单经人工复核；D 盘宿主与 VM 内水位线可执行；基线报告落盘。

### Phase 1：构建隔离运行时（不导入全量数据）

1. 在 D 盘创建 Ubuntu VM、独立系统/数据 VHDX、内部虚拟交换机或受控网络。
2. 安装同主版本 ClickHouse、Python 运行环境和项目依赖；启用 systemd 服务自启动、日志轮转、VM 关机时的有序停库。
3. 创建最小权限的 ClickHouse 服务账号、专用凭据与 endpoint 配置；禁止把凭据、IP 或 VM 路径硬编码到代码。
4. 在 VM 内运行一个小表读写验证、服务重启验证和本地回测 smoke test。
5. 配置宿主与客户机容量/健康监控：VM 可达、ClickHouse query/write、磁盘、内存、队列积压、重放积压、worker 状态。

**Phase 1 准入**：VM 重启后服务恢复；小表读写与本地回测成功；未改动 Windows 现有生产调度器。

### Phase 2：连接抽象与并发模型改造

1. 将 `ch_writer.py` 的 WSL 专用发现与 subprocess fallback 改为显式 endpoint 配置；保留本地可靠落盘语义，但取消对 WSL 生命周期的业务依赖。
2. 统一 `ch_reader.py`、`buffered_writer.py`、`local_replay.py`、`scheduler.py` 与回测数据访问层使用同一 endpoint 契约。
3. 将 Windows 常驻 `python -m zephyr.data.scheduler` 移入 VM；Windows 只保留受控任务提交与观察接口。
4. 为多事件驱动仿真建立独立队列：写入队列、回测队列、回放队列分离；按 worker 资源配额限流，防止回测淹没写入与 ClickHouse 合并。
5. 保留 `LOCAL_DURABLE` / `DEFERRED_PERSISTENCE` 状态，补齐重放成功后对原任务的可追溯闭环；禁止把本地落盘伪装为 ClickHouse 已提交。

**Phase 2 准入**：不再需要 `wsl.exe` 才能读写新 endpoint；单元与集成测试覆盖 endpoint、掉线、重放和并发限流。

### Phase 3：单向滚动数据迁移（用户接受无完整备份）

每一批均执行以下固定顺序：

1. 选择不超过 20GB 的单月/单分区批次；先迁移较小分区以验证全链路。
2. 在目标库导入该批，校验 schema、行数、主键/时间范围、关键聚合和抽样 hash。
3. 在目标 VM 运行依赖该批数据的代表性回测，与基准结果对比。
4. 仅当校验完全通过时，按 Owner 授权删除源端**同一批次**数据。
5. 对 WSL 文件系统执行空间回收/压缩的受控流程，确认 D 盘实际已释放后记录容量账本。
6. 再进入下一批；任何失败保留源批次，停止后续迁移并诊断。

迁移顺序建议：小型维表与日线 → 分钟线 → `news_data` → `tick_data`。逐笔表按月、按市场类型进一步拆分，绝不全表一次迁移。

### Phase 4：切换、压力验收和旧环境退役

1. 关闭 Windows→WSL 的常驻 scheduler，仅启用 VM 内 scheduler。
2. 切换 endpoint 后做一轮增量数据写入、重放、查询与回测验证。
3. 执行 8--12 小时混合压力运行；记录 p50/p95 查询延迟、吞吐、磁盘水位、队列积压和结果一致性。
4. 验收通过后，保留 WSL 环境但停止其 ClickHouse 服务；旧 `ext4.vhdx` 的删除是独立、显式、不可自动执行的 Owner 授权动作。
5. 删除后更新运行手册、基础设施注册表、接口契约、蓝图、索引/目录注册表与运维 Dashboard；运行注册表/依赖图/漂移检查。

## 6. 影响清单与更新原则

当前已定位的直接影响面如下；Phase 0 必须扩大为机器生成清单后才允许改动。

| 类别 | 已定位项目 | 迁移原则 |
|---|---|---|
| 写入连接 | `src/zephyr/data/ch_writer.py` | 取消 WSL 专属 host 发现与 subprocess 业务依赖，改为可配置 endpoint。 |
| 读取连接 | `src/zephyr/data/ch_reader.py` | 只依赖统一 writer/endpoint 契约，不散落连接信息。 |
| 可靠落盘 | `buffered_writer.py`、`local_replay.py` | 保持数据语义与重放审计；将本地路径明确为 VM 路径。 |
| 调度与健康 | `scheduler.py` | 移除 WSL 探针/重启的职责，改监测 VM 内服务与队列。 |
| 任务状态 | `task_queue.py`、`progress_store.py` | 保留延迟持久化状态并实现回放闭环。 |
| 配置与部署 | data 配置、服务定义、环境变量 | 端点、凭据、目录都从受控配置读取，不能硬编码。 |
| 回测访问 | `zephyr.backtest` 消费者与 tests | 只用统一 reader；回测 worker 在 VM 本地启动。 |
| 文档/索引 | 数据集成蓝图、ClickHouse 蓝图、基础设施注册表、接口契约、目录索引 | 先更新真源，再生成/校验派生索引；不可仅改索引。 |

## 7. 风险、禁止项与恢复口径

| 风险 | 控制措施 | 恢复口径 |
|---|---|---|
| 迁移批次损坏 | 每批校验后才删除源批次 | 用户授权从数据供应商重新下载；不得把未校验批次视为完成。 |
| D 盘满导致 VHDX/CH 损坏 | 宿主与客户机双水位线；每批后确认物理释放 | 立即停写与停迁移，清理非关键产物或扩容 NVMe。 |
| 并发回测挤压写入 | 队列隔离、worker 限流、ClickHouse 资源上限 | 降低回测并发，优先保证写入和元数据一致。 |
| VM/Windows 重启 | systemd 自启动、有序停机、任务幂等与重放 | 任务从持久化状态恢复，不依赖内存状态。 |
| 索引/文档漂移 | 真源优先、变更清单、注册表与 depgraph 检查 | 阻断切换，补齐影响面后再验收。 |

禁止项：

- 未经逐批校验直接删除源分区或旧 VHDX；
- 直接复制运行中的 `ext4.vhdx` 作为数据库迁移方法；
- 把 ClickHouse 主数据盘放到 E 盘机械硬盘；
- 在 Windows 端跨网络执行大数据回测；
- 使用 `wsl --shutdown` 作为新的服务恢复机制；
- 把本地 TSV fallback 标为 ClickHouse 成功；
- 未通过压力验收即停止旧运行时。

## 8. Owner 需要确认的施工授权

本方案建议的裁定是：**批准先完成 Phase 0（只读清单、基线与准入检查），然后再由 Owner 对 Phase 1--4 的环境创建、逐批删除源分区和最终删除旧 VHDX 分别授权。**

这比一次性授权所有破坏性动作更安全，也保留了每个阶段的性能和容量否决权。
