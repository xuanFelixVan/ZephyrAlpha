## 升级流水线（与业务层标准库同构，四步）

1. **提案（自动，AI 层）**：月度标准体检（挂 L1 感知段的内监慢周期）——门禁触发率/误拦漏拦
   统计（reconcile_execution_log 已有）、阈值漂移检测、业界治理新实践扫描（从胃点菜的治理轨）。
   事故自动喂案例库：2026-09-17 传送带 serializer pathspec bug 即第一案（死因→缺陷模式→阈值提案）。
2. **立案（治理层）**：提案进治理层标准库走变更流程（规则 YAML/裁定登记）。**AI 层不能持有
   自己的尺子**——它的考纲/阈值/rubric 也放治理层标准库，AI 层只有使用权+提案权
   （运动员不持尺，与业务层"考纲=治理层"归属同款）。
3. **裁决（Owner）**：修标归 Owner——"**AI 提案、治理立案、Owner 修标**"（与业务层三段同款）。
4. **重考历史（上线前强制）**：新阈值/新 rubric 对历史提交集**重放**，证明拦截排序不变
   （误拦没暴增、该拦的没放走）——业务层"改尺子必须重考历史"的 AI 层版；重放不过=一票否决。

## 递归限制（防套娃）

标准升级流程本身也是标准——**递归只允许一层**（"升级流程的升级"=Owner 直接管），锚点=Owner
修宪权。与业务层裁定的递归上限一致。
