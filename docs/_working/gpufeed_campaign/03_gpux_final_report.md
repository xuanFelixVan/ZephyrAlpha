# 终报（st-gpux-20261011，工单「引擎 GPU 化工单」）

## 〇、一句话与大白话

**一句话**：eval 面确实搬上了卡并且数值可证等价（单进程 eval 3.55x、199 格排名 Spearman ρ=1.0），
但工单两条验收线——**探索吞吐 ≥3x 与 GPU 持续利用率 ≥70%——今晚实测未达标**（6 路并发聚合折算约
1.1x，本进程归因 SM 均值 3.5%），根因不是"没搬上去"，而是**"每格一 kernel"这种搬法在并发下喂不饱卡**；
设备已按缺省关（`--eval-backend cpu`）入库，不会有人误吃这条路径。

**大白话**（给 Owner，不带行话）：
- 我们原来想的是"这台电脑的显卡在闲着，把算得的活分给它就快了"。今晚把最重的那块活（给股票打分排序）
  真的搬上显卡了，一个人干的时候确实快了 2-3 倍。
- 但**同时开 6 个工人去用同一张卡**时，每个人都要排队等卡，而且每人给卡开的"工位"（CUDA 上下文）
  光占地方就吃掉 12GB/24GB 显存——结果 6 个人加起来反而比原来在 CPU 上慢。
- 打个比方：不是"厨房没灶"，是**每人只做一道菜就喊一次灶**，灶火 90% 时间在等；要达标必须
  "一次端 50 道菜进灶"（把共用同一批数据的许多格合并成一次批量计算），这是下一班要造的家伙，
  不是今晚再调调参数能出来的。
- 还有一件更要紧的事：原本用来判"卡有没有被喂饱"的那把尺（nvidia-smi 的利用率）**本身会被桌面图形
  污染**——我实测开着零计算时它也能显示 8-57%。要是直接拿它当验收尺，我可以很轻松地"做出"70% 的假绿。
  今晚把这把尺换成了"只认我们引擎自己那份占用"的版本，所以现在的 3.5% 是**真数**，不是没测到。

## 三、未达的原因分解与下一班入口（三清单之二：残余）

**为什么搬上卡却没到 3x（三条都有数）**：

1. **Amdahl 帽**：eval 只占格耗时 82%；单格剩余 CPU 侧（bt 0.107s + 五档成本门 + 编排 + 把设备结果
   物化回 pandas）构成地板。级 2 GPU 的 hit 格 tot=0.184s 里 eval 只占 0.127s ⇒ 就算 eval 归零也只有 ~1.8x。
2. **并发争用**：6 分片把 hit 格单格耗时从 0.184s 撑到 0.487s（2.6x），且 **6 个 CUDA 上下文常驻吃掉
   12,171MiB/24576MiB** 显存——这与 `search_space_prereg.yaml:106 vram.concurrency: 1`（"单卡禁共存"）
   的在册口径正面冲突，也在挤压本地 LLM 预算。
3. **"每格一 kernel"喂不饱卡**：单格设备时长 ~0.02-0.05s，中间全是 CPU 空隙 ⇒ 归因 SM 只有 3.5%。
   这正是 `00_gpufeed_report.md §五 T2-D`（多 worker 喂单 GPU 流/异步流水线）与
   `p1_wiring_benchmark.md §五` 当年立为候补、至今未造的那件家伙。

## 七、N-3 跨夜配对为什么被本班判废（配对方法学缺陷，非数值结论）

**触发**：六路×25,000 格 GPU 波（05:36）与昨晚 p2 纯 CPU 基线（23:37）逐字同参，本班原打算
直接拿它当级 3 容差报告。join 后 16,626 同格里 sharpe 越线 32／ann_return 25／max_drawdown 41，
且最大差分到 **rel 0.34、abs 0.116**（-0.3413 → -0.4572）——这个量级**不可能是浮点尾差**，
也远超 §二·补"近并列翻转"的 ~1e-16 序差范畴。

**三路对照把它判死**（`.runtime/tmp/st-gpux-20261011/n3_three_way.py`，只读产物零卡时）：

| 对照 | 同格数 | sharpe 越线 | ann_return | max_drawdown | 结论 |
|---|---|---|---|---|---|
| A-vs-B：昨晚 CPU(p2 s4) vs **今晨同参 CPU 整波重跑**(055023 s4) | 4,158 | 1（0.024%） | 0 | 4（0.096%） | **纯 CPU 自己跨夜就不复现** ⇒ 存在与后端无关的噪声底 |
| B-vs-C：今晨 CPU(055023 s4) vs 今晨 **GPU**(053559 s4)（同日） | 1,790 | **0** | **0** | 1（0.056%，abs 2e-4） | 同日 CPU/GPU 差分 **≤** 上一行的噪声底 |
| 被测：昨晚 CPU vs 今晨 GPU（跨夜） | 16,626 | 32（0.192%） | 25（0.150%） | 41（0.247%） | 越线格宇宙分布=**zz500 57 处，hs300 0，all_a_ex_st 0**（三宇宙基数各≈5,500） |

**判读**：越线 100% 集中在单一宇宙（另两个宇宙严格 0），而同宇宙内的差分在"同日 CPU/GPU"下消失、
在"同日 CPU/CPU"下也几乎消失——这是 **zz500 成分/权重面在 23:37→05:36 之间被数据链改过**的签名
（成分快照=executor `_load_universe:260-266` → `_c4_engine.load_index_constituents("000905.SH")`，
`index_constituent` 真源），不是设备面把数算错了。top10×窄宇宙的格对成分变动最敏感，故差分能到
0.1 量级——属**离散选择对输入的本性**，与裁定②"边界效应是离散选择的本性，禁为过线去动卡"同理。

**本班自犯的方法学错**：把"同 seed 同参"当成"同输入"。**同 seed 只保证抽的是同一批格子，不保证
面板取值相同**——配对实验必须让两侧读同一数据态。故级 3 改法（正在跑，产物落
`data/strategy_intake/grid_20261011-06*`，两侧一律 `--exploration-ledger` 分册）：CPU 先跑、GPU 紧接跑，
单进程无并发，前后各取一次 hs300/zz500 成分集 sha1 指纹；**指纹不等则本配对自动作废**，不把漂移当差分。
探针与判读脚本（皆只读）：`n3_ladder3.py`／`n3_control_cpu_vs_cpu.py`／`n3_three_way.py`／`n3_ladder3_run.py`。

**顺带得到的两条硬结论**（不依赖级 3 结果）：
① CPU 回退路径**实证生效**：s0/s4 两路 GPU 波中途 MemoryError → 既有 L2-C fail-closed 整波重跑 CPU，
   零半成品混合后端出分，s4 重跑 4,166 格全数完成（1,639s，neg=8 与基线同量级）；
② 但那次重跑暴露本班缺陷 22 格（详见 01 件 §六 D-F：内存压力被记成 eval 阴性），已随袋两条腿修好。

## 八、级 3 第一轮为什么整轮作废，以及它意外量到的一条硬事实

**事故**：06:32 本班投的"GPU 臂"**一格都没上卡**。产物 `summary.eval_gpu` 十项全零、
`engine_degrade` 缺席，形态上完全兼容"跑完了，准入闸决定走 CPU"——**计量面对失败态是瞎的**。
真相在该轮 stderr：`[grid-instrument] fail-open eval_backend_resolve: ImportError: cannot import name
'nvml_device_memory' from 'zephyr.backtest.gpu_core' (**D:\ZephyrAlpha\src**\zephyr\backtest\gpu_core.py)`
共 1,050 行＝每格一次。根因=driver 起的子进程 **PYTHONPATH 未指车道**，`zephyr` 包解析到**主区旧字节**
（本机主区以包路径常驻，worktree 裸 `python` 默认导主区——在册旧教训"worktree 裸 python 导主区包=假绿"，
本班今天仍踩）。发现路径不是计量面而是**旁证异常**：该"GPU"臂稳态 eval_s 0.445 与 CPU 臂 0.452 几乎同速。

**三条已落地的修法**：①`_dev_xp` 两条静默出口各加计数器 `resolve_not_gpu`/`dev_attempt_failed`
（零计数今后必须能区分"没尝试/尝试失败/被预算拒"三态）；②试件
`test_device_attempt_failure_is_never_silent_in_counters`（四相钉，漏加计数即红）；
③driver 纪律：显式 `PYTHONPATH=src`＋跑前断言 `gpu_core.__file__` 落在车道＋**任何配对的两侧
都必须先出示 `eval_gpu.cell_gpu>0` 与 argv 一致**，否则不进容差判定。

**意外量到的硬事实（这条比事故更值钱）**：那两臂虽不是 CPU-vs-GPU，却是一组**同日同数据态的
CPU-vs-CPU 配对**（前后成分面 sha1 逐字相同）。其全精度 net 面读数：

| 对照 | 同格 | 整列逐位等 | 超册上 FP64 日线（逐日相对差 >1e-8） | 最大绝对差 |
|---|---|---|---|---|
| CPU₁(062219) vs CPU₂(063203) | 1,049 | **0 格（0.0%）** | **17 格（1.62%）** | 6.19e-4 |
| CPU₁ vs GPU 真臂(064740) | 1,049 | 0 格 | 26 格（2.48%） | 1.38e-3 |

⇒ **本引擎对自己都不逐位复现**：同数据态、同后端、同参数、同日两跑，1,049 列净值里**没有一列逐位相同**，
并且 1.62% 的列违反册上 FP64"逐日 ≤1e-8"这条线。设备面在同样判据下是 2.48%，净增 ≈0.86pp（≈9 格），
形态同族（差异集中在 1–4 个调仓日的持仓翻转，聚合五项指标全部线内）。
⇒ 两条结论：①Owner 裁定②"禁追求 bitwise"在此有了**实测根据**，不再是偏好；
②册上那条 1e-8 日线**作为 GPU 等价性判据已不可用**（引擎自身就过不了），
   要它有意义必须先重定为"设备差分 ≤ CPU 自对照底 × 同量级"或按实测底调线——**这是改判据面，本班不自裁**，
   已登记 §四 追加项 ⑤ 待 Owner/裁定通道。
待补的一针（不在本袋）：这 1.62% 的自身不可复现**归因未定**——候选=CH 查询无 ORDER BY 的行序→列序→并列序，
与 BLAS 线程数相关的归约序。判据=同进程内同一格跑两次比 net（排除跨跑数据面），若同进程内仍差 ⇒ 归约序；
若同进程内逐位等 ⇒ 跨跑数据/行序面。
