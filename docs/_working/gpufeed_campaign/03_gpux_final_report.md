# 终报（st-gpux-20261011，工单「引擎 GPU 化工单」）

## 〇、一句话与大白话

**一句话**：eval 面确实搬上了卡并且数值可证等价（单进程 eval 3.55x、199 格排名 Spearman ρ=1.0），
但工单两条验收线——**探索吞吐 ≥3x 与 GPU 持续利用率 ≥70%——今晚实测未达标**（6 路并发聚合折算约
1.1x，本进程归因 SM 均值 3.5%），根因不是"没搬上去"，而是**"每格一 kernel"这种搬法在并发下喂不饱卡**；
设备已按缺省关（`--eval-backend cpu`）入库，不会有人误吃这条路径。

**大白话**（给 Owner，不带行话）：
- 我们原来想的是"这台电脑的显卡在闲着，把算得的活分给它就快了"。今晚把最重的那块活（给股票打分排序）
  真的搬上显卡了，一个人干的时候确实快了 2-3 倍。
- 但**同时开 6 个工人去用同一张卡**时，每个人都要排队等卡，而且每人给卡开的"工位"（CUDA 上下文）
  光占地方就吃掉 12GB/24GB 显存——结果 6 个人加起来反而比原来在 CPU 上慢。
- 打个比方：不是"厨房没灶"，是**每人只做一道菜就喊一次灶**，灶火 90% 时间在等；要达标必须
  "一次端 50 道菜进灶"（把共用同一批数据的许多格合并成一次批量计算），这是下一班要造的家伙，
  不是今晚再调调参数能出来的。
- 还有一件更要紧的事：原本用来判"卡有没有被喂饱"的那把尺（nvidia-smi 的利用率）**本身会被桌面图形
  污染**——我实测开着零计算时它也能显示 8-57%。要是直接拿它当验收尺，我可以很轻松地"做出"70% 的假绿。
  今晚把这把尺换成了"只认我们引擎自己那份占用"的版本，所以现在的 3.5% 是**真数**，不是没测到。

## 三、未达的原因分解与下一班入口（三清单之二：残余）

**为什么搬上卡却没到 3x（三条都有数）**：

1. **Amdahl 帽**：eval 只占格耗时 82%；单格剩余 CPU 侧（bt 0.107s + 五档成本门 + 编排 + 把设备结果
   物化回 pandas）构成地板。级 2 GPU 的 hit 格 tot=0.184s 里 eval 只占 0.127s ⇒ 就算 eval 归零也只有 ~1.8x。
2. **并发争用**：6 分片把 hit 格单格耗时从 0.184s 撑到 0.487s（2.6x），且 **6 个 CUDA 上下文常驻吃掉
   12,171MiB/24576MiB** 显存——这与 `search_space_prereg.yaml:106 vram.concurrency: 1`（"单卡禁共存"）
   的在册口径正面冲突，也在挤压本地 LLM 预算。
3. **"每格一 kernel"喂不饱卡**：单格设备时长 ~0.02-0.05s，中间全是 CPU 空隙 ⇒ 归因 SM 只有 3.5%。
   这正是 `00_gpufeed_report.md §五 T2-D`（多 worker 喂单 GPU 流/异步流水线）与
   `p1_wiring_benchmark.md §五` 当年立为候补、至今未造的那件家伙。

- **实测瓶颈分解**（同日同在窗 i<1700，六路并发）：CPU tot 0.604s/格 = eval 0.495 + bt 0.102 + 其余 0.007；

  不是算子本身（归因 SM 仅 1–7% 同证：卡几乎全程空转）。

四对跨形态的 max_abs 全部落在两对同形态底（1.6653e-16／1.9429e-16）的**同一量级**内（≤ 4.4e-16），
且三档越线**六对全 0** ⇒ 跨形态差与"同形态换个进程"的差不可区分＝**刀二在全格集上零新增分歧**。


**读数**：隔离形态下 `isoR0（刀二关）↔isoR1（刀二开）`＝**共有 1,049 格、逐位等 1,014 格、
三档（1e-8／1e-6／1e-4）越线各 0 格、max_abs=2.498002e-16**，`degraded=0`、`engine_degrade=null`、
`rets_hit=1047／rets_put=3`（缓存确实吃了 1,047 格）。
⇒ **十六·B 那 4 格越线确属 R1 臂位离群，不是刀二**：跨进程干净态下刀二开与关在 1,049 格上
一格都不越线，最大差是 1 ULP 级末位（35 格有差全带内），与在册"GPU 面跨进程换末位"同族。

**同形态底的量级本身也是一条读数**：跨进程"同码同开关两跑"在 1,049 格上是 35 格有末位差、
max_abs 1.7–1.9e-16、三档越线 0——这与 §十一·B 的 CPU 面 `p₀≡0` **不是同一件事**
（在册限定词：`p₀≡0` 只属同进程 CPU 两跑，不得外推到设备面），
也与 §十三·C① 那句"GPU 设备臂逐位不可复现"逐字相容；本节的贡献是把它**在全格集尺度钉了数**。

**臂位离群与形态无关的证据链闭合**：同进程针里凡含 R1 的对照（R0↔R1、R1↔R1b、A↔R1）报同一组 4 格、
同一 max_abs 7.690378e-02，而 R0↔R1b（同为该进程内的两个非首位臂）差 3.05e-16；
换到独立进程后这 4 格**全部消失**（六对越线全 0）。
⇒ 那 4 格＝**同进程内 R1 那一臂位的产物**（其族签名 `A1=raw × A2=ic_ir × G=hs300` 落在 eval 侧前缀／
`_dev_fwd_ranked` 的 id 键面上，见 §十四·E），与 bt 侧的刀二无因果。

#### 十三·验·七、归因改靶（本班最硬的一条读数：all_a 设备 bt 核的主成本不是 B2 砍掉的那 30ms）

`b2_ffill_attribution.json`（同一形状 970×5,217，每核同步，**两序交错**各测一遍，只报同针比值）：

| 帧形态 | tensor_core 设备入参 | tensor_core 主机入参 | 其中 `_ffill_axis0(px)` 段 |
|---|---|---|---|
| N0＝无 NaN（`mask.any()` 短路） | **2.72 / 2.54 ms** | 19.10 / 15.00 ms | 0.14 / 0.13 ms |
| N1＝含 NaN（3%） | **131.85 / 125.19 ms** | 163.44 / 142.82 ms | 63.06 / 78.15 ms |

**N1/N0 = 48.5x**。机制：`gpu_core._ffill_axis0` 在含 NaN 帧上走在册处方
`asnumpy → numpy.maximum.accumulate(axis=0) → asarray`（cupy 缺该原语），
代价＝(T,S) int64≈40MB 的双向跨边界＋主机列向跨步累计，**与 NaN 密度无关，只要有一个 NaN 就整段发生**。
生产面两帧都必然含 NaN：px 有停牌/未上市 NaN，权重帧未选中位是 NaN（`base=where(mask,1.0,nan)`）。

对照在册：§十一·F⑥ 那句"ffill 0.24ms、两张稠密 f64 的 H2D 占设备 bt 核 63%"是在**无 NaN 合成帧**上量的
（同一短路），而 §十一·F④ 在真批上量到 all_a GPU bt **211.8ms/格**——本针把这两个数接上了：
173.8（本班 seam 针）/131.9（本针）＝同一主体，且 89% 落在两次 ffill 往返（`hidden_roundtrip_share=0.889`）。

⇒ **下一步的正解不是继续消往返，而是把行号 running-max 放上卡**（整数累计，天然逐位确定、无浮点结合序问题）
 ＋把 px 的 rets 面批级共享（同窗同宇宙算一次，`rets_from_close_panel` 本班存证件里已抽好唯一实现位）。
 按本针量级：all_a bt 腿 131.9→约 5–10ms/格 量级，才是把 1.7x 推到 ≥3x 的那把刀；
 B2 今晚消掉的 30ms 在其中是零头。
