CPU、内存、GC、goroutine 数量   - 查询速率、磁盘 IO   - 连接数、运行时间  业务指标（ClickHouse）：   - 下单延迟三段拆分   - 订单成功率、失败原因分布   - 每窗口 P&L   - 信号置信度分布  Grafana：   - Prometheus 数据源 → 系统面板   - ClickHouse 数据源 → 业务面板 ```  ### 2.3 网络层内置统计  - UDP 路由内置丢包计数器 - WebSocket 重连次数、重连间隔分布  ---  ## 三、ZephyrAlpha 待定义的内容  当一个模块（无论是 l00 的数据接入、l06 的交易执行，还是其他）开始进入生产运行状态时，需要为它定义以下打点标准：  ### 3.1 每个模块 MUST 暴露的指标  | 指标类别 | 具体指标 | 类型 | 说明 | |---------|---------|------|------| | 吞吐量 | `requests_total` | Counter | 总处理请求数 | | 延迟 | `latency_seconds` | Histogram | p50/p90/p99 | | 错误 | `errors_total` | Counter | 按错误类型分 label | | 成功率 | 推导自 requests/errors | — | Grafana 侧计算 |  ### 3.2 延迟打点阶段拆分（按模块定制）  | 层 | 建议的打点阶段 | |----|--------------| | L00 数据接入 | WS recv → parse → quality_gate → emit | | L02 因子计算 | receive → compute → normalize → emit | | L03 信号合成 | receive → combine → threshold → emit | | L06 交易执行 | build → sign → post（直接对标对手） | | L07 TCA 分析 | receive → attribution → report |  每一段的命名建议遵循 `<action>_duration_seconds` 的 Prometheus 命名约定。  ### 3.3 日志格式  ```python # 建议的结构化日志格式 {     "timestamp": "2026-01-01T00:00:00.000000Z",     "layer": "ex_core",     "module": "order_manager",     "level": "INFO",     "event": "order_submitted",     "order_id": "uuid-xxx",     "latency_stage": "build",     "latency_ns": 123456,     "trace_id": "uuid-yyy" } ```  ### 3.4 健康检查端点  每个模块 MUST 暴露 `GET /health`，返回： ```json {"status": "ok", "uptime_seconds": 123456} ```  ---  ## 四、与 ZephyrAlpha 现有基础设施的关系  | 现有资产 | 如何利用 | |---------|---------| | infra_ops | 此层目前是空壳，可观测性契约落地后应归属此层 | | tenacity (技术雷达 Adopt) | 重试逻辑已有标准库，错误计数器可直接联动 | | pybreaker (技术雷达 Trial) | 熔断器状态变化必须打点（状态转换事件） | | Prometheus (技术雷达 Trial) | /metrics 端点只需要 `prometheus_client` 库 | | Grafana (技术雷达 Adopt) | Dashboard JSON 可由 AI 生成 |  ---  ## 五、推荐的实施时机  | 触发条件 | 做什么 | |---------|--------| | 第一条 l00→l02 数据管道跑通 | 为 L00 + L02 定义打点阶段 + 实现 /metrics 端点 | | 第一条限价单被提交 | 为 L06 实现 build/sign/post 三段打点 | | 第一个模块稳定运行 >24h | 搭建 Grafana Dashboard（AI 生成 JSON） | | 出现第一次"不知道哪里慢了"的困惑 | 补充各模块的打点阶段拆分 | | 准备给别人看系统运行状态 | 统一日志格式 + trace_id 贯通全链路 |  ---  ## 六、结论  > **不定义不会爆炸。定义了以后省事。这是一个"记住要做"的东西，不是"现在必须做"的东西。**
