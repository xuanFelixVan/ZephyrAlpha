# 依赖图深挖审查方案 v2.0

## 目标
从任意文档（想法.md/聊天记录.md/草稿.md等）中，**1-2轮**推导出依赖图缺少的全部子模块，避免反复造轮子。深挖产出的所有内容最终**写入能力定位书**，写入时必须经过准入判断、格式适配和级联更新三步协议，确保能力定位书作为唯一真理无前后矛盾。

---

## 核心方法论：11维全息审查法

每一句话，同时用以下11个维度审查，而不是每轮只用1-2个维度：

### 维度1：功能分解（R1主力维度）
- **问**：这段话提到或暗示了什么功能模块？
- **例**："VaR三种方法并发"→ VaR并发计算编排器

### 维度2：实现细节（R2主力维度）
- **问**：具体怎么实现？用什么算法/数据结构/计算流程？
- **例**："Cholesky分解50×50协方差矩阵"→ 协方差矩阵分解器

### 维度3：技术选型（R3主力维度）
- **问**：用什么库/框架/工具？需要集成什么？
- **例**："empyrical最轻量"→ empyrical集成器

### 维度4：错误处理与边界条件（R4主力维度）
- **问**：出错怎么办？超时多少？降级策略？Fail-Closed/Fail-Open？
- **例**："检查超时=拒绝"→ Fail-Closed降级处理器

### 维度5：契约生产/消费（R5主力维度）
- **问**：谁生产什么契约(CTR-xxx)？谁消费什么契约？契约格式？
- **例**："产出CTR-003 RiskLimits"→ CTR-003 RiskLimits生产者

### 维度6：DDD建模（R5主力维度）
- **问**：聚合根(AGG-xxx)是谁？实体(ENT-xxx)是谁？值对象？聚合根边界？
- **例**："AGG-007 RiskPolicy + ENT-005 RiskLimit"→ DDD聚合根管理器

### 维度7：跨域交互（R4/R5维度）
- **问**：跨域事件(E-xxx)有哪些？谁发布谁消费？时序保证？
- **例**："风控熔断E-RK-01→信号撤销E-SG-02"→ 风控-信号交互时序管理器

### 维度8：配置与可运维性（R3/R4维度）
- **问**：什么需要可配置？阈值？策略？YAML/DSL？热更新？
- **例**："规则从硬编码→YAML可配置"→ 风控规则YAML运行时加载器

### 维度9：监控可观测性（R4维度）
- **问**：SLA多少？健康检查？指标采集？TraceContext？审计追踪？
- **例**："超时阈值50ms(CTR-003 SLA)"→ Pre-Trade 50ms SLA监控器

### 维度10：迁移与进化（R6维度）
- **问**：从现有代码/架构怎么迁移到目标？迁移策略？回退？
- **例**："IV参数法→历史模拟法"→ IV参数法VaR→历史模拟法迁移器

### 维度11：运维与数据管理（R7维度）
- **问**：备份策略？数据隔离？WAL？缓存？分区？冷热分层？
- **例**："治理数据实时备份，行情数据批量归档"→ 差异化备份策略管理器

## 执行流程（两轮制）

### 第一轮：11维全息审查（产出90%+子模块）

```
对文档的每一句话：
  1. 读取当前句
  2. 同时用11个维度审查，列出所有可推导的子模块
  3. 去重检查：该子模块是否已在依赖图中？
  4. 在原文后添加审查备注（含推导出的子模块清单）
  5. 将新子模块暂存到"本轮新增清单"
  6. 进入下一句

全部句子审查完毕后：
  7. 将"本轮新增清单"批量加入依赖图对应域文件
  8. ★ 对每项新增内容执行入书协议（见下文§入书协议）
```

### 第二轮：查漏补缺（产出剩余10%子模块）

```
1. 重新通读全文，只关注"审查备注"覆盖不到的原始文本
2. 重点检查：
   - 表格中的隐含需求（阈值、格式、枚举值）
   - 代码块中的隐含需求（类名、方法名、字段名）
   - 对比表中的隐含需求（"现有vs目标"差距）
   - 技术选型中的隐含需求（具体库名、版本、API）
3. 补充遗漏的子模块
4. 批量加入依赖图
5. ★ 对每项新增内容执行入书协议
```

## 审查备注格式

每段话后的审查备注统一格式：

```html
<!-- 审查记录：已审查，推导出N个缺失子模块：①D-XXX:子模块名(简要说明) ②D-XXX:子模块名(简要说明) ... 其中D-XXX-YY已有不重复加入。已无法推导更多子模块 -->
```

关键要素：
- **推导出多少个**：明确数量
- **每个子模块的域归属和名称**：D-XXX:英文名
- **简要说明**：一句话说清这个子模块干什么
- **去重说明**：哪些已有不重复加入
- **完工标记**："已无法推导更多子模块"

---

## 去重检查方法

推导出新子模块时，必须检查：

1. **同域同功能**：D-RISK已有"VaR并发计算编排器"，不再加"VaR并行调度器"
2. **跨域同功能**：D-AUTONOMY已有"Kill Switch"，D-RISK不再重复加
3. **粒度差异**：如果已有大粒度模块覆盖了小粒度功能，不加小粒度
4. **编号连续**：从各域当前最后编号+1开始

## 入书协议：深挖产出→能力定位书的三步写入流程

> **核心原则**：能力定位书是系统设计的唯一真理。深挖产出的任何内容写入能力定位书之前，必须经过"准入判断→格式适配→级联更新"三步，确保写入后全书无矛盾、无遗漏、无冗余。

### 第一步：准入判断（该不该加？已有没有？冲突怎么办？）

深挖产出的每项内容，先回答三个问题：

**问题1：这项内容属于能力定位书的哪个/哪些章节？**

11个维度产出的内容类型不同，对应能力定位书的不同章节。先定位章节，再判断准入：

| 深挖维度 | 产出类型 | 主要写入章节 | 辅助写入章节 |
|---|---|---|---|
| 维度1 功能分解 | 新功能模块/能力 | §5能力清单 | §4能力全景图、§9域映射矩阵 |
| 维度2 实现细节 | 算法/数据结构/计算流程 | §5能力清单（实现描述） | §6质量边界 |
| 维度3 技术选型 | 库/框架/工具/集成 | §2架构决策、§8外部系统关系 | §5能力清单（非功能约束） |
| 维度4 错误处理 | 降级/超时/边界条件/Fail策略 | §6质量边界（§6.1-§6.4边界规则） | §5能力清单（成功标准/非功能约束） |
| 维度5 契约生产/消费 | 契约定义(CTR-xxx) | §5能力清单（依赖能力） | §9域映射矩阵 |
| 维度6 DDD建模 | 聚合根/实体/值对象 | §4能力全景图 | §9域映射矩阵 |
| 维度7 跨域交互 | 跨域事件/时序/发布订阅 | §9域映射矩阵 | §5能力清单（依赖能力） |
| 维度8 配置与可运维 | 可配置项/阈值/YAML/热更新 | §6质量边界 | §2架构决策 |
| 维度9 监控可观测性 | SLA/指标/健康检查/审计 | §6质量边界（§6.7质量属性） | §5能力清单（成功标准） |
| 维度10 迁移与进化 | 迁移策略/回退方案 | §5能力清单 | §14缺失分析 |
| 维度11 运维与数据管理 | 备份/隔离/缓存/冷热分层 | §2硬件约束 | §6质量边界 |

**问题2：目标章节中是否已存在同类内容？——三态判断**

| 状态 | 判断标准 | 处理方式 |
|---|---|---|
| ✅ **已存在且一致** | 目标章节已有相同或等价内容，语义不冲突 | 不加入，审查备注标记"已有不重复加入" |
| ⚠️ **已存在但矛盾** | 目标章节已有相关内容，但数值/定义/描述与新产出冲突 | 不盲目加入，标记"⚠️冲突待裁定"，列出旧值vs新值，由人工裁定 |
| 🆕 **不存在** | 目标章节无同类内容 | 进入第二步格式适配后加入 |

**矛盾裁定的四种典型场景**：

| 矛盾类型 | 示例 | 裁定原则 |
|---|---|---|
| 数值矛盾 | 旧版"月停机<20分钟"vs新版"月停机<50秒" | 以数学推导/行业标准为准，记录修正原因 |
| 术语矛盾 | "容量管理"vs"资源管理" | 以更精确的术语为准，消除歧义 |
| 范围矛盾 | 旧版"60±15"vs新版"60" | 以更无歧义的表述为准，消除误导性区间 |
| 归属矛盾 | 同一功能在两个域出现 | 以核心支撑域(●)为准，另一域降级为辅助(◐)或间接(○) |

**问题3：如果准入通过，编号怎么分配？**

- 新增能力：C-xxx编号从§5能力清单当前最大编号+1开始
- 新增边界规则：B-xxx编号从§6当前最大编号+1开始
- 新增假设：A-xxx编号从§11当前最大编号+1开始
- 新增术语：按术语表分类（量化交易/架构设计/A股市场）追加
- 新增子模块：D-XXX-YY编号从对应域当前最大编号+1开始

### 第二步：格式适配（按目标章节的格式规范写入）

每项新增内容必须严格遵循目标章节的既有格式。以下是各章节的格式规范：

| 章节 | 格式规范 | 关键字段 |
|---|---|---|
| §5能力清单-总揽表 | 表格行：编号/能力名/P级/类型/一句话 | 类型枚举：基础设施/工厂/自治能力/博弈能力/博弈智能/风控增强/执行质量/扩展能力/运维能力 |
| §5能力清单-详细卡片 | 表格行：能力描述/用户角色/典型场景/成功标准/非功能约束/对应域/依赖能力 | 依赖标注：✅硬依赖/🛡️控制依赖/📐接口级依赖/脚注补充 |
| §4能力全景图 | 分层架构图(L0-L4)+Mermaid血缘图 | 层级归属+P级标注+数据流方向 |
| §9域映射矩阵 | §9.1能力→域表(核心●/辅助◐/间接○)+§9.2域→能力表+§9.3域统计+§9.4观察 | 三级支撑强度标记 |
| §6质量边界 | §6.1-§6.4表格：编号/禁止事项/理由/执行机制；§6.5：编号/不做的事/理由/替代方案 | 边界规则必须有执行机制 |
| §2架构决策 | 约束表格+约束说明 | 硬约束vs架构决策的层级区分 |
| §10术语表 | 表格行：术语/全称/含义 | 歧义消解规则必须补充 |
| §11假设清单 | 表格行：编号/假设/影响范围/打破信号/应对策略 | 影响范围必须列出具体C-xxx编号 |
| §12成功指标 | 三档制(🟢生存/🟡健康/🔴卓越)+失败指标 | 每项指标必须有衡量方式 |
| §13优先级排序 | P0按批次/P1按轮次/P2按触发条件 | 依赖链+降级说明 |
| §14缺失分析 | 表格行：#/严重度/缺失项/归属层级/已补充位置/行业参考/参考技术选型 | 严重度枚举：🔴严重/🟧重要/🟡建议 |

**格式适配检查清单**（写入前逐项确认）：

- [ ] 新增内容的字段是否与目标章节表格列完全对齐？
- [ ] 编号是否连续且无冲突？
- [ ] P级/类型枚举值是否在合法范围内？
- [ ] 依赖关系标注是否使用了正确的符号(✅/🛡️/📐)？
- [ ] 域映射是否使用了正确的强度标记(●/◐/○)？
- [ ] 新增术语是否需要补充歧义消解规则？

### 第三步：级联更新（写入后全面检查，消除前后矛盾）

> **这是入书协议最关键的一步**。能力定位书是一个高度关联的整体——一个地方改了，可能牵连多个章节。只加不管=埋雷。

**级联更新规则**：任何章节的变更，必须按以下清单逐一检查所有可能受影响的章节。

#### 级联更新检查矩阵

| 触发变更 | 必须级联检查的章节 | 检查内容 | 检查方式 |
|---|---|---|---|
| §5能力清单新增/修改能力 | §4能力全景图 | 全景图中是否体现？五象限归属是否正确？层级(L0-L4)是否正确？ | 搜索能力名，确认出现在正确层级 |
| §5能力清单新增/修改能力 | §9.1能力→域映射 | 核心域(●)/辅助域(◐)/间接域(○)是否补全？ | 新增行或更新已有行，确认三级标记正确 |
| §5能力清单新增/修改能力 | §9.2域→能力映射 | 域行中是否包含该能力的标记？ | 在对应域行中添加●/◐/○标记 |
| §5能力清单新增/修改能力 | §9.3域统计 | 各域的●/◐/○计数是否正确？ | 重新统计受影响域的计数 |
| §5能力清单新增/修改能力 | §9.4架构观察 | 观察结论是否仍成立？ | 检查观察中引用的数值是否需要更新 |
| §5能力清单新增/修改能力 | §6质量边界 | 该能力的SLA/降级/边界条件是否定义？B-xxx是否需要新增？ | 确认能力有对应的边界规则或显式声明"无需边界" |
| §5能力清单新增/修改能力 | §12成功指标 | 是否需要新增衡量指标？三档值是否受影响？ | 检查新增能力是否引入新的衡量维度 |
| §5能力清单新增/修改能力 | §13优先级排序 | 优先级是否已分配？开发批次/轮次是否已安排？ | 确认能力出现在§13的某个批次/轮次中 |
| §5能力清单新增/修改能力 | §14缺失分析 | 缺失表中对应项是否可标记为已补？ | 搜索缺失项关键词，如匹配则更新"已补充位置"列 |
| §5能力清单修改依赖关系 | §4 Mermaid血缘图 | 箭头是否需要新增/删除？ | 检查新增依赖是否在图中有对应箭头 |
| §5能力清单修改依赖关系 | §9.1/§9.2映射矩阵 | 辅助域/间接域是否需要因依赖传递而更新？ | 依赖新增→检查是否引入新的域触达 |
| §5能力清单修改P级 | §4全景图 | P级标注是否同步？ | 全景图中P级标签是否一致 |
| §5能力清单修改P级 | §13优先级排序 | 是否需要移动到不同批次/轮次？ | P级变更→开发排序必须同步调整 |
| §2架构决策变更 | §5能力清单 | 能力是否受影响？非功能约束是否需要更新？ | 搜索相关能力，确认约束引用 |
| §2硬件约束变更 | §6.7质量属性 | 性能预算是否需要重新计算？ | 检查数值推导链是否仍成立 |
| §6新增边界规则 | §5能力清单 | 执行机制引用的能力是否存在？成功标准是否有验证项？ | 确认B-xxx→C-xxx闭环 |
| §6新增边界规则 | §7角色与旅程 | 审批矩阵是否需要新增人工介入点？ | 检查边界规则是否引入新的人工审批需求 |
| §10术语变更/新增 | 全文 | 新术语是否在所有出现处一致使用？旧术语是否全部替换？ | 全文搜索旧术语，确认无残留 |
| §11假设变更 | 全文依赖此假设的能力 | 假设变更是否影响依赖此假设的能力的设计决策？ | 检查"影响范围"列中所有C-xxx的设计前提 |

#### 级联更新的执行流程

```
写入完成后：
  1. 识别变更类型（新增能力/修改能力/修改约束/修改术语/修改假设）
  2. 从级联更新检查矩阵中取出对应的检查清单
  3. 逐一检查每个受影响章节
  4. 发现不一致→立即修复→记录修复项
  5. 修复后重新检查是否引入新的级联影响
  6. 全部检查通过→标记"级联更新完成"

级联更新完成标准：
  - 所有检查矩阵中的受影响章节均已检查
  - 无未解决的⚠️冲突标记
  - 数值引用链无断裂（如§2预算→§5成功标准→§12指标→§6.7质量属性）
  - 术语全文一致（无旧术语残留）
  - 域映射三方一致（§9.1/§9.2/§9.3数值吻合）
```

#### 级联更新中的冲突处理

级联更新过程中发现冲突时，按以下优先级处理：

| 优先级 | 冲突类型 | 处理方式 | 示例 |
|---|---|---|---|
| 🔴 P0 | 数值矛盾（同一指标在不同章节出现不同数值） | 立即裁定，以更权威的来源为准（§5详细卡片>总揽表>全景图） | §12 uptime 99.9%但§6.7写99%→以§5 C-008卡片99.9%为准 |
| 🔴 P0 | 依赖矛盾（§5卡片依赖列表vs§9映射矩阵不一致） | 以§5详细卡片为权威来源，同步更新矩阵 | C-013依赖列表有C-004但矩阵缺→补矩阵 |
| 🟧 P1 | 术语不一致（同一概念在不同章节使用不同术语） | 统一为更精确的术语，旧术语全文替换 | "容量管理"→"资源管理"（C-006⑩） |

## 质量保障

### 为什么11维全息审查能1-2轮到位？

| 传统方式（1-2维/轮） | 全息方式（11维/轮） |
|---|---|
| R1只看功能→遗漏实现细节 | 一句话同时看功能+实现+技术+错误+契约+DDD+跨域+配置+监控+迁移+运维 |
| 需要7轮才能覆盖全部维度 | 1轮覆盖全部维度 |
| 每轮遗漏60-80%的子模块 | 每轮遗漏<10%的子模块 |
| 总耗时7轮 | 总耗时1-2轮 |

### 边界条件

- 如果文档超过500行，分批审查（每批100行），但每批内部仍用11维全息审查
- 如果推导出的子模块数/原文行数 < 0.05，说明该段已穷尽，快速跳过
- 第二轮如果新增<5个子模块，确认穷尽，停止
