# 价值提取协议 (Value Extraction Protocol)

> **核心理念**：git history 就是归档。不需要"搬文件"式的物理归档。
> 退役文件的唯一合法处置路径是：**提取知识 → 删除原件**。
>
> 对标来源：Citadel 六步失败分析法 / Two Sigma Model Lifecycle / 企业知识管理 "Keep what is required, dispose the rest" 原则

---

## 一、为什么废弃"归档"范式

传统做法：`Active 文件 → 移入 06_ARCHIVE/ → 永久堆积`

问题：
- 归档区本身成为需要治理的系统（本仓库曾同时存在 4 个归档区）
- 每个归档文件 = 永久增加的搜索噪音 + AI 认知负担
- "归档"让删除决策无限延后（"先放这里以后再说"）
- git history 已完整保留所有变更记录，物理副本完全冗余

**新范式**：退役 = 提取 + 删除。归档区不是退役目的地，是等待处置的中转站。

---

## 二、三问决策树（每个文件 ≤3 分钟判定）

```
Q1: 这个文件是否包含原创的设计决策、技术洞察、或失败教训？
│
├── 否 → 直接删除（git history 已保留，零损失）
│
└── 是 → Q2: 这个知识是否已被其他活跃文件覆盖？
           │
           ├── 是 → 直接删除
           │
           └── 否 → Q3: 这个知识能否浓缩为 <30 行的知识条目？
                      │
                      ├── 是 → 提取到知识库对应桶 → 删除原件
                      │
                      └── 否（极少数）→ 保留原件（记录保留理由）
```

**关键原则**：过程文档（迭代报告、审计快照、补充轮次文档）几乎永远是 Q1=否，直接删除。

## 三、知识提取目标位置（五个桶）

| 桶编号 | 路径 | 存放内容 | 典型来源 |
|--------|------|---------|---------|
| B1 | `docs/02_ARCHITECTURE/TECH_DECISION_RECORDS.md` | "为什么选 A 不选 B" 类技术决策 | 被替代的蓝图、失败的方案 |
| B2 | `docs/08_KNOWLEDGE/BEST_PRACTICES/` | 可复用的技术方法论、模式 | 有效实践的总结 |
| B3 | `docs/01_GOVERNANCE/REGISTERS/lessons-learned-register.md` | "别这么做" 类失败教训 | 错误操作、架构陷阱 |
| B4 | `docs/08_KNOWLEDGE/FACTOR_LIBRARY/` 或 `STRATEGY_LIBRARY/` | 可复用的因子公式/策略模式 | 退役蓝图的核心算法 |
| B5 | `docs/08_KNOWLEDGE/` 术语/概念 | 新定义的领域术语 | 任何引入新概念的文件 |

## 四、知识条目标准格式

每条提取的知识必须包含以下字段（写入对应文件的表格行或列表项）：

```markdown
### KE-{序号}：{简短标题}

- **来源文件**：`{原始文件路径}`
- **提取日期**：{YYYY-MM-DD}
- **分类**：ADR / BEST_PRACTICE / LESSON / FACTOR / STRATEGY
- **摘要**：{1-3 句话，说明核心知识点}
- **详情**：{可选，技术细节}
- **提交留痕**：`salvaged: KE-{序号}` 写入 commit message
```

## 五、批量处置分类标准

处置大量文件时，按以下类型快速分类：

| 文件类型 | 典型特征 | 处置 |
|---------|---------|------|
| 自动生成的审计快照 | module_id 含 AUTO_、owner 是 System_Guardian | **直接删除** |
| 迭代过程文档 | 文件名含 `第N轮`、`round-N`、`supplementary` | **直接删除** |
| 空壳指针文件 | 内容只有 YAML + canonical 指向，无正文 | **直接删除** |
| 运维中间产物 | `.json` 格式的审计快照、check_report | **直接删除** |
| 带 overlap- 前缀的副本 | 去重操作产生的副本标记 | **直接删除** |
| 带时间戳的 stub 目录 | `_ARCHIVED_20260413_` 格式目录 | **整体删除** |
| 编码损坏文件 | 含阿拉伯文乱码、目录名乱码 | **直接删除**（内容已不可用）|
| 有实质内容的退役蓝图 | 正文 >500 字，有原创设计决策 | **提取后删除** |

## 六、Citadel 六步萃取法（用于有价值的退役文件）

当 Q3 判断需要提取时，用以下六步确保知识完整提取：

1. **原始意图**：这个文件/项目最初要解决什么问题？
2. **实际结果**：它实际做到了什么？
3. **因果分析**：为什么成功/失败？
4. **替代反思**：如果重来，会怎么做？
5. **浓缩教训**：用 1-3 句话描述可操作的知识点
6. **写入对应桶**：按五桶分类写入，附来源文件链接

## 七、禁止行为

- **禁止**将文件从 `Active 区` 移入 `06_ARCHIVE/` 作为最终处置（06_ARCHIVE 是等待清空的遗留区）
- **禁止**创建新的归档目录（`docs/XX_ARCHIVE/` 格式）
- **禁止**以"保险起见"为由保留无价值文件（git history 就是保险）
- **禁止**在 `docs/09_AUDIT/STATE/` 中创建一次性审计快照后不设过期标记

---

## 八、06_ARCHIVE 的最终命运

`docs/06_ARCHIVE/` 是历史遗留的中转站，其清空目标是：

1. 逐步提取其中有价值内容（按本协议）
2. 有价值内容提取完毕后，**删除 06_ARCHIVE/ 整个目录**
3. 完成后更新 `docs/subsystem-registry.yaml` 移除此条目

预计完成时间：Phase D（当前 Phase 2 施工阶段不强制，但每次 session 应处置至少 10 个文件）
