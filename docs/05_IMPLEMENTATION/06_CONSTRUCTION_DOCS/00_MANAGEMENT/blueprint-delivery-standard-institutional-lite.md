# 蓝图交付标准 — 机构精华版（本仓库目标态）

> **用途**：把「专业机构常见的蓝图/设计包交付」压缩成**本仓库可勾选、可对照门禁**的目标态；不要求外部审计签字，但**验收口径与机构习惯同构**。
> **架构总览**：全库文档分层（L0～L5）与控制流见 文档治理架构。
> **执行顺序**：先读本节「四根支柱」→ **若目标含整仓资产**：读 §1.5 与 任务清单「全仓库分层治理」→ 打开 施工门禁 §0～§3 → 用 终稿定义 + 阶段任务清单 逐项落实。

## 1. 与机构交付对齐的四根支柱

| 支柱 | 机构常见含义 | 在本仓库中的验收抓手 |
|------|----------------|----------------------|
| **A. 基线（Baseline）** | 经批准的、用于施工的设计版本，可指认日期/版本 | 终稿定义 第 2～3 节；Owner 自检并在任务清单或登记表记日期 |
| **B. 范围与映射（Scope & mapping）** | 「应有设计」与「正式稿路径」一一对应，无歧义 | 任务清单 任务 1；唯一总清单（如 蓝图阶段完整总结） |
| **C. 可追溯（Traceability）** | 接口与重大设计决策可链到契约/TDR，施工前可核对 | 施工门禁 §0.3 第 4 条；`API_Contract.md`、`TECH_DECISION_RECORDS.md` |
| **D. 施工输入包（Implementation package）** | 从基线到编码的主路径、计划、方案、验收顺序 | 施工门禁 §0.3（第 2 阶段交付） |

## 1.5 全仓库分层治理（仓库根 `ZephyrAlpha/` · 与蓝图终稿并列）

> **定位**：Owner 要求「整仓分层管严、该有规矩的地方都有规矩、证据可追溯」时，**不**把「蓝图终稿」那一套（主要针对设计类文档与总清单）**原样套在每一种文件上**；而是按**资产类型**分层设验收口径——与专业机构 **CM / 文档控制 / 工程惯例** 的分工一致。
> **执行真源**：分阶段勾选见 阶段任务清单 **「全仓库分层治理（扩展轨）」**。

### 1.5.1 分层一览（R0～R4）

| 层级 | 大致范围 | 「治理清晰」在本仓库中的含义（摘要） | 典型证据（须可追溯） |
|------|-----------|--------------------------------------|----------------------|
| **R0 文档与设计** | `docs/` 下正文（含建设文档、审计、归档等子树） | 索引与磁盘一致、内链健康、同主题单一正式口径（副本已裁决或标注）、活跃稿无悬空置位 | 任务清单 1～6、L1 扫描报告路径、`CANONICAL_POINTERS`、卫生总案对照记录 |
| **R1 仓库配置与门面** | 仓库根目录的 `.gitignore`、`.gitattributes`、根 `README*`、`LICENSE*`、EditorConfig 等 | 不该进库的产物与密钥被规则挡住；门面文档能指到 canonical 入口 | `.gitignore` 与根 README 的维护记录；必要时安全扫描/密钥扫描报告路径 |
| **R2 脚本与自动化** | `scripts/` 及 CI/钩子脚本（若在仓内） | 关键脚本可复跑、与文档互指（或头注释说明用途）、大改后仍有执行记录 | commit 说明、任务清单勾选、相关 `09_AUDIT/STATE` 或 PR 记录 |
| **R3 源码与工程** | 业务代码目录（如 `src/`、`packages/` 等，以本仓实际为准） | 目录约定清晰、生成物不冒充手改源文、与契约/TDR 可追溯（与门禁 §0.3 衔接） | 工程 README/贡献约定、门禁与契约链接 |
| **R4 刻意排除层** | 依赖缓存、虚拟环境、`__pycache__`、构建产物等 | **不要求**逐文件登记；**要求**不得误提交、且与 R1 规则一致 | `.gitignore` / CI 拦截记录；**不**将本层纳入「总清单式枚举」 |

### 1.5.2 与「蓝图终稿」的边界（避免混为一谈）

- **蓝图终稿**（终稿定义）：约束 **蓝图类设计文档** 的质量、位置与唯一正式链接；**不等于**「仓库内每一个字节都是终稿」。
- **全仓库分层治理（本节）**：约束 **各层资产** 的最低规矩与证据链；**完成 R0～R4 勾选** 才可以说「按本仓库机构式分层，整仓治理目标闭环」，与「蓝图阶段任务 1～6 全勾」可**先后或交叉**推进，但**不得互相替代**。

### 1.5.3 「每个文件都清晰」在本标准中的精确含义

- **是**：在 **R0～R3** 范围内，每一类资产都有 **归属层级、验收要点、证据指到哪**；新增/搬迁时有 **可查记录**（任务清单、登记表、commit 等至少一种）。
- **否**：不要求对 **R4** 中第三方依赖与缓存文件做「文档式总清单」；专业机构同样用 **忽略规则 + 不提交** 处理。

**仓库根事故处置**（垃圾文件名、敏感配置误入库、运行时数据误入库、误放根下的正式稿归位）：见 仓库根治理 Playbook。

## 2. 三阶段门禁（目标态 = 各阶段放行条件满足）

与 施工门禁 **§0** 一致，不另起炉灶：

| 阶段 | 机构说法 | 本仓库达标判据（摘要） |
|------|----------|------------------------|
| **第 1 阶段** | 设计基线 / 蓝图批准 | §0.1 + §0.2 范围内**全部**满足终稿条件；详见门禁正文 |
| **第 2 阶段** | 施工就绪包 | §0.3 四项（流程、计划、方案、契约对齐）齐备且有索引入口 |
| **第 3 阶段** | 按图施工 | §3（及门禁 §2 基线复跑等）满足后方可大规模写代码 |

**「优化到本标准」**在操作上即：**第 1 阶段终稿闭环**（终稿定义 + 任务清单 + 卫生总案无硬性缺口）→ **第 2 阶段交付** → **第 3 阶段放行** 均可对照门禁勾选。

## 3. 办公室「蓝图交付侧」与全库审计（`09_AUDIT`）—— 专业机构怎么切、本仓库怎么做

### 3.1 两种「包含审计」不要混为一谈

| 说法 | 专业机构常见含义 | 本仓库对应 |
|------|------------------|------------|
| **A. 端到端闭环（推荐口径）** | 从蓝图交付到**可审计状态**：受控文档齐、证据链齐、链接与健康扫描可复跑，审计按方案来查时有东西可抽样 | **是**：办公室侧任务清单 + CANON 门禁 + 卫生总案对齐 + L1 + 重复/孤儿规则，就是在做 **audit readiness（审计就绪）**；与 全库治理文档导航 所链审计方案**衔接** |
| **B. 办公室目录吞并审计部全套** | 把审计计划、全阶段报告、`STATE` 台账等**全部**搬进 `00_MANAGEMENT` 当唯一工作区 | **否**：本仓库**有意**保持 `docs/09_AUDIT/` 为审计类正文与台账的**分区真源**；办公室只做**导航 + 与蓝图/施工强绑定的 CANON**，避免职责与链接体系搅在一起 |

**独立性提醒**：许多机构会区分 **document control / PMO**（管交付物与版本）与 **audit / QA**（按既定程序核查与出结论）。二者**流程上衔接**，但若由同一批人「自交付自审计」且无任何区分，在严格合规语境下会削弱**独立性**；个人仓库可弱化形式，但**概念上**仍建议：**交付侧产证据，审计侧（或同一 Owner 的「复查角色」）按方案核对**。

### 3.2 全库审计程序真源放哪、交付侧要做什么

- **审计方案与阶段**（例如全系统文档审计 A～H 等）：真源在 `docs/09_AUDIT/PROCEDURES/` 等；入口见 全库治理文档导航，例如 全系统文档审计方案。
- **交付侧必须做的**（使「审计」有物可查、而非空转）：完成本文 §4 自检与 任务清单；门禁与卫生总案无未关闭硬缺口；大改 docs 后保留 L1 扫描产物路径可追溯。
- **结论**：按专业机构习惯，**办公室蓝图交付侧应覆盖「与审计衔接的全流程责任」（就绪 + 证据 + 对照方案执行整改），但不等于把 `09_AUDIT` 整树合并进办公室。若你希望把「某审计阶段 ↔ 某门禁任务」做成一张对照表，可单开维护表（避免本文件过长）；需要时可加在 `00_MANAGEMENT` 或 `09_AUDIT/STATE`。

## 4. 精华版自检清单（合并视角）

以下为**合并视角**的一页纸；细项仍以 阶段任务清单 与 终稿定义 为准。任务 1：**链接核对默认为 Owner 要求的 100% 全量**（抽检仅书面豁免）；重复裁决同节。

- [ ] **总清单**：唯一总清单中，每个「应有蓝图」条目均有 canonical 链接；**全量**链接验证与重复裁决按任务 1 勾选（任务 1）
- [ ] **路径真源**：`06_CONSTRUCTION_DOCS` canonical 与遗留副本关系写明（任务 2）
- [ ] **图纸柜**：`01_BLUEPRINTS` 根目录符合 图纸柜规则（任务 3）
- [ ] **大门口**：`06_CONSTRUCTION_DOCS/INDEX.md` 与真实目录一致（任务 4）
- [ ] **活跃蓝图**：无未解释的占位（任务 5）
- [ ] **卫生/审计**：与 卫生总案 及台账对齐（任务 6）
- [ ] **单篇终稿**：§0.2 范围内每篇满足 终稿定义 第 1 节四条
- [ ] **施工包**：§0.3 与契约/TDR 可追溯（门禁）
- [x] **蓝图终稿验证任务**：执行7级29项验证任务（文件系统基线、目录架构、元数据完整性、全局索引闭环、架构边界、文档质量、施工准入最终校验），评分≥90分，符合施工准入标准（2026‑04‑12；验收证：蓝图终稿施工准入验收证）
- [ ] **链接健康**：大改 docs 后 rerun `python scripts/governance/sentinel_l1_governance_scan.py`（门禁 §2 相关习惯）
- [ ] **全仓库分层（扩展轨）**：任务清单 中 **W0～W4** 按 Owner 节奏勾选；与 §1.5 对照

## 5. 刻意不纳入本标准的内容（避免机构冗余）

以下**不**作为「达到本标准」的必要条件（个人项目可省略）：

- 外部第三方正式审计签字、多部门会签流程
- 重复的「第二套」总清单（与唯一总清单冲突时以总清单 + 登记表为准）
