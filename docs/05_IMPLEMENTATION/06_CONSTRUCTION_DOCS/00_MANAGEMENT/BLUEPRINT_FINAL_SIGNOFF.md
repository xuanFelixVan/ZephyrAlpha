# 蓝图终稿 — 定义与认可

> **用途**：回答两件事——**什么叫蓝图终稿**、**谁算认可**；与 [图纸柜摆放规则](./01_BLUEPRINTS_REPOSITORY_RULES.md)、[阶段任务清单](./BLUEPRINT_PHASE_CLOSURE_TASK_LIST.md) 一起使用。  
> **机构目标态（精华版）**：若要把全库优化到「机构级蓝图交付」口径，以 [蓝图交付标准（机构精华版）](./BLUEPRINT_DELIVERY_STANDARD_INSTITUTIONAL_LITE.md) 为**一页纸目标**；本文第 1～2 节为其子集定义。  
> **全库范围**：本文约束「蓝图类文档」的质量与状态；**全库唯一总清单**仍以 [蓝图阶段完整总结](../../../01_FRAMEWORK/BLUEPRINT_STAGE_COMPLETE_SUMMARY.md)（或后续指定的唯一总清单）为准。

---

## 1. 「单份蓝图」终稿须同时满足

1. **内容**：正文为模块/系统设计说明，**无**未解释的「待定 / 以后再说 / TBD」类占位（归档区、代码里状态名如 `DRAFT = "draft"` 除外，见任务清单说明）。  
2. **元信息**：文件头或文首具备可识别的 **版本号**、**负责人（Owner）**、**最近更新日期**（与仓库 front matter 或团队约定一致即可）。  
3. **位置**：若在 `01_BLUEPRINTS` 柜内，须符合 [图纸柜规则](./01_BLUEPRINTS_REPOSITORY_RULES.md)（根目录仅 `*BLUEPRINT.md` 与 `INDEX.md`；过程稿不在根目录）。  
4. **唯一性**：同一主题在全库只有 **一份**「正式稿」链接；若有副本，须在总清单或 [受控文档登记表](./CONTROLLED_DOCUMENTS_REGISTER.md) 中注明「只读副本 / 待废弃」。

满足以上四条，**单份蓝图**可记为 **终稿**。

---

## 2. 「全库蓝图阶段」终稿须同时满足

1. **总清单**：唯一总清单中，每个「应有蓝图」的条目均有对应正式链接，且抽检通过（见 [阶段任务清单](./BLUEPRINT_PHASE_CLOSURE_TASK_LIST.md) 之任务 1）。  
2. **路径真源**：canonical 路径与遗留副本关系已写明（见同清单之任务 2）。  
3. **图纸柜整洁**：过程报告已迁出根目录（见同清单之任务 3）。  
4. **大门索引**：`06_CONSTRUCTION_DOCS/INDEX.md` 与子目录一致（见同清单之任务 4）。  
5. **卫生对齐**：与 [蓝图阶段文档卫生总计划](./CANON/BLUEPRINT_PHASE_DOCUMENT_HYGIENE_MASTER_PLAN_20260408.md) 无未关闭的硬性缺口（或已备注例外）。

以上全部达成且 [阶段任务清单](./BLUEPRINT_PHASE_CLOSURE_TASK_LIST.md) 中相关项已勾选，可记为 **全库蓝图阶段终稿闭环**。

---

## 3. 谁算「认可」

| 场景 | 认可方式 |
|------|----------|
| 个人项目 + AI 协作 | **Owner（本人）** 对照第 1、2 节自检，并在任务清单或登记表中记录日期。 |
| 多人团队 | 由 **文档负责人 / 技术负责人** 书面确认（可为 PR 批准、会议纪要一句、或登记表签字栏）。 |

**不要求**外部审计签字；若日后引入，在本表下增一行即可。

---

## 4. 终稿之后若要修改（变更原则）

1. **小改**（措辞、笔误、链接）：更新文件内版本或 `last_updated`，必要时 rerun `python scripts/generate_01_blueprints_index.py`。  
2. **实质改设计**（范围、接口、职责变更）：升级版本号（如 minor/major），并在总清单或登记表备注「变更摘要 + 日期」。  
3. **废弃 / 合并**：旧文件标为归档或删除前，**先**更新总清单与登记表，避免断链。

---

## 5. 与登记表的关系

正式稿路径、版本、终稿日期建议登记在 [受控文档登记表](./CONTROLLED_DOCUMENTS_REGISTER.md)；总清单很长时，登记表可只登记 **跨目录核心** 或 **易混淆模块**。
