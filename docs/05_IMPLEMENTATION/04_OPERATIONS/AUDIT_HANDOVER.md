## 🔄 审查触发机制（个人版）

### 按需审查触发条件

审查在以下情况触发，**不进行定期审查**：

| 触发条件 | 审查范围 | 完成时限 |
|----------|----------|----------|
| **新蓝图完成后** | 全量审查 | 创建蓝图后1周内 |
| **AI讨论新内容后** | 相关模块+交叉影响 | 讨论完成后1周内 |
| **重大架构变更后** | 相关模块+交叉影响 | 变更后1周内 |
| **版本升级前后** | 全量版本一致性检查 | 升级前后各1次 |
| **代码库增长>20%** | 新增代码专项审查 | 增长发生后2周内 |
| **引入新依赖** | 安全+兼容性审查 | 引入前完成 |

### 审查类型

| 类型 | 覆盖范围 | 检查粒度 | 适用场景 |
|------|----------|----------|----------|
| **快速扫描** | 关键路径(20%) | 文件级别 | 日常巡检、小变更后 |
| **标准审查** | 主要路径(60%) | 模块级别 | 新蓝图审查、AI讨论后 |
| **深度审计** | 全部内容(100%) | 行级别 | 重大变更、季度总结 |
| **专项审计** | 特定领域(100%) | 细节级别 | 问题修复后、依赖引入 |

## 📝 审查流程概览

### 四步执行流程

```
第一步: 判断是否需要审查
   - 检查是否有新蓝图完成
   - 检查是否有AI讨论新内容
   - 检查是否有重大变更

第二步: 准备阶段
   - 确认审查类型和深度
   - 确保审查脚本可执行
   - 创建审查分支: git checkout -b audit-YYYYMMDD

第三步: 执行审查
   - 自动化扫描: python scripts/audit_filesystem.py
   - 人工检查: 按检查清单逐项检查
   - 问题记录: 详细记录发现的问题
   - 严重性分级: P0-P4分类

第四步: 报告与修复
   - 填写审查报告
   - 计算健康度评分
   - 制定修复优先级
   - 执行修复
   - 优化审查方案
```

## ⚠️ 问题严重性分级

| 等级 | 标识 | 影响范围 | 修复时限 |
|------|------|----------|----------|
| **P0: 阻塞性** | 🔴 | 系统无法运行/严重安全漏洞 | 24小时内 |
| **P1: 严重** | 🟠 | 核心功能受影响/数据丢失风险 | 3个工作日内 |
| **P2: 中等** | 🟡 | 用户体验受影响/维护成本增加 | 1周内 |
| **P3: 轻微** | 🟢 | 代码质量/文档美观问题 | 1月内 |
| **P4: 建议** | 🔵 | 优化建议/非必需改进 | 下次审查考虑 |

## 🔧 核心审查原则

1. **无损优先** - 诊断优先于修改，隔离优先于删除
2. **量化评估** - 可测量的审查标准（如30%重复率）
3. **渐进改进** - 每次审查优化审查方案自身
4. **全面覆盖** - 文件、代码、配置、文档、资产
5. **自我驱动** - 个人审查，无需团队协作

## 📁 关键审查检查项

### 文件系统审查 (L1)
- 目录分离正确性: src/、tests/、docs/、config/、scripts/、data/
- 目录嵌套深度: 不超过4层
- 文件漂移检查: 文档在代码目录？代码在文档目录？
- 孤儿文档识别: System_Manifest.md未记录的文件

### 文档完整性审查 (L2)
- System_Manifest.md可达性: 所有引用100%可达
- 断裂引用扫描: 100+处断裂引用检查
- 版本混用检查: v4.0/v5.0/v5.1标识统一
- 单文件职责检查: 一个文件承担多种职责

### 代码质量审查 (L3)
- 类型提示覆盖率: Python类型提示使用率>80%
- 测试覆盖率: 单元测试覆盖率>70%
- 静态分析检查: 无严重linting错误

### 配置管理审查 (L4)
- 环境变量使用: 敏感信息使用环境变量
- 密钥硬编码检查: 无硬编码的API密钥、密码

### 资产管理审查 (L5)
- 研究日志完整性: 09_RESEARCH_LOG/目录结构
- 策略草稿管理: Strategy_Backlog.md更新及时性
