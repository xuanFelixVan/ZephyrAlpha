## 2. 背景与定位

### 2.1 痛点

项目文档体系庞大（design_memo 48+ 篇、SOP 4+ 篇、规范 20+ 篇、蓝图 40+ 篇、全景图 6 张），AI 会话接手文档维护时面临三类问题：
1. **上下文丢失**：前脚做完的审查结论，后脚忘（关联原指令集#11 基础设施盘点的动机——"先清楚有什么，才能知道怎么改"）。
2. **标准漂移**：同一功能反复返工（如成本线七返工、图标消失），因为"什么样子算对"从未冻结标准。
3. **踩坑重复**：花三小时试错的结论（如 priceLine 价签删不掉），下一任 AI 继续试。项目缺一个**可继承的事实库**。

### 2.2 本 SOP 的解法

- **七轮循环工作法**：把文档审查拆为七个固定环节，按顺序逐轮执行，不跳过。
- **循环退出条件量化**：问题数量=0 且缺失功能/模块数量=0，连续两轮零发现才退出（不是"感觉差不多了就停"）。
- **每轮修复即提交**：发现问题→修复→走 GitCommitGateway 提交→重读全文→下一轮（闭环，不是攒到一轮末尾再一次性提交）。

### 2.3 与 construction_workflow_sop 的分工

| SOP | 管什么 | 何时触发 |
|---|---|---|
| construction_workflow_sop | **代码**建设（功能开发、施工、上线） | 新建/修改代码时 |
| 本文档（document_review_and_optimization_sop） | **文档**维护（审查、回填、去旧、对齐） | 文档 review、里程碑归档、跨域对齐检查时 |

## 3. 审查触发条件

以下场景**必须**启动本文档规定的七轮审查流程：

| 编号 | 场景 | 说明 |
|---|---|---|
| T1 | **新文档首次定稿** | 新建 design_memo / SOP / 技术手册，写完初稿后必须走一轮七轮审查 |
| T2 | **活跃文档定期 review** | 每个 status=active 的文档，每季度至少走一轮（由目录注册表巡检触发） |
| T3 | **后端代码变更后前端文档同步** | 代码改了，前端技术手册 / 验收单 / 全景图必须同步更新 |
| T4 | **Owner 触发专项审查** | 用户发现文档漂移、AI 发现与其他文档冲突、缺口总账指向某文档过期 |
| T5 | **里程碑归档前** | 一批文档结项归档前，确保内容完整、交叉引用不漂移、版本号对齐 |

## 4. 七轮循环工作法

> **总原则**：按顺序执行，不跳过；每轮发现问题→立即修复→提交 git→进入下一轮；连续两轮零发现才退出。

### 4.1 第 1 轮：基础设施盘点（只读不改）

**目的**：先清楚"项目里现在有什么"，才能判断该保留/修改/退役什么。

**操作**：
1. 用 Read（offset/limit 分段）或 Grep 定位章节，通读全文。
2. 按以下类别全面扫描项目代码和配置，找出与文档主题相关的**所有**已建设施：
   - **代码模块**：`src/zephyr/` 下相关 Python 模块/类/函数（Glob + Grep 搜关键词）
   - **配置文件**：`config/`、`tasks.yaml`、`.env` 等
   - **Schema 定义**：`schemas/` 下相关表定义
   - **注册表条目**：`capability_canonical_file_registry.yaml`、`architecture_issue_registry.yaml` 等
   - **测试文件**：`tests/` 下相关测试覆盖
   - **脚本工具**：`scripts/` 下相关治理/运维脚本
   - **前端组件**：`frontend/` 下相关 dashboard/panel（前端文档审查时必做）
   - **治理规则**：`docs/01_policies_and_standards/` 下相关规则
   - **其他文档引用**：用 Grep 搜本文档标题/ID 的交叉引用

**产出**：在文档中新增或更新「已施工设施盘点」节，表格格式：
```
| 类别 | 路径/位置 | 内容简述 | 状态（production/draft/deprecated） |
```

**通过条件**：盘点表完整到"读者从文档就知道这个功能在项目里有哪些设施"。

---

### 4.2 第 2 轮：内容审查与回填

**目的**：验证文档内容与实际设施是否一致，补全缺失内容。

**操作**：
1. **事实核验**：对照盘点表逐项反查——文档写"已实现"的，验证代码/配置里是否真的存在。
2. **参数/费率校准**：费率、阈值、默认参数等数字类内容，反查代码或外部数据源验证是否最新。
3. **schema 审查**：如果文档涉及 schema 设计，审查字段是否覆盖业务需求、状态机是否完整、编号格式是否合规。
4. **回填缺口**：文档中"待补充""占位""口空"的位置，能补则补，不能补→进第 3 轮登记为缺失。

**通过条件**：文档内容与实际设施一致率≥95%（允许少量前沿/远期内容暂时空缺，但必须标 TODO）。

---

### 4.3 第 3 轮：缺失环节与算法审查

**目的**：识别文档未覆盖但实际需要的环节/算法/机制。

**操作**：
1. **裁定审查**：如果文档含裁定/决策，逐项审查依据是否充分，后续修正是否已落实。
2. **边界检查**：文档的业务范围是否完整——上下游环节有没有遗漏（如 regime 检测器 spec 是否漏了回测验证计划）。
3. **数据来源映射**：文档中引用的数据来源（code_path / API / 表名）是否准确，能否反查到。
4. **缺失登记**：发现文档未覆盖但实际存在的设施，或文档需要但未施工的环节→在「开放问题/待定问题」节登记。

**通过条件**：没有"文档写了但项目里没有"也没有"项目里有但文档没写"的隐藏项。

---

### 4.4 第 4 轮：前沿搜索与替代方案更新

**目的**：让文档保持对最新实践的跟踪，不锁死在老方案上。

**操作**：
1. **WebSearch 搜索**：限定当年（如 2026），搜与文档主题相关的最新研究/开源实践/行业对标。
2. **搜索词规范**：`"关键词 2026"`，优先 2026-07/08 的最新。
3. **结果处理**：找到更好的算法/方案→登记到文档「考虑过的替代方案」或新增「前沿演进方向」节；**不直接替换已定决策**（已定决策如需替换，必须升大版本+写推翻理由）。

**通过条件**：文档至少有一条当年最新行业实践的引用或"前沿演进方向"节（证明查过，不是闭门造车）。

---

### 4.5 第 5 轮：过度工程审查

**目的**：防文档写太多、太复杂、太提前——个人项目不需要团队级/集群级/多期工程级设计。

**判定基准**：以 [system_charter.md §2 硬边界约束](../../02_enterprise_architecture/04_architecture_principles_decisions/system_charter.md) + 实际施工方式为唯一基准：
- 人力：1 人全栈+AI 协作，代码 100% AI 生成
- 硬件：单机 PC 工作站（i7-12700KF / RTX 3090 24GB / 64GB RAM），无集群/K8s
- 资金：个人双账户（实盘+QMT 模拟），miniQMT 10笔/秒、Tick=3秒
- 规则：T+1、涨跌停、融券受限、日频及以上
- 运维：单机部署无热备，RTO<5分钟
- 范式：AI 生成代码需交叉验证+依赖锁定+自治熔断

**凡是超出以上硬边界的 = 过度工程**，一律从文档中去掉或降级为 P4/P5/远期愿景。

**操作**：
1. 逐项审查文档中的机制/设计/规划，用硬边界卡。
2. 过度项的处理：
   - **直接去掉**：纯为团队协作/集群/热备/外部交付设计的机制。
   - **降级保留**：有价值的远期思路→标 P4/P5/远期愿景，但必须在文档中明确可见（不能伪装成 P1）。
   - **保留的项**：必须能说出"为什么这个人+这个机器+这个钱够用"。

**通过条件**：文档中没有"需要多人协作才能用"或"需要超出单机算力"的伪装成 P1 的内容。

---

### 4.6 第 6 轮：一致性与交叉引用审查

**目的**：防文档之间口径打架、引用断裂、版本号漂移。

**操作**：
1. **配对一致性**：与本主题有配对关系的文档（如 62 号建 schema vs 63 号盘点表）逐项对口径。
2. **上下游一致性**：与引用本文档的其他文档互相验证——数字/状态/裁定是否一致。
3. **交叉引用完整性**：
   - 含 `#L行号` 锚点的引用是否断裂（行号偏移了要更新）。
   - 章节编号不强制统一，但引用必须指向对的位置。
   - 不为"结构统一"重排已有章节（防锚点断裂）。
4. **版本号对齐**：改动后升 version（小改 `1.x.0→1.x.1`，大改 `1.x.0→1.(x+1).0` 或 `2.0.0`），修订记录补一行。

**通过条件**：任意两个互相引用的文档，同一事实口径一致；锚点引用零断裂。

---

### 4.7 第 7 轮：文档质量与规范符合性

**目的**：形式合规，让文档可读、可继承、可机读。

**操作清单**：
1. **frontmatter 齐全**：ttl/doc_type/title/owner/language/status/version/date/topic/scope 必须全。
2. **结构合规**：
   - design_memo 类：按 `01_design_memo_management_spec §4` 的段位编号制和结构模板。
   - SOP 类：按本文档的"触发→操作→通过条件→失败处置"编排。
   - 技术手册类：按事实四段式（触发词→想做什么→内置能否→坑→正确做法→代码锚点）。
3. **修订记录**：末尾必须有「修订记录」节，每次改动补一行（日期+版本+改了什么+为什么改）。
4. **开放问题**：必须有「开放问题/待定问题/待裁定」等价节，AI 不替人拍板的问题必须列在这。
5. **引用稳定**：引用代码用稳定 path（禁止 node_id/edge_id）；引用其他文档用相对 path。
6. **状态准确**：status=active 表示还在演进，status=deprecated 表示已归档/迁移，status=draft 表示初稿未审。

**通过条件**：形式检查 100% 通过（形式不过关=不让过，防 sloppy）。

## 5. 循环条件与退出机制

### 5.1 每轮内部闭环

```
第 N 轮开始 → 执行操作 → 发现问题？
   ├─ 是 → 修复问题 → git add <修改的文件> → git commit（走 GitCommitGateway） → 重新通读全文 → 进入第 N 轮（重新跑）
   └─ 否 → 本轮零发现 → 记录本轮零发现 → 进入第 N+1 轮（或第 1 轮，若已完成七轮）
```

### 5.2 全局退出条件

必须**同时满足**以下两个条件，且**连续两轮**都满足，才允许退出：
1. **问题数量 = 0**：本轮发现的文档内容问题、事实错误、过度工程、引用断裂已全部修复。
2. **缺失功能/模块数量 = 0**：本轮发现的项目里有但文档没写的隐藏项已全部登记或补写。

> **防骗机制**：如果第 7 轮零发现，必须再从第 1 轮重新跑一遍确认——连续两轮零发现才算真零发现（防止"刚好这轮没查到"的侥幸心理）。

### 5.3 退出后动作

1. 在文档「修订记录」节补最后一行（日期+最终版本+"七轮审查闭环完成"）。
2. 如果 status=draft→改 status=active（或 deprecated，如归档）。
3. 更新 directory_registry / rule_catalog_registry 中该文档的 last_reviewed 字段。

## 6. 约束与铁律（逐字适用）

以下约束来自项目既有规则，本 SOP 只编排流程位置，**规则内容以原文件为准**。

### 6.1 三层分治（来自原指令集#1）
- design_memo 只写 **why**（决策推理），不写 **what is** 的细节。
- 当前状态由 battle_map + depgraph 维护，不在 memo 里重复写。
- 引用用稳定 path/blueprint_id，**禁止 node_id/edge_id**（会漂移）。

### 6.2 修订升版本（来自原指令集#4）
- 改动后必须升 version：小改 `1.x.0→1.x.1`，大改 `1.x.0→1.(x+1).0`。
- 修订记录补一行：日期+版本+改了什么+为什么改。

### 6.3 不擅自定决策（来自原指令集#8）
- 需人决策的开放问题标在「待定问题」节，AI 不替人拍板。
- 已 active 的定稿决策如要推翻，必须升大版本+写推翻理由+标「待裁定」。

### 6.4 Git 安全铁律（来自原指令集#9）
- **每轮修改后立即 `git add <你修改的文件>`**——staged 文件不会被 `git clean -fd` 删除。
- **禁止执行**：`git clean`、`git clean -fd`、`git reset --hard`、`git checkout --`、`git restore`、`git stash`、`git checkout .`
- 如需清理/丢弃修改：标在「开放问题」节等用户决策，不擅自用危险 git 命令。

### 6.5 文件锁（来自原指令集#10）
- 修改文件前：`python scripts/lock_files.py acquire <file> <session_id>`
- 完成后：`python scripts/lock_files.py release <file> <session_id>`
- check 返回 LOCKED → 等 5 分钟重试，不强制修改。

### 6.6 Proposed 议题查询（来自原指令集#12）
- 启动前 MUST 查询 `architecture_issue_registry.yaml` 中所有 `status=proposed` 的与本次主题相关的议题。
- 完成 MUST：①在「开放问题」节列出相关 proposed 议题；②更新 registry 对应议题的 `last_updated`。

## 7. 前端文档特别说明

前端文档（技术手册、验收单、全景图、模块契约）审查时，第 1 轮和第 2 轮需额外覆盖：

| 额外检查项 | 说明 |
|---|---|
| **前端组件盘点** | `src/zephyr/frontend/` 下相关组件、页面、样式、JS 模块 |
| **后端接口对齐** | 前端展示的数据项，反查后端是否有对应 API/表/字段 |
| **缺口总账交叉** | 对照《前端有→后端没有缺口总账》和反向账，确认状态一致 |
| **视觉标准符合性** | 颜色/字号/间距是否来自统一 CSS variables（防漂移） |
| **缓存版本检查** | index.html / loader.js 是否仍带 Date.now() 版本参数（破缓存机制是否在位） |
