# 交易决策地图逐层讨论 SOP——防撞车·防越级·防枝末先行

> **定位**：交易决策地图（69 号设计备忘录）血肉填充阶段的逐层讨论标准流程。
> **诞生背景**（2026-09-05 撞车事故）：情绪六段列轴与项目已有情绪周期五态（10 号 spec §3.3）撞车——根因是**讨论前未盘点项目已有资产**。本 SOP 把教训固化为流程，适用于地图所有后续环节（板块层/个股层/买卖点层/持仓流/离场流/组合流/币圈）的讨论。
> **核心原则**（Owner 2026-09-05 裁定）：先结构后填装；先主干后枝末；**裁定按第一性原理选效果最好的方案，不以推翻成本为由迁就**（尚未施工的部分，现在就是未来的地基）。

## 1. 三个反模式（本 SOP 防什么）

| 反模式 | 事故实例 | 后果 |
|---|---|---|
| **撞车**：讨论前不盘点项目已有资产 | 情绪六段 vs 已有情绪周期五态（10 号 spec）词汇撞车 | 第二真源/返工/词汇分裂 |
| **越级**：下层未定先讨论上层依赖它的内容 | 六段没定就讨论矩阵格子的策略挂载 | 上层一改，下层全部重写 |
| **枝末先行**：主干未清就讨论枝丫细节 | 大盘层没定就讨论"选股里怎么区分中军/龙头"（个股层内的枝末） | 枝末失去依附的主干，讨论结果悬空 |

## 2. 地图定位声明与节点规范（v1.3，2026-09-05 Owner 裁定）

### 2.1 定位声明（唯一真源边界）

> **交易全景图 = "这个项目怎么交易的，就看这张图"。**
> 一套完整的交易逻辑决策树：遇到什么情况 → 怎么判 → 做什么动作，无限分叉（可能数千数万枝末），每个选择的最优解挂在树上、每个依据可索引到各库。**它是动作流程的唯一真源——凡同等职责（描写动作流程）的文档一律按第一性原理判定后合并进来**；公式/因子/策略的具体内容各归各库，地图只做索引。

| 层 | 真源 | 管什么 | 地图引用字段 |
|---|---|---|---|
| 决策结构 | 交易决策地图（本文档管辖） | 环节/判据/动作/优先级/父子层级 | —（本体） |
| 策略库 | REG-STR-001 | 策略定义 | strategy_refs: [STR-*] |
| 因子库 | REG-FCT-001 | 因子定义 | factor_refs: [FCT-*] |
| 数据库 | REG-DATAFLOW-001 | 数据表 | data_refs: [DS-*] |
| 算法库 | REG-IND-001（技术指标 IND-*）/ REG-EXA-001（执行算法 EXA-*） | 算法定义，条目自身索引代码（module_id） | algo_refs: [IND-*/EXA-*] |
| 算法附件文档 | 22 号等 spec | 公式细节/回测口径（被地图吸收动作语义后降级为附件） | doc_ref: "path#§" |
| 依赖全景图 | depgraph | 模块号与模块关系 | module_id: MOD-* |
| 实现代码 | src/zephyr | 落码状态 | module_ref: 代码路径（空=缺口红节点） |

### 2.2 节点规范 v1.5（七要素 + 五联锚 + 四执行治理字段）

```yaml
- node_id: TDM-E-L2-01            # 层码-环节-序号（天然带层级）
  parent_node: TDM-E-L2           # 父子关系只写一行；祖父/子孙自动推导，不重复写
  name_zh: 板块强度评估           # ①名称
  decision_question: 哪个板块最强、强到值得看？      # ②决策问题
  judgment_basis:                 # ③判据（看什么）
    factor_refs: [FCT-*]          #   因子库（空=缺口节点）
    data_refs: [DS-*]             #   数据库
  strategy_refs: [STR-*]          # ④挂载策略 → 策略库
  action: 输出强度前20→入候选池   # ⑤动作/输出
  algo_refs: [IND-*/EXA-*]        # ⑥算法库引用（条目自带代码索引；空=缺口）
  doc_ref: "docs/…/22_sector_rotation_spec.md#§3.1"  # ⑦算法附件（公式细节）
  activation: intraday            # 【v1.4】时效窗：premarket/intraday/postmarket/weekly/on_demand
  invalidation: null              # 【v1.4】失效条件：什么情况下本判断作废（打板类必填，如炸板）
  ai_autonomy: auto               # 【v1.5】治理档位（见 2.2.1）
  fallback: null                  # 【v1.4】降级路径：数据缺/模块挂时的替代动作（可空）
  module_id: MOD-SIG-026          # 五联锚：全景图模块号
  module_ref: src/zephyr/...      # 五联锚：实现代码（空=红节点）
  conflict_priority: null         # 兄弟节点并发时优先级
  confidence: proposed            # verified/proposed/untested（R6 强制）
```

#### 2.2.1 ai_autonomy 实盘治理阶梯（2026-09-06 D18，宪章 B-007 同源）

| 档位 | 语义 | 换档要求 |
|---|---|---|
| shadow | 影子并行，不下真单，日志对比 | 初始可设 |
| paper | 模拟盘自动跑（**项目初始档**） | 初始档 |
| pilot | 小资金实盘自动跑 | Owner dated 裁定 |
| daily_review | 每日交易方案人工过目，单笔自动执行 | Owner dated 裁定 |
| auto | 全自动 | Owner dated 裁定（永久豁免） |

**铁律**：①实盘执行节点必带本字段，非实盘节点恒 auto；②换档是唯一人工审批点，档内单笔执行不设审批；③`autonomy_log` 记录晋级/降级（D-NN 编号+日期），AI 不可自动升档（熔断可自动降档）；④kill switch 全局常驻（X-R1 应急保命承载），任何档位不可移除。机构依据：MiFID II RTS 6 Art.5(2) 部署授权 / Art.14(2) kill switch 强制 / 量化社区 staged rollout（shadow→paper→pilot→full，promote 需 sign-off）。

**上下游不设字段**：流转依赖用地图已有 edges（from_node/to_node）表达，与父子关系分离。
**枝干分级不设字段**：主干/树枝/枝末由树位置自动推导（第一层=主干；有子=树枝；叶=枝末），SOP 枝末先行检查用推导值。
**契合点**：指标库条目自带 regime_valid（因子生效市场环境），状态矩阵路由直接消费。

### 2.3 合并政策

同等职责（描写动作流程）文档 = 候选吸收对象：第一性原理逐条判定 → 语义入节点（action/question/basis）→ 公式留 doc_ref → 判定完成后原文档 frontmatter 标 `superseded_by: TDM-*`（或保留为纯算法附件）。禁止地图之外再出现第二份动作流程真源。

## 3. 六步流程（每层/每个环节讨论 MUST 依序执行）

### Step 1 · 已有资产盘点清单（防撞车，MUST 第一个做）

讨论任何环节前，MUST 先全项目搜索并罗列**该环节相关的所有已有内容**，逐项标注处置：

| 搜索范围 | 搜什么 |
|---|---|
| 设计备忘录（07 域 design_memos/） | 相关 spec/工程计划（如 regime→10 号、板块→22 号、策略→24-28 号） |
| 作战地图三表（battle_map_steps） | 相关环节及其锚点（BM-BUY-02-A 等） |
| 注册表（REG-STR-001/REG-FCT-001/REG-DATAFLOW-001） | 相关策略/因子/数据条目 |
| 代码（src/zephyr 对应域） | 已实现模块（如 regime_detector.py） |
| 其他地图（frontend_map/预案引擎/触发注册表） | 相邻系统的重叠功能 |

每项标注五选一：**吸收**（同等职责动作语义→建节点，公式细节留 doc_ref，见 §2.3 合并政策）/ **融合**（词汇合并，映射表记录）/ **扩展**（已有条目的细分升级，需回写原 spec）/ **废弃**（过时，走三步审判）/ **引用**（纯算法/数据条目，挂 algo_refs/data_refs，不重建）。

**通过判据**：清单落盘到讨论备忘录 + 每项有处置标注 + 真源唯一自查（本层不产生第二状态/词汇真源）。

### Step 2 · 四路外部调研（Owner 裁定：AI 先查再问，不许让 Owner 凭空发明）

| 路 | 查什么 | 来源 |
|---|---|---|
| 学术前沿 | 最新论文/arXiv/算法（近 12 个月优先） | WebSearch |
| 机构实践 | 顶级机构公开方法论/产品文档 | WebSearch |
| 量化社区 | 开源实现/实证框架/卖方研报 | WebSearch |
| 实战社区 | A股实战体系（与本层相关时） | WebSearch |

**通过判据**：调研结论附来源+新旧对照；与 Step 1 已有资产做"谁更优"的第一性原理对比（效果优先，非成本优先）。
**禁止**：不调研就让 Owner 答结构问题（Owner 提供的是实战纠偏，不是算法发明）。

### Step 3 · 上层完整性检查（防越级，顺序依赖铁律）

讨论第 N 层前，MUST 确认**第 N-1 层（及所有更上游层）已定稿**：

```
主干链顺序（已定稿标 ✅）：
L1 大盘总闸 ✅（六段+灰度+仲裁+预算带，D7-D13）
  → ①E-L2 板块层（待讨论）
    → ②E-L3 个股层（依赖①的候选板块池）
      → ③E-L4 买卖点层（依赖②的个股池）
横向：P 流（依赖 L4 产出的持仓）/ X 流（依赖 P 流的持仓）/ F-C1（依赖 L1+全流）/ C2/C3（依赖 C1）
```

**检查动作**：对照地图 YAML 的 edges，本层所有 `from_node` 上游环节是否"定稿"（定稿=该层讨论备忘录+YAML 内容+置信度标注齐备）。
**不通过处置**：上游未定稿 → **禁止讨论本层**，回退上游（哪怕 Owner 想跳，也 MUST 先补上游）。
**通过判据**：上游依赖链逐项列出+定稿状态确认，记录在讨论备忘录。

### Step 4 · 枝干分级检查（防枝末先行）

讨论议题前判定它在树上的位置：

| 级别 | 判定 | 前置要求 |
|---|---|---|
| **主树干** | 地图 flow 层级节点（L/P/S/F/C 各层 gate/stage） | 其上游主干全部清晰 |
| **树枝** | 主干节点内部的子结构（如 L3 内 5 策略各自的选股链） | 本主干节点定稿+同层兄弟树枝定稿或明确挂起 |
| **枝末** | 树枝内的操作细节（如"个股怎么区分中军/龙头"——L3 选股树枝内的细节） | **整条主干链+本树枝全清晰**；枝末结论必须能回答"它挂在哪个树枝上" |

**判定工具**：地图 YAML 的 edges 依赖链——从议题节点向上回溯到根，路径上任何未定稿节点=禁止讨论。
**通过判据**：议题的树上位置声明（挂哪个节点下）+ 回溯路径全绿。

### Step 5 · 讨论与裁定（AI 查证打底 + Owner 实战纠偏）

1. AI 按 Step 1/2 产出"已有资产×外部调研"对比矩阵
2. Owner 以实战经验纠偏/拍板（AI 禁止替 Owner 编决策规则）
3. 裁定按第一性原理记录：判据+论证+放弃方案及理由（效果优先，成本让位）
4. 裁定编号顺延（D-NN），同步更新讨论备忘录

### Step 6 · 落盘与校验

1. YAML 更新（config/trading_decision_map.yaml）——按节点规范 v1.3（§2.2）：五联锚只存稳定标识符（STR-*/FCT-*/DS-*/IND-*/EXA-*/MOD-*/path），禁复制内容；algo_refs 指向算法库条目（条目自身索引代码），doc_ref 指向算法附件文档
2. 新增/变化因子缺口显性化（factor_refs 留空=缺口节点）
3. 69 号设计备忘录升版（新增 §小节记录裁定）
4. 讨论备忘录补轮次记录（D-NN+落地内容）
5. 循环验收：`pytest tests/trading/test_decision_map.py tests/governance/test_alignment_gates_red_blue.py`（真源回归锚必须全绿）
6. GitCommitGateway 提交（capability lookup 先行；禁 --no-verify）
