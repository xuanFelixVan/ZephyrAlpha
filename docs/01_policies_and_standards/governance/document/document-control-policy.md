# 文档控制原则

> module_id: GOV-DOC-009 | version: 1.8.2 | status: active | layer: cross_layer

---

## 1. 目的与范围

本策略定义 ZephyrAlpha 文档体系的8条控制原则。这些原则是所有文档治理操作的前提条件，优先级高于任何具体规则。

适用于：`01_policies_and_standards/` 下所有文件的创建、修改、合并、删除、引用操作。

本策略源自 Phase 0~4 施工验收中的查重合并实践，结合专业机构标准与 Vibe Coding 社区实践，提炼为持久生效的控制原则。

> **编号说明**：本文件使用领域唯一前缀 `DOC-`（DOC-001~DOC-008），与 `../../meta/behavior-boundaries-standard.md`（PS-STD-003）的 ABS 编号（ABS-01~ABS-48）全局不冲突。体系架构决策见 `../../meta/meta-standard-constitution.md`（PS-STD-000）§3——行为边界集中存储（PS-STD-003），操作控制原则分散存储 + 集中注册。

## 2. 八条控制原则

### DOC-001：SSoT 唯一（Single Source of Truth）

每个架构事实有且仅有一份权威来源文件。禁止同一内容存在于两个文件中。

- **规则**：任何规则、数据、流程定义只能在一个文件中定义。其他文件只能引用，不能重复定义。
- **违反后果**：AI 按错误版本执行，治理信号矛盾
- **验证方式**：`check_ssot_conflicts.py`；人工查重审查
- **专业参考**：ISO 27001 Annex A → Information Management

### DOC-002：责任二选一（Clear Accountability）

每个文件的管辖范围必须明确，不能与其他文件重叠。一个文件要么负责某项内容，要么不负责。

- **规则**：文件的 title 和 summary 必须准确反映其管辖范围。如果两个文件的管辖范围有重叠，必须重新划分责任边界或合并为一个文件。
- **违反后果**：AI 判断错误，后续 AI 连锁误判
- **验证方式**：审查文件的 title/summary/depends_on 是否与实际内容一致
- **专业参考**：COBIT → Governance Accountability

### DOC-003：安全删除（Safe Deletion）

删除任何内容之前，必须确认被删除的内容在其负责的目标文件中确实存在。如果不存在，必须先将内容融入目标文件，确认融入后再删除。

- **规则**：
  1. 列出待删除内容的每一条
  2. 逐条确认目标文件中是否包含该内容
  3. 如果目标文件没有该内容：先融入，再删除
  4. 如果目标文件已有该内容：直接删除
  5. 融入后必须验证目标文件内容完整
- **违反后果**：内容永久丢失，不可恢复
- **验证方式**：删除前逐条核对清单
- **专业参考**：ITIL → Change Management / ISO 27001 → Asset Disposal

### DOC-004：完整路径引用（Full Path Traceability）

所有文件间的引用必须使用完整绝对路径，禁止使用相对路径或仅使用 module_id 引用。

- **规则**：引用格式为 `../../../01_policies_and_standards/{子路径}\{文件名}.md`（GOV-XXX-NNN）。同时提供路径和 module_id。
- **违反后果**：AI 无法定位引用目标，引用链断裂
- **验证方式**：`check_dead_links.py`；人工审查引用格式
- **专业参考**：ISO 27001 → Document Control / NIST 800-53 → AU-6 Audit Trail

### DOC-005：创建前必查（Pre-Creation Check）

AI 在创建任何文件或目录之前，必须执行"验架构 → 选位置 → 查重 → 融入或创建"工作流。创建新文件永远是最后选项，不是第一反应。

- **规则**：

  **前置步 —— 架构上下文自检（先看结构对不对）**
  - 执行 `../../meta/governance-methodology-standard.md`（PS-STD-011）MTH-002（架构上下文自检）的四步流程
  - 确认目标架构层完整——该层已有架构描述文件且已通过验证
  - 若该层架构不完整 → 优先补全架构文件，不得在不完整的架构层中创建孤立文件

  **Step 1 —— 精准定位（选对放的地方）**
  - 先查 `../../governance/document/directory-structure-standard.md`（GOV-DOC-002）是否定义了该文件类型应放置的位置
  - 如果项目标准已定义 → 严格遵守
  - 如果项目标准未定义 → 参考 `../../meta/governance-methodology-standard.md`（PS-STD-011）中的 MTH-001 标准先行原则，参考专业机构做法（ITIL SACM / ISO 9001 §7.5）确定位置
  - 禁止凭直觉或习惯随手放置文件

  **Step 2 —— 查重扫描（有没有类似的）**
  - 在确定的目标位置及整个项目中搜索功能/主题相似的文件
  - 使用 glob + grep 搜索文件名、frontmatter summary、tags 字段
  - **操作定义**："内容接近" = 两个文件对同一架构事实（同一个规则、同一个实体、同一个流程）有定义或描述。针对不同事实的两个文件，即使用词相似，也不视为"内容接近"
  - 如果发现针对同一架构事实的相似文件 → 进入 Step 3
  - 如果未发现 → 直接创建，且仅创建一份（遵循 DOC-001 SSoT 唯一）

  **Step 3 —— 融入优先（不重复造轮子）**
  - 如果存在针对同一架构事实的相似文件：评估是否可以融入现有文件（扩展内容 / 补充章节）
  - 融入优于创建——优先修改现有文件，而非新建
  - 如果融入会导致文件职责不清 → 先按 DOC-002 重新划分责任边界，再决定是否需要新文件
  - 如果确认需要独立文件 → 必须在两个文件的 depends_on 中互相引用，明确管辖范围边界

- **违反后果**：目录结构混乱、同一内容分散在多个文件中、AI 在多个文件间不确定哪个是权威来源
- **验证方式**：每次文件创建操作后审查是否有功能重复的现有文件被遗漏
- **专业参考**：ITIL SACM → Golden Record / ISO 9001 §7.5 → Document Creation Review / Vibe Coding 社区 → creation-guard 技能

> **本原则与其他原则的关系**：DOC-005 的查重扫描（Step 2）是 DOC-001（SSoT 唯一）的执行保障——没有查重就不会发现重复。融入与独立文件的判断（Step 3）依赖 DOC-002（责任二选一）定义的责任边界。位置确定（Step 1）依赖 GOV-DOC-002 的目录结构规范。DOC-003（安全删除）与 DOC-005 互为反操作——删除前确认目标文件有内容（Step 1~3），创建前确认没有重复（Step 2~3）。

### DOC-006：先读后改（Read-Before-Modify）

任何文件操作（修改、删除、扩展）之前，必须先读取该文件及其 `depends_on` 中声明的所有依赖文件的完整内容。禁止凭记忆或猜测操作。

- **规则**：
  1. 操作前必须读取目标文件全文
  2. 操作前必须读取目标文件 `depends_on` 中列出的所有文件
  3. 如果操作涉及交叉引用，也必须读取被引用文件的相关章节
  4. 读取完成后才能执行修改/删除
- **违反后果**：基于过时或不完整的信息操作，产生逻辑矛盾；已有的交叉引用被破坏
- **验证方式**：操作完成后检查是否所有被引用文件的当前内容与修改一致
- **专业参考**：Anthropic Claude Code 官方指南 → "Never speculate about code you have not opened" / ISO 9001 §7.5 → Document Review Before Change

### DOC-007：引用不复制（Reference, Don't Duplicate）

两个文件之间传递信息只能使用引用，禁止将内容从一个文件复制粘贴到另一个文件中。即使措辞不同，只要表达的是同一个含义，也必须改为引用。

- **规则**：
  1. 如果需要引用另一个文件的规则/定义/数据 → 使用完整路径引用（遵循 DOC-004）
  2. 禁止在新文件中重新声明已有文件中定义过的规则
  3. 即使措辞不同，只要表达的是同一个含义，也必须改为引用
  4. 如果需要补充/细化 → 在原文件中扩展，然后在其他文件中引用扩展后的章节
- **违反后果**：产生隐形重复——后续修改原文件时副本不同步，形成信息分叉
- **验证方式**：任何新增段落如果包含"必须"、"禁止"、"应当"等规范用语，检查该规范是否已在其他文件中定义过
- **专业参考**：Cursor 官方 Rules 指南 → "Reference files instead of copying content into rules" / DRY（Don't Repeat Yourself）原则

### DOC-008：上下文预算意识（Context Budget Awareness）

每个新增的文件都会消耗 AI 的上下文窗口。创建新文件有成本，不是免费的。保持文件精简、避免碎片化，是对 AI 决策效率的直接保障。

- **规则**：
  1. 创建任何新文件前，先问："这个文件的内容是否可以通过引用已有文件来表达？"
  2. 如果一个文件的内容少于 20 行实质规则定义，优先考虑融入已有文件
  3. 如果一个文件的唯一作用是转发/重定向到另一个文件，应直接使用引用替代
  4. 定期审查：自创建后超过 30 天未被任何其他文件依赖或引用的文件，应评估是否可删除或融入
- **违反后果**：上下文窗口被低价值文件占用，AI 决策时需要扫描更多文件才能找到关键规则，响应质量下降
- **验证方式**：`depends_on` 反向查询——检查哪些文件引用了目标文件，无引用文件标记为审查候选
- **专业参考**：Windsurf 平台规则 → 6000字符/规则硬限制 / Cursor Rules 指南 → "只写 AI 反复犯错的点"

### DOC-009：引用链完整性（Reference Chain Integrity）

`depends_on` 关系必须构成有向无环图（DAG）。禁止引用环、禁止引用已废弃的目标、引用链深度超过阈值时必须告警。

- **规则**：

  1. **无环约束**：`depends_on` 关系及其传递闭包（A→B→C→…）中，任意文件不得引用自身或其上游祖先。禁止 A→B→A 或 A→B→C→A。
  2. **断裂检测**：当 `depends_on` 引用的目标文件不存在、已被物理删除、或 `status: deprecated` 时，引用方在读写时必须立即阻断并告警。
  3. **深度阻断（死规则）**：引用链深度必须 = 1 层（A→B，直接声明）。不允许传递依赖（A→B→C）。如果 A 需要 C 的知识，A 必须直接在 depends_on 中声明 C。超过 1 层 → V1 阻断，不可绕过。对标 npm `dependencies` 字段——只声明直接 `import` 的包，传递依赖由工具解析。对 AI 治理体系而言，不存在"工具解析"——AI 就是消费者，依赖图必须平坦。
  4. **行级精度（Token 优化死规则）**：`depends_on` 必须使用结构化格式 `{target: module_id, at: "§N", why: "原因"}`。`at` 字段精确声明引用目标的章节/行号范围，禁止仅声明文件级依赖。"读整篇"行为直接浪费 AI 上下文窗口（每 100 行无效读取 ≈ 1500 token 虚耗），对标 Anthropic CLAUDE.md "上下文窗口是最重要的有限资源" + PS-REG-001 CODE 域已有 `money.py L152-158` 行级精度格式。缺失 `at` 字段 → V2 警告，累计 3 次 → V1 阻断。
  5. **重定向链防范**：禁止仅作为转发/重定向用途的文件（如"本文件已废弃，请参见 X"的占位文件）。废弃内容走 `superseded_by` 字段，不走节点跳转。

- **违反后果**：引用环导致 AI 无限循环引用解析；断裂引用导致运行时错误或治理信号失真；引用链过长降低解析性能并增大烟囱倒塌风险（改底层文件时不知道上游有谁依赖）；缺失行级精度导致 AI 每次引用全篇阅读，在 100% vibe coding 环境下造成大量 token 虚耗
- **验证方式**：pre-commit 或 CI 中执行所有 `depends_on` 的传递闭包可达性校验；校验 `at` 字段存在性（缺失 → V2 警告）；未被任何其他文件引用的文件标记为潜在废弃候选（与 DOC-008 补充审查）
- **专业参考**：npm → `dependencies` 字段只声明直接 `import` 的包，传递依赖由工具解析 / Kubernetes API → 用户可见引用必须直接，不存在 Deployment→ReplicaSet→Pod 的依赖链 / Anthropic CLAUDE.md → 上下文窗口是最重要的有限资源，精确引用优于全篇加载 / PS-REG-001 CODE 域 → 已有 `money.py L152-158` 行级精度先例

### depends_on 结构化格式规范（新增）

> **版本**：v2.0 | **生效日期**：2026-05-01 | **状态**：active

```yaml
# 新格式（必须）——结构化 map 数组
depends_on:
  - {target: PS-STD-003, at: "§3.1~§3.5", why: "ABS 定义"}
  - {target: PS-STD-001, at: "§2.1~§2.8", why: "frontmatter 字段 SSoT"}

# 旧格式（兼容但触发 V2 警告）——纯字符串数组
depends_on:
  - PS-STD-003
  - PS-STD-001
```

| 字段 | 必需 | 格式 | 说明 |
|------|:---:|------|------|
| `target` | ✅ | `module_id` | 引用目标的全局唯一标识符 |
| `at` | ✅ | `"§N"` / `"§N~§M"` / `"§N ¶X"` | 精确到章节（§）或段落（¶）或行号（L） |
| `why` | ✅ | 短句（≤40字符） | AI 可读的依赖原因，消除"这个依赖是干嘛的"的猜测成本 |

**at 字段格式细则**：
- `"§3"` → 整个第 3 章节
- `"§3.1"` → 第 3.1 小节
- `"§3.1~§3.5"` → 从 §3.1 到 §3.5 的范围
- `"§3 ¶4"` → §3 的第 4 段落
- `"L152-L158"` → 第 152 行到第 158 行（代码文件）

## 3. 原则优先级

当原则之间发生冲突时，按以下优先级处理：

| 优先级 | 原则 | 理由 |
|:------:|------|------|
| 1 | DOC-003 安全删除 | 内容丢失不可逆，优先级最高 |
| 2 | DOC-005 创建前必查 | 杜绝源头重复，从入口处控制质量 |
| 3 | DOC-001 SSoT 唯一 | 重复定义导致治理混乱 |
| 4 | DOC-007 引用不复制 | 杜绝隐形重复，与SSoT联动 |
| 5 | DOC-002 责任二选一 | 责任不清导致连锁误判 |
| 6 | DOC-006 先读后改 | 操作前置条件，违反后果可逆 |
| 7 | DOC-004 完整路径引用 | 引用断裂导致治理信号失真 |
| 8 | DOC-009 引用链完整性 | 引用环和断裂引用导致解析失败，行级精度关乎 token 效率，与 DOC-004 联动 |
| 9 | DOC-008 上下文预算意识 | 效率优化，但可事后补救 |
