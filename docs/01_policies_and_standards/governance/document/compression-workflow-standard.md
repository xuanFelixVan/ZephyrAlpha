# 第一篇：产出物规格

> 本篇定义规格化后的产出物**必须长什么样**——什么可以没有、什么必须有、什么不能缺。
> AI 做规格化时直接对照本篇执行。不需要理解"为什么"——只需要知道能不能删、能不能改。

---

## §0 时态判定规则

> **核心原则**：蓝图中的内容按"时态"分类——永久时态保留，临时时态执行完毕后删除。
> 这是 §1 可删清单的元规则——所有可删判定先过时态分类。

### 0.1 时态分类

| 时态 | 定义 | 蓝图处置 | 示例 |
|------|------|---------|------|
| **永久时态** | 描述当前架构/接口/约束/状态的事实——不因执行完毕而过期 | **保留** | 接口签名、架构设计、约束条件、错误处理、§0.1 代码存在性 |
| **临时时态** | 描述"从A到B的过程"——有明确起点和终点，执行完毕即成历史 | **执行完毕→删除；未执行→保留** | 迁移方案、升级执行计划、ContractBus 批次迁移、施工步骤细节 |
| **施工声明** | AI 进入蓝图修改/施工时必读的防护规则——删掉 = 失去防漂移防线 | **永久保留在蓝图中**——不可改为链接引用（AI 不会主动跳转链接读取） | 铁律、安全删除协议、必备链接、已有类似功能、涉及文件范围 |

### 0.2 临时时态内容判定流程

```
遇到蓝图中的内容 → 问：这是"当前事实"还是"从A到B的过程"还是"施工声明"？
├ 当前事实（永久时态）→ 保留，走 §2 不可删清单
├ 从A到B的过程（临时时态）→ 检查执行状态：
│   ├ 未执行 → 保留（仍是可操作的指令）
│   ├ 部分执行 → 保留未执行部分，删除已执行部分
│   └ 已全部执行 → 删除前 MUST 验证：
│       ├ 正确方案/代码是否已实现？→ 否 → 保留（可能需要回退）
│       └ 是 → 代码是否可运行？(pytest+mypy+ruff) → 否 → 保留（代码有问题不能删保护网）
│           └ 是 → 可以删除
│   ⚠️ 删除前置条件见 §0.3
└ 施工声明（铁律/安全删除/必备链接/类似功能/文件范围/治理信息）→ 永久保留
    不可改为链接引用——AI 不会主动跳转链接读取
```

### 0.3 常见临时时态内容

> ⚠️ **所有删除操作 MUST 先验证"正确方案已实现且可运行"**——不管是临时时态内容还是备选方案。
> 如果正确方案还没实现，备选方案不能删（可能需要回退）。如果正确方案已实现且通过验证，备选方案就是历史，可删除。

| 临时时态内容 | 判定方法 | 已执行后处置 | 删除前置条件 |
|------------|---------|------------|------------|
| 迁移方案（§5.3） | 检查目标文件是否已在目标位置、引用是否已更新 | 从蓝图删除 | 目标文件存在+引用已更新+代码可运行 |
| ContractBus 批次迁移表 | 检查 `contractbus-migration-tracker.yaml` 中批次状态 | 从蓝图删除 | 批次状态=completed+代码可运行 |
| 升级执行步骤 | 检查代码是否已按步骤实现 | 从蓝图删除，§17 只保留升级后的当前架构 | 代码存在+pytest+mypy+ruff 通过 |
| 施工步骤细节（§16） | 检查产出物是否已存在且通过验证 | 保留施工指引框架，删除已完成步骤的详细操作，只留"步骤 N: 已完成" | **缺一不可**：①代码文件存在且非空 ②`pytest` exit 0 ③`mypy` 通过 ④`ruff` 通过 |
| 配置文件完整示例 | 检查配置文件是否已存在 | 从蓝图删除，只保留路径+关键字段约束 | 配置文件存在+格式正确 |
| §7 备选方案 | 检查 §18 中选中的方案是否已实现且可运行 | 从蓝图删除（§18 已覆盖备选方案信息） | §18 选中方案已实现+pytest+mypy+ruff 通过 |
| §15 正面后果 | 检查 §1 目标是否已实现 | 删除正面后果（与 §1 重复），负面后果合并到 §14 | §1 目标已实现+代码可运行 |
| 蓝图内已实现代码块 | 检查代码文件是否存在且通过验证 | 删除实现代码，只保留接口签名（§4） | 代码文件存在+pytest+mypy+ruff 通过 |

### 0.4 施工声明内容（永久保留）

| 施工声明内容 | 保留理由 | 不可改为链接引用的理由 |
|------------|---------|---------------------|
| 铁律（15条） | 防止 AI 编写/修改蓝图时犯错 | AI 不会主动跳转链接读取，删掉 = 失去防漂移防线 |
| 安全删除协议 | 防止 AI 施工时误删文件 | 同上 |
| 必备链接 | AI 改蓝图前必须先读的上下文 | 同上 |
| 已有类似功能 | 防止重复造轮子 | 同上 |
| 涉及文件范围 | 防止 AI 越界修改 | 同上 |
| 治理信息（SSoT/消费者/同步规则/修改条件） | 声明蓝图的治理边界和变更规则 | 治理元数据，永久时态 |

## §1 可删清单

> 最终交付物中**允许不存在**的内容。以下 5 类——**只此 5 类**。

| # | 可删类型 | 示例 |
|---|---------|------|
| 1 | "大白话解释"/"大白话总结"段落 | AI 不需要人类翻译 |
| 2 | "对标 K8s/ITIL/Unix/..."长篇对比段落 | 专业框架映射表保留 |
| 3 | "AI 意识植入"散文 | "你创建的每一个临时文件都是对未来的承诺..." |
| 4 | "修订记录/变更历史"段落 | git log 已有 |
| 5 | ASCII/mermaid 流程图 | **条件**：图中信息已在表格或步骤中完整表达 → 可删。表和图中信息不一致 → 保留图 |
| 6 | 已实现代码的蓝图内重复 | §0.1 标记`已实现`的模块——代码文件是 SSoT，蓝图只保留 §4 接口签名 |
| 7 | 已执行完毕的临时时态内容 | 迁移方案/升级计划/ContractBus批次迁移表已执行完毕→从蓝图删除。判定流程见 §0.2 |
| 8 | 配置文件完整示例 | YAML/JSON 示例已存在于实际配置文件中——蓝图只声明配置路径和关键字段约束 |
| 9 | 技术栈"理由"/"选择理由"列 | "为什么选 SQLite"属于决策过程→§18 决策记录；蓝图只保留"选了什么" |
| 10 | §7 备选方案独立章节 | §18 决策记录的"选项"列已包含备选方案信息——§7 与 §18 重复率 8%-100%（抽样验证）。正确方案已实现且可运行 → 删除 §7 |
| 11 | §15 正面后果 | 与 §1 目标重复——正面后果本质是"目标已实现"的确认，无增量。负面后果合并到 §14 风险 |

## §2 不可删清单

> 最终交付物中**必须存在**的内容。以下 15+3 类——**一个都不能少**。

| # | 不可删 | 举例 |
|---|--------|------|
| 1 | frontmatter 字段 | module_id, title, version, layer, depends_on, tags |
| 2 | 路径 | 绝对路径 `D:/ZephyrAlpha/...` 和相对路径 |
| 3 | module_id 引用 | MOD-INF-XXX, PS-STD-XXX |
| 4 | 命令和代码模板 | `python scripts/...`、代码块 |
| 5 | 表格 | 状态表、映射表、对照表、约束表 |
| 6 | "禁止/必须/SHOULD/MUST"约束 | 所有约束语句 |
| 7 | 漂移防护语句 | "修改此文件必须同步更新 X/Y/Z" |
| 8 | 异常处理表格和流程 | 所有异常处理 |
| 9 | 状态不变量约束 | 所有状态不变量 |
| 10 | depends_on 依赖声明 | 所有依赖声明 |
| 11 | 触发条件/适用场景 | "何时应执行此规则"的判定逻辑 |
| 12 | 完成标准/通过条件 | "此流程完成"的 exit criteria |
| 13 | 多步流程中的步骤 | 不可部分删除——删一步则全流程断裂 |
| 14 | 可解析引用 | 项目术语 ADR/KB/TaskCard/Gate 后必须有路径 |
| 15 | 导航路径/冷启动序列 | "新 AI 如何找到这个文件、如何开始使用"——命令链或 3-5 步路径 |
| 16 | 蓝图特有内容 | 写在"蓝图特有章节"内+标注三要素（来源/仅本蓝图/不可砍）= 不可删。写在章节外 = 视为冗余可删 |
| 17 | 反向进化发现的通用新增 | 待写入模板的有价值内容——见 §4 B-15/B-17 |
| 18 | 蓝图概述段 | 蓝图开头 3-5 句概述——AI 建立心理模型的第一入口。不是"大白话总结" |

## §3 必须补充清单

> 规格化后**必须检查并补充**的 10 类内容。缺失 = 规格化未完成。

| # | 必须补充 | 形式 |
|---|---------|------|
| 1 | 可达性入口 | 文件在 L0/L1/registry 中有引用 |
| 2 | frontmatter 完整 | 所有必填字段已填写（见蓝图+施工图模板字段表） |
| 3 | 负向责任 | 声明"本文件不涉及 X/Y/Z"——防止 AI 越界查找 |
| 4 | SSoT 声明 | 声明本文件是哪个领域的唯一真源 |
| 5 | 消费者注册表 | 列出谁依赖本文件——改了谁知道 |
| 6 | 触发条件 | AI 什么时候该读这个文件（关键词/场景/操作类型） |
| 7 | 可解析引用 | 所有项目专有术语后面有路径 |
| 8 | 导航路径 | 新 AI 怎么找到这个文件（3-5 步命令链） |
| 9 | 漂移防护 | "修改此文件必须同步更新 X/Y/Z" |
| 10 | 铁律/禁止清单 | 从历史教训转化的硬约束 |

## §4 蓝图专项铁律

> 蓝图是核心设计文档——AI 施工的唯一依据。以下铁律定义蓝图规格化的额外约束。

### 4.1 蓝图铁律（B-00 ~ B-19）

| # | 铁律 |
|---|------|
| B-00 | **Layer 1 先于 Layer 2**——蓝图+施工图模板要求的章节（概述 + §0-§18）不得被规格化砍削 |
| B-01 | **施工步骤（§16）禁止砍**——每一步都是 AI 执行的指令 |
| B-02 | **接口契约（§4）禁止砍**——下游模块和施工者依赖此节 |
| B-03 | **架构设计（§3）禁止砍**——组件交互和数据流是蓝图核心 |
| B-04 | **功能描述（§2）禁止砍**——模块做什么必须说清 |
| B-05 | **错误处理（§6）禁止砍**——异常场景和恢复策略 |
| B-06 | **产出物路径（§11）禁止砍**——AI 按此路径存放文件 |
| B-07 | **必备链接表禁止砍**——AI 零记忆，每次需要完整路径 |
| B-08 | **安全删除协议禁止砍**——删除是不可逆操作 |
| B-09 | **设计过程可砍**——蓝图只保留最终设计结果，不记录决策过程 |
| B-10 | **对标段可砍**——AI 不需要知道"为什么这样设计" |
| B-11 | **蓝图铁律表禁止砍**——每条都是实战伤疤 |
| B-12 | **容量估算（§5.2）禁止砍**——AI 不知道系统能容纳多少 |
| B-13 | **蓝图 MUST 标注成熟度**——在 frontmatter 中标注 `codification_level: L0~L5` |
| B-14 | **不可因模板砍价值**——蓝图中有价值但模板未覆盖的内容，MUST NOT 以"不符合模板"为由删除 |
| B-15 | **反向进化原则**——蓝图中有价值且所有蓝图都可能需要的内容，MUST 推动蓝图+施工图模板进化 |
| B-16 | **蓝图特有内容保留**——超出模板下限的内容 MUST 写在"蓝图特有章节"内+标注三要素。写在章节外 = 可删。标注三要素 = 不可删。内容 MUST 已压缩至最简 |
| B-17 | **反向进化流程**——发现通用新增时：①写入蓝图+施工图模板 → ②通知 Owner 审批 → ③更新 REQUIRED_SECTIONS → ④全项目蓝图按需补充 |
| B-18 | **规格化前 MUST 建立内容价值映射**——对蓝图每个章节/段落分类：模板必需/通用新增/蓝图特有/可砍。未分类 = 禁止动手 |
| B-19 | **概述段禁止砍**——蓝图开头的 3-5 句概述是 AI 建立心理模型的关键上下文。砍概述 = AI 读 400 行才理解模块用途 |
| B-20 | **已实现代码不在蓝图中重复**——§0.1 标记`已实现`的模块，蓝图只保留 §4 接口签名。代码文件是 SSoT，蓝图复制代码 = 双源漂移 |
| B-21 | **临时时态内容执行完毕后从蓝图删除**——迁移方案、升级执行计划等临时时态内容，一旦执行完毕即成为历史，从蓝图删除。蓝图只保留永久时态内容。判定流程见 §0.2 |
| B-22 | **蓝图内容拆分判定**——职责不同→拆分独立蓝图；职责相同→原地升级。判定标准见 §4.5 |

### 4.2 蓝图可砍内容

| 可砍 | 示例 |
|------|------|
| 对标段 | "对标 TOGAF 三层架构" |
| 设计过程叙述 | "我们考虑了方案A/B/C，最终选了C" |
| 重复的模块拓扑 | 已在 SYS-MASTER-001 中定义的拓扑树 |
| 💡提示框中的"为什么" | "为什么必须写容量？实战教训..." |
| 变更记录 | git log 已有 |
| 已实现代码的蓝图内重复 | §0.1 标记`已实现`的模块的 Python/YAML 完整实现——代码文件是 SSoT |
| 已执行完毕的临时时态内容 | 迁移方案/升级计划/ContractBus批次迁移表已执行完毕→从蓝图删除（§0 时态判定） |
| 配置文件完整示例 | error_budget_config.yaml / sandbox_policy.yaml 完整内容——蓝图只声明路径+关键字段 |
| 技术栈"理由"列 | "终选 SQLite，理由：零依赖"→ 理由移至 §18 决策记录，蓝图只保留"选了 SQLite" |
| 重复出现的模块列表 | §0 和 §19 同一列表出现两次→合并为一处 |
| Phase 路线图"人日"列 | 项目管理数据，AI 不需要人日估算 |
| §7 备选方案独立章节 | §18 决策记录已覆盖——正确方案已实现且可运行 → 删除 §7 |
| §15 正面后果 | 与 §1 目标重复——删除正面后果，负面后果合并到 §14 风险 |

> ⚠️ **施工声明不可砍**：铁律、安全删除协议、必备链接、已有类似功能、涉及文件范围、治理信息——
> 这些内容永久保留在蓝图中，不可改为链接引用。AI 不会主动跳转链接读取，删掉 = 失去防漂移防线。

|---------|------|----------------------|

| §10.2 依赖图对齐声明 | 蓝图依赖与全局依赖图一致 | §10.2 |
| §10.3 内部依赖图 | 蓝图内部脚本间执行顺序+数据流依赖 | §10.3 |
| §10.4 自动化规格 | 是否需要/如何实现/如何触发——AI 写蓝图时自动考虑自动化 | §10.4 |

| §18 决策记录 | ADR 级决策需在蓝图中留痕 | §18 |
| codification_level 标注 | 规格化进度追踪 | frontmatter |
| 蓝图特有章节 | 标记为"蓝图特有" | §3 或附录 |

**判定三步**：

```

STEP 3: 拆分后验证

  - 本蓝图 §10 依赖关系新增子蓝图引用

```

## §6 常见反模式

### 6.1 砍错模式

> 根因：跳过了第二篇 STEP 2（转化），直接进入 STEP 3（查重/砍留）。

| 砍错类型 | 症状 | 正确做法 | 转化后形式 |
|---------|------|---------|-----------|
| 把"触发条件"当散文 | 砍掉"适用场景"列表——AI 不知何时调用 | 转化为二元规则 | `当 <条件> 时，MUST 触发 <规则>` |
| 把"反模式"清单当散文 | 砍掉反例清单——AI 失去对照 | 转化为禁止规则 | `禁止 <行为>——MUST <正确做法>` |
| 把"完成标准"当散文 | 砍掉 exit criteria——AI 不知道算不算做完 | 转化为通过条件 | `当 <条件1+条件2> 全部满足时，标记为通过` |
| 部分删除流程步骤 | 砍掉"治根处理"步骤——AI 不知道下一步 | 流程步骤全留或全删 | (保持完整步骤链) |
| 保留不可解析引用 | 文档写"一篇 ADR"但没有路径 | 所有项目术语后跟路径 | `Breaking change → 一篇 ADR（存入 KB:decisions）` |
| 砍掉导航路径 | 砍掉"最小必读路径"——新 AI 不知道从哪开始 | 导航路径 = 命令链，不是散文 | `新 AI → AGENTS.md → index.md → 本标准 → 自检清单` |
| 因模板砍价值 | 蓝图有盲点对照表/容量升级方案——AI 以"模板无此章节"为由砍掉 | B-14 铁律：先分类再处置 | 通用新增 → 推动模板进化；蓝图特有 → 保留 |
| 未分类就动手 | AI 不做内容价值映射就直接开始砍 | B-18 铁律：先分类四类 | 模板必需/通用新增/蓝图特有 → 禁止删除 |

### 6.2 漏补模式

> 根因：只关注"砍什么"，忽略了"缺什么"。

| 漏补类型 | 症状 | 正确做法 | 补充后形式 |
|---------|------|---------|-----------|
| 缺可达性入口 | 文件规格化后 AI 仍然找不到 | 在 L0/L1/registry 中添加入口 | `registry-of-registries.yaml` 新增 REG 条目 |
| 缺负向责任 | AI 在本文档找不属于它的内容 | 声明"不涉及 X/Y/Z → 见 GOV-XXX" | `**负向责任**：不涉及任务卡字段（→ GOV-TASK-001）` |
| 缺 SSoT 声明 | 两个文件都说自己管同一领域 | 声明唯一真源 | `**SSoT 声明**：本文件是 X 领域唯一规则来源` |
| 缺消费者注册表 | 改了文件没人知道 | 列出谁依赖本文件 | `**消费者**：task-lifecycle-standard.md / G7 门禁` |
| 缺触发条件 | AI 不知道什么时候该读 | 标注触发关键词/场景 | `**触发**：任务状态变更 / COMPLETED→VERIFIED` |
| 缺漂移防护 | 修改后未同步更新依赖文件 | 声明同步更新规则 | `**漂移防护**：修改 §3 必须同步更新 G7 门禁配置` |
| 缺铁律/禁止清单 | 历史教训只写在散文中 | 转化为 MUST/禁止 格式 | `**铁律**：MUST 执行清扫三步法后才能声明 COMPLETED` |
| 缺可解析引用 | 写"一篇 ADR"但无路径 | 术语后跟路径 | `ADR（存入 KB:decisions）` |
| 缺导航路径 | 新 AI 不知道怎么找到这个文件 | 写 3-5 步命令链 | `新 AI → L0 速查表 → registry → 本标准` |
| 缺 frontmatter 字段 | 新增字段未填写 | 补充 actual_disk_path / generation 等 | frontmatter 完整 |

## §8 规格化前置流程（强制七步）

> 核心原则：规格化是双向操作——该减的减，该加的加。
> 减：砍掉冗余/散文/对标。加：补充缺失的入口/属性/链接/铁律/验证。
> 执行顺序：先 Layer 1（蓝图+施工图模板合规），后 Layer 2（规格化砍削）。

```
STEP 0: 判受众
  IDE AI（Trae/Cursor，自由搜项目） → 可砍导航内容，交叉引用即可
  内部 Agent（Pipeline 注入，封闭上下文） → 导航内容必须保留

STEP 0.5: [蓝图专属] Layer 1 合规检查 — 蓝图+施工图模板 v4.0 章节完整性
  0.5.0 内容价值映射 [MUST — B-18 铁律]
    对蓝图每个章节/段落分类：
    ├ 模板必需 — 模板 REQUIRED_SECTIONS 中要求的
    ├ 通用新增 — 所有蓝图都可能需要的 → 推动模板进化(B-15)
    ├ 蓝图特有 — 仅本蓝图需要的 → 保留在特有章节(B-16)
    └ 可砍 — 冗余/对标/散文 → 进入 STEP 2 转化
    未完成分类 = 禁止动手。

  0.5.1 章节完整性检查
    1. 读取蓝图+施工图模板 v4.0
    2. 对照模板要求的章节清单，检查蓝图是否包含所有必需章节
    3. 缺失章节 → 必须补充
    4. 多余章节 → 评估是否为蓝图特有内容(B-16)

  0.5.2 反向进化检查 [MUST — B-15 铁律]
    蓝图中有价值但模板未覆盖的内容：
    ├ 所有蓝图都需要？→ 写入蓝图+施工图模板(通用新增)
    └ 仅本蓝图需要？→ 保留在蓝图特有章节

  所有蓝图统一标准（v4.0）：
  概述 / §1 设计背景与目标 / §2 模块边界
  / §3 架构设计 / §4 接口契约 / §5 约束条件 / §6 错误处理
  / §7 备选方案 / §8 安全考量 / §9 测试策略 / §10 依赖关系
  / §11 产出物目录 / §12 集成目标 / §13 更新内容
  / §14 风险 / §15 后果 / §0 代码对齐验证
  / §16 施工指引 / §17 容量升级 / §18 决策记录 / 治理信息

  Layer 1 不通过 → 不得进入 Layer 2

STEP 1: 搜 — 全项目 Grep + SearchCodebase → 找到目标文件的所有引用和依赖

STEP 1.5: 时态判定 [MUST — 遇到临时时态内容必须执行]
  对蓝图每个章节/段落问：这是"当前事实"还是"从A到B的过程"？
  ├ 永久时态（当前事实）→ 保留，进入 STEP 2
  └ 临时时态（从A到B的过程）→ 检查执行状态：
      ├ 未执行 → 保留（仍是可操作指令），进入 STEP 2
      ├ 部分执行 → 保留未执行部分，删除已执行部分
      └ 已全部执行 → 直接删除（不进入 STEP 2，无转化价值）
      判定方法见第一篇 §0.3 常见临时时态内容表

STEP 2: 转化 [MUST — 任何疑似"散文"段落，必须先过此步才能决定删除]
  问：这段内容能改写成二元规则吗？
  （格式："当/如果 <条件> → 则/必须 <动作>"）
  ├→ 能 → 改写为二元规则，保留。替换原文
  └→ 不能 → 进入 STEP 3 查重

STEP 3: 查重 — 该规则是否已在 L0/L1/L2 中存在？
  YES → 删除，改为引用真源文件（`→ PS-STD-XXX §N`）
  NO  → 保留规则，归类到对应层级

STEP 3.5: 幻觉安全验证 [MUST — 砍掉任何内容前必须过此步]
  问：砍掉这段内容后，一个全新 AI 进项目，会不会：
  a) 不知道某东西在哪？（路径漂移）
  b) 不知道某东西有没有？（存在性幻觉）
  c) 不知道某东西怎么用？（操作幻觉）
  d) 不知道某东西什么时候该用？（触发幻觉）
  全部 NO → 可以砍
  任意 YES → 进入 STEP 3.6 三桶判定

STEP 3.6: 三桶判定 [MUST — 幻觉安全验证未通过的内容，必须分类处置]
  对 STEP 3.5 中任意 YES 的内容，按以下逻辑判定：

  桶1: ✅ 可删除 — 标题+表格列名已自解释，AI不会幻觉
    判定条件：
    - 该信息的核心含义已被标题/表格列名/铁律/其他章节完全覆盖
    - AI仅凭结构上下文即可正确填写
    - 删除后不会导致AI编造或遗漏
    示例：§1.4"运行场景约束"标题+表格已说明用途，⚠️块"AI需要知道模块在什么环境下运行"是重复

  桶2: 🔧 可压缩 — 删掉会漂移，但可以更短
    判定条件（满足任一即入此桶）：
    - 包含区分信号（如"与§6不同：运行时 vs 施工时"）→ 保留区分信号，删除解释
    - 包含防漂移约束（如"frozen不可改，volatile谨慎改"）→ 保留约束，删除解释
    - 包含触发条件（如"版本变更后MUST重新填写"）→ 保留触发条件，删除目的说明
    - 包含时态分类（如"迁移方案属于临时时态"）→ 用[时态:临时]标签替代3行解释
    - 包含判定标准（如"删掉后AI会编造→保留"）→ 保留判定标准，删除与铁律重复的解释
    压缩原则：保留AI会漂移的部分，删除AI不会漂移的部分

  桶3: 🛡️ 必须保留 — 删掉会导致幻觉或漂移，且无法压缩
    判定条件（满足任一即入此桶）：
    - 删掉后AI会重复犯已知错误（如§5.1"蓝图只保留约束本身"防止AI重新加回"原因"列）
    - 删掉后AI会对不同章节产生混淆（如§10.4自动化粒度表防止AI对所有蓝图填一样规格）
    - 属于不可删清单中的18类内容
    - 属于施工声明（铁律/安全删除/必备链接/治理信息）

  判定优先级：桶1 > 桶2 > 桶3（优先尝试删除，其次压缩，最后保留）

STEP 4: 标注可执行性 [MUST — 规格化后的每条规则必须标注执行方式]
  对文件中的每条核心规则，标注：
  - 可发现: 入口在哪？（L0/L1/registry/触发关键词）
  - 可强制: 有没有门禁？（GateEngine/脚本/无）
  - 可审计: 审计日志在哪？（Session Log/无）

STEP 5: 补充缺失 [MUST — 规格化不只是砍，也是补]
  对照第一篇 §3 必须补充清单逐项检查。缺少 → 补充。

STEP 5.5: [代码文件专属] 十字段验证
  对照第一篇 §5.1 字段表逐项检查代码文件头部。
  缺失 → 必须补充。
  [BLUEPRINT] 指向的蓝图不存在 → 标记为孤儿文件。

STEP 6: 审计 — 对照第一篇 §6 常见反模式自查
```

## §9 按文档类型规格化策略

### 9.1 IDE 规则类（.trae/rules/、AGENTS.md、CLAUDE.md）

**目标**：L0 自含（≤500 tokens）+ L1 触发加载。**保留**：表格、命令、路径、约束、状态不变量。**砍掉**：原理、对标、AI 意识植入、触因/根因、修订历史。**必须补充**：可达性入口、触发条件。

**分层判定（四问法）**：
| Q | 问 | YES → |
|---|-----|-------|
| 1 | 不知道会造成不可逆破坏？ | L0 |
| 2 | 是机械命令？ | L0 |
| 3 | 是"为什么"/背景？ | L2 |
| 4 | 是特定场景流程？ | L1 |

### 9.2 蓝图类（blueprint.md）

## §10 安全原则

| 类型 | 内容 |
|------|------|
| **防幻觉最高** | **防幻觉/防漂移 > 一切其他规则**。删掉会导致幻觉或漂移的内容，即使它是"理由""背景""原因"也必须保留。此原则优先级高于"AI只需规则不需理由" |
| **核心原则** | 规格化是双向操作：该减的减 + 该加的加 + 反向进化。只减不加 = 越规格化越脆弱。削足适履 = 丢失实战经验 |
| **AI只需规则** | 不会导致幻觉的理由/背景/原因可删。区分信号（"与§X不同"）= 规则边界，不是理由，不可删 |
| **转化优先** | 读到散文 → 先试转化为二元规则 → 能转化就保留；不能转化才判定砍/留。砍是最后手段，不是默认操作 |
| **幻觉安全** | 砍前必须通过四问验证（路径漂移？存在性幻觉？操作幻觉？触发幻觉？）。砍掉防幻觉规则 = 重新引入幻觉 |
| **三桶判定** | 四问验证未通过的内容，MUST 按 STEP 3.6 三桶判定分类处置：桶1可删除（标题+表格自解释）/桶2可压缩（保留区分信号+防漂移约束，删除解释）/桶3必须保留（删掉导致幻觉且无法压缩）。判定优先级：桶1>桶2>桶3 |
| **可达性铁律** | 规格化后的文件 MUST 在 L0/L1/registry 中有入口。0%可达 = 规格化未完成 |
| **可执行性铁律** | 规格化后的规则 MUST 标注执行方式：AI自觉 / 脚本门禁 / 策略引擎。纯 MD 声明且无执行机制 = 规格化未完成 |
| **补充铁律** | 规格化后 MUST 对照第一篇 §3 检查并补充缺失项 |
| **反向进化铁律** | 蓝图中有价值但模板未覆盖的内容 MUST NOT 以"不符合模板"为由删除（B-14）。必须先分类再处置 |
| **价值优先铁律** | 规格化前 MUST 建立内容价值映射（B-18）。未分类 = 禁止动手 |
| **裁决原则** | 不确定 → 保留。宁可多留，不可误删 |
| **执行原则** | 每次只改一个文件，改完确认再下一个 |

## §11 规格化后步骤

```
1. 更新 depends_on 声明（新增/移除引用）
2. python scripts/governance/sync_rule_registry.py
3. 在 frontmatter 中标记: codification_level: L{0~5} + codification_at: 日期
4. 跑 DriftDetector 确认无新增漂移
5. [可达性验证] 确认文件在 L0/L1/registry 中有入口
6. [可执行性验证] 确认核心规则标注了执行方式
7. [补充验证] 确认第一篇 §3 必须补充清单全部完成
```

## §12 成熟度参考

> 规格化的长期目标是让规则从被动文本变成主动执行。以下 6 维成熟度模型仅供参考——日常规格化对照第一篇执行即可。

| 等级 | 名称 | 条件 | 遵从率 |
|:---:|------|------|:---:|
| L0 | 被动文本 | 规则写在 MD 中，无任何执行机制 | ~30% |
| L1 | 可发现 | 在 L0/L1/registry 中有入口 | ~50% |
| L2 | 可强制 | 有 Python 门禁脚本强制执行 | ~85% |
| L3 | 可证明 | 执行后能证明遵守了规则 | ~95% |
| L4 | 可注入 | 规则自动注入 AI 工作计划 | ~98% |
| L5 | 可进化 | 规则根据反馈自动进化 | ~99% |

**当前目标**：所有规则文件 MUST 达到 L1（可发现），核心规则 MUST 达到 L2（可强制）。
