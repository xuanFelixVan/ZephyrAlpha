# 系统合格判定标准

> **目的**：定义 ZephyrAlpha 系统在"工程基础""架构专业性"两个维度的合格判定标准。供 AI session 自评和架构门禁参考。量化策略结果层标准（夏普率等）属于业务层，不在本文档范围。
>
> **来源**：提取自 `项目目标/project-qualification-standard.md` v0.2.0（2026-04-26）。

---

## §1 常见误区澄清

**"模块数量"本身几乎不说明任何水平。**

模块数量既可能代表复杂度高，也可能代表拆分过度、设计混乱。顶级量化系统有的模块很多，但也有极其精简、靠抽象和复用取胜的。

**核心原则**：模块数量 ≠ 系统水平。

---

## §2 系统合格判定框架

### §2.1 工程层——基础是否合格

系统必须满足以下基础工程要求：

| 检查项 | 合格标准 | 验证方式 |
|--------|---------|---------|
| 模块边界清晰 | 模块间低耦合、高内聚，无循环依赖 | 依赖图分析 |
| 统一日志/Tracing | 全链路可追踪，支持上下文传递 | 日志审计 |
| 回测&实盘一致性 | 同一套代码逻辑，不同执行模式 | 回归测试 |
| 异常处理机制 | 单点故障不扩散，有降级策略 | 混沌测试 |
| 数据质量校验 | 价格跳空检测、重复数据检测、时间戳一致性 | 数据质量报告 |
| 延迟监控与 SLI | 端到端延迟分布（P50/P99/P99.9）可观测 | 监控仪表盘 |

> **判定规则**：本层任何一项不满足 = 系统尚未达到"工程级"门槛。

### §2.2 架构层——是否专业

关键看 5 个核心能力：

| 序号 | 能力项 | 合格标准 |
|------|--------|---------|
| ① | 数据流标准化 | 市场数据 → 特征 → 信号 → 决策 → 执行，链路清晰 |
| ② | 统一消息/数据总线 | 基于标准化总线（事件驱动/数据流/混合均可），非硬编码调用 |
| ③ | 可扩展性 | 新增策略无需修改 20 个模块 |
| ④ | 统一风控层 | 风险敞口集中管控，非各策略自行处理 |
| ⑤ | 回放&仿真 | 可复现任意历史日期的决策过程 |

**架构模式说明（2026年共识）**：

| 架构模式 | 适用场景 | 2026年趋势 |
|----------|----------|------------|
| 事件驱动 (EDA) | 高频、复杂事件处理 | 仍主流，但混合模式增多 |
| 数据流驱动 (Dataflow) | 中低频、批量特征计算 | 因 Apache Flink/Beam 成熟，占比上升 |
| 请求-响应 (RPC) | 策略配置、风控查询 | 与 EDA 混合使用 |
| **混合架构** | 大型机构 | **2026年主流**，非纯 EDA |

> **判定规则**：满足 5 项中的至少 4 项 = "专业级系统"。

## §3 系统水平综合公式

```
系统水平 = 架构成熟度 × 策略质量 × 风控能力 × 执行稳定性
```

**不是**：
```
模块数量 = 水平 ❌
```

## §4 顶级机构级标准（7 问法）

| 序号 | 问题 | 合格标准 |
|------|------|---------|
| 1 | 是否可以无人值守运行一周？ | 全自动运维，无需人工干预 |
| 2 | 是否可以回放任意一天并 100% 复现决策？ | 决策完全可回溯 |
| 3 | 新策略是否可以在 1 天内接入？ | 标准化接入流程 |
| 4 | 是否可以同时跑 100+ 策略？ | 多策略并行无冲突 |
| 5 | 是否有统一风险敞口控制？ | 全局风控，非分散管理 |
| 6 | 交易成本是否可控？ | 冲击成本 + 佣金 + 滑点 < 收益的 20% |
| 7 | 是否满足合规审计要求？ | 订单簿快照、决策日志、风控触发记录完整 |

> **判定规则**：7 项全部满足 = 接近机构级系统。

## §6 模块数量与系统水平的关系

| 情况 | 说明 |
|------|------|
| 模块多 + 结构清晰 | 有"机构级雏形" |
| 模块多 + 调用混乱 | "复杂，但不高级" |
| 模块少 + 抽象复用强 | 高水平设计 |
| 模块少 + 功能单薄 | 玩具项目 |

**关键判断依据**：模块是否正交、是否有清晰分层、是否有统一数据流/事件流。
