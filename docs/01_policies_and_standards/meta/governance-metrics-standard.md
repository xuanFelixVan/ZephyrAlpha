# ZephyrAlpha 治理度量标准

> **module_id**: PS-STD-006 | **version**: 1.1.1 | **status**: active | **layer**: cross_layer

---

## 1. 目的与范围

### 1.1 目的

定义 ZephyrAlpha 规则体系的**可量化健康度指标**，回答一个核心问题：**"规则体系在变好还是变坏？"**

> **对标**：
> - ISO 42001 §9.1：AI 管理系统必须定期评估绩效
> - COBIT 2019 EDM05：绩效管理——确保治理目标达成可被度量
> - ITIL 4 Service Value Chain：度量驱动持续改进
> - Kubernetes SIG-Arch：Conformance 报告通过率作为生态健康指标

### 1.2 适用范围

适用于 `01_policies_and_standards/` 下所有规则文件。

### 1.3 术语

| 术语 | 含义 |
|------|------|
| **KPI** | Key Performance Indicator——关键绩效指标 |
| **基线** | 首次度量时建立的参照值 |
| **告警阈值** | 触发治理告警的 KPI 边界值 |
| **度量周期** | 两次度量之间的时间间隔 |

---

## 2. 核心 KPI（6 项）

### 2.1 KPI 总览

| # | KPI | 含义 | 度量方式 | 越低越好/越高越好 |
|:--:|------|------|---------|:---:|
| K1 | 规则合规率 | frontmatter 完全符合 PS-STD-001 的文件比例 | 自动化扫描 | ↑ 越高越好 |
| K2 | 规则新鲜度 | `date` 在 30 天内的文件比例 | 自动化扫描 | ↑ 越高越好 |
| K3 | 引用链健康度 | `depends_on` 引用全部指向存在文件的比例 | 自动化扫描 | ↑ 越高越好 |
| K4 | 格式错误密度 | 每千行规则文本中的格式错误数（如分隔符错误、类型错误） | 自动化/人工 | ↓ 越低越好 |
| K5 | 一致性违规率 | stability↔ai_autonomy 等一致性约束被违反的比例 | 自动化扫描 | ↓ 越低越好 |
| K6 | SSoT 冲突数 | 同一概念在多个文件中被定义的次数 | 人工审查 | ↓ 越低越好 |

### 2.2 K1：规则合规率

| 属性 | 值 |
|------|-----|
| **公式** | `合规文件数 / 总文件数 × 100%` |
| **合规定义** | frontmatter 所有必填字段存在 + 值在受控词表中 + 类型正确（`version` 为 string） |
| **数据源** | PS-STD-001 §2.2（分阶段闸门）+ §2.6（一致性约束） |
| **当前基线** | 待首次度量后建立 |
| **告警阈值** | < 80% |
| **目标** | ≥ 95% |

### 2.3 K2：规则新鲜度

| 属性 | 值 |
|------|-----|
| **公式** | `date 在 30 天内的文件数 / 总文件数 × 100%` |
| **新鲜定义** | `date` 字段值与度量日期的差距 ≤ 30 天 |
| **注意** | `frozen` 文件不强制新鲜度（稳定型规则不需要频繁更新） |
| **当前基线** | 待首次度量后建立 |
| **告警阈值** | < 30%（活跃文件） |
| **目标** | ≥ 60%（活跃文件） |

### 2.4 K3：引用链健康度

| 属性 | 值 |
|------|-----|
| **公式** | `所有 depends_on 引用目标存在且版本匹配的文件数 / 有 depends_on 的文件数 × 100%` |
| **健康定义** | `depends_on` 中每个引用指向的文件存在且路径正确 |
| **补充检查** | 引用链深度必须 = 1 层（DOC-009 死规则：A→B 直接声明，禁止 A→B→C） |
| **当前基线** | 待首次度量后建立 |
| **告警阈值** | < 90% |
| **目标** | 100% |

### 2.5 K4：格式错误密度

| 属性 | 值 |
|------|-----|
| **公式** | `格式错误总数 / 总规则行数 × 1000` |
| **格式错误示例** | frontmatter 分隔符非 `---`、YAML 非法转义、`version` 为 number 类型 |
| **数据源** | PS-STD-012 §2.1（V1 阻断条件） |
| **当前基线** | 待首次度量后建立 |
| **告警阈值** | > 5 错误/千行 |
| **目标** | 0 错误/千行 |

### 2.6 K5：一致性违规率

| 属性 | 值 |
|------|-----|
| **公式** | `一致性约束被违反的文件数 / 受约束的文件数 × 100%` |
| **检查约束** | `frozen` → `immutable_core`（单向强制） |
| **数据源** | PS-STD-001 §2.6 + PS-STD-004 §6.3 |
| **当前基线** | 待首次度量后建立 |
| **告警阈值** | > 5% |
| **目标** | 0% |

### 2.7 K6：SSoT 冲突数

| 属性 | 值 |
|------|-----|
| **公式** | `被多次定义的核心概念数`（手动计数） |
| **冲突判定** | 同一概念在 glossary.md 外被 ≥ 2 个文件定义 |
| **数据源** | glossary.md（META-GLS-001）作为仲裁基准 |
| **当前基线** | 待首次度量后建立（已知：`SSoT` 曾在 PS-STD-003 和 PS-STD-001 中被独立定义，现已统一） |
| **告警阈值** | > 3 个冲突 |
| **目标** | 0 |

## 3. 度量周期与责任

| KPI | 度量方式 | 周期 | 执行者 | 报告对象 |
|:---:|---------|:---:|--------|---------|
| K1~K3 | 自动化扫描 | 每次 pre-commit | CI 脚本 | Owner |
| K4~K5 | 自动化扫描 | 每次 pre-commit | CI 脚本 | Owner |
| K1~K5 | 趋势报告 | 每月 | AI 汇总 | Owner |
| K6 | 人工审查 | 每季度 | Owner | Owner（自审） |

---

## 4. 报告格式

月度度量报告应有以下结构：

```markdown
# ZephyrAlpha 治理度量月报 —— YYYY-MM

## KPI 快照
| KPI | 本月值 | 上月值 | 趋势 | 状态 |
|-----|--------|--------|:---:|:---:|

## 趋势分析
- 变化 > 10% 的 KPI 的原因分析（5 Whys）
- 是否触发告警阈值

## 改进建议（如适用）
- 建议的规则修改
- 建议的新规则
```

---

## 5. 告警响应流程

```
KPI 触发告警阈值 → 自动通知 Owner → Owner 判定：

A. 误报（度量脚本故障）：
   → 修复度量脚本 → 重新度量

B. 真实退化（规则体系正在变坏）：
   → 5 Whys 根源分析 → 诊断反转验证（初始诊断与深挖结论一致？不一致→追问"为什么错了？"）→ 制定修复计划 → 执行修复 → 下次度量验证

C. 阈值不合理（规则体系在变好，但阈值太严）：
   → Owner 调整告警阈值 → 更新本标准
```

---

## 6. 禁止行为

- **禁止**：无理由跳过月度度量周期
- **禁止**：手动修改度量数据以"美化"报告
- **禁止**：告警触发后超过 14 天不分析、不修复
- **禁止**：连续 3 个月同一 KPI 在告警状态而不调整策略

---

## 7. 基线建立流程

首次度量前执行：

1. **确定度量范围**：列出 `01_policies_and_standards/` 下所有规则文件
2. **执行全量扫描**：对 K1~K6 逐项运行度量脚本/人工审查
3. **记录基线值**：将各 KPI 首次度量值写入本标准 §2 各 KPI 的"当前基线"字段
4. **校准阈值**：如基线值已低于告警阈值，Owner 重新评估阈值合理性
5. **产出首次报告**：按 §4 格式产出基线报告

**基线后的首次度量不计入"趋势恶化"判定**——它只是起点。

---

## 8. 新增 KPI 流程

Owner 认为需要新增度量指标时：

1. **提议**：在 Session Log 中提议新 KPI，格式：`新增KPI: {编号} / {名称} / {公式} / {目标} / {告警阈值} / {对标框架}`
2. **审核**：确认新 KPI 不与现有 KPI 重复、度量方式可行（有可自动化的数据源）
3. **添加**：在本标准 §2 中新增 KPI 条目，更新 §3 度量周期表
4. **实现**：CI 度量脚本增加新扫描规则
5. **回填基线**：首次运行建立新 KPI 基线

**禁止**：添加无法自动度量的 KPI（AI 自行掌握尺度会导致数据不可比）。
