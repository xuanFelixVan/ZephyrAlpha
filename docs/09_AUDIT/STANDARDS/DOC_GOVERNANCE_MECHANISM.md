## 二、文档命名规范

### 2.1 命名原则

**核心原则**:
1. **职责反映**: 文件名必须反映文档核心职责
2. **英文优先**: 使用英文命名，避免中文
3. **版本标识**: 重要文档需包含版本号
4. **层级清晰**: 使用下划线分隔层级

### 2.2 命名格式

**蓝图文档**: `{MODULE_NAME}_BLUEPRINT.md`
```
STRATEGY_ENGINE_BLUEPRINT.md
RISK_MONITORING_BLUEPRINT.md
```

**技术规格书**: `{MODULE_NAME}_TECHNICAL_SPECIFICATION.md`
```
SCENARIO_ANALYZER_TECHNICAL_SPECIFICATION.md
STRESS_TEST_REPORTER_TECHNICAL_SPECIFICATION.md
```

**使用指南**: `{MODULE_NAME}_USAGE_GUIDE.md`
```
PORTFOLIO_OPTIMIZER_USAGE_GUIDE.md
```

**API文档**: `{MODULE_NAME}_API_REFERENCE.md`
```
LAYER7_REPORT_API_REFERENCE.md
```

### 2.3 禁止的命名

❌ 禁止使用:
- 中文文件名
- 空格字符
- 特殊字符（除下划线、连字符外）
- 过于通用的命名（如 `README.md`、`DOCUMENT.md`）

## 三、文档归档流程

### 3.1 归档触发条件

**自动归档**:
- 文档超过3个版本
- 文档被新文档替代
- 文档职责已合并到其他文档

**手动归档**:
- 审计发现重复文档
- 职责边界不清晰
- 文档长期未更新（>6个月）

### 3.2 归档操作流程

```
1. 识别需要归档的文档
     ↓
2. 确认保留的文档版本
     ↓
3. 移动文档到归档目录
     ↓
4. 添加归档后缀（_ARCHIVED）
     ↓
5. 创建归档说明文档
     ↓
6. 更新索引（移除归档文档）
     ↓
7. 更新相关文档的引用
```

### 3.3 归档目录结构

```
docs/06_ARCHIVE/
├── duplicate_documents/
│   └── {日期}_{审计名称}/
│       ├── {文档名}_ARCHIVED.md
│       └── ARCHIVE_README.md
├── deprecated/
│   └── {日期}_{模块名}/
│       └── ...
└── legacy/
    └── v4_development/
        └── ...
```

## 四、定期审计机制

### 4.1 审计频率

| 审计类型 | 频率 | 范围 | 重点 |
|---------|------|------|------|
| 快速扫描 | 每周 | Layer 7 | 职责重叠、重复文档 |
| 深度审计 | 每月 | 全系统 | 五大原则合规性 |
| 专项审计 | 每季度 | 指定模块 | 文档质量评估 |

### 4.2 审计清单

**每周快速扫描**:
- [ ] 检查是否有新增重复文档
- [ ] 检查职责边界是否清晰
- [ ] 检查索引是否完整

**每月深度审计**:
- [ ] 检查五大原则合规性
- [ ] 检查命名规范性
- [ ] 检查版本管理
- [ ] 检查文档时效性

### 4.3 问题跟踪

**问题等级定义**:
- 🔴 P0级: 职责混乱、重复文档、安全风险
- 🟡 P1级: 索引不完整、命名不规范
- 🟢 P2级: 格式问题、次要优化

**问题处理时限**:
- P0级: 立即处理（≤24小时）
- P1级: 本周处理（≤1周）
- P1级: 本月处理（≤1月）

## 五、职责边界定义

### 5.1 文档层次结构

```
第一层: 索引文档
├── docs/INDEX.md (主索引)
└── docs/{目录}/INDEX.md (子目录索引)

第二层: 蓝图文档 (概述层)
└── docs/05_IMPLEMENTATION/06_CONSTRUCTION_DOCS/01_BLUEPRINTS/
    └── {MODULE}_BLUEPRINT.md

第三层: 技术规格书 (详细层)
└── docs/05_IMPLEMENTATION/05_TECHNICAL_SPECIFICATIONS/
    └── {MODULE}_TECHNICAL_SPECIFICATION.md

第四层: 使用指南 (应用层)
└── docs/05_IMPLEMENTATION/05_TECHNICAL_SPECIFICATIONS/
    └── {MODULE}_USAGE_GUIDE.md

第五层: API文档 (接口层)
└── docs/05_IMPLEMENTATION/05_TECHNICAL_SPECIFICATIONS/
    └── {MODULE}_API_REFERENCE.md
```

### 5.2 各层职责

| 层级 | 文档类型 | 职责 | 内容范围 |
|------|---------|------|---------|
| 第一层 | 索引文档 | 导航入口 | 链接集合、概览 |
| 第二层 | 蓝图文档 | 架构设计 | 模块概述、架构图、实施路径 |
| 第三层 | 技术规格书 | 详细设计 | 接口定义、数据模型、算法实现 |
| 第四层 | 使用指南 | 应用说明 | 使用示例、最佳实践 |
| 第五层 | API文档 | 接口参考 | API端点、参数说明 |

### 5.3 禁止事项

❌ **禁止在蓝图文档中**:
- 包含详细代码实现
- 包含完整API定义
- 复制技术规格书内容

❌ **禁止在技术规格书中**:
- 包含使用示例代码（应放在使用指南）
- 重复蓝图文档的概述内容
- 包含与本模块无关的内容

## 六、新增文档流程

### 6.1 创建前检查

1. **职责检查**: 确认文档职责是否已有文档承担
2. **命名检查**: 确认文档命名符合规范
3. **位置检查**: 确认文档放在正确目录

### 6.2 创建时要求

1. **必须包含YAML头部**:
```yaml
---
module_id: {MODULE_ID}
version: 1.0.0
status: Active
created_date: 2026-04-03
owner: 负责人
---
```

2. **必须包含目录**: 便于导航
3. **必须引用相关文档**: 建立文档关系

### 6.3 创建后操作

1. **更新索引**: 在对应INDEX.md中添加链接
2. **更新System_Manifest.md**: 如需要全局索引
3. **通知相关人员**: 如有影响范围

## 七、违规处理

### 7.1 自动检测

**工具检测**:
- 文档重复度检测工具
- 链接检查工具
- YAML验证工具
- 命名规范检查工具

### 7.2 人工审查

**审查场景**:
- 新增文档审批
- 定期审计
- 代码审查中的文档检查

### 7.3 违规处罚

**轻微违规** (P2级):
- 口头警告
- 要求限期整改

**中等违规** (P1级):
- 书面警告
- 暂停文档创建权限
- 要求提交整改计划

**严重违规** (P0级):
- 冻结文档权限
- 强制归档或删除
- 纳入绩效考核
