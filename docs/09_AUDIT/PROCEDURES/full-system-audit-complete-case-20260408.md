## 第三部分：重复内容——分类、判定与处理办法



### 3.1 重复类型（便于对号入座）



| 类型 | 典型表现 | 检测线索 |

|------|----------|----------|

| **A. 精确或近精确复制** | 大段相同 Markdown、仅改标题/日期 |  diff、段落 hash、连续相同小节 |

| **B. 语义重复（双真理）** | 两篇都是某模块「权威说明」，表述不同 | 同一 `module_id` 主题、INDEX 链到多篇「主文档」 |

| **C. 版本链未收敛** | `FINAL`、`V24`、`SUMMARY` 多份并存于活跃目录 | 文件名关键词、同一审计事件多报告 |

| **D. 归档未隔离** | 旧稿仍在 `docs/01_FRAMEWORK` 等与现行架构冲突 | 日期旧、`status: Deprecated` 缺失 |

| **E. 模板化重复** | 多个子目录内 INDEX/README 结构相同且正文高度雷同 | `08_HUMAN_AI_INTERFACE` 等多子目录场景 |

| **F. 跨区重复** | 同一段落在 `09_AUDIT/REPORTS` 与 `05_IMPLEMENTATION/.../audit_state` 再次整文件出现 | 标题或「审计结论」段完全一致 |



### 3.2 判定流程（建议顺序）



1. **是否同一主题、同一受众、同一生命周期？**  

   - 否 → 可能是「相关但非重复」，改为划清**职责边界**（在各自文档写「不负责」并互链）。  

   - 是 → 进入下一步。  

2. **是否有一篇已明确为入口（INDEX / System_Manifest / ARCHITECTURE 指向）？**  

   - 是 → 该篇优先作为 **Canonical（权威篇）** 候选。  

   - 否 → 先补入口再合并，避免合并后仍无人知道读哪篇。  

3. **较新的一篇是否仅为「过程稿」？**（如单次审计 Round N）  

   - 是 → **过程稿**迁入 `docs/06_ARCHIVE/...` 或 `09_AUDIT/REPORTS` 下按日期子目录；活跃目录只保留 **一篇综述** 或链到归档。  

4. **是否仍需保留历史措辞证据？**（合规、对账）  

   - 是 → **禁止硬删除**，使用 `git mv` 至 archive，Canonical 中加「历史版本见…」。  

   - 否 → 备份 tag 存在时，可删除重复文件，但须在 `REMEDIATION_BACKLOG` 记录路径与原因。



### 3.3 处理动作矩阵（重复怎么办）



| 情形 | 推荐动作 | 具体操作要点 |

|------|----------|--------------|

| 两篇真重复，保留一篇即可 | **合并 + 归档次要篇** | 将独有章节并入 Canonical；次要篇 `git mv` 到 `docs/06_ARCHIVE/...`，顶部 YAML 设 `status: Archived`，`supersedes` 或正文说明替代关系 |

| 多篇审计报告同一事件 | **保留 1 篇综述 + 其余归档** | 综述放 `09_AUDIT/REPORTS` 或 `STATE`；其余按日期进 `06_ARCHIVE/202604xx_...` |

| 语义重复但各有侧重 | **拆分职责，不硬合并** | Canonical 保留主链路；另一篇改名为 `*_SUPPLEMENT.md` 或移入更合适目录，互写「边界」 |

| 仅 INDEX/模板句重复 | **抽取公共片段** | 维护一段「标准说明」单篇，各 INDEX 链至该篇，避免复制粘贴 |

| 根目录 `temp_*.md` 与正式蓝图重复 | **归位或删除** | 内容已进正式路径则删 temp；否则合并后删 |

| `module_id` 冲突 | **全局唯一** | 保留 Canonical 的 id；他篇改 id 或归档停用 id（在 STATE 中登记旧 id→新 id） |



### 3.4 Git 与删除纪律（重复清理时强制）



1. 打标签：`audit-snapshot-YYYYMMDD`（见分方案第三节）。  

2. **优先 `git mv`** 到 `docs/06_ARCHIVE/...`，便于历史追溯。  

3. 确需删除：仅在 tag 已存在且 backlog 已记录的前提下执行；**禁止**在未提交状态下批量 `rm`。  

4. 合并后：更新 **双方父目录 `INDEX.md`**、修正 **入链**（死链扫描）。  



### 3.5 Canonical 文档内建议增加的「防重复」段落（可选）



在权威篇增加固定小节（中文撰写即可）：



```markdown

## 文档关系与替代

- **权威版本**：本文。

- **已归档/历史**：链接到 `docs/06_ARCHIVE/.../xxx.md`（原因：过程稿/旧 Layer 叙事）。

- **不负责**：…（指向其他 Canonical）

```



### 3.6 交给 AI（如 GLM-5）做「重复裁决」时的输入模板



```text

禁止建议无 Git tag 时物理删除。输出表格：路径|与Canonical关系|动作|备注。
```

## 第七部分：Git 对象与历史——「工作区之外」的有价值内容



仅审计当前 `HEAD` 树**不够**：有价值段落可能留在**历史提交、已删除路径、未合并分支**中。本部分可与分方案 **阶段 I** 合并执行。



### 7.1 审计目标



| 目标 | 说明 |

|------|------|

| **误删恢复候选** | 某路径曾在 `audit-snapshot-*` 或旧 tag 存在，当前消失，需判断是否应恢复或归档引用 |

| **未合并分支上的文档** | `backup/*`、`feature/*` 等分支是否含有未合入 `main` 的独有价值蓝图或报告 |

| **历史版本对照** | 同一文件在重大架构变更前后的差异，用于判断「现行文档是否丢段」 |

| **大文件 / 二进制** | 若文档以 PDF/附件形式存在，是否在 Git 历史中占用过大（可考虑 Git LFS 策略，个人项目可选） |



### 7.2 推荐命令（在仓库根执行，结果粘贴至审计报告）



```bash

# 与备份标签相比，哪些路径被删除（状态 D）

git diff --name-status audit-snapshot-YYYYMMDD HEAD



# 某路径在全历史中的提交（判断「最后谁改过」）

git log --oneline --follow -- path/to/file.md



# 列出曾删除过的 blob 相关记录（需结合具体路径）

git log --diff-filter=D --summary



# 未合并入当前分支的提交（是否有「文档-only」提交未合并）

git branch -a --no-merged



# 近期 HEAD 移动（误操作恢复）

git reflog --date=local -20

```



### 7.3 价值判定（写入 `DELETED_FILES_REVIEW_*.md`）



对每条「曾存在→不存在」或「仅分支上存在」的路径：



1. **是否仍与现行架构一致？** 否 → 归档引用即可，不必恢复正文。  

2. **是否被合并进其他文件？** 是 → 在 Canonical 中写「内容已吸收自 …（commit）」。  

3. **是否合规/对账需要留痕？** 是 → **禁止仅依赖 reflog**，应 `git show <commit>:path` 取证后迁入 `docs/06_ARCHIVE/`。  

4. **恢复方式**：优先在**新分支**上 `git checkout <good-commit> -- path` 再审阅后合并，避免污染主分支历史。



### 7.4 与「清单文件」的关系



`MD_FILES_BY_SUBDIRECTORY_*.md` 只反映**当前工作区**；Git 审计产出单独表格：**历史路径 | 最后提交 | 当前状态 | 建议**。

## 第八部分：审计过程中还可能遇到哪些问题（技术与管理）



以下为个人 + AI 维护场景下的**高发问题**，建议在 L1/L2 中显式勾选。



### 8.1 编码（Encoding）



| 现象 | 风险 | 处理 |

|------|------|------|

| 非 UTF-8（如 GBK）混入 | 部分工具与 AI 读乱码、检索失败 | 统一为 **UTF-8**（是否带 BOM 由编辑器与 `pre-commit` 统一）；仓库内已有 `encoding` 类脚本可对照运行 |

| 乱码「」残留 | 历史损坏段落误导读者 | 标 P1：修复或整段删除并指向归档副本 |

| 同一文件混用不同编码片段 | diff 困难 | 整文件转码后一次性提交 |



### 8.2 文档名称（Naming）



| 现象 | 风险 | 处理 |

|------|------|------|

| `FINAL`、`V2`、`copy`、`temp_` 堆叠 | 用户不知读哪篇 | 收敛 Canonical + 归档或重命名 |

| 空格与非常用字符 | 跨平台、脚本引用失败 | 改为 `SCREAMING_SNAKE` 或与目录内惯例一致 |

| 大小写仅差一字母 | Linux/CI 上链接失效 | 统一大小写并全局替换链接 |



### 8.3 相关文件的联动更新（Ripple / 入链）



| 场景 | 风险 | 处理 |

|------|------|------|

| 移动/重命名单篇文档 | 死链、INDEX 漏改 | **变更清单**：该文 + 所有 `](...)` 指向它的文件 + 父 `INDEX.md` + `parent_document` |

| 合并两篇 | 第二篇入链全部改指向 Canonical | 用仓库内 `link`/`reference` 类脚本扫描 |

| YAML `parent_document` 指向已删路径 | L3 元数据失效 | 合并批次内一并修 |



### 8.4 文档与程序、脚本的重新归类



| 场景 | 建议 |

|------|------|

| 某 `scripts/*.py` 实为「文档生成器」 | 在 `docs/09_AUDIT/TOOLS` 或实施手册中**登记说明**，避免「代码区」与「文档流程」脱节 |

| 规范写在 `*.md` 但检查在 `*.py` | 在规范文增加「自动化检查：脚本路径」**双向互链** |

| `src/` 内注释与 `docs/` 冲突 | 纳入可选 **doc-code** 抽样（分方案阶段 4） |



### 8.5 文件夹治理与「是否像专业机构」



| 现象 | 说明 |

|------|------|

| **双轨目录**（如根目录 `05_IMPLEMENTATION/` 与 `docs/05_IMPLEMENTATION/`） | 不符合「单一事实来源」；需审计后合并或明确「仅归档侧」 |

| **稀疏目录**（单文件长期独占一层） | 导航成本高；可合并到主题子目录或上移 |

| **分类交叉**（同一文档可归入多类） | 用「主分类目录 + front matter `applicable_scope` + 互链」表达，避免物理复制 |

| **`06_ARCHIVE` 根散落过多** | 与机构「归档亦要有索引」一致；应分主题子夹并维护 archive 根 `INDEX.md` |



### 8.6 路径深度过深



| 指标 | 建议 |

|------|------|

| 从 `docs/` 起算 **≥6～7 层** 且频繁访问 | 标记为 P2：考虑主题聚合或中间层 `INDEX` |

| 深度来自日期归档 `202604xx_*` | 一般可接受；重点保证**可检索**（索引或标签） |



**可选自动化**：对清单中每条路径计算深度分布，输出「最深 50 条路径」供治理 backlog。

## 第九部分：按专业机构审计方式——当前方案还缺什么、如何补齐



以下为**典型**证券/量化机构文档与信息控制实践的抽象（不同公司命名不同），用于**对照自查**，而非要求个人仓库照搬全套。



### 9.1 机构侧常见能力（摘要）



| 能力域 | 典型做法 |

|--------|----------|

| **独立性与职责分离** | 编写人 ≠ 唯一复核人；敏感发布双人复核 |

| **抽样与全覆盖的结合** | 关键政策全量；长尾按风险分层抽样 |

| **证据留存** | 审计底稿、版本、邮件/审批记录可追溯 |

| **变更管理** | 文档变更与系统变更有 ticket/变更单对应 |

| **访问与分发** | 权限分级、对外版本与水印（个人仓库通常不适用） |

| **定期复审** | 年度/季度复审日历与过期策略 |

| **自动化控制** | CI 中链接检查、合规词、秘密扫描 |



### 9.2 与你当前方案的映射（已有）



| 机构能力 | 本仓库方案中已有对应物 |

|----------|------------------------|

| 清单与分批 | `MD_FILES_BY_SUBDIRECTORY_*.md` + 阶段 A～I |

| 版本与回溯 | Git tag、`06_ARCHIVE`、重复与 Canonical 策略 |

| 自动化辅助 | `scripts/` 大量治理脚本、可选 pre-commit |

| 元数据 | YAML、`module_id`、INDEX 体系 |

| 删除与误删 | tag 对比、第七部分 Git 历史、归档优先 |



### 9.3 仍建议补齐的「缺口」（按性价比排序）



| 缺口 | 风险 | 个人可落地的补齐 |

|------|------|------------------|

| **无独立第二人复核** | AI 与作者盲区 | 对 **P0 文档**（`ARCHITECTURE`、`docs/INDEX`、核心风控蓝图）固定「二次会话」：不同 Prompt/模型交叉只读；或打印清单人工勾选 |

| **无正式变更单（ticket）** | 文档与代码变更脱钩 | 在 `REMEDIATION_BACKLOG` 或 `docs/09_AUDIT/STATE/` 增加 **CHG-编号**，合并 PR/commit message 引用同一编号 |

| **无定期复审日历** | 文档静默过期 | 在 front matter 用 `last_reviewed`（可选）+ 季度提醒（日历/脚本 `periodic_document_review.py` 若已存在则对接） |

| **CI 未强制文档门控** | 死链反复进入主分支 | 在 CI 跑 `pre_commit_link_checker` 或等价脚本（失败则阻断合并） |

| **抽样方法未书面化** | 长尾遗漏无法解释 | 在审计报告中写清：**本次抽样规则**（如按目录分层随机 10%、或仅审含 `BLUEPRINT` 的文件） |

| **外部依赖与密钥** | 文档中误提交秘密 | 机构用 secret scan；个人至少 grep 高熵串 + `.env` 不入库（与代码审计合并） |

| **业务连续性** | 单点仓库 | 机构有多副本；个人至少 **远程 + 定期 tag**（你已部分做到） |



### 9.4 结论



当前方案在**文档工程**层面已覆盖 L1～L3、重复、Git 历史、编码与目录治理等**主要技术维度**；与「专业机构」差距主要集中在 **组织与流程控制**（独立复核、变更单、定期复审、CI 强制门控）。对个人项目，建议优先落地：**P0 二次复核、BACKLOG 编号、CI 链接检查、季度复审触发**——其余按精力递增。
