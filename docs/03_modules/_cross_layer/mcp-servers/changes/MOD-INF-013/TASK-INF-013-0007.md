## 施工步骤

### Step 1: 全链路压力测试（Phase 8）
- 新建 `tests/performance/test_mcp_stress.py`
- 测试场景：
  - 并发 20 session 同时 tools/call → 验证无死锁
  - 峰值 QPS 100 → 验证 RateLimit 生效，P95 延迟记录
  - knowledge_base.search 大结果集（1000+ KE）→ 验证截断不 OOM
  - 7 Server 全量启动 8h soak test → 验证无内存泄漏（关闭 B234）
- 产出：stress_test.py + 运行结果 + 性能基线报告
- 检查：峰值 QPS ≥100 时 P95 <5s，零 OOM

### Step 2: 混沌工程（Phase 8，关闭 B179/B188）
- 新建 `tests/chaos/test_mcp_chaos.py`
- 至少 5 个混沌实验：
  1. ChromaDB 进程 kill → 恢复——验证 knowledge_base 降级行为
  2. SQLite 文件锁抢占——验证 task_manager 等待/超时
  3. stdin 管道断开→重连——验证 Server 不崩溃
  4. 内存压力（填满至 90%）→ GC 恢复——验证响应延迟可控
  5. hammering：1 session 1000 并发请求——验证 RateLimit + CircuitBreaker 联动
- 产出：chaos_test.py + 混沌实验报告
- 检查：所有实验 within expected behavior，恢复时间 <30s

### Step 3: 安全审计（Phase 8）
- STRIDE 六维威胁建模（关闭 B187/R134）
- OWASP Agentic Top 10 覆盖率评估（关闭 B193）
- 输入净化框架落地（关闭 B188/R135）
- 产出：安全审计报告 + 威胁模型文档 + 安全评分卡
- 检查：高危发现 ≤0，中危发现含缓解计划

### Step 4: Runbook 实例化（Phase 8，关闭 B119/R66）
- 新建 `docs/03_modules/_cross_layer/mcp-servers/runbook.md`
- 按 `runbook-template.md` 格式：≥8 个 incident scenario
- 包含：Server OOM / CrashLoop / ChromaDB 不可达 / SQLite locked / stdin hang / OLLAMA 超时 / 工具注册漂移 / 内存泄漏
- 每个 scenario 含：severity + symptom + diagnostic commands + step-by-step response + rollback
- 产出：runbook.md
- 检查：8 个 scenario 全覆盖，每项有明确诊断命令

### Step 5: 1人+AI 维护验收（Phase 9）
- 模拟真实 1 人+AI 工作流：
  - Session 1: 打开 IDE → MCP 自动连接 → AI 调用 decompose_blueprint → 返回正确 task 列表
  - Session 2: 模拟 ChromaDB 故障 → AI 收到降级提示 → 自动切换备选 tool
  - Session 3: 模拟高负载 → RateLimit 生效 → AI 等待后继续
- 产出：验收报告——正常/异常/降级/恢复四路径均通过
- 检查：AI session 不中断，无需 Owner 干预即可完成完整流程
