## 3. 设计决策

### 3.1 为什么划分四阶段（手动 → 半自动 → 全自动+人审 → 自我进化）

**决策：全局路线固定为四阶段，阶段性质 = 系统自治水平，不是时间盒。**

依据：

1. **约束锁定**：00_index.md §4 已把阶段性质写死——「Phase 2 保留人工审核」「Phase 3 用 ICL 替代 MAML/EWC」两条约束天然把「全自动」和「自我进化」分成两个阶段；「架构手动来」约束把 Phase 0（纯手动）锁定为不可跳过的起点。
2. **外部元框架映射**（01 号文 §3.2 Agentic Engineering 三层架构，Karpathy 2026-02）：Phase 0 = 只有意图层；Phase 1 = 协作生成层由人工触发；Phase 2 = 三层贯通但意图层保留人工；Phase 3 = 协作生成层获得自我改进能力。四阶段与该演进路径一一对应，且 01 号文明确判断「三层成熟度必须自下而上」——工程保障层不稳固就上协作生成层自动化 = 把错误放大器装上流水线。
3. **内部缩影印证**：13 号文（模块工厂，自动化程度最高的组件）§4 的四阶段命名（手动 SOP → 半自动 → 全自动+人审 → 自我进化）与全局四阶段完全同构——全局路线就是组件成熟度的最大公约数。
4. **人机分工的硬边界**：四阶段的本质区别在「谁做决策」——Phase 0 人做全部决策；Phase 1 机器做采集/分类/建议、人做入库/审核；Phase 2 机器跑全链路、人审把闸门（L4 人审不可降级，13 号文 §4.3）；Phase 3 机器参与改进自己的生成质量（ICL 案例库），但架构决策与晋升签批仍归人。

**考虑过的替代方案**：

| 替代方案 | 为什么不推荐 |
|---|---|
| 三阶段（合并 Phase 2/3） | Phase 2 的人审硬门与 Phase 3 的自我改进是两种自治性质——前者人仍在回路内，后者机器进入自我提升回路；合并会让「自我进化启动」这个最高风险决策失去独立的阶段门 |
| 五阶段（把 Phase 1 拆成「辅助」与「半自动」） | 粒度冗余：1 人维护下单 AI 会话即可覆盖 Phase 1 全部形态，多一个阶段门只增加文书负担 |
| 按组件独立演进不设全局 Phase | 全局阶段门的价值在于「系统性风险闸」——如 Phase 2 启动要求自治边界（15 号文）与 LSG（09 号文）先 production；无全局门则各组件可越过安全保障各自自动化 |

### 3.2 双层 Phase 结构：全局 Phase ≠ 各文档内部 Phase

**决策：全局 Phase 与 03~16 号文内部 Phase 是两层不同维度，用映射矩阵（§4.6）关联，不做强制对齐。**

- **维度差异**：各文档内部 Phase 是「组件成熟度」维度（如 04 号文 Phase 1 = T1 容量拐点，按触发矩阵实测度量启动，与自动化水平无关）；全局 Phase 是「系统自治水平」维度（机器在回路中的位置）。
- **真源分工**：组件级施工步骤与验收标准以各施工文档为唯一真源（本文不复制）；全局阶段定义、进入/退出条件、Phase 归属映射以本文为唯一真源。两层冲突时，组件细节服从各文档，阶段归属服从本文（§6 Q3 待裁定确认此分工）。
- **why 不强制 1:1**：若强制「全局 Phase 1 = 全部文档内部 Phase 1」，则 04 号文 T1 拐点（模块数 >200 才触发）会被虚假地绑定到半自动阶段——制造假依赖、虚报阶段进度。映射矩阵只回答「该文档该内部 Phase 的施工成果服务于哪个全局阶段」。

**考虑过的替代方案**：全局 Phase = 各文档同编号 Phase 的简单集合——否决，理由如上（04 号文触发式 Phase 与全局自治 Phase 无必然同步关系）；全局 Phase 只取最关键 3~4 个文档定义——否决，阶段门的意义是全覆盖检查，漏掉 09/15 等安全文档会让阶段门失效。

### 3.3 自下而上原则：保障设施先行于进化能力

**决策：全局 Phase 0/1 的施工优先级 = 保障设施（08/09/15/16 号文 Phase 0/1）先于自我进化能力（11/12/13 号文）的自动化。**

- **why**：01 号文 §3.2 的核心判断——工程保障层不稳固就上协作生成层自动化 = 错误放大器。落到本项目：提交队列（08）未就位时，多 AI 并发产出的自动入库无串行化通道；LSG 主链路（09）未贯通时，LLM 生成物存在绕过路径；运行时三分类 gate（15）未就位时，AI 写操作无权限边界；统一事件流（16）未就位时，前三者的事件无可观测出口。这四项是任何自动化施工的「安全带」。
- **落地**：全局 Phase 0 关键路径（§4.7）把 08 提交队列 MVP 列为第一优先（它是三件套唯一缺口，且解锁会话隔离升硬的连锁项）；11/12/13 号文的内部 Phase 0（手动形态：假设注册表、L1 反思、手动 SOP）可与保障设施并行——因为手动形态本身不产生自动化风险。

### 3.4 阶段进入/退出条件的二元判定设计

**决策：全部阶段门用「可二元判定的检查清单」表达，不设结果类指标。**

- **why**：用户已明确不要不可二元判定的指标（骨架 Q2，如转化率/Sharpe 贡献）；13 号文同款纪律（人审拦截率只摸清基线、不设目标值）。阶段门的每一项必须能回答 yes/no——「某文档某 Phase 验收项是否全绿」「某链路是否端到端跑通一次」「某门禁是否零绕过」。
- **验收证据形态**：以各文档 §4 验收标准（测试全绿 / depgraph 状态翻转 / 故障注入通过 / 端到端跑通留痕）为判定输入，本文汇总为阶段检查表（§4.2~§4.5），不新造验收口径。

### 3.5 Phase 3 技术路线：ICL 替代 MAML/EWC

**决策：全局 Phase 3 的自我进化机制 = ICL 案例库（成功/失败案例结构化沉淀 → 生成 prompt 自动注入同类案例），不做 MAML/EWC 元训练。**

- **why**：单 GPU RTX 3090 24GB（00_index.md §4 约束）不支撑元学习训练；01 号文 §5.3 已定此裁定；13 号文 §4.4 将其落地为「ICL 案例库 + 语义空间选择增强 + 技能沉淀 + 反思驱动再生成」四件套。
- **远期属性声明**：全局 Phase 3 整体为**远期工程（P4）**，不承诺时间表、不设硬性验收（13 号文同款口径）；其启动需 Owner 显式裁定（§4.5）。

### 3.6 触发式排期：不设日历时间表

**决策：本文不给出任何「第 N 周/第 N 月」的日历排期；阶段推进只由进入/退出条件驱动。**

- **why**：①1 人 + 多 AI 会话的施工吞吐不可预测（约束一）；②04 号文已建立触发矩阵范式（容量拐点按实测度量启动，未触发不施工）；③13 号文 Phase 3「不承诺时间表」是先例；④日历排期在单人项目里只会制造过期承诺。
- **例外**：13 号文内部 Phase 给出的工作量预估（Phase 0 1~2 周 / Phase 1 3~4 周 / Phase 2 6~8 周）是组件级参考，本文引用其相对量级（模块工厂 Phase 2 是全局 Phase 2 的最大单件工作），但不转写为全局日历。

## 4. 施工计划

> 路线类文档无新建模块，通用规则 19（depgraph L1 铁律）不适用。本节组织：总览 → 逐阶段（目标/组成/进入/退出/验收）→ 映射矩阵 → 关键路径。

## 5. 不做什么

1. **不跳过 Phase 0 直接启动自动化**——保障层不稳固就上自动化 = 错误放大器（01 号文 §3.2 判断）；GP0 退出检查表无豁免项（E0-8 的裁定豁免须 Owner 显式批准，见 §6 Q4）。
2. **不做 Phase 2 零人工审核**——L4 人审闸门不可降级（13 号文 §4.3：门禁强制、非自觉）；零审核 = 自杀（00_index.md §4 约束原文口径）。
3. **不做 Phase 3 MAML/EWC 元训练**——单 GPU 约束（00_index.md §4），01 号文 §5.3 已裁定 ICL 替代，本文不复活。
4. **不设日历时间表**——触发式排期（§3.6）；任何「第 N 周完成 GP1」式承诺不进本文档。
5. **不复制各施工文档的组件级细节**——施工步骤/验收标准真源在 03~16 号文，本文只做阶段定义与映射（真源唯一，规则 16）。
6. **不复制施工顺序与解锁点定义**——U1~U8 真源在 00_index.md §5，本文只登记其就绪状态实测值。
7. **不做路线级功能扩张**——不新增组件、不新增阶段、不调整各文档施工范围（如 04 号文触发式 Phase 的启动阈值归 04 号文裁定）。
8. **不替交易决策侧排期**——G04/62 号等交易决策侧产出只登记就绪状态；发现需同步改的记 §6 标「待用户裁定」。
9. **不设结果类成功指标**——不设 Sharpe 贡献/拦截率目标值等不可二元判定指标（§3.4）；阶段门只用检查清单。
