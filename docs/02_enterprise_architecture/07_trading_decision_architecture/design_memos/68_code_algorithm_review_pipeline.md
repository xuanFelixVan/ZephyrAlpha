# 代码与算法多模型审查流水线

> 本文档定义"施工后审查线"：对已 merge 回 dev 的模块代码、算法实现与运行情况，用多模型轮流交叉审查+自主治本修复，与前方施工线 **5+5 路并发**开工，统一由统筹会话调度。
> 执行蓝本：[docs/audit_prompts_20_ai.md](../../../audit_prompts_20_ai.md)（AI-00 总控+域子代理+自主裁定框架+零打扰闭环，v3.2 已实证）。
> 性质：跨切治理层（6x 段位）流程规范，2026-08-17 用户裁定转 active 并首开 5+5 十路并发。

## 1. 背景

### 1.1 项目处境

- 施工线高速推进：2026-08-13~17 完成第一批~第 4 批+紧急插队批+AI-RFIX-001/AI-REDIS-001/AI-DGR-001/AI-LVL3-001/AI-THD-001/AI-GOVA-001 等批次，全部 merge 回 dev，代码 100% AI 生成
- 施工时点的质量保障只有两层：pre-commit 门禁（机械检查）+ 批次测试绿——只能证明"能跑、没破别人的"，不能证明"算法对、代码好、跑得正常"
- system_charter §2 约束六（AI 生成代码需交叉验证+依赖锁定+自治熔断）目前只在施工时点单批生效，merge 之后没有独立的二次审查机制

### 1.2 核心问题

已 merge 模块缺乏系统性回头看，四类隐患门禁测不出来：

1. **算法逻辑错误**：公式实现与备忘 spec 漂移、边界条件错、数值稳定性差（RFIX 批修的 15 文件 3 处死代码+算法修复即为实证——施工时全绿，复审才发现）
2. **过度工程**：超出 system_charter §2 硬边界的机制混进代码
3. **运行异常**：模拟/实盘跑起来的行为与设计不符（偏离、误触发、降级抖动），只有运行数据能暴露
4. **同源盲区**：施工模型审自己写的代码，系统性偏差无法自纠

### 1.3 与现有体系的边界（为什么不复用已有三件套）

| 现有体系 | 管什么 | 不管本文档的什么 |
|---|---|---|
| AI_review_instructions.md（23 路并发） | 审查 design_memos **文档**（why 层回填/清理） | 不审代码实物（what 层） |
| 55_monitoring_review.md | 运行时**监控基建**（采集日志/告警/对账/偏离数据） | 只采集不研判——数据给谁看、看出问题怎么办，没有承接方 |
| pre-commit 门禁+测试 | L1 机械检查 | 无智能，读不懂算法对不对 |

本文档是 what 层实物+运行情况的**智能审查体系**，与三者互补不重叠。

### 1.4 约束条件

- 1 人+多 AI 并发，无专职审查人力——审查必须 AI 化、异步化
- token 预算敏感（2026-08-17 成本测算：GLM Coding Plan 包月+Kimi 按量组合）——审查是 token 密集型工作，须分级投入
- 多模型可用性波动（各模型渠道/限额不同）——轮换机制须容忍单模型缺席降级
- 审查线与施工线共用同一工作树与 tracker——须防写冲突

## 2. 决策

### 2.1 决策一：双线 5+5 并发制（施工线 5 路 + 审查修复线 5 路）

- **施工线 5 路**：现有批次制不变（tracker 第五节施工批次规划），5 个并发对话继续向前施工新模块/修复
- **审查修复线 5 路**：5 个并发对话，复用 audit_prompts_20_ai.md 的 20 域划分，每路领 4 个域（AI-R1→AI-01~04、AI-R2→AI-05~08、AI-R3→AI-09~12、AI-R4→AI-13~16、AI-R5→AI-17~20），尾随施工线对已 merge 模块做独立审查+自主治本修复
- **统一统筹调度**：两条线都由统筹会话（用户或总控 AI）派单、验收、merge；审查线派单与施工线派单共用一个 tracker，不开第二套调度
- **可行性依据**（2026-08-17 裁定：并发可行）：worktree 隔离（session_worktree.py）+ 文件锁（lock_files.py）+ GitCommitGateway 串行提交 + 66 号提交队列串行化，四项防冲突基建已全部 production；5 任务零文件冲突并发已实证（2026-08-17 A/B/C/D/E 五批分析）

### 2.2 决策二：审查对象三件套

| 对象 | 审什么 | 重点 |
|---|---|---|
| 模块代码 | 正确性、可读性、过度工程、与 blueprint/注册表一致性、死代码 | src/zephyr/ 已 merge .py |
| 算法 | 数学公式 vs 代码实现、边界条件、数值稳定性、与备忘 spec 漂移、行业实证差异 | 风险模块（var_calculator/drawdown_controller/tail_risk_monitor/kill_switch）> 策略模块 > 治理/工具模块（风险优先原则） |
| 运行情况 | 日志异常模式、告警合理性、对账差异、净值偏离、降级事件抖动、成交异常 | 消费 55 号监控基建产出，不新建采集 |

### 2.3 决策三：多模型轮流交叉审查

交叉验证（cross-validation，多模型互查防同源盲区）是约束六的施工后落地。

- **模型池（2026-08-17 用户确认，待定问题 #1 闭环）**：Kimi-K3 / GLM-5.3 / Qwen3.8-Max，统一在 Trae CN 模型选择器手动切换；审计与修复全程在 Trae CN 内完成，不走外部 API
- **轮换三铁律**：
  1. 同一模块的初审模型 ≠ 复审模型
  2. 同一模型不连续审同一业务域（防系统性盲区固化）——按批次顺移轮换
  3. 红队对抗审查由初审、复审之外的第三方模型担任
- **轮换矩阵（首批静态绑定，每批次初审列顺移一位）**：

| 路次 | 领域（audit 20 域） | 初审+修复 | 复审 | 仲裁/红队 |
|---|---|---|---|---|
| AI-R1 | AI-01~04（根目录/配置/运行时/数据） | Kimi-K3 | GLM-5.3 | Qwen3.8-Max |
| AI-R2 | AI-05~08（执行模拟/交易/回测ML/因子信号） | GLM-5.3 | Qwen3.8-Max | Kimi-K3 |
| AI-R3 | AI-09~12（风控合规/组合持仓/治理规则/治理审计） | Qwen3.8-Max | Kimi-K3 | GLM-5.3 |
| AI-R4 | AI-13~16（治理其余/基础设施/共享层/自治前端） | Kimi-K3 | Qwen3.8-Max | GLM-5.3 |
| AI-R5 | AI-17~20（政策文档/模块文档/测试/脚本） | GLM-5.3 | Kimi-K3 | Qwen3.8-Max |

- **成本适配**：初审+修复在同一对话同一模型内完成（上下文已加载，复用零切换成本，token 大头在此）；复审只读初审留痕+diff（小头）；仲裁/红队极小头。GLM Coding Plan 包月额度优先排初审+修复路次，Kimi/Qwen 按量补位

### 2.4 决策四：审查线自主治本修复 + 避让纪律（v1.1.0 修订，推翻 v1.0.0 只读纪律）

用户 2026-08-17 裁定：审查线不只是登记，要**自我循环修复**且**全自动化**。

- **自主治本修复**：审查线发现问题直接治本修复→复检→循环直到零问题，走完整施工纪律（专属 worktree `AI-AUDIT<NN>-001` 前缀 + GitCommitGateway 提交 + pre-commit 门禁全量过 + 总控串行 merge），与 audit_prompts_20_ai.md §0.10 同款
- **避让纪律（替代停工等待）**：每路审查 AI 开工前探测在途施工 session 的 held_files 清单，与本域重叠的文件**跳过不动**并登记避让项，其余文件照常修——冲突防护从 audit 原版的"MODE-A 停工等待"升级为"域隔离+文件级避让"，这是 5+5 并发的核心改动
- **禁止事项不变**：reconciler 只 warn/skip/fix-in-place；不绕过门禁；不删除/覆盖在途 session 的工作；高危删除/大重构证据不足时记遗留清单（唯一允许的"不修"形式，必须可审计）

### 2.5 决策五：触发与节奏

| 审查类型 | 触发 | 节奏 |
|---|---|---|
| 增量代码/算法审查 | 批次 merge 回 dev 即入队 | 统筹派单，先进先出，风险模块插队 |
| 运行情况审查 | 55 号监控数据日汇总 | 日自动汇总（脚本）→ 周审查（模型读汇总找异常模式）→ 月轻量复盘（对齐 55 号"日自动/周人工/月轻量"节奏） |
| 存量回补审查 | 队列空时兜底 | 按风险优先级从高到低逐步回补存量模块 |

### 2.6 决策六：审查流程六步闭环（全自动化版）

1. **入队**：merge 批次号/commit/触及模块清单登记入审查队列（统筹或总控 AI 自动完成）
2. **派单**：统筹会话按优先级指派审查路次与初审模型，写明域范围与重点
3. **初审**：模型 A 审代码+算法（+运行数据），产出问题清单：发现+证据（文件/常量名/方法名锚点）+分级
4. **交叉复审**：模型 B（≠A）复核初审结论——确认/推翻/补充，防初审误报与漏报
5. **分歧仲裁**：A/B 结论冲突时，模型 C 仲裁；三模型仍分歧或涉及推翻 active 决策的，登记 proposed 议题（architecture_issue_registry.yaml，status=proposed），**不中断流水线**，其余问题照常修——议题积累到一次性汇报呈用户裁定
6. **修复闭环**：确认的问题由审查线按决策四自主治本修复（P0 插队/P1 当轮修/P2 登 CAND 候选库）；修复后复检，域内连续 2 轮复检零问题判定该域完成；修复记录（commit hash+验证命令）留痕

### 2.7 决策七：问题分级与流转

| 级别 | 定义 | 流转 |
|---|---|---|
| P0 阻断 | 算法错误可导致错误交易/风控失效/数据损坏 | 插队施工批立即修（对齐 tracker P0 惯例） |
| P1 缺陷 | 逻辑瑕疵/与备忘漂移/过度工程/测试缺口 | 登记 tracker 遗留项，排期修 |
| P2 观察 | 风格问题/轻微优化点/远期增强点子 | 登记 candidate_module_registry.yaml（CAND 候选库），不进施工队列 |

### 2.8 决策八：红队对抗审查（red team，专责找茬）

- 延续 RFIX 批红队传统（F1/F2+F4/P1c/P1a/P1b 场景）：审查线不只验证"对不对"，还主动构造异常输入、边界场景、极端行情数据找茬
- 红队场景库随审查积累，沉淀为各模块测试套件的回归用例

### 2.9 决策九：全自动化零打扰（v1.1.0 新增，用户 2026-08-17 裁定）

审查线全程**不问用户、不汇报中间态**，复用 audit_prompts_20_ai.md 的自主化机制：

- **自主裁定框架**（沿用 audit §0.8）：遇到问题自行裁定，禁止请示用户——①全面调研（文档+代码现状，证据先行）→ ②第一性原理质疑元问题（该不该存在/能否删除/能否合并）→ ③客观专业架构师视角（面向 100% AI 开发现实，长短期权衡）→ ④输出"分析摘要+裁定+治本方案"并直接执行 → ⑤仍拿不定参照专业机构/量化社区/vibe coding 社区做法 → ⑥裁定留痕（commit message 注明依据）
- **唯一两次打扰例外**（其余一律不打扰）：
  1. **P0 阻断级发现**（算法错误可导致错误交易/风控失效/数据损坏）——立即向用户输出一条简报（问题+证据+已采取的处置），不等周期汇报；风险优先原则压过零打扰
  2. **周期一次性汇报**（对齐 audit 总控 §7 大白话汇报格式）：成果/问题数与轮次/已修复清单含 commit hash/自主裁定摘要含依据/遗留项/全局验证结果/最终判定——频率待定问题 #3
- **零打扰不等于零留痕**：所有裁定、修复、避让、遗留全部落 commit message 或 tracker，用户随时可审计

### 2.10 决策十：5+5 并发冲突防护五机制（v1.1.0 新增）

| # | 机制 | 内容 |
|---|---|---|
| 1 | 文件级互斥 | 审查 AI 开工探测在途施工 session held_files，重叠文件跳过+避让登记（决策四）；修改前 `lock_files.py acquire` |
| 2 | 域隔离派单 | 统筹派施工批时声明触及域；审查线 5 路优先派**与在途施工零域重叠**的审查任务，重叠域挂起排后 |
| 3 | merge 串行 | 两线所有 merge 走统一串行队列（66 号提交队列+总控串行执行），主仓重建自然吸收 |
| 4 | 契约冻结 | 对已登记"在施工中"模块的对外接口，审查线只审不改签名/退出码/语义（跨层契约违反是最高危冲突源） |
| 5 | 审计公告 | 审查线每轮修复 merge 后在 tracker 写一行公告（域+commit+触及模块）；施工线开工前必读——防"审计修了算法 bug、施工批还基于旧行为写测试"的语义冲突 |

**止损降级线**：若并发干扰事故率超阈值（单批 ≥2 次失败归因于对方线），自动降级为 audit 原版串行模式（施工窗口冻结，审查独占），并立即汇报用户。

### 2.11 决策十一：Trae CN 模型切换调度协议（v1.2.0 新增，用户 2026-08-17 裁定）

**约束现实**：Trae CN 每个对话绑定单一模型，"换模型审查"=用户在模型选择器手动切换+开新对话。多模型轮换因此落地为**任务链+手动切换**，而非程序自动调度。

- **调度卡（handoff card，任务交接卡）**：每个审查/修复对话完成任务后，**必须在结果末尾输出下一步调度卡**，三要素齐全：
  1. **切换模型**：下一步该在 Trae CN 选择器里切到哪个模型（Kimi-K3 / GLM-5.3 / Qwen3.8-Max）
  2. **执行任务**：路次+阶段（如"AI-R1 复审"）+一句话目标
  3. **一键复制指令**：填好全部参数的完整指令块（从附录模板实例化），用户切完模型开新对话直接粘贴即开工，零填写
- **指令自包含原则**（沿用 audit 总控 §2 纪律）：指令块自带任务背景/域范围/纪律/返回格式，不依赖上对话上下文；域文件清单不一一内嵌，指路 `docs/audit_prompts_20_ai.md` 对应 AI-XX section（唯一真源，指令块保持短小）
- **输入传递走留痕不走口述**：复审所需初审问题清单一律从 tracker 遗留项+commit diff 读取（指令块只写条目编号范围），不在指令块里复制长清单——调度卡因此始终短小可一键复制
- **队列锚点**：审查队列与批次进度以 tracker 为唯一真源；调度卡的"下一步"由完成方按轮换矩阵（§2.3）+队列现状推导，拿不准时在调度卡标"请统筹确认"而非瞎指
- **并发与串行两形态兼容**：用户开 5 个审查窗口即 5 路并发（每窗口绑一路模型）；只开 1 个窗口即退化为串行任务链（切模型→粘贴→完成→下一张调度卡），机制不变

**调度卡模板**（每个审查对话的输出契约，附录 D 同款）：

```text
【下一步调度卡】
切换模型：<Kimi-K3 / GLM-5.3 / Qwen3.8-Max>
执行任务：<路次+阶段+一句话目标>
一键复制指令：
<完整指令块，即贴即用>
```

## 3. 考虑过的替代方案

| 方案 | 裁定 | 理由 |
|---|---|---|
| 施工模型自审自查 | 拒绝 | 违反交叉验证铁律，同源盲区无法自纠；RFIX 批证明施工时全绿≠无问题 |
| 纯人工逐行审查 | 拒绝 | 1 人约束，代码量已超人工可审规模；人的角色是裁定分歧与拍板，不是初审 |
| 商业 AI 代码审查服务（CodeRabbit/Cubic 类） | 暂缓 | 策略代码不出本地（隐私）；与 tracker/注册表体系集成成本高；保留为远期选项 |
| 起点即全量重审存量代码 | 拒绝 | 存量过大一次性审不现实、token 不可承受；从增量开始，存量按风险优先级兜底回补 |
| 审查线只登记不修复（v1.0.0 原案） | 推翻 | 用户 2026-08-17 裁定要"审查+自我循环修复"全自动闭环；只登记会把修复压力全压回施工线，双线变单线 |
| 串行独占模式（施工冻结→审查独占，audit 原版 MODE-A/B） | 降级保留 | 用户裁定 5+5 并发优先；串行仅作止损降级线触发时的退路（决策十） |

## 4. 上限定义

- **审查线不改架构**：发现"设计错了"只登记 proposed 议题呈人裁定，不推翻 active 决策（自主红线，自动化不废除此铁律）
- **审查线修复有边界**：治本修复走完整施工纪律（worktree+Gateway+门禁+串行 merge）；高危删除/大重构证据不足时记遗留清单而非蛮干；在途施工持有文件一律避让不动
- **并发上限 5+5=10 路**：超过则 merge 串行队列与单机算力成为瓶颈， token 消耗线性翻倍；施工线扩容优先于审查线扩容
- **审查深度上限**：不做形式化验证（formal verification，数学证明级验证）、不做全路径穷举——审查是高性价比抽查+重点深审，不是数学证明
- **上下文上限**：单模型单次上下文有限，超大模块（如 4000+ 行注册表施工总案对应的代码族）分片审查、分片修复
- 为何是上限而非妥协：对齐 system_charter §2 单人+单机约束，追求"有限预算下风险加权收益最大"，不追求完美覆盖
