## §1 Agent分层指挥链

> **设计哲学**：分层指挥链将"宏观战略决策"与"微观执行操作"解耦，与TiMi(ICLR 2026)的"策略开发与分钟级部署解耦"理念一致，也与Hi-DARTS(arXiv 2025)的"元Agent分析波动率→动态激活专门化Agent"的分层结构对齐，也与ContestTrade(arXiv 2025, Stepfun+FinStep)的"Data Team+Research Team两层解耦+内部竞赛机制"理念呼应，也与AGENTICAITA(arXiv 2026, U of L'Aquila)的"推理门控+确定性安全门控"理念呼应，也与QuantAgent(arXiv 2025, Stony Brook/CMU/Yale)的"价格行动驱动+多维度Agent→决策合成"管道架构呼应，也与MAN+ESM(Adya, 2026)的"去中心化事件驱动+事件溯源"架构理念呼应。本系统采用三层架构：战略Agent关注组合配置与市场状态，战术Agent关注信号生成与择时，执行Agent关注下单与路由。

### §1.5 跨层交互规则

#### §1.5.1 三种流

| 流类型 | 方向 | 内容 | 约束 |
|--------|------|------|------|
| **指令流** | 战略→战术→执行（自上而下） | 战略意图→交易指令→订单提交 | 每层可细化但不可违背上层意图；执行层不可跳过战术层直接接收战略指令 |
| **反馈流** | 执行→战术→战略（自下而上） | 成交回报→信号效果→归因报告 | 反馈必须逐层聚合，避免底层噪声直达战略层；聚合规则：执行层1分钟聚合→战术层5分钟聚合→战略层日频聚合 |

### 决策树与强化学习交易决策架构（Decision Tree & RL Trading Decision Architecture）

**架构现状**: 完全缺失。架构有各层模块，但缺乏**从信号到操作的端到端决策流程**——即23个决策节点的标准化流程。

**核心逻辑**: 23节点决策流程是人为设定的固定决策树，不适应市场状态变化。专业机构用**Decision Tree Learning**从数据中自动学习决策规则，或用**Reinforcement Learning**端到端优化交易策略。固定决策树是起点，但最终应被数据驱动的决策架构替代。

**缺失功能**:

#### 46.1 决策树学习

| 功能点 | 量化方法 | 说明 |
|--------|---------|------|
| 特征工程 | 将各模块输出作为决策树输入特征 | 情绪指数/体制概率/资金流/量能/技术指标 |
| 决策树训练 | CART/Random Forest/Gradient Boosting | 从历史数据中自动学习决策规则 |
| 特征重要性 | 各模块输出的特征重要性排名 | 量化各模块的决策贡献度 |
| 剪枝 | CCP(Cost-Complexity Pruning) | 防止过拟合 |

#### 46.2 强化学习优化

| 功能点 | 量化方法 | 说明 |
|--------|---------|------|

| 动作空间 | 买入/卖出/持有+仓位比例 | 交易动作 |

### 动态信号权重模型（Dynamic Signal Weighting via Bayesian Model Averaging）

**架构现状**: 完全缺失。架构有各层模块，但缺乏**跨模块的动态信号权重机制**——当不同模块给出矛盾信号时，如何根据各信号在当前市场体制下的历史预测精度动态分配权重。

**核心逻辑**: "主力行为>市场情绪>技术分析"这个固定优先级是主观的。在不同市场体制下，各信号的预测力不同——趋势市场中动量信号更有效，均值回归市场中情绪反转信号更有效。专业机构用**Bayesian Model Averaging (BMA)**或**Dynamic Conditional Correlation**自动确定各信号权重，而非人为排优先级。

**缺失功能**:

#### 48.1 信号预测力评估

| 功能点 | 量化方法 | 说明 |
|--------|---------|------|
| 信号IC值 | 各信号与次日收益的Spearman相关系数 | IC>0.03=有效信号；IC<0.01=噪声 |
| 信号ICIR | IC均值 / IC标准差 | ICIR>0.5=稳定信号；ICIR<0.3=不稳定 |
| 信号衰减 | 信号IC的N日移动平均趋势 | IC衰减>50%=信号失效，权重应降为0 |
| 体制条件IC | 在不同市场体制（趋势/均值回归/混沌）下分别计算IC | 同一信号在不同体制下IC可能相反 |

#### 48.2 动态权重分配

| 功能点 | 量化方法 | 说明 |
|--------|---------|------|
| BMA权重 | w_i ∝ P(Data\|Model_i) × P(Model_i) | 根据各模型（信号）对数据的拟合度动态分配权重 |
| IC加权 | w_i = IC_i / Σ\|IC_j\| | 按IC绝对值比例分配权重 |
| 体制自适应权重 | 在当前体制下各信号IC的归一化权重 | 趋势体制：动量信号权重↑；均值回归体制：情绪反转信号权重↑ |
| 权重平滑 | w_t = α·w_{t-1} + (1-α)·w_new | 防止权重突变，α=0.9 |

#### 48.3 矛盾信号处理

| 功能点 | 量化方法 | 说明 |
|--------|---------|------|
| 信号一致性 | 所有信号的方向一致性比例 | >80%=高一致性→高置信度；<50%=矛盾→低置信度 |
| 矛盾解决 | 按动态权重加权投票 | 权重大的信号在矛盾时占主导，但权重由数据决定而非人为设定 |
| 置信度调整 | 信号一致性 × 平均ICIR | 低一致性+低ICIR=不操作 |

#### 48.4 学术与业界对标

**对标1: Hoeting et al. "Bayesian Model Averaging" (1999, Statistical Science)**

BMA框架：不选择单一"最优"模型，而是对所有模型加权平均。权重由模型的边际似然决定。这是动态信号权重的理论基础。

**对标2: Rapach & Zhou "Forecasting Stock Returns" (2013, Handbook of Economic Forecasting)**

组合预测：多信号组合预测的精度优于任何单一信号。等权组合已优于单一最优模型，IC加权进一步提升。

**对标3: Man Group AlphaGPT实践**

可解释性要求：每个信号的权重必须可解释。权重由IC/IR决定，而非人为设定。信号失效时自动降权至0。

**建议归属层**: 决策编排器（跨模块信号融合与动态权重分配）

## §3 Agent间通信协议

> **设计哲学**：参考Google A2A Protocol（2025.1版本支持WebSocket/SSE流式传输+OAuth 2.0认证+状态回滚） (2025年4月)，适配本系统单机部署场景。A2A协议定义Agent间的能力发现、任务委托和结果返回；MCP (Model Context Protocol)定义Agent对工具的调用。两者互补：A2A管Agent间通信，MCP管Agent-工具通信。

### §3.1 A2A检查协议（单机适配版）

Google A2A协议原设计为多机分布式场景，本系统为单机部署，适配策略如下：

| A2A原设计 | 本系统适配 | 适配理由 |
|-----------|-----------|---------|
| HTTPS传输 | 进程内函数调用+Redis消息总线 | 单机无需网络开销，Redis提供持久化和发布/订阅 |
| JSON-RPC 2.0 over HTTP | JSON-RPC 2.0 over Redis Pub/Sub | 保留JSON-RPC 2.0语义，传输层替换为Redis |
| Agent Card通过HTTP发现 | Agent Card存储于Agent Registry（Redis Hash） | 单机无需HTTP发现，直接从Registry读取 |
| SSE流式推送 | Redis Pub/Sub + 消费者组 | Redis Pub/Sub天然支持发布/订阅模式 |
| OpenAPI兼容认证 | 进程内身份校验（Agent ID + 层级签名） | 单机无需网络认证，但保留Agent身份校验以防Agent冒充 |

**A2A检查网关架构**：

```
┌─────────────────────────────────────────────────────┐
│                  A2A 检查网关                         │
│                                                     │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐ │
│  │ 身份校验     │  │ 能力匹配     │  │ 边界检查     │ │
│  │ Agent ID    │→ │ 发送方能力   │→ │ 自治边界     │ │
│  │ 层级签名    │  │ 是否覆盖目标 │  │ 是否允许     │ │
│  └─────────────┘  └─────────────┘  └─────────────┘ │
│         │                │                │          │
│         ▼                ▼                ▼          │
│  ┌──────────────────────────────────────────────┐   │
│  │           检查结果：PASS / DENY / GATED       │   │
│  │  PASS → 消息放行                              │   │
│  │  DENY → 消息丢弃 + 审计日志                   │   │
│  │  GATED → 消息挂起 + 人工审批请求               │   │
│  └──────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

**A2A检查规则**：

| 检查项 | 规则 | 失败处理 |
|--------|------|---------|
| 身份校验 | 发送方Agent ID必须存在于Agent Registry | DENY + 审计告警 |
| 层级校验 | 跨层消息必须符合§1.5交互矩阵 | DENY + 审计告警 |
| 能力匹配 | 发送方必须声明了目标能力 | DENY + 通知编排Agent |
| 自治边界 | 消息内容不得超出接收方的ai_modifiable范围 | GATED（human_gated内容）或 DENY（immutable内容） |
| 频率限制 | 同一Agent对同一目标的请求频率不超过配置上限 | DENY + 限流告警 |

### §3.2 消息格式（JSON-RPC 2.0 + A2A Task/Message/Part）

#### §3.2.1 Task生命周期状态机

参考A2A协议的Task生命周期，适配本系统场景：

```
                    ┌───────────┐
                    │ submitted │ ← 任务提交
                    └─────┬─────┘
                          │
                    ┌─────▼─────┐
              ┌────→│  working  │ ← Agent处理中
              │     └─────┬─────┘
              │           │
              │     ┌─────▼──────────┐
              │     │ input-required │ ← 需要额外输入（人工审批等）
              │     └─────┬──────────┘
              │           │ 输入提供
              │           └──────────┐
              │                      │
              │     ┌────────────────▼────────────┐
              │     │           working           │
              │     └──┬────────┬────────┬────────┘
              │        │        │        │
              │  ┌─────▼──┐ ┌───▼────┐ ┌▼────────┐
              │  │completed│ │ failed │ │ canceled│
              │  └────────┘ └────────┘ └─────────┘
              │
              └── 重试（最多3次，指数退避）

              ┌─────────────────────────────────────────────┐
              │           SUSPENDED 暂停分支                 │
              │                                             │
              │   working ──(暂停)──→ suspended             │
              │   suspended ──(恢复)──→ working             │
              │   suspended ──(回滚)──→ submitted           │
              │                                             │
              │   说明：任务暂停等待外部事件或人工审批         │
              └─────────────────────────────────────────────┘
```

| 状态 | 含义 | 超时 | 转换条件 |
|------|------|------|---------|
| submitted | 任务已提交，等待分配 | 30s未分配→failed | Agent接受任务→working |
| working | Agent正在处理 | 按层级延迟目标×3 | 处理完成→completed；处理失败→failed；需额外输入→input-required |
| input-required | 需要人工审批或额外数据 | 24h未响应→canceled | 输入提供→working |
| completed | 任务成功完成 | — | 终态 |
| failed | 任务失败 | — | 可重试（最多3次）→submitted |
| canceled | 任务取消 | — | 终态 |
| suspended | 任务暂停等待外部事件或人工审批 | 72h未恢复→canceled | 恢复→working；回滚→submitted |

### §3.3 超时与重试

#### §3.3.1 分层超时策略

| 层级 | 超时基准 | 超时倍数 | 最大超时 | 理由 |
|------|---------|---------|---------|------|
| 执行层 | 100ms | ×3 | 300ms | 执行层延迟目标<100ms，3倍余量覆盖网络抖动 |
| 战术层 | 1s | ×3 | 3s | 战术层延迟目标<1s，3倍余量覆盖LLM推理 |
| 战略层 | 5s | ×3 | 15s | 战略层延迟目标<5s，3倍余量覆盖API调用 |
| 跨层 | 上层超时+下层超时 | — | 两层超时之和 | 跨层消息需经过两层处理 |

#### §3.3.2 重试策略

| 场景 | 重试次数 | 退避策略 | 降级策略 |
|------|:-------:|---------|---------|
| Agent临时不可用 | 3 | 指数退避（1s/2s/4s） | 转发至同层备用Agent |
| LLM推理超时 | 2 | 固定间隔（2s） | 降级至本地LLM或规则引擎 |
| Redis连接失败 | 5 | 指数退避（0.5s/1s/2s/4s/8s） | 本地内存队列缓冲 |
| 风控检查超时 | 0 | 不重试 | 默认拒绝（安全优先） |
| 人工审批超时 | 0 | 不重试 | 24h后自动取消任务 |

#### §3.3.3 降级策略矩阵

> 系统降级(SysDeg)与§8.3.3 LLM成本降级(LLMDeg)为不同维度的降级策略：SysDeg针对Agent间协作故障，LLMDeg针对LLM推理成本超限。

| 降级级别 | 触发条件 | 降级行为 | 恢复条件 |
|---------|---------|---------|---------|
| SysDeg-0(正常) | 所有Agent健康 | 全功能运行 | — |
| SysDeg-1(轻度) | 非关键Agent不可用 | 受影响功能降级为规则引擎 | Agent恢复健康检查通过 |
| SysDeg-2(中度) | 战术层Agent不可用 | 信号降级为上次快照，新信号暂停 | Agent恢复+验证通过 |
| SysDeg-3(重度) | 战略层Agent不可用 | 仅执行层运行，按最后战略意图执行 | Agent恢复+人工确认 |
| SysDeg-4(紧急) | 风控Agent不可用 | 全系统暂停交易，等待人工介入 | 风控Agent恢复+人工重启确认 |

### §3.4 通信安全

| 安全维度 | 措施 | 实现方式 |
|---------|------|---------|
| 身份认证 | Agent ID + 层级签名 | 每条消息携带Agent ID和层级标签，A2A网关校验 |
| 消息完整性 | 消息哈希校验 | 每条消息附带SHA-256哈希，接收方校验 |
| 审计追踪 | 全量消息日志 | 所有A2A消息写入审计日志（Redis Stream），保留≥7年 |
| 敏感数据隔离 | 数据脱敏 | Agent间通信禁止传输持仓金额/交易记录等敏感数据，仅传输脱敏后的信号/评分 |
| 串谋检测 | 通信模式分析 | 监控Agent分析Agent间通信频率/模式，异常模式触发告警（详见§10 HB-A7-007） |

### §3.5 Agent错误恢复与优雅降级

> **设计哲学**：传统微服务的错误恢复假设无状态服务可随时替换，但Agent是有状态的——它维护对话上下文、学习偏好和专业知识。2025-2026年行业实践（Galileo AI多Agent故障恢复、AWS Resilient AI Agents、multi-agent-patterns开源项目）表明，Agent错误恢复需要三重机制：Saga分布式事务补偿、熔断器状态感知、状态检查点与回滚。本系统在单机部署约束下，采用轻量级实现。

#### §3.5.1 错误分类与恢复策略

| 错误类型 | 特征 | 恢复策略 | 示例 |
|---------|------|---------|------|
| 工具错误 | 外部API超时/500/权限不足 | 重试+降级+回退链 | miniQMT下单超时→重试1次→降级为限价单→最终失败转人工 |
| 推理错误 | Agent误判意图/选错工具 | 验证+护栏+人工复核 | 信号Agent误判市场状态→风控Agent否决→人工确认 |
| 上下文错误 | 缺少必要信息导致幻觉 | 置信度评分+显式"未知"处理 | 研究Agent缺少行业数据→输出"数据不足，无法生成结论" |
| 级联错误 | 单Agent失败引发连锁反应 | 熔断器+隔离+回滚 | 研究Agent产出错误→信号Agent基于错误信号→风控否决阻断级联 |
| 状态错误 | Agent内部状态不一致 | 检查点恢复+状态重建 | 做T Agent持仓状态与实际不符→从miniQMT重建状态 |

#### §3.5.2 Saga分布式事务补偿

> 当多Agent协作完成一个任务时，单Agent错误恢复不够——需要Saga模式：为每个执行步骤定义补偿操作，出错时逆序执行补偿，保证系统状态一致性。

```
正常流程:  研究Agent分析 → 信号Agent生成信号 → 风控Agent检查 → 执行Agent下单
                                                                    ↓ 失败
补偿流程:  (无需补偿)    ← 信号Agent撤销信号  ← 风控Agent无需补偿  ← 执行Agent取消订单
```

| 协作流程 | 步骤 | 补偿操作 | 触发条件 |
|---------|------|---------|---------|
| 买入流程 | 研究Agent分析 | 无需补偿（只读操作） | — |
| | 信号Agent生成买入信号 | 标记信号为"已撤销" | 后续步骤失败 |
| | 风控Agent通过检查 | 无需补偿（只读操作） | — |
| | 执行Agent下单 | 撤单（若已报未成） | 下单失败或超时 |
| 做T流程 | 做T Agent买入 | 卖出（若已成交） | 卖出腿失败 |
| | 做T Agent卖出 | 无需补偿（T+1约束下不可逆） | — |
| 策略调整 | 研究Agent提出调整 | 无需补偿（待审批） | — |
| | Trader审批通过 | 回滚参数（若已执行） | 执行后发现问题 |

#### §3.5.3 熔断器（Circuit Breaker）

| Agent | 失败阈值 | 熔断时间 | 半开探测 | 熔断后行为 |
|-------|---------|---------|---------|----------|
| 研究Agent | 3次/5分钟 | 5分钟 | 每5分钟探测1次 | 降级为规则引擎生成研究摘要 |
| 信号Agent | 3次/5分钟 | 3分钟 | 每3分钟探测1次 | 使用上次信号快照 |
| 风控Agent | 1次/任何时间 | 永久（需人工恢复） | 不自动半开 | 全系统暂停交易 |
| 执行Agent | 3次/5分钟 | 2分钟 | 每2分钟探测1次 | 订单进入待执行队列 |
| 做T Agent | 2次/5分钟 | 5分钟 | 每5分钟探测1次 | 暂停做T操作 |
| 编排Agent | 2次/5分钟 | 3分钟 | 每3分钟探测1次 | 战略层核心，快速熔断保护 |
| 监控Agent | 3次/5分钟 | 5分钟 | 每5分钟探测1次 | 自身故障时告警降级为日志记录 |
| 归因Agent | 3次/5分钟 | 5分钟 | 每5分钟探测1次 | V3上线，全自主Agent需兜底 |
| 择时Agent | 3次/5分钟 | 3分钟 | 每3分钟探测1次 | V2上线，信号类Agent快速熔断 |
| 市场状态Agent | 2次/5分钟 | 3分钟 | 每3分钟探测1次 | V2上线，状态判断关键路径 |
| 路由Agent | 3次/5分钟 | 5分钟 | 每5分钟探测1次 | V2上线，路由失败降级为默认路由 |

#### §3.5.4 状态检查点与回滚

| 检查点类型 | 触发时机 | 存储位置 | 回滚粒度 |
|----------|---------|---------|---------|
| 决策前快照 | Agent做出关键决策前 | Redis + SQLite | 单次决策 |
| 参数基线 | 策略参数变更审批通过后 | SQLite + Parquet | 参数组 |

### §3.6 A2A检查网关策略引擎

> **设计哲学**：Microsoft Agent Governance Toolkit (2026年4月, MIT开源)提供了7包治理工具栈，其中Agent OS是无状态策略引擎，在Agent动作执行前拦截，延迟<0.1ms p99，支持YAML/OPA Rego/Cedar策略语言。本系统借鉴其核心思想，在A2A检查网关中嵌入轻量级策略引擎，实现"策略即代码"（Policy as Code）。同时参考Dual-Layer Gate Model (2026)的全局策略vs单Agent门控双层架构。

#### §3.6.1 双层门控架构

> **NeMo Guardrails v0.22 (NVIDIA, 2026)对标**：IORails并行执行引擎将输入/输出护栏（内容安全/主题控制/越狱检测）并行化，延迟仅~0.5s，检测率提升1.4倍。本系统MVP因单机约束采用YAML+if-else串行检查（详见LP-001），未来升级门禁：GPU≥48GB 且 Agent≥15个 且 有第二位开发人员加入（三个条件同时满足）时可引入NeMo Guardrails IORails并行护栏。

> **LlamaFirewall (Meta, 2025)对标**：三护栏架构——PromptGuard 2(越狱检测BERT模型)、Agent Alignment Checks(链式思维审计，检测提示注入+目标错位)、CodeShield(在线静态分析，防止不安全代码)。本系统MVP因单机约束采用YAML+if-else串行检查，但借鉴了LlamaFirewall的"三层防御"思想：输入检查(A2A检查层)→推理审计(自反Agent反思)→输出检查(自治边界三区)。未来升级门禁：①Agent≥15个（三层防御收益显著）；②有第二位开发人员加入；GPU≥48GB为可选条件（PromptGuard 2为BERT小模型，不强制要求大GPU）。

### §3.7 多智能体编排框架选型（A1§29.27迁移）

> **迁移来源**：A1交易决策架构 §29.27。本节包含框架选型分析和MCP协议设计，原在A1中作为架构增强补充。

> **核心思想**：§29.11 LLM Agent和§20.14决策六已定义LLM路由策略（Qwen本地→DeepSeek→GPT/Claude），但当前架构缺乏多智能体编排框架的系统性选型。2025-2026年多智能体编排框架已从实验性工具演进为生产级框架，CrewAI/AutoGen/LangGraph三足鼎立，Google A2A协议和Anthropic MCP协议正在标准化智能体间通信。本节基于本系统的约束（确定性控制流+金融合规+本地部署）进行框架选型，并补充MCP协议集成方案。

> **关键发现**：Cheng等人（PeerJ CS, 2026.03）的三层框架（LLM语义处理+多智能体协作+DRL自适应决策）在5只美股25年数据上实现53.87%年化收益/Sharpe 1.702，验证了LLM+多智能体+RL的架构可行性。但其使用CrewAI编排——对于本系统，LangGraph更适合，因为其确定性图论控制流更符合金融合规要求。

```
多智能体编排框架选型:

1. 三大框架对比
   ├─ CrewAI: 角色扮演+层级协作
   │   ├─ 核心概念: Agent(Role/Goal/Backstory) + Task + Crew
   │   ├─ 流程模式: Sequential / Hierarchical(经理Agent分配任务)
   │   ├─ 优势: 角色定义清晰, 类似投委会组织架构, 确定性决策流程
   │   ├─ 劣势: 依赖LangChain(本系统不使用), 流程灵活性有限
   │   └─ 适合: 结构化金融工作流(如投研报告生成, 合规审查)
   ├─ AutoGen 2.0: 对话式智能体编排
   │   ├─ 核心概念: ConversableAgent + UserProxy + GroupChat
   │   ├─ 流程模式: 自由对话(非确定性), 人类在环
   │   ├─ 优势: 灵活的智能体间对话, 内置人类审批
   │   ├─ 劣势: 对话流程不确定→不符合金融合规要求(不可审计)
   │   └─ 适合: 研究探索(非生产决策)
   └─ LangGraph: 有状态工作流引擎
       ├─ 核心概念: StateGraph + Node + Edge + ConditionalEdge
       ├─ 流程模式: 循环状态机(确定性+可审计)
       ├─ 优势: 图论控制流→确定性执行路径→可审计→符合金融合规
       │       支持循环(智能体间多轮交互) + 条件分支(市场状态路由)
       │       内置持久化(checkpoint) → 故障恢复
       ├─ 劣势: 低级API→开发成本高, 需要显式定义所有状态转换
       └─ 适合: 生产级金融决策管道(本系统首选)

2. 本系统选型: LangGraph
   理由:
   ├─ 确定性控制流: 图论执行→每条路径可审计→满足§20.14决策三加密审计链要求
   ├─ 状态持久化: checkpoint→故障恢复→满足§20.14决策一灾备要求
   ├─ 条件分支: 市场状态(C-021)→路由到不同决策节点→满足C-005多情景对策
   ├─ 循环支持: 智能体间多轮交互(如风控否决→信号修正→重新提交)→满足C-047裁决
   └─ 无LangChain依赖: LangGraph v0.3+可独立使用(仅需langgraph-core)
       → 不引入本系统不使用的LangChain依赖

3. MCP协议集成 (Model Context Protocol)
   核心思想: Anthropic提出的标准化工具集成协议→替代碎片化的自定义API
   ├─ MCP定义: 统一的工具发现/调用/结果返回协议
   │   → 工具提供方: 实现MCP Server(暴露工具列表+调用接口)
   │   → 工具消费方: LLM Agent通过MCP Client发现和调用工具
   ├─ 在本系统中的应用:
   │   ├─ MCP Server 1: Feature Store查询(§29.2) → 暴露get_features(entity, date_range)
   │   ├─ MCP Server 2: 知识图谱查询(§7) → 暴露query_causal_chain(entity, depth)
   │   ├─ MCP Server 3: 风控查询(C-004) → 暴露check_risk(position, action)
   │   └─ MCP Client: §29.11 LLM Agent → 通过MCP调用上述工具
   ├─ 与当前§29.11 LLM路由的关系:
   │   → 当前: LLM Agent通过硬编码API调用工具→新增工具需改代码
   │   → MCP后: LLM Agent通过MCP动态发现工具→新增工具零代码改动
   └─ 安全约束:
       ├─ MCP工具调用必须记录到加密审计链(§20.14决策三)
       ├─ MCP工具不可直接执行交易(须经C-047裁决)
       └─ MCP Server必须实现输入验证(§20.14决策六L1)

4. Google A2A协议 (Agent-to-Agent)
   核心思想: 标准化智能体间通信协议→跨框架互操作
   ├─ 当前状态: 2025年4月发布, 早期阶段
   ├─ 与本系统的关系: 当前系统内智能体通信通过内部消息总线(§29.1)
   │   → A2A更适合"跨系统"智能体通信(如与外部数据源智能体交互)
   │   → 当前阶段: 观望, 不集成(过早采用风险)
   └─ 未来: 如果系统需要与外部AI服务交互(如券商AI接口), A2A可作为通信协议

5. 实现路径
   ├─ Phase 1: LangGraph核心决策管道 → 替代当前硬编码决策流程
   │   → 将C-009信号→C-016因果→C-047裁决流程建模为LangGraph状态图
   │   → 优势: 决策路径可审计+故障可恢复+条件可路由
   ├─ Phase 2: MCP协议集成 → LLM Agent工具调用标准化
   │   → Feature Store/知识图谱/风控查询封装为MCP Server
   │   → LLM Agent通过MCP Client动态发现和调用
   └─ Phase 3: A2A协议评估 → 跨系统智能体通信(观望)

6. 约束
   ├─ LangGraph状态图的每条边必须有明确的条件谓词(不可有隐式跳转)
   ├─ MCP工具调用延迟不可超过100ms(否则阻塞决策管道)
   ├─ LangGraph checkpoint必须加密存储(与§20.14决策三对齐)
   └─ 多智能体编排不可引入非确定性(所有决策路径必须可复现)
```

## §4 Agent自治边界

> **设计哲学**：参考NVIDIA Agentic Autonomy Levels (2025年2月)的4级自治模型和AWS Agentic AI Security Scoping Matrix (2025年11月)的Agency vs Autonomy区分，将原有三级边界（ai_modifiable/human_gated/immutable）增强为四级自治模型。NVIDIA的Level 0-3与AWS的Agency-Autonomy矩阵形成互补：NVIDIA定义自治能力级别，AWS定义架构安全分类。

### §4.1 四级自治模型

| 自治级别 | NVIDIA对标 | 含义 | 安全控制 | 本系统对应 |
|---------|-----------|------|---------|-----------|
| **Level 0** | Level 0-推理API | Agent仅执行确定性指令，无自主决策 | 输入/输出完全受控 | 执行Agent、路由Agent |
| **Level 1** | Level 1-确定性系统 | Agent在硬编码规则内自主执行，参数微调自主 | 规则不可修改，参数变更可审计 | 风控Agent、信号Agent、择时Agent、做T Agent、监控Agent |
| **Level 2** | Level 2-弱自主 | Agent可自主决策，但关键变更需人工审批 | 关键决策点设人工门控 | 编排Agent、研究Agent、市场状态Agent |
| **Level 3** | Level 3-全自主 | Agent完全自主决策和执行 | 事后审计+异常检测+熔断机制 | 归因Agent |

**AWS Agency vs Autonomy矩阵映射**：

| | 低Agency（工具调用） | 高Agency（自主行动） |
|---|---|---|
| **低Autonomy（规则驱动）** | Level 0：执行Agent（工具调用+规则驱动） | Level 1：信号Agent（规则驱动+参数微调自主） |
| **高Autonomy（推理驱动）** | Level 2：编排Agent（推理驱动+人工门控） | Level 3：归因Agent（推理驱动+完全自主） |

### §4.2 ai_modifiable（自治区：Agent可自主修改的范围）

| Agent | 可自主修改项 | 修改约束 | 审计要求 |
|-------|-----------|---------|---------|
| 编排Agent | 任务优先级排序、Agent激活/休眠决策、协作模式选择 | 不得违反硬边界；激活/休眠决策需记录理由 | 每次修改写入审计日志 |
| 研究Agent | 因子提案内容、知识图谱更新、搜索策略 | 因子入池需通过IC验证；知识更新需标注来源 | 因子提案记录完整推导链 |
| 归因Agent | 归因方法选择、报告格式、优化建议内容 | 优化建议不得直接修改在线策略 | 归因报告版本化管理 |
| 风控Agent | 风控参数微调（在硬边界±10%范围内）+独立对冲执行（在硬编码对冲规则内，对冲规则不可修改） | 不得降低风控等级；不得关闭任何风控检查 | 参数变更记录前后值+理由 |

### §4.6 人在闭环（HITL）机制

> **设计哲学**：LLM的随机性（Stochastic nature）与生产环境严苛的确定性要求之间存在天然鸿沟。2025-2026年行业共识（NexTrade生产级多Agent交易系统、Galileo AI HITL监督框架、EU AI Act Article 14）表明，HITL不是"可选增强"而是"生产必需"。本系统通过§4.3 human_gated层实现HITL，本节定义其具体机制。

#### §4.6.1 HITL触发条件与分级

| 触发条件 | HITL级别 | 人工介入方式 | 超时处理 | 参考 |
|---------|---------|------------|---------|------|
| Agent置信度<70% | 自动升级 | Agent输出+置信度→Trader审核 | 5min未响应→维持现状 | NexTrade confidence-based escalation |
| human_gated边界操作 | 强制审批 | Agent提交申请+依据→Trader审批 | 24h未审批→自动取消 | 本系统§4.3 |
| 大额下单（超限额） | 强制审批 | 执行Agent拦截→Trader确认 | 5min未响应→取消订单 | 能力定位书§6 B-013.6约束 |
| 风控参数变更 | 强制审批+双重确认 | 风控Agent申请→Trader+Administrator双重审批 | 1h未审批→维持现状 | 安全优先 |
| 串谋/涌现告警 | 告警+人工确认 | 监控Agent告警→Trader确认是否阻断 | 10min未响应→自动阻断 | 安全优先 |
| 系统降级/熔断恢复 | 人工确认 | Administrator确认后恢复 | 不自动恢复 | 安全优先 |

#### §4.6.2 置信度驱动的升级策略

```
Agent决策输出
    │
    ▼
置信度评分 ≥ 90%? ──Yes──→ 自动执行（ai_modifiable区）
    │
    No
    ▼
置信度评分 ≥ 70%? ──Yes──→ 执行但标记"低置信度" + 异步人工复核
    │
    No
    ▼
置信度评分 ≥ 50%? ──Yes──→ 暂停执行 + 人工审批（human_gated区）
    │
    No
    ▼
置信度评分 < 50% ────→ 拒绝执行 + 人工介入 + 反思触发
```

| 置信度区间 | 执行策略 | 人工介入 | 反思触发 |
|-----------|---------|---------|---------|
| ≥90% | 自动执行 | 无（异步抽检10%） | 否 |
| 70%-89% | 执行+标记 | 异步复核（Trader 5min内确认） | 否 |
| 50%-69% | 暂停等待 | 同步审批（Trader必须确认） | 是（L1反思） |
| <50% | 拒绝执行 | 人工介入+分析原因 | 是（L1+L2反思） |

### §5.5 Agent版本管理策略

> **设计哲学**：Agent版本化不是简单的代码版本化——Agent行为由prompt、模型、知识库、工具接口、记忆状态共同决定。2025-2026年行业实践（AuxilioBits四层版本化分类法、Zylos AI安全升级模式、SparkCo企业Agent版本化策略）表明，必须对行为影响因子分层版本化，否则回滚代码而不回滚上下文将导致不一致行为。本系统采用四层版本化+影子模式测试策略。

#### §5.5.1 四层版本化分类法

| 版本层 | 版本化对象 | 版本格式 | 存储位置 | 回滚策略 |
|--------|----------|---------|---------|---------|
| L1-认知层 | Prompt模板、系统指令、Agent Card | SemVer (MAJOR.MINOR.PATCH) | Git + 版本管理数据库 | 回滚至上一版本+哈希校验 |
| L2-模型层 | LLM模型版本、超参数(temperature/max_tokens) | 模型名+版本号 | 路由配置 | 切换至上一模型版本 |
| L3-知识层 | 语义记忆快照、因子库版本、策略规则版本 | 快照时间戳+哈希 | Parquet快照 | 恢复至上一快照 |
| L4-工具层 | 工具接口版本、SKILL.md版本、API契约 | SemVer | Git + SKILL.md | 回滚至上一版本 |

#### §5.5.2 Agent升级安全模式

| 升级模式 | 描述 | 适用场景 | 风险等级 |
|---------|------|---------|---------|
| 影子模式(Shadow) | 新版本Agent与旧版本并行运行，比较行为差异但不执行新版本操作 | L1认知层变更、L2模型层变更 | 低 |
| 金丝雀部署(Canary) | 新版本Agent接收5%流量，监控行为指标，逐步扩大 | L1/L4变更 | 中 |
| 蓝绿部署(Blue-Green) | 新旧版本同时存在，一键切换 | L2模型层变更 | 中 |
| 热修复(Hotfix) | 直接替换，跳过渐进部署 | 仅限L4工具层紧急修复 | 高（需人工审批） |

#### §5.5.3 版本兼容性矩阵

| 变更类型 | L1认知层 | L2模型层 | L3知识层 | L4工具层 | 需要全量回归测试 |
|---------|---------|---------|---------|---------|:---------------:|
| MAJOR（不兼容变更） | 是 | 是 | 否 | 是 | ✓ |
| MINOR（向后兼容新增） | 是 | 否 | 否 | 否 | ✗ |
| PATCH（向后兼容修复） | 否 | 否 | 否 | 否 | ✗ |
| 模型切换 | — | 是 | 否 | 否 | ✓ |
| 知识库全量更新 | — | — | 是 | 否 | ✓ |

## §6 自反Agent（Reflexion）

> **设计哲学**：参考Reflexion (Shinn et al., 2023)的语言反思+情景记忆机制、MAR (Multi-Agent Reflexion, 2025, 密歇根大学)的多Agent扩展、Agent-R (2025, 浙大+阿里通义)的实时轨迹内反思、SAMULE (EMNLP 2025, AWS AI Labs)的三级反思、ReflCtrl (NeurIPS 2025 Workshop, UCSD)的反思频率控制、PreFlect (arXiv 2026)的前瞻反思（从回顾性修正转向前瞻性预判）。本系统将自反机制嵌入Agent架构，形成"执行→评估→反思→修正"的闭环。

### §6.1 自反架构（Actor-Evaluator-SelfReflection三组件）

```
┌─────────────────────────────────────────────────────────────────┐
│                    自反Agent架构                                  │
│                                                                 │
│  ┌───────────────┐     ┌───────────────┐     ┌───────────────┐ │
│  │   Actor       │     │  Evaluator    │     │ SelfReflection│ │
│  │  (执行器)      │────→│  (评估器)      │────→│  (自反思器)    │ │
│  │               │     │               │     │               │ │
│  │ · 接收任务     │     │ · 评估执行结果 │     │ · 语言反思     │ │
│  │ · 生成行动序列 │     │ · 对比预期目标 │     │ · 情景记忆     │ │
│  │ · 执行行动     │     │ · 计算奖励信号 │     │ · 修正策略     │ │
│  │ · 输出结果     │     │ · 输出评估报告 │     │ · 输出修正建议 │ │
│  └───────────────┘     └───────────────┘     └───────────────┘ │
│         ↑                                           │         │
│         │              ┌──────────────┐             │         │
│         └──────────────│ 修正建议应用  │←────────────┘         │
│                        │ (异步，不阻塞 │                       │
│                        │  当前决策)    │                       │
│                        └──────────────┘                       │
│                                                                 │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │              情景记忆 (Episodic Memory)                    │ │
│  │  · 轨迹存储：每次执行的完整轨迹（输入→行动→结果→反思）       │ │
│  │  · 检索策略：相似任务检索Top-K轨迹作为上下文                │ │
│  │  · 容量管理：LRU淘汰，保留最近1000条轨迹                   │ │
│  │  · 存储：Redis Hash + 向量索引(FAISS)（FAISS为MVP轻量实现，使用本地LLM隐式生成向量或预计算离线导入，不含独立嵌入模型。完整RAG嵌入模型因GPU显存限制不能建，详见LP-002。替代方案：SQLite FTS5全文检索作为补充）                     │ │
│  └───────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

**三组件职责**：

| 组件 | 输入 | 输出 | LLM需求 | 延迟目标 |
|------|------|------|---------|---------|
| Actor | 任务描述+情景记忆 | 行动序列+执行结果 | 视任务复杂度：简单任务用本地LLM，复杂任务用API | 按Agent层级延迟目标 |
| Evaluator | 执行结果+预期目标 | 评估报告+奖励信号 | 本地LLM（结构化评估） | <2s |
| SelfReflection | 评估报告+轨迹+情景记忆 | 反思文本+修正建议 | 视反思级别：L1本地LLM（低延迟），L2/L3 API优先（高质量） | <10s（异步，不阻塞） |

### §6.2 多级反思（参考SAMULE三级反思）

| 反思级别 | 触发条件 | 反思范围 | 输出 | 频率 | 存储位置 |
|---------|---------|---------|------|------|---------|
| **L1-单轨迹反思** | 每次任务执行完成后（ReflCtrl可跳过，但偏差>20%/风控否决/执行失败时强制触发，详见§6.5） | 单次执行轨迹 | 轨迹级反思文本+即时修正建议 | 每次执行 | 情景记忆（Redis热区，近期条目24h内高频访问，90天保留，详见§7.2） |
| **L2-任务内反思** | 同类任务执行N次后（N=5）/ 同类L1反思≥3次 / 连续亏损≥3次 | 近N次同类任务轨迹 | 任务级模式识别+参数调整建议 | 每5次同类任务 | 语义记忆（Redis缓存+SQLite持久，详见§7.2） |
| **L3-任务间反思** | 日度/周度定时触发 / L2反思≥3个不同类别 / 月度复盘 | 跨任务类型轨迹 | 全局策略优化建议+能力演进建议 | 日度（盘后） | 语义记忆+程序记忆（SQLite+SKILL.md，详见§7.2） |

**L1-L3反思流程**：

```
任务执行完成
    │
    ├──→ L1-单轨迹反思（即时）
    │     · 这次执行哪里做得好？哪里可以改进？
    │     · 输出：即时修正建议（应用于下次同类任务）
    │
    ├──→ 累积5次同类任务
    │     │
    │     └──→ L2-任务内反思（批量）
    │           · 近5次执行有什么共同模式？
    │           · 参数是否需要系统性调整？
    │           · 输出：参数调整建议（需审批后应用）
    │
    └──→ 日度/周度定时
          │
          └──→ L3-任务间反思（全局）
                · 不同任务类型之间有什么关联？
                · 全局策略是否需要优化？
                · 是否需要新能力/退役旧能力？
                · 输出：全局优化建议（需审批后应用）
```

### §6.3 前瞻反思（参考PreFlect）

PreFlect (arXiv 2026)提出前瞻反思机制，将反思范式从"事后纠正"转向"事前预判"——在Agent执行前批评和精炼计划，而非执行后补救。本系统在L2/L3反思中嵌入前瞻机制。

| 前瞻场景 | 触发条件 | 前瞻内容 | 修正动作 |
|---------|---------|---------|---------|
| 战略意图下发前 | 编排Agent制定战略意图后、下发前 | "当前市场状态是否支持此意图？历史类似意图的成功率？" | 成功率<50%→标记低置信度+人工确认（前瞻预警≠§4.6.2决策置信度，处理力度不同） |
| 信号聚合前 | 信号Agent聚合多策略信号后、输出前 | "信号冲突率是否异常？历史类似信号组合的表现？" | 冲突率>30%→降权冲突信号+增加人工确认 |
| 大额下单前 | 执行Agent构建大额订单后、提交前 | "当前流动性是否支持？历史类似时段的滑点分布？" | 预估滑点>阈值→拆单或延迟执行 |

**前瞻反思与回顾反思的互补关系**：

| 维度 | 回顾反思(L1-L3) | 前瞻反思 |
|------|-----------------|---------|
| 时机 | 执行后 | 执行前 |
| 目的 | 从错误中学习 | 预防错误发生 |
| 数据来源 | 历史轨迹+反思记录 | 历史轨迹+当前上下文 |
| LLM需求 | API优先（深度分析） | 本地LLM（快速预判） |
| 修正范围 | 后续决策 | 当前决策 |

### §6.4 实时轨迹内反思（参考Agent-R）

Agent-R (2025, 浙大+阿里通义)提出实时轨迹内反思，在执行过程中即时检测偏差并修正，而非等待任务完成后反思。

| 场景 | 触发条件 | 反思内容 | 修正动作 | 延迟约束 |
|------|---------|---------|---------|---------|
| 信号生成偏差 | 信号强度偏离历史均值>2σ | "当前信号是否受异常因子值影响？" | 降权异常信号，增加人工确认标记 | <500ms |
| 执行滑点异常 | 实际滑点>预估滑点×2 | "市场流动性是否发生变化？" | 暂停后续拆单，重新评估流动性 | <200ms |
| 风控参数漂移 | 风控参数偏离基准值>10% | "参数漂移是否合理？" | 回滚至基准值，触发L2反思 | <1s |
| 市场状态突变 | 状态转换概率>90%但未触发 | "是否遗漏了状态转换信号？" | 立即触发状态重新评估 | <3s |

**实时反思与L1反思的区别**：

| 维度 | 实时轨迹内反思 | L1-单轨迹反思 |
|------|-------------|-------------|
| 时机 | 执行过程中 | 执行完成后 |
| 目的 | 即时纠偏 | 事后总结 |
| LLM需求 | 本地LLM（低延迟） | API优先（高质量） |
| 修正范围 | 当前执行轨迹 | 下次同类任务 |
| 推理成本 | 低（简单判断） | 中（深度反思） |

### §6.5 反思频率控制（参考ReflCtrl）

ReflCtrl (NeurIPS 2025 Workshop, UCSD)通过表示工程控制反思频率，节省33.6%推理token。本系统采用分层频率控制：

| Agent层级 | 反思频率 | 触发条件 | 跳过条件 | 预估token节省 |
|----------|---------|---------|---------|:-----------:|
| 执行层 | 低频 | 仅异常时触发 | 正常成交不反思 | ~80% |
| 战术层 | 中频 | 每5次同类任务L1+每日L2 | 信号连续5次在预期范围内跳过L1 | ~50% |
| 战略层 | 高频 | 每次任务L1+每周L2+每月L3 | 无（战略决策必须反思） | ~20% |

**频率控制决策矩阵**：

| 执行结果质量 | 连续成功次数 | 反思决策 | 理由 |
|:-----------:|:----------:|---------|------|
| 优秀（超出预期） | ≥5 | 跳过L1，记录成功模式 | 连续成功说明策略有效，反思边际收益低 |
| 正常（符合预期） | ≥3 | 跳过L1，仅L2聚合反思 | 正常结果反思价值有限 |
| 轻微偏差 | — | 执行L1 | 偏差可能暗示参数漂移 |
| 严重偏差 | — | 执行L1+立即L2 | 严重偏差需要系统性分析 |
| 失败 | — | 执行L1+立即L2+触发L3 | 失败需要全局反思 |

| 策略优化建议（immutable） | 仅记录，不自动应用 | 人工评估 | — |

## §7 Agent记忆架构

> **设计哲学**：LLM本质无状态，Agent的"智能连续性"完全依赖外部记忆系统。2025-2026年行业共识（Mem0/Letta/LangMem/AgentDock/Zep/Graphiti/MAGMA）将Agent记忆分为四层：工作记忆（Working）、情景记忆（Episodic）、语义记忆（Semantic）、程序记忆（Procedural）。本系统基于单机部署约束（Redis+本地SQLite+Parquet），采用轻量级四层记忆架构，与§6自反Agent的反思轨迹和§5技能注册的程序记忆深度集成。

### §7.1 四层记忆模型

```
┌─────────────────────────────────────────────────────────────┐
│                    工作记忆 (Working Memory)                  │
│    存储: Redis内存 | 生命周期: 单次会话 | 容量: 上下文窗口     │
│    用途: 当前对话上下文、中间推理步骤、临时计算结果            │
├─────────────────────────────────────────────────────────────┤
│                    情景记忆 (Episodic Memory)                 │
│    存储: Redis+SQLite | 生命周期: 跨会话持久 | 容量: 近90天    │
│    用途: 交易决策轨迹、反思记录、异常事件日志                  │
├─────────────────────────────────────────────────────────────┤
│                    语义记忆 (Semantic Memory)                 │
│    存储: SQLite+Parquet | 生命周期: 永久 | 容量: 无上限       │
│    用途: 市场知识、因子定义、策略规则、用户偏好                │
├─────────────────────────────────────────────────────────────┤
│                    程序记忆 (Procedural Memory)               │
│    存储: SKILL.md+scripts/ | 生命周期: 版本化 | 容量: 技能库   │
│    用途: 技能模板、成功模式、执行流程、最佳实践                │
└─────────────────────────────────────────────────────────────┘
```

### §7.2 各层记忆规格

| 记忆层 | 存储介质 | 写入触发 | 读取触发 | 保留策略 | 容量约束 | 对应域 |
|--------|---------|---------|---------|---------|---------|--------|
| 工作记忆 | Redis (内存) | 每次Agent交互 | 每次Agent推理 | 会话结束清空 | 受上下文窗口限制(4K-32K tokens) | D-INFRA-RUNTIME |
| 情景记忆 | Redis(热)+SQLite(温) | 决策完成/反思触发/异常发生 | 反思推理/归因分析/漂移检测 | 90天热+1年温+7年冷(Parquet) | 热:近1000条决策轨迹 | D-AUTONOMY-CORE |
| 语义记忆 | SQLite+Parquet | 知识更新/因子定义变更/策略规则变更 | Agent推理时RAG检索 | 永久保留，版本化管理 | 无硬上限 | D-KNOWLEDGE |
| 程序记忆 | 文件系统(SKILL.md) | 技能注册/技能版本升级 | Agent冷启动/技能匹配 | 版本化保留，旧版保留≥5年 | 28项技能(当前) | D-AUTONOMY-CORE |

### §7.3 记忆巩固与遗忘

> 参考 LangMem (LangChain 2025) 的记忆巩固机制和 AgentDock 的惰性衰减系统。

| 巩固操作 | 触发条件 | 执行方式 | 示例 |
|---------|---------|---------|------|
| 情景→语义 | 同类事件出现≥3次 | 提取共性事实写入语义记忆 | "连续3次该因子在震荡市IC<0.01"→"该因子在震荡市无效" |
| 情景衰减 | 事件超过90天且未被检索 | 从Redis热区迁移到SQLite温区 | 90天前的决策轨迹从内存移至磁盘 |
| 语义去重 | 语义记忆新增时 | 向量相似度检测，相似度>0.95合并 | "因子A在震荡市无效"与"因子A不适合震荡环境"合并 |
| 程序升级 | 反思有效率持续>70% | 将成功模式提取为技能模板 | 做T Agent连续20次成功→提取为做T技能最佳实践 |
| 工作记忆压缩 | 上下文窗口使用>80% | 摘要压缩早期对话，保留关键决策点 | 50轮对话压缩为10条关键决策摘要 |

**2026年行业共识：五阶段记忆流水线**（与上方巩固遗忘操作表为同一记忆系统的不同视角：操作表=本系统具体实现，五阶段=行业抽象框架）（参考CoALA/TMLR 2024、Mem0/Letta/Zep生产实践）：

| 阶段 | 操作 | 本系统实现 |
|------|------|----------|
| 1.写入 | 原始交互记录存入工作记忆 | Redis Hash实时写入 |
| 2.抽取 | 从原始记录中提取关键事实/模式 | LLM提取→语义记忆(SQLite) |
| 3.整合 | 去重+冲突解决+版本化 | 相似度>0.95去重+时间戳版本化 |
| 4.检索 | 按相关性召回记忆 | FAISS向量检索+SQLite结构化查询 |
| 5.遗忘 | 衰减/归档/删除过期记忆 | 90天热→1年温→7年冷分级衰减 |

> 关键发现：Databricks 2026年4月研究表明，无策展的记忆会把一次性错误固化成永久谎言——Agent会引用之前运行里错误的输出，再以更高的信心复用。本系统通过§6自反Agent的反思机制+§7.3巩固去重来缓解此问题。

### §7.4 记忆与自反Agent的集成

| 自反Agent组件 | 消费的记忆层 | 产出的记忆层 | 说明 |
|--------------|------------|------------|------|
| Actor | 工作记忆+语义记忆 | 工作记忆 | 推理时读取上下文和知识，产出写入工作记忆 |
| Evaluator | 情景记忆+语义记忆 | — | 评估时检索历史同类决策和规则标准 |
| Self-Reflection | 情景记忆 | 情景记忆+语义记忆 | 反思时检索历史轨迹，产出反思记录和可能的语义知识 |
| L1单轨迹反思 | 情景记忆(单条) | 情景记忆 | 纠正单次决策错误 |
| L2任务内反思 | 情景记忆(同类多条) | 语义记忆 | 提取错误模式写入语义知识 |
| L3任务间反思 | 情景记忆+语义记忆(跨类) | 语义记忆+程序记忆 | 提取可迁移洞察，可能升级为技能 |

### §7.5 记忆安全约束

| 约束 | 说明 | 执行机制 |
|------|------|---------|
| 敏感数据不入记忆 | 持仓/金额/交易记录不写入任何记忆层（能力定位书§6 B-011约束） | Agent写入记忆前脱敏过滤 |
| 记忆不可篡改 | 情景记忆写入后不可修改，仅可追加反思 | 不可变日志+哈希校验 |
| 记忆访问控制 | Agent仅可访问其层级对应的记忆 | 按Agent层级划分记忆访问权限 |
| 记忆一致性 | 同一事实在情景/语义/程序记忆中不可矛盾 | 写入时跨层一致性检查 |
| 记忆恢复 | 系统崩溃后记忆可从Parquet冷存储恢复 | RPO=0(情景记忆), 定期快照(语义记忆) |

## §11 方法论约束与设计决策

> 记录Agent架构中的关键设计决策及其理由，避免"为什么这样设计"的知识流失。

| 决策编号 | 决策 | 理由 | 替代方案 | 替代方案被拒理由 |
|---------|------|------|---------|---------------|
| D-A7-001 | Agent分三层指挥链（战略→战术→执行） | 与交易决策天然分层对齐：战略层关注组合配置，战术层关注信号与择时，执行层关注下单与路由；分层后职责清晰、故障隔离、便于独立演进 | 扁平Agent网络（无层级）：灵活但易导致决策冲突和资源竞争 |
| D-A7-002 | Agent自治边界分四级（Level 0-3） | 三级边界（ai_modifiable/human_gated/immutable）粒度不够，无法区分"完全无自主决策"与"规则内自主"；四级模型与NVIDIA Agentic Autonomy Levels对齐，与行业标准一致 | 二级边界（自治/人工）：粒度不够，无法区分"可优化但需审批"与"绝对不可变" |
| D-A7-003 | 需要自反Agent（Reflexion） | Agent在执行后需要自我评估决策质量，发现偏差并修正，形成闭环学习；没有自反机制则Agent无法从错误中自主改进 | 纯外部评估：依赖人工或外部系统评估，反馈延迟高，无法实时修正 |
| D-A7-004 | LLM路由需要成本控制 | LLM API调用成本随请求量线性增长，不加控制将导致不可预期的运营成本；分时分任务路由可在保证决策质量的前提下优化成本 | 全部使用API：成本不可控；全部使用本地模型：决策质量不足 |
| D-A7-005 | Agent冷启动需要技能注册 | 新Agent上线时必须声明其能力范围，否则无法被指挥链调度、无法通过A2A检查、无法确定自治边界；技能注册是冷启动的前提 | 隐式能力发现：Agent运行时动态声明能力，但会导致调度不确定性和安全漏洞 |
| D-A7-006 | A2A检查不可绕过 | 单机部署虽无网络攻击面，但Agent冒充和权限提升风险依然存在；A2A检查是Agent间通信的安全基线 | 信任所有Agent：简化通信但丧失安全边界，无法检测串谋和涌现行为 |
| D-A7-007 | 反思为异步执行 | 反思需要LLM推理，同步执行将阻塞当前决策，违反延迟目标；异步反思结果应用于后续决策 | 同步反思：延迟不可接受（战略层+5-10s，战术层+2-5s） |
| D-A7-008 | 风控否决可穿透任意层 | 风控是系统最后一道防线，否决信号必须以最短路径到达执行层；逐层传递会增加延迟，可能错过最佳处置时机 | 逐层传递否决：延迟增加，风险窗口扩大 |
| D-A7-009 | 本地LLM优先用于低延迟任务 | RTX 3090本地推理延迟1-5s，API推理延迟2-10s+网络延迟；低延迟任务（执行层/战术层）必须使用本地LLM或规则引擎 | 全部使用API：延迟不可控，且成本高 |
| D-A7-010 | 串谋检测采用通信模式分析 | NBER Working Paper (2025)证明RL交易Agent无需通信即可维持超竞争利润，因此串谋检测不能仅依赖通信内容分析，还需分析行为相关性 | 仅检测显式通信：无法检测隐式串谋 |

| Administrator | Agent部署与资源调度；Agent版本管理与回滚；监控Agent运行状态与资源消耗；GPU显存分配策略调整 | 低：部署和调度需人工确认，Agent不可自行扩缩容 | Agent部署审批；资源分配决策；版本发布审批；故障恢复决策；降级策略调整 | 命令行+监控仪表盘 |
| AI | Agent自主执行日常交易决策；自我反思与策略修正（ai_modifiable级）；Agent间协作通信；涌现行为初步检测与告警 | 高：在自治边界内完全自主，仅在human_gated/immutable边界处受限 | 无直接人工介入；通过自治边界和硬约束间接约束AI行为 | A2A协议+Redis消息总线 |
| 风控系统(A4) | 风控否决穿透任意Agent层；仓位上限强制执行；熔断指令下发 | 极高：风控规则硬编码，自动执行，不可被AI绕过 | 风控参数变更审批；熔断后恢复确认 | 否决流+Redis Pub/Sub |

## §14 冲突与矛盾矩阵

> Agent架构中固有的冲突与矛盾，记录仲裁规则和优先级，确保冲突发生时有明确的处理依据。

| 冲突方A | 冲突方B | 冲突场景 | 仲裁规则 | 优先级 |
|---------|---------|---------|---------|--------|
| Agent自治 | 安全约束 | Agent自主优化策略参数时触及硬边界 | 安全约束绝对优先；Agent自治仅在安全约束允许范围内生效 | P0-安全优先 |
| Agent协作效率 | A2A检查开销 | 高频Agent间通信时A2A检查成为性能瓶颈 | A2A检查不可跳过；通过批量检查、缓存机制优化性能，而非削弱检查 | P1-合规优先 |
| LLM成本 | 决策质量 | 使用本地模型替代API以降低成本，但决策质量下降 | 关键决策路径（战略层）强制使用高质量模型；非关键路径允许降级；成本控制不得牺牲核心决策质量 | P2-质量优先（核心路径）/ 成本优先（非核心路径） |
| 自反反思 | 执行延迟 | 自反Agent反思耗时导致执行延迟增加 | 反思为异步执行，不阻塞当前决策；反思结果应用于后续决策而非当前决策 | P3-执行优先（当前决策）/ 反思优先（后续优化） |
| 串谋检测灵敏度 | 协作效率 | 过度灵敏的串谋检测误报导致正常Agent协作被阻断 | 串谋检测告警需人工确认后才阻断；误报率>10%时调低灵敏度 | P4-协作优先（误报场景）/ 安全优先（确认串谋） |
| Agent自治进化 | 系统稳定性 | Agent快速迭代导致系统行为不可预测 | 每次迭代变更范围≤3个关联参数（能力定位书§6 B-008约束）；迭代后24h观察期 | P5-稳定优先 |
| 信息共享 | 数据隔离 | Agent间需要共享信息但敏感数据不可传输 | 敏感数据脱敏后共享；仅传输信号/评分/状态，不传输持仓/金额/交易记录 | P6-隔离优先 |
| 降级可用性 | 降级质量 | 降级后系统可用但决策质量下降 | 降级保证核心路径质量（风控/执行不可降级），非核心路径允许质量下降 | P7-核心质量优先 |

## §15 Agent可观测性

> **设计哲学**：多Agent系统的可观测性是安全与治理的基础。2025-2026年行业实践（OpenTelemetry多Agent语义约定、GAAT治理感知遥测、Microsoft Agent Governance Toolkit (2026.4)的七包治理栈（Agent OS策略引擎+Agent Mesh密码学身份+Agent SRE可靠性工程）、eBPF无侵入Span补全）表明，传统"观测但不执行"的范式已不足够——需要在遥测采集与策略执行之间建立闭环。本系统基于单机部署约束，采用OpenTelemetry+Redis的轻量级可观测架构，与§4自治边界和§10硬边界深度集成。

### §15.1 可观测性三支柱

| 支柱 | 实现方式 | 采集点 | 存储介质 | 保留策略 |
|------|---------|--------|---------|---------|
| Traces（链路追踪） | OpenTelemetry SDK + W3C TraceContext | 每次Agent间通信、LLM调用、工具执行 | SQLite(热7天)+Parquet(冷7年) | 交易相关≥7年，系统相关≥1年 |
| Metrics（指标度量） | Prometheus格式 + Redis时序 | Agent延迟、协作成功率、成本、反思有效率 | Redis(实时)+Parquet(历史) | 实时1小时，历史按日聚合保留5年 |
| Logs（结构化日志） | JSON结构化 + 不可变追加 | Agent决策、自治边界检查、风控否决、异常事件 | SQLite(热30天)+Parquet(冷7年) | 审计日志≥7年，决策日志≥3年 |

> **Microsoft Agent 365 OTel (2026)对标**：Agent 365提供直接OTLP/HTTP+JSON遥测接入，支持S2S和OBO认证，Span映射Agent运行步骤。本系统MVP采用本地OTel SDK+JSON文件导出（详见§15.5可观测性安全约束），未来升级门禁：多机部署+企业级监控需求+有第二位开发人员加入时可接入Agent 365 OTel管道。

### §15.2 Trace层级模型

> 参考 Microsoft/Cisco 2025年提出的OpenTelemetry多Agent语义约定和GAAT (arXiv 2026, Apple)的治理感知遥测架构。

```
Trace (一次完整交易决策流程)
 ├── Root Span: 编排Agent接收决策请求
 │    ├── Agent Span: 研究Agent执行分析
 │    │    ├── LLM Span: 本地LLM推理调用
 │    │    └── Tool Span: 因子计算工具调用
 │    ├── Agent Span: 信号Agent生成信号
 │    │    ├── LLM Span: API模型推理调用
 │    │    └── Retriever Span: 语义记忆RAG检索
 │    ├── Agent Span: 风控Agent检查
 │    │    └── Rule Span: 风控规则引擎评估
 │    └── Agent Span: 执行Agent下单
 │         ├── Tool Span: miniQMT API调用
 │         └── A2A Span: A2A检查网关验证
```

> **Flow ID传播（参考MAN+ESM, Adya 2026）**：借鉴MAN+ESM的Flow ID概念，本系统在§3.2消息格式的metadata中传播traceId（与W3C TraceContext惯例一致），实现全链路可追踪。MVP使用SQLite存储trace，未来升级门禁同LP-015。

### §15.3 治理感知遥测（GAAT适配）

> GAAT (Governance-Aware Agent Telemetry, arXiv 2026) 在标准OpenTelemetry上扩展治理属性，实现"遥测→检测→执行"闭环。本系统适配其核心思想。

| GAAT概念 | 本系统适配 | 实现方式 |
|---------|----------|---------|
| Governance Telemetry Schema (GTS) | 每个Span附加治理属性 | agent.autonomy_level, agent.boundary_zone, governance.policy_id |
| 实时策略违规检测 | A2A检查网关内嵌规则引擎 | OPA兼容声明式规则，检测延迟<200ms |
| Governance Enforcement Bus (GEB) | Redis Pub/Sub治理执行总线 | 分级干预：告警→限流→阻断→熔断 |
| Trusted Telemetry Plane | 审计日志哈希链 | 每条Trace附加前条哈希，防篡改 |

**Microsoft AGT (Agent Governance Toolkit) 概念映射**：

| Microsoft AGT概念 | 本系统适配 | 实现方式 |
|---------|----------|---------|
| Agent OS (策略引擎) | A2A检查网关内嵌策略层 | YAML规则+if-else（MVP替代OPA Rego），延迟<1ms |
| Agent Mesh (密码学身份) | Agent Card DID标识 | Agent ID + 启动时注册哈希（MVP简化版），未来升级Ed25519 |
| Agent SRE (可靠性工程) | §16测试与混沌工程 | SLO定义+熔断器+混沌实验，MVP在仿真环境执行 |
| Agent Runtime (执行环) | §4自治边界执行环 | Level 0-3对应Ring 3-0（高自治=低Ring），kill switch=风控熔断 |

### §15.4 关键可观测性指标

| 指标 | 采集方式 | 告警条件 | 对应§13成功指标 |
|------|---------|---------|---------------|
| Trace完整率 | Span数/预期Span数 | <90% | — |
| Agent决策延迟P99 | Span耗时统计 | 超§13目标值×2 | Agent决策延迟 |
| A2A检查通过率 | A2A Span统计 | <99% | Agent协作成功率 |
| 自治边界违规 | 治理属性检测 | >0 | Agent自治边界违规次数 |
| LLM调用成本 | LLM Span token统计 | 超§13预算110% | LLM路由成本控制率 |
| 串谋行为相关性 | 行为模式分析 | 相关性>阈值 | 串谋检测召回率 |
| 涌现行为检测 | 集体行为异常检测 | 检测到异常模式 | 涌现行为检测延迟 |

### §15.5 可观测性安全约束

| 约束 | 说明 | 执行机制 |
|------|------|---------|
| 敏感数据不入Trace | 持仓/金额/交易记录不写入Span属性 | Span写入前脱敏过滤（能力定位书§6 B-011约束） |
| Trace不可篡改 | 审计Trace附加哈希链 | 类区块链结构，篡改可检测 |
| Trace访问控制 | 按角色限制Trace查询范围 | Trader看决策Trace，Administrator看系统Trace |
| Trace存储合规 | 交易相关Trace保留≥7年 | 冷存储自动归档到Parquet |
| 可观测性开销限制 | 可观测性引入的延迟<5% | 采样率动态调整，非关键路径1/10采样 |

## §16 Agent测试与混沌工程

> **设计哲学**：多Agent系统的测试不能沿用传统确定性验证——Agent行为具有概率性、上下文依赖和级联特性。2025-2026年行业实践（MASTest ISSTA 2024多样性引导探索、Multi-Agent Chaos Engineering、NexTrade 80+自动化测试）表明，Agent测试需要从"验证系统做什么"转向"保证系统在各种情况下如何表现"。本系统基于单机部署约束，采用仿真+混沌+行为分析三层测试架构。

### §16.1 测试层级模型

| 测试层级 | 目标 | 方法 | 环境 | 频率 |
|---------|------|------|------|------|
| L1-单Agent单元测试 | 验证单个Agent逻辑正确性 | 固定输入→预期输出 | 隔离环境 | 每次代码变更 |
| L2-Agent间集成测试 | 验证Agent协作流程正确性 | A2A消息模拟→流程断言 | Redis模拟环境 | 每日构建 |
| L3-端到端仿真测试 | 验证完整交易决策流程 | 历史行情回放→决策质量评估 | 仿真环境(D-SIMULATION) | 每周+每次策略变更 |
| L4-混沌工程 | 验证系统在异常条件下的韧性 | 故障注入→行为边界验证 | 仿真环境(D-SIMULATION) | 每月+每次架构变更 |
| L5-行为模式测试 | 验证无串谋/无涌现/无漂移 | 多Agent并行运行→行为模式分析 | 仿真环境 | 每季度 |

### §16.2 混沌工程实验库

> 参考 MASTest (ISSTA 2024, 中科院软件所) 的多样性引导探索和自适应关键状态利用，以及 multi-agent-patterns 的混沌工程实践。

| 实验编号 | 故障注入类型 | 注入目标 | 预期系统行为 | 可接受降级 | 不可接受行为 |
|---------|------------|---------|------------|----------|------------|
| CHAOS-001 | Agent进程崩溃 | 研究Agent | 同层备用Agent接管或降级为规则引擎 | 研究质量下降 | 系统整体崩溃 |
| CHAOS-002 | LLM推理超时 | 战略Agent | 降级至本地LLM或规则引擎 | 决策延迟增加 | 无限等待 |
| CHAOS-003 | Redis连接断开 | 消息总线 | 本地内存队列缓冲+自动重连 | 消息延迟 | 消息丢失 |
| CHAOS-004 | miniQMT API不可用 | 执行Agent | 订单进入待执行队列+人工告警 | 下单延迟 | 静默失败 |
| CHAOS-005 | 风控Agent熔断 | 风控Agent | 全系统暂停交易+人工介入 | 交易暂停 | 继续交易无风控 |
| CHAOS-006 | Agent输出异常（幻觉） | 信号Agent | 风控否决+反思触发 | 信号被否决 | 异常信号被执行 |
| CHAOS-007 | 多Agent同时故障 | 信号+研究Agent | 执行层按最后战略意图运行 | 决策质量下降 | 执行层自主修改策略 |
| CHAOS-008 | GPU显存不足 | 本地LLM | 自动卸载至API | 成本增加+延迟增加 | 系统崩溃 |
| CHAOS-009 | Agent状态不一致 | 做TAgent | 从miniQMT重建状态+暂停做T | 做T暂停 | 基于错误状态下单 |
| CHAOS-010 | 串谋模式模拟 | 信号+研究Agent | 监控Agent检测+告警+人工确认 | 误报告警 | 串谋未检测到 |

### §16.3 行为模式测试（参考MASTest）

| 测试维度 | 检测目标 | 度量方式 | 合格标准 |
|---------|---------|---------|---------|
| 个体多样性 | Agent行为是否过于单一 | 行为分布熵值 | 熵值>阈值（非退化分布） |
| 团队多样性 | Agent协作模式是否过于单一 | 协作路径分布 | 协作路径类型≥3种 |
| 串谋检测 | Agent间是否存在隐式串谋 | 行为相关性+利润异常 | 相关性<阈值，利润无异常 |
| 涌现检测 | 系统整体行为是否偏离预期 | 系统行为基线偏离度 | 偏离度<10% |
| 漂移检测 | 策略参数是否缓慢偏移 | 参数基线对比 | 偏移率<10%/月 |

| L1单Agent单元测试 | 每次git push | 本地开发环境 | 100%通过 | 阻止合并 |

## §17 遗留问题裁定

> **裁定原则**：每项功能二元结论——现在能建或因硬边界不能建。不能建的写明硬边界门禁条件。不分P1/P2，所有功能同等对待。裁定依据：能力定位书§2硬边界约束一~六 + 2025-2026年量化社区/头部机构实践。门禁条件除硬边界约束一~六外，还包括前置依赖条件（如核心闭环稳定运行）和外部触发条件（如法规出台），这些条件虽非硬边界但同样构成建设门禁。
> 门禁条件为摘要，完整条件见§17.1~§17.21各条目。

### §17.1 LP-001 OPA Rego策略引擎

**大白话**：OPA是个"策略裁判"，帮你的系统自动检查每一步操作是否违规。MVP阶段规则才8条，请法官管3人村子，杀鸡用牛刀。

**裁定：🔴 MVP暂缓(不能建)**

| 维度 | 说明 |
|------|------|
| MVP替代方案 | 8条全局策略(GP-001~008)用Python YAML配置+if-else硬编码写在A2A检查网关里 |
| 不能建的硬边界理由 | 约束一(单人开发)：学Rego+调试策略=额外开发成本，MVP不划算；约束六(AI代码不可信)：Rego策略也需人工审核，增加审核负担 |
| 未来开通门禁 | ①Agent数量≥8个且规则≥20条时引入OPA；②有第二位开发人员加入时（策略需多人协作管理） |

### §17.2 LP-002 Agent记忆向量检索(RAG)

**大白话**：向量检索是"语义搜索"，能理解你的意思找相关内容。但需要嵌入模型+向量数据库，吃GPU显存。你盘中GPU已经8-10GB了，再塞嵌入模型可能爆。

**裁定：🔴 MVP暂缓(不能建)**

| 维度 | 说明 |
|------|------|
| MVP替代方案 | SQLite全文检索(FTS5)+Redis缓存；语义记忆用结构化表（因子定义/策略规则/市场状态映射） |
| 不能建的硬边界理由 | 约束二(硬件)：GPU显存盘中8-10GB，嵌入模型需~2GB，挤占本地LLM空间；量化系统记忆核心是结构化数据不是自然语言 |
| 未来开通门禁 | ①GPU显存≥48GB（可同时跑本地LLM+嵌入模型）；②需要研报/新闻等非结构化数据语义检索时；③AUM≥500万需更深度知识管理时 |

### §17.3 LP-003 串谋检测阈值

**大白话**：串谋检测看Agent们是否"偷偷串通"。阈值设太低误报一堆，设太高漏网之鱼。没有历史数据标定就没有"万能阈值"。

**裁定：🟢 MVP能建（简化版）**

| 维度 | 说明 |
|------|------|
| MVP实现方式 | 简化版3项检测：①Agent间通信频率>基线3倍即告警；②同层Agent决策一致性>80%即告警；③利润异常检测：Agent组合利润显著偏离基准即告警；④阈值初始保守设定，运行3个月后根据误报率调整 |
| 能建的硬边界依据 | 约束二(单机5-11个Agent)：串谋概率低，简化版足够；约束三(AUM 50万)：串谋损失上限有限 |
| 未来升级门禁 | ①Agent数量≥15个时引入行为相关性分析；②有历史行为数据≥6个月时用统计方法标定阈值 |

### §17.4 LP-004 影子模式测试

**大白话**：影子模式是"新旧版本同时跑"对比结果。两个Agent同时跑LLM，显存翻倍，3090盘中已8-10GB，再塞一个可能爆。

**裁定：🔴 MVP暂缓(不能建)**

| 维度 | 说明 |
|------|------|
| MVP替代方案 | 金丝雀部署：新版本Agent先处理5%请求，监控决策质量，逐步扩大到100%。战略Agent升级用API推理做影子对比（不占本地GPU） |
| 不能建的硬边界理由 | 约束二(硬件)：GPU显存盘中8-10GB，影子模式需额外8-10GB，总计16-20GB接近24GB上限 |
| 未来开通门禁 | ①GPU显存≥48GB；②多GPU架构；③或战略Agent影子测试全部走API推理（不占本地显存） |

### §17.5 LP-005 EU AI Act正式合规文档

**大白话**：EU AI Act是欧洲AI法律，要求高风险AI系统有人类监督。你是个人A股量化系统，人在中国管A股，不归欧洲法律管。

**裁定：🔴 正式合规文档暂缓(不能建)（HITL机制本身已建）**

| 维度 | 说明 |
|------|------|
| MVP状态 | 正式合规文档不需要；HITL机制已在§4.6完整设计（置信度升级+人工审批+风控否决），这是最佳实践与法律无关 |
| 不能建的硬边界理由 | 约束三(A股市场)：不涉及欧盟管辖；约束一(单人开发)：正式合规文档成本极高 |
| 未来开通门禁 | ①面向欧洲客户/市场时；②AUM≥5000万需机构级合规时；③中国出台类似AI法规时 |

### §17.6 LP-006 混沌工程环境

**大白话**：混沌工程是"故意搞破坏看系统扛不扛得住"。单机部署没有第二台机器做"生产镜像"，但可以在仿真环境用历史行情回放模拟。

**裁定：🟢 能建（在仿真环境执行）**

| 维度 | 说明 |
|------|------|
| MVP实现方式 | 在仿真环境(D-SIMULATION)执行混沌实验，用历史行情回放模拟真实条件；非交易时段可在生产环境做轻量级测试（如Agent进程崩溃恢复） |
| 能建的硬边界依据 | 约束五(RTO<5分钟)：混沌实验不影响生产；约束三(miniQMT模拟盘可用) |
| 生产镜像环境 | 不能建——约束二(单机部署)限制，需第二台PC或云服务器 |

### §17.7 LP-007 11个Agent分阶段上线

**大白话**：11个Agent就像11个岗位，一开始全招人管理成本爆炸。先招5个核心岗位跑通最小闭环，再逐步增加。

**裁定：🔴 11个暂缓(不能全部MVP建)**

| 阶段 | Agent | 裁定 | 门禁条件 |
|------|-------|:----:|---------|
| MVP | 编排+研究+信号+风控+执行(5个) | 🟢 能建 | 无（最小闭环必需） |
| V2 | 择时+市场状态+监控+路由(4个) | 🟢 能建 | MVP 5个Agent稳定运行≥1个月+核心闭环无故障 |
| V3 | 做T+归因(2个) | 🟢 能建 | V2稳定运行≥2个月+AUM≥80万或需做T增强收益 |

| 不能全建的硬边界理由 | 说明 |
|-------------------|------|
| 约束一(单人开发) | 11个Agent同时开发维护成本极高 |
| 约束二(GPU显存) | 盘中8-10GB，11个Agent同时运行LLM推理不可行 |
| 约束三(AUM 50万) | 做T/归因等高级功能初期不需要 |

### §17.8 LP-008 本地LLM选型

**大白话**：本地LLM是"装在自己电脑上的AI大脑"，不用联网，延迟低不花钱。Qwen2.5-7B是中文最强7B模型，4-bit量化后只占4GB显存，3090能跑。

**裁定：🟢 能建**

| 维度 | 说明 |
|------|------|
| MVP选型 | Qwen2.5-7B-Instruct + DeepSeek-7B(备选)，均AWQ 4-bit量化（~4GB显存），用于战术层/执行层低延迟任务；战略层用API(DeepSeek V4 Pro/GLM-5.1) |
| 显存预算 | 盘中GPU：本地LLM ~6GB(含KV cache, 其中模型权重~4GB+KV cache~2GB) + 交易引擎 ~4GB = ~10GB（详见§8.2.3 GPU显存分配表），在24GB范围内 |
| 备选方案 | Qwen3-8B稳定版发布且AWQ 4-bit量化可用时可升级（需验证显存≤6GB） |
| 未来升级门禁 | ①Qwen3-8B稳定+AWQ可用时；②GPU≥48GB可跑14B模型；③本地LLM质量持续低于API且影响决策质量→全部切换API |
